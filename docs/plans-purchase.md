# Wardrobe plans: "Bought it" for a plan

The detail behind `src/web/plans/CLAUDE.md`'s "Bought it" bullet (34b). The rule itself is atop `src/web/plans/purchase.ts`; moved here verbatim to keep the area doc under its cap.

**"Bought it" for a plan (34b; `purchase.ts`, the rule in full there)**: buying is the wishlist's `buy` (`buyGarment`, `setGarmentStatus`); matching being derived, the item becomes owned (or partly) by itself **when the garment is the kind the item asks for**. The owner's Bought it page shows each item the garment is a candidate for (`planPurchases`): that it fulfils it (the status after, `matchPlan` with the purchase in the closet), or that it does not match ("This doesn't match the plan item: blue vs black") with "Change the item to match" **unticked** (`fitTargetTo`: only what differs; an item it matches is never rewritten); and the item's other candidates offered for removal from the wishlist (a delete), ticked only when the purchase leaves the item owned and the candidate stands for nothing else. When the purchase replaces a closet garment the page offers to archive, each item is judged both ways (`planPurchases`' `replaced`: the box is ticked after the page is drawn): a removal is suggested only when the item is owned either way, and an item archiving would leave short says so (`afterArchiving`, "If you also archive …"; #123). `buyCandidate` does the buy and the follow-ups in one transaction (anything posted outside the garment's own candidacies is ignored) and unlinks removed photos after the commit. The other candidates are read unlocked, so each is deleted only while still on the wishlist (`deleteGarment(..., 'wishlist')`, the status judged under the row lock): one bought meanwhile by another "Bought it" is kept and logged (`shopping.spec.ts` holds that purchase open).
