# Closet

Self-hosted digital wardrobe for the household: catalog garments (photo with background removal, category, brand, size, color), compose outfits, plan them on a calendar, and share a wardrobe with another user. Fork of Libre Closet (Lazztech, AGPL-3.0; repo `agandhi4/closet`, upstream remote `lazztech/libre-closet`). Deployed on the homelab as `closet.box`.

**The primary interface is the installed PWA on phones.** Every feature must work as an installed, offline-tolerant app first and as a desktop web page second.

## Stack

Conventions: `backend.md`, `frontend.md`, `frontend-pwa.md`, `frontend-htmx.md` (hypermedia principles only; the Jinja2/FastAPI specifics do not apply)

- **Runtime**: Node 22 (`.nvmrc` pins `v22.20.0`), TypeScript, **Fastify 5**, plain: no framework on top (`FastifyReply`, `reply.setCookie`, Fastify plugins and hooks). NestJS left on 2026-09-26, the last step of the platform migration (Jest to Vitest, MikroORM to Drizzle, Handlebars to JSX, Nest to plain Fastify). Built by `tsc` (`tsconfig.build.json`, `src/` to `dist/`).
- **Views**: server-rendered HTML with htmx 2 for interactivity; the little client logic left is inline handlers and small modules in `public/js/` (`_hyperscript` was removed on 2026-09-26, see Conventions). Not a SPA. There is no JSON API for the UI. Every page is typed JSX (`hono/jsx`, rendered to strings, no Hono server) in `src/web/` (see Web layer), the 404 and error page included.
- **CSS**: Tailwind v4 (`@tailwindcss/cli`) + daisyUI. Source `views/assets/main.css`, compiled to `public/bundle.css` by `npm run generate:tailwind`.
- **Data**: PostgreSQL only (17 in production on pgvault, 17 in CI, pgvault-dev locally). **Drizzle ORM owns the schema, the migrations and every query** (`src/db/schema.ts`, `drizzle/`, applied at boot by `src/db/migrate.ts`; see Changing the schema). MikroORM left the app on 2026-09-26 with the garment port; its frozen migration tree lives in `test/support/legacy-migrations/`, run only by `test/support/legacy-migrations.ts` to build production-shaped databases for the migration specs (`@mikro-orm/core`, `/postgresql` and `/migrations` are devDependencies for that alone). SQLite was dropped on 2026-09-25: its test tier passed on behavior production never had (case-insensitive `LIKE`, unbounded `varchar`, a drifted `color` type) and its migration tree wiped rows.
- **Auth**: login is always required (the upstream `AUTH_ENABLED=false` mode was removed 2026-09-25). Ported to the web layer on 2026-09-26 (`src/web/auth/`, `src/web/sharing/`). JWT (HS256, `jsonwebtoken`, claims `userId`, `email`, `pwf`, 365 days) in an `access_token` cookie: httpOnly, `SameSite=Lax`, `Max-Age` 31536000 seconds (the token's own lifetime), never `Secure` (Conventions). bcrypt passwords. Emails are stored trimmed and lower case (`normalizeEmail`) and unique case-insensitively: the `user_lower_email_unique` index on `lower(email)`, which the lookups use. `drizzle/0005_email_lower_outfit_text.sql` normalized the older rows and aborts the boot, naming the user ids, if two would collide. Register and update-email still check first for a field message; the index's unique violation is the race's answer. The session is resolved once per request by `createSessionResolver` (`src/web/auth/session.ts`: cookie, JWT, user row, password fingerprint) into `req.auth` (`{ user: { id, email } }`, never the hash). Routes are gated by `requireSession`, which only reads `req.auth`: every route needs a session unless it says `config: { public: true }`; without one a page navigation is a 302 to `/auth/login` and an htmx fragment or fetch a 401 with `HX-Redirect: /auth/login`. Handlers take the user as `sessionUserId(request)`. There is no password reset by email (removed with `src/email/` on 2026-09-25); a signed-in user changes it at `/auth/change-password`, which needs the current password, revokes every other session through the fingerprint and reissues this one's cookie. Changing the email (`/auth/update-email`) needs the current password too (checked before the address clash, so whether an address is taken is only told to the account's owner). **Step-up rule:** every route that changes or hands out a credential asks for the current password (change password, change email, delete account, creating a personal access token), so a borrowed unlocked phone or a stolen cookie cannot take the account or mint a credential that outlives signing out; each is `ACCOUNT_LIMIT`ed. Routes that only narrow access (sign out, revoke a token) do not ask. Signing out is `POST /auth/logout` (see Request security, Logout). A locked-out user's password is set by `npm run user:set-password -- <email>` (Deployment, Locked out). Wardrobe permissions come from one `resolveWardrobeAccess` (`src/web/sharing/access.ts`). The MCP endpoint takes personal access tokens instead of the cookie (see MCP server). `DISABLE_REGISTRATION` sends every registration route to the login page. See Architecture, Request security.
- **PWA**: Workbox `injectManifest` over a hand-written service worker (`views/assets/src-sw.ts`, esbuild to `.js`, injected to `public/sw.js`), `/manifest.json` served from config by `src/web/shell`, `@khmyznikov/pwa-install` (browser tabs that can install) and `pulltorefreshjs` (iOS standalone), both imported by `public/js/pwa.js` only where they apply, Web Push via `web-push` + VAPID keys (`src/web/push/`, see Web Push). Gated by `PWA_ENABLED`.
- **Images**: `sharp` for transcoding, `heic-decode` (libheif) for HEIC uploads. Background removal runs on the server only: BiRefNet 512x512 with `onnxruntime-node` in a child process (`src/cutout/`). The in-browser model (`@imgly/background-removal`, `onnxruntime-web`) and the `CUTOUT_MODE` switch were removed on 2026-09-26. See Architecture, Images and Background removal.
- **Storage**: local disk under `DATA_PATH`, the only backend (the S3 backend, `nestjs-s3` and the AWS SDK were removed 2026-09-26; production never used them).
- **i18n**: English only, strings in `src/i18n/en/lang.json` (the other five languages were deleted on 2026-09-26), read through `t('KEY')` from `src/web/i18n.ts`, typed to the catalog's keys.
- **Logging**: one pino logger (`src/logger.ts`), pino-pretty to stdout and to `app.log` under `DATA_PATH`, a child per module (`context`). See Architecture, Logging.
- **Tests**: three tiers. Vitest unit (`src/**/*.spec.ts`, mocks everything, verifies wiring); Vitest integration (`test/integration/`, the real app in-process on a scratch Postgres database per spec file, driven through `app.inject()`, verifies behavior: HTML, headers, rows, files); Playwright e2e (`test/*.spec.ts`, real browser against a built server). Both Vitest tiers are projects of one `vitest.config.ts` (Vite's esbuild transform, JSX settings from `tsconfig.json`; specs import `describe`/`it`/`expect`/`vi` from `'vitest'`, no globals). Integration specs assert rows through `t.db` (Drizzle) and log lines through `t.logs` (what the app really wrote; `captureLogs()` in `test/support/log-capture.ts` for a unit). `recordQueries(work)` (harness) counts the statements and rows a request reads, with their SQL text, for proving a page reads what it shows. Plus autocannon load test (`scripts/load-test.ts`) and Lighthouse CI. Vitest replaced Jest on 2026-09-25, the first step of the platform migration that ended with NestJS's removal on 2026-09-26.

### Routes

`GET /` is Today, the home screen (#15; signed out it sends to the login page like any page); there is no landing page, and no privacy, terms or sitemap routes. Public (`config: { public: true }`; reachable signed out): login, registration, logout (the POST, and the GET that asks first), `/about`, `/offline.html`, `/healthz`, `/manifest.json`, `/.well-known/*`, the Open Graph share page `/share`, the invite landing `/wardrobe-share/invite/:token`, and every `/file/**` image except an outfit selfie's (a 404 there, whoever asks). Everything else needs a session, except `/mcp`, which needs a personal access token and never reads the cookie (`config: { bearer: true }`, see MCP server). `/laundry` is the signed-in user's own hamper (see Wears and washes), and `/wardrobe/insights` their own figures (see Insights). `/wardrobe/plans`, `/wardrobe/shopping`, `/wardrobe/:id/plan-items` and `/auth/profile/style` are the signed-in user's own plans, shopping list, candidate links and style profile (see Wardrobe plans), and `/wardrobe/:id/outfit-count` their own wishlist item's "Goes with my closet" count (see Wishlist). `/weather/*` is the signed-in user's own weather and exists only with `WEATHER_ENABLED` (see Weather). `/calendar/plan` plans one more outfit on a day (see Calendar); `/calendar/plan-week` and its Undo, and `/auth/profile/week`, are the signed-in user's own weekly auto-plan and week template (see Weekly auto-plan). `/trips/*` are the signed-in user's own trips and packing lists, the Calendar's Trips tab (see Trips). `/outfits/ideas` is the Outfits page's Ideas tab, generated outfits to pick (see Outfit gallery). `/today/*` is Today's Refresh and "Wear this", the signed-in user's own day (see Today). `POST /calendar/:id/selfie`, `POST /selfies/:id/delete` and the images `GET /selfies/:fileName` and `/selfies/thumb/:fileName` are the signed-in user's own outfit selfies, served to them alone (see Outfit selfies). `/push/*` exists only with `PWA_ENABLED` (see Web Push). `/about` carries the upstream attribution. `manifest.json` is not a static file: `src/web/shell` serves it from config so `APP_NAME` and `ICON_NAME` flow into the installed PWA's name and icon.

### Request flow

Every request goes through the root hooks in `app.ts` (the same-origin check at onRequest; session into `req.auth` and `ViewContext` into `reply.locals` at preValidation, skipped on static paths), then:

- **A route** (`src/web/<feature>/routes.tsx`): the plugin's `requireSession` preValidation hook → the route's schema validation (400 page on failure) → the handler → `renderPage(reply, <FeaturePage ctx={viewContext(reply)} />)` or `renderFragment(...)` → JSX components in the shared `Layout`.
- **A static root** (`public/`, `/modules/*`, ...): `@fastify/static` with the cache policy in `registerStaticAssets`.
- **No route**: the not-found handler throws `HttpError(404, 'Cannot GET <url>')` into the error handler, which renders the 404 page (signed-in chrome included: the root hooks ran) or, on a static path, answers `{ statusCode, message }`.

Every response gets the security headers (root onSend) and, off the static paths, one log line (root onResponse).

htmx in the browser swaps fragments returned by further routes. A route that serves both a page and a fragment decides with `isFragmentRequest` from `src/htmx/fragment-request.ts` (shared with the service worker's cache keys) and sets `Vary`: in the web layer, `wantsFragment(request, reply)` does both.

### Web layer (adding a feature)

A feature lives whole (routes, queries, views) in `src/web/<feature>/`, a Fastify plugin registered from `webPlugin` in `src/web/plugin.ts`. The integration specs drive HTTP: they are the proof that a change keeps behavior.

- **Routes**: `src/web/<feature>/routes.tsx` exports a plugin (`FastifyPluginCallbackTypebox<WebOptions>`, or `FastifyPluginCallback` for a feature without input); add `app.register(featureRoutes, options)` to `webPlugin`. Config the routes need is resolved once in `createApp()` into `WebConfig`; nothing in `src/web/` reads `Config` or `process.env`.
- **Validation**: Fastify's own JSON-schema validation, schemas written with TypeBox (`@sinclair/typebox`, 0.34; `typebox` 1.x is ESM-only and the build is CommonJS) and request types inferred through `@fastify/type-provider-typebox`: declare `schema: { body, querystring, params }` on the route and `request.body` is typed from it. No class-validator DTOs, no hand-parsing in handlers. A request that fails the schema never reaches the handler: the error handler renders the 400 error page with Fastify's message (`body/date must match format "date"`). Fastify's ajv coerces form strings (`Type.Integer()` accepts `"12"`), strips unknown properties, and validates `format: 'date'` as a real calendar date (ajv-formats, full mode). A body the route may receive empty is `Type.Union([Type.Object(...), Type.Null()])` (Fastify validates a missing body as null). Decide per parameter whether malformed input is a 400 (data a write would store) or a fallback (navigation state in a URL, as the calendar's `?week=`), and say which at the route. Because the session hook and the root hook run at preValidation, an anonymous request is sent to log in before its input is judged, and a 400 has its page context.
- **Auth**: every route needs a session; `{ config: { public: true } }` opts out. `requireSession` (`src/web/auth/require-session.ts`) answers with `decideSessionAccess` (`src/web/auth/session-access.ts`): a page navigation without a session is a 302 to `/auth/login` and an htmx fragment or fetch a bodiless 401 with `HX-Redirect`. A handler reads the user from `request.auth` (always set past the hook on a non-public route).
- **Queries**: Drizzle, `options.db` (built in `createApp()`), in `src/web/<feature>/queries.ts`. A handler reads the user id with `sessionUserId(request)` (`src/web/auth/require-session.ts`). Row assertions go through `t.db`.
- **Views**: one `.tsx` per page or fragment beside the routes, typed against its data. Pages take `ctx: ViewContext` and render `<Layout>`, `<Navbar>` and `<Dock>` from `src/web/layout/`. Strings: `t('KEY', { param })`; a misspelled key is a type error.
- **Navigation**: a tap is a boosted `<a href>` or an htmx request, never script setting `location` (a full document load; `expectNoScriptNavigation` in `test/integration/pages.ts` fails any page that does). A card that holds a form (the outfit card's calendar dropdown, the calendar chip's delete) uses a stretched link: the card is `relative`, its link gets `after:absolute after:inset-0`, the form `relative z-10`. An htmx write that ends on another page (archive, delete) answers `navigateTo(reply, path)` (`src/web/render.ts`): `HX-Location` swapping the body with `HX-Boosted: true` on the follow-up GET, so the server and the worker treat it as the page it is. `HX-Redirect` reloads the document and is only for the 401 to the login page (the session is gone; start clean) and, until the photo flow is rebuilt, the photo upload.
- **Rendering**: `return renderPage(reply, <Page ctx={viewContext(reply)} />, { status })` (adds the doctype) or `renderFragment(...)`; both set `text/html; charset=utf-8` and throw instead of sending twice. JSX escapes `&` in attribute values (`href="...?a=1&amp;b=2"`, which the browser reads as `&`); specs that match URLs in markup read the body through `unescapeHtml` (`test/integration/harness.ts`). Void elements render as `<input type="hidden" name="x" value="1"/>`.
- **Errors**: `throw new HttpError(404)` (`src/web/errors.tsx`). The error handler (one, set at the root by `createApp()`) renders `ErrorPage` in the layout with the status: an `HttpError` or a Fastify 4xx keeps its message, anything else is a 500 without detail, logged with its stack. Without a page context (a static path, a body that failed to parse) the answer is `{ statusCode, message }`.
- **Logging**: `options.logger`, the `Web` child of the app's pino logger: `logger.info(message)`, `logger.warn(message)`, `logger.error({ err }, message)` (the error serializer keeps the stack). Name a request with `loggableUrl(request)`. The request line itself (`GET /about 200 5.6ms`) is the root onResponse hook's, context `Http`.
- **Escaping**: `hono/jsx` escapes every text child and attribute value, including text inside `<script>`. The one way to emit markup as-is is `dangerouslySetInnerHTML={{ __html }}`: grep for it, and every use needs a reason at the site. Feed it `tHtml(key, params)` (trusted template, escaped params) or `jsonForScript(value)` (inline JSON that cannot close its `<script>`), never a raw value. `hono/html` (`raw`, `html`) is banned by ESLint so there is no second hatch.

### Request security

- **CSRF**: `createSameOriginHook` (`src/web/security/same-origin.ts`) is a root `onRequest` hook added in `createApp()` before any route, so it runs before all of them and before the body is read. A POST, PUT, PATCH or DELETE must name in `Origin` (or `Referer` when there is no Origin) either the origin it was sent to (`requestOrigin`: scheme and Host as Fastify trusts them, see Trusted proxies) or `SITE_URL`'s origin; anything else, no header included, is a 403. Browsers send Origin on every such request; tools do not: the integration harness adds `Origin: http://localhost` by default (`sameOrigin: false` opts out), Playwright's `page.request` posts use `SAME_ORIGIN` / `signUpHeaders()` (`test/support/e2e-session.ts`), and the load test sets it. The cookie is also `SameSite=Lax`. Nothing changes state on a GET: signing out is a POST since 2026-09-26 (a cross-site link or image could sign someone out). A bearer route (`config: { bearer: true }`: `/mcp`) is the one exception to "no header is a 403": programs send no Origin, a cookie grants nothing there, and a page cannot add `Authorization` cross-site without a CORS preflight (never answered); a present foreign Origin is still a 403 (the MCP spec's DNS-rebinding rule).
- **Rate limits**: `@fastify/rate-limit`, registered at the root with `global: false` (`src/web/security/rate-limit.ts`); a route opts in with `config: { rateLimit: SIGN_IN_LIMIT }` (login, registration: 5 a minute per client address, before the body is read) or `ACCOUNT_LIMIT` (change password, change email, delete account, create a personal access token: every route that checks the current password; 5 a minute per signed-in user, a preHandler after the session gate) or `LINK_IMPORT_LIMIT` (the link import and its photo choice, the routes that fetch a user's URL: 10 a minute per signed-in user, same shape) or `MCP_LIMIT` (`/mcp`: 120 a minute per personal access token, a preHandler after the endpoint authenticated it). The MCP tool `add_garment_from_link` gets its own 10 a minute per user through the plugin's `createRateLimit` (`MCP_LINK_IMPORT_LIMIT`), since it is a call to `/mcp`, not a route. Counters are in process memory, one per route. A refusal is the 429 error page. Tests give each sign-up its own `X-Forwarded-For` (`uniqueClient()` in the harness, `signUpHeaders()` for Playwright), which only works because 127.0.0.1 is a trusted proxy there.
- **Trusted proxies**: `request.ip`, `request.protocol` and `request.host` read `X-Forwarded-*` only from peers in `TRUSTED_PROXIES` (Fastify `trustProxy`). Behind Caddy it **must** include Caddy's address, or every visitor is Caddy's IP to the rate limiter (one person's typos lock out the household for a minute) and the same-origin check falls back to `SITE_URL` for the https name. The homelab audit found production's value does not cover Caddy: a homelab config change.
- **Refusals do not reveal ids**: what the requester cannot see does not exist for them, a 404 like an unknown id (another user's wardrobe without a share, a garment or capsule outside the addressed wardrobe, anyone else's outfit or calendar entry, a share the user is no party to); what they can see but may not change is a 403 (a VIEW grantee writing, a grantee archiving or deleting). `WardrobeAccess` (`src/web/sharing/access.ts`) documents it; `test/integration/authorization.spec.ts` is the matrix.
- **Public pages never show an email**: the share page (`/share`) and its Open Graph and Twitter tags say "Shared by" the owner's first name when set (`sharedBy`, `src/web/share/share-page.tsx`), else nothing and the layout's default description; its query reads no email. Anonymous visitors and link-preview crawlers keep what they read.
- **Outbound fetches (SSRF)**: the server sits on the homelab LAN beside the NAS, pgvault and the router, so a URL a user supplies (the link import, #6) is fetched only through `createOutboundFetcher` (`src/web/security/outbound-fetch.ts`): http(s) on the default port, no credentials in the URL; the name is resolved once and refused if any answer fails `isPublicAddress` (`public-address.ts`: loopback, RFC 1918, 100.64/10, link-local, multicast, documentation and reserved ranges, IPv6 outside 2000::/3 or in its special blocks, and IPv4-mapped, NAT64 and 6to4 forms judged by their IPv4 address); the socket then connects to **the checked address** through a pinned `lookup` (no second DNS query, so DNS rebinding cannot swap it) while Host, SNI and the certificate check keep the name; at most 3 redirects, each checked the same way; one 10 s timeout over the whole chain; the body is read only for a content type the caller accepts and refused the moment its decoded bytes pass 2 MB (HTML) or 15 MB (images); no cookies are sent or kept; one log line per fetch naming hosts only (a product link can carry tokens). A refusal is an `OutboundFetchError` whose `reason` names the rule. **A fixed third-party API** (the weather's Open-Meteo, #14) uses the same fetcher: its requests name their `hosts` (the allow-list, checked on every hop, so a redirect elsewhere is `host-not-allowed` before it resolves) and accept `json` (512 KB cap); `createApp()` builds the weather its own instance of it (same rules, so a spec's stand-in is admitted for the weather alone). `createApp()` builds the one fetcher of user URLs (context `OutboundFetch`) and hands it to the web layer as `WebOptions.fetcher`; the per-user rate limit belongs on the route that calls it (`LINK_IMPORT_LIMIT`). The link import turns each `reason` into a translated sentence (`REFUSALS`, `link-import/import.ts`) that never names a host or an address. `test/integration/outbound-fetch.spec.ts` covers each rule against real sockets.
- **Redirect targets**: a user-supplied "go back here" value (`?returnTo=` on the outfit form) goes through `safeReturnTo` (`src/web/security/return-to.ts`): same-site paths only, anything else becomes the route's default. Never render or redirect to such a value without it.
- **Secrets in logs**: a route whose path carries a secret (the invite token) sets `config: { secretPath: true }`; every log line names requests through `loggableUrl()`, which then logs the route pattern. Invite links are built on `requestOrigin`, not the raw Host header, and reach their copy handler as a data attribute (`copyAndFlash`, `src/web/share/share-button.tsx`), never spliced into script text.
- **Logout**: `POST /auth/logout` (public, CSRF-checked by the same-origin hook like every POST) clears the cookie, sends `Clear-Site-Data: "cache"` and answers 303 to `/auth/login`; the service worker drops its page cache when a POST to `/auth/logout` or `/auth/delete-account` answers with a redirect (`views/assets/src-sw.ts`) and re-warms the offline page signed out (it does the same when `/auth/login` or `/auth/register` answers with one; see PWA, Page cache ownership). `images-v1` stays: its URLs are unguessable and only reachable from a page that shows them. The control is one hidden `PostForm` (`#logout-form`, `src/web/auth/logout.tsx`) that the navbar renders once, submitted by the desktop bar's and the drawer's buttons through their `form` attribute (a form inside a daisyUI menu item would lose the item's styling). `GET /auth/logout` signs nobody out: pages cached by the installed app before the change still link there, so it shows a one-button "Sign out" page to a signed-in visitor and sends anyone else to the login page.
- **Session revocation**: a session token lives a year and carries `pwf`, the last 8 characters of the user's bcrypt hash. `createSessionResolver` compares it with the row on every request, so any new hash (change password, `user:set-password`; bcrypt salts every hash, so even the same password again) ends every token issued before it, which is what an `iat` check against a password-changed timestamp would do, without the column. Deleting the account ends them with the row. Signing out ends only this browser's cookie: a copied token stays valid until the password changes, which is the one server-side revocation (there is no session table). Rotating `ACCESS_TOKEN_SECRET` signs everyone out. A new password also revokes every personal access token (`updatePasswordHash`, the one writer of a password, does both in one transaction); rotating the secret does not touch them (they are random, not signed).

### Images

Every photo is a set of WebP files sharing one base name: `<uuid>.webp` (original, 1080px, q90), `<uuid>-nobg.webp` (the cutout, made by the server, padded to a transparent square; photos stored before 2026-09-26 keep the one the browser made), `<uuid>-thumb.webp` (400px, q80, derived from the cutout when present). Only the original has a `File` row, which also carries the cutout's state (see Background removal); `File.version` is bumped whenever bytes under an existing name are rewritten (a mask edit, a server cutout), and every variant URL carries `?v=<version>` so the `/file` routes (`src/web/files/routes.ts`) serve all three immutable for a year. Views never build `/file/...` by hand: `imageUrl(photo, 'thumb')` (`src/web/files/image-url.ts`; grids and strips, with `loading="lazy"` and dimensions) or `'nobg'` (detail, share, Open Graph). Thumbs missing in storage are generated on first request, single-flighted, which backfills old photos. Deletion always goes through `deleteVariants`. An outfit selfie (#19) is the same set without the cutout (`unwanted`: original and thumb only), served under `/selfies/` by `selfieUrl`, never under `/file/` (Outfit selfies).

All of it is `Photos` (`src/web/files/photos.ts`, plain TypeScript, Drizzle for the `file` table) over `PhotoStorage` (`storage.ts`: a flat directory, `DATA_PATH`, the only storage; atomic writes through `.incoming/`). One instance per process, built by `createPhotos()`: the thumb single-flight map lives in it, so everything in the server shares it (`createApp()` builds it from config with `photosConfig()`, hands it to `webPlugin` as `photos` and returns it to `server.ts` for the nightly reconciliation; the reconcile CLI, a separate process, builds its own). Uploads (`storeUpload`, and `storeUploadParts` for the garment form's multipart: its `photo` part, every other part drained unread; both adapt `storeImage`, which takes any `ImageSource` stream: the seed's art, link import's fetched photo #6) and copies (`copy`) write bytes only and return the `file` row to insert (`NewPhotoRow`); see Gotchas for the commit contract. `pendingPhotoRow` builds that row for a link import's photo stored earlier (while its bytes are still there), and `preview` makes a small WebP in memory, never stored (link import's choices). A link import's photo before its form is saved is a **pending photo**: bytes plus a `pending_photo` row (`src/web/files/pending-photos.ts`: file name, the user who fetched it, when), at most `MAX_PENDING_PER_USER` (10) a user (storing another evicts their oldest, bytes and row, in the same step); only that user may claim it (the save, which deletes the row in the transaction that inserts the `file` row) or discard it (another pick); reconciliation removes day-old ones outside its guard, and account deletion removes a user's with their photos. A cutout of an existing photo (`saveEditedCutout`, the mask editor; `saveModelCutout`, the server job) is written by `writeCutout` under the row's lock and only when the cutout state machine accepts it. `cutoutInput` and `composeCutout` hold the server cutout's image rules (the model's stretched input; the original with the mask as alpha, padded square). Failures are `HttpError`s (400 unreadable, 400 "Image too large", 413 HEIC over the byte cap, 404 missing original), which the error handler answers with their status.

**Every decode is bounded by `MAX_INPUT_PIXELS`** (64 MP, `photos.ts`): sharp pipelines are only built through `decoder()` (`limitInputPixels`, which refuses from the header, before any pixel), and a HEIC's dimensions are checked before heic-decode allocates its pixels. sharp's own default (~268 MP) let a few KB of PNG or HEIC claim a gigabyte. A new sharp call site goes through `decoder()` or passes the limit itself; `writes.spec.ts` uploads such a bomb.

### Background removal

The server makes every photo's cutout: the photo form posts the photo alone and the upload queues it. Built 2026-09-26 for the move to linux-box (a Ryzen 7 8845HS; `docs/audits/2026-09-25-program2/bg-removal-benchmark.md` chose the model); the in-browser path (`@imgly/background-removal`, `onnxruntime-web`, `/bg-removal-models`, `background-removal.js`) and the `CUTOUT_MODE` switch were deleted the same day. A page the installed app cached before that still posts the browser's cutout (`nobgPhoto`) with the photo: `Photos.storeUploadParts` drains and ignores it (logged, context `Photos`) and the photo is queued like any other; the upload route accepts two files for it (`cutout-upload.spec.ts`). A leftover `CUTOUT_MODE` in an env file is ignored.

- **The state machine** (`src/cutout/state.ts`) is the one place that decides a cutout's state: `none -> pending` (request: every upload; `none` is left only on photos stored before 2026-09-26, whose cutout the browser made), `pending -> pending` (start: attempts + 1, the job's photo version recorded, the row leased to the worker; release: a job cut short by shutdown frees its own lease), `pending -> ready | failed` (succeed/fail, accepted only while pending and on the photo version the job started for), `failed -> pending` (retry: "Try again", the nightly retry; a pending row is queued or running already, so a retry of it is refused and a running job keeps its result: #45), `any -> edited` (edit: the mask editor, which always wins), except `unwanted`: an outfit selfie keeps its background, so it is stored `unwanted` (`initialCutoutState('unwanted')`, by `setEntrySelfie`) and no event applies to it, request and edit included, so no job, backfill of `none` rows or mask ever cuts the person out of the room (and, never pending, it is never claimed or leased). Every event but start leaves the row without a lease. The columns (`file.cutout_status`, `cutout_attempts`, `cutout_job_version`, `cutout_requested_at`, `cutout_worker`, `cutout_started_at`; a check constraint on the status, and `file_cutout_lease_check`: both lease columns or neither, and only on a pending row) are written only by `applyCutoutEvent` (`src/cutout/queries.ts`) under the row's `FOR UPDATE` lock. A new row starts through `initialCutoutState` (upload: `pending`; clone: the source's status). `src/cutout/state.spec.ts` covers every edge.
- **The queue** (`CutoutQueue`, `queue.ts`) is the pending rows no live lease holds, oldest `cutout_requested_at` first, one at a time (`claimNextCutout`, `SKIP LOCKED`; see Across servers). Before each claim it waits for the runner's model (`CutoutRunner.ready`), so no lease is held through a first boot's download; while the model cannot be had (a failed download, a refused checksum) it claims nothing, logs `Cutout queue cannot run the model (...)`, and tries again every 5 min, so photos wait pending rather than fail for an ops problem. `createApp()` builds it for every app and stops it on close; only `serve()` (`server.ts`) starts it, with the runner it is given (`main.ts`: the `ModelRunner`; `test/support/test-server.ts`: a stub that answers in 3 s), so the harness and the CLIs never run jobs (a spec starts it with a fake runner: `fakeRunner()` in `test/integration/cutouts.ts`, then `t.cutouts.whenIdle()`, which only a look that starts after the call answers: one already in flight may predate the spec's last write). **It looks for work four ways**: a write in this process wakes it (`cutouts.wake()`); every write that makes a row pending, in any process (a CLI such as the seed, a second server during an overlapping deploy), sends `NOTIFY closet_cutout_queued` inside its transaction, so it is delivered only on commit (`notifyCutoutQueued`, called by `applyCutoutEvent` for request, retry and release and by `insertPhotoRow` for a pending row; a new writer of pending rows goes through one of them), and the listener wakes the queue; at start it resumes whatever is pending (a restart loses nothing); and while idle it polls every `CUTOUT_POLL_SECONDS` (default 60), one indexed claim, never while a job runs. A poll that finds work logs `Cutout poll found photo <id> (<name prefix>) pending without a notification`: a lost notification or a listener that was down (or a lapsed lease: the poll is what finds one). A job cut short by shutdown stays pending and releases its lease, so the next start or another server runs it at once. The nightly retry (`retryFailedCutouts`, scheduled by `server.ts` at 03:00) requeues failed rows under `MAX_CUTOUT_ATTEMPTS` (3); "Try again" has no cap.
- **The listener** (`CutoutListener`, `listener.ts`) is one dedicated `pg` Client outside the pool (LISTEN belongs to a session; a pooled client serves other queries), opened by the queue's `start()` and ended by its `stop()`, so the harness and the CLIs never hold one. It connects with the pool's settings (`connectionOptions(dbConfig)`), as `application_name` `closet-cutout-listener` (find it in `pg_stat_activity`), with TCP keepalive and a 10 s connect timeout. A dropped connection is reopened with backoff (1 s, doubling to 60 s, reset once listening), and every (re)connect wakes the queue, because notifications sent while it was down are lost. **Pool budget**: a server with its queue running holds the pool's 10 connections plus this one on pgvault. `test/integration/cutout-notify.spec.ts` covers a row inserted through a second connection, the poll, `pg_terminate_backend` and the reconnect, and shutdown.
- **Stopping is bounded and cannot lose its signal.** Each `start()` gets its own `AbortController`; the loop, its sleeps and a job's cancellation all watch that signal, so a `stop()` that lands while a claim is in flight still ends the loop (a plain `stopping` flag plus waking a sleep lost that wake-up and slept a whole poll interval: the intermittent CI hang of 2026-09-26, PR #51). `stop()` always resolves: the listener owns its socket (pg's `stream` option) and destroys it if a clean close takes over 5 s (a database that stopped answering), and the runner's close plus the loop's end get 10 s (`settlesWithin`, `deadline.ts`), after which it logs a warning and returns, leaving a running job pending under its lease (it may yet finish; releasing it could start a second run beside it), which lapses. It never rejects (a failed runner close is logged), so the app still ends the pool. Any new wait inside the loop must take the `halt` signal.
- **Across servers a photo is run once and written once: a lease** (#45, `drizzle/0021_cutout_lease.sql`). A started job stays `pending` (a crashed server's job must stay claimable), so the claim's own statement also leases the row: `start` sets `cutout_worker` (the queue's worker id, `<host>:<pid>:<8 hex>`, new per `start()`, logged as `Cutout queue started as worker ...`) and `cutout_started_at` (the database's `now()`, so the servers' clocks never matter). `claimNextCutout` skips a row whose lease is younger than `CUTOUT_LEASE_MS` (`queries.ts`: 5 min, five times the model's 60 s kill; a job is the decode, that one bounded model run and the write, and the model file is readied before the claim), so during an overlapping deploy `SKIP LOCKED` keeps the servers apart while one claims and the lease while it runs. Succeed, fail and edit clear the lease with the status; a shutdown releases it (`release`, only the worker's own: a lease that lapsed and was taken since is left alone), and so does a result refused as `stale` on a still-pending row. **A crash** leaves the lease to lapse: after 5 min the next claim (the poll, a start, a notification) takes the row over and logs `Cutout lease of worker <id> lapsed after 5 min; running ... again` at warn. Why a lease and not a per-photo advisory lock: it is visible in the data (`select file_name, cutout_worker, cutout_started_at from file where cutout_worker is not null`), survives the listener's or the pool's connection drops, and costs no connection per job beside the listener's. The state machine still keeps the first result should two runs ever meet (a job that outlived its lease): `Cutout discarded (not-allowed)`. `cutout-notify.spec.ts` runs two servers on one pending photo and on eight (the runner called once per photo); `cutout-queue.spec.ts` covers a live lease skipped, a lapsed one taken, the shutdown release and "Try again" mid-job.
- **The runner** (`runner.ts`) runs the model in a forked child (`child.ts`), not a worker thread: onnxruntime cannot be interrupted, so the 60 s limit per image kills the process; an idle process exits after 15 min and returns its ~3 GB; an OOM kill takes the child, not the server. CPU only, `enableCpuMemArena: false`, `CUTOUT_THREADS` intra-op threads (default 4). Pixels travel over IPC with `serialization: 'advanced'`.
- **The model** (`model.ts`, `BIREFNET_512`) is not in the image: `CutoutModel.ready()` downloads it into `MODELS_PATH` (a local volume, not NFS) from a revision-pinned Hugging Face URL, hashing on the way, and renames it into place only on the pinned SHA-256; a mismatched file on disk is refused (`npm run cutout:fetch-model` replaces it). `main.ts` verifies (or starts downloading) it at boot, so any `node dist/main.js` (`start:dev` and `start:prod` included) fetches 940 MB into `./models` once; point `MODELS_PATH` at a copy to avoid it. Tests never boot `main.ts`: Playwright, the load test and Lighthouse run `npm run start:test`. The queue waits for the model (`ModelRunner.ready`) before it claims a job, outside the 60 s limit and outside the job's lease.
- **The page** (`garment-page.tsx`, `GarmentPhotoView`): pending shows the original with "Removing background…" and polls `GET /wardrobe/:id/cutout` (`hx-trigger="every 2s"`, `hx-swap="outerHTML"`, its own `hx-indicator` so the navbar spinner stays still); the answer without the trigger ends the polling. Failed shows the original and a `PostForm` to `POST /wardrobe/:id/cutout/retry`. `none` (a photo from before 2026-09-26) shows its cutout and the pencil, without polling. The phone downscales every photo first (`public/js/photo-input.js`: 1600 px JPEG, or the file as it is when the browser cannot decode it).
- **Logs** (contexts `Cutout`, `CutoutModel`): the queue's start with its worker id; one line per job start and end (`Cutout ready|failed|discarded (<reason>): garment <id> photo <file id> (<name prefix>) ...; queue wait, inference, total ms, model process RSS and peak`, and what became of the lease when it was not cleared by the result), a lapsed lease taken over (warn), model process start/load/exit (expected or not), model verify/download; the listener's connected, lost or could not connect (with the retry delay) and closed, and each notification at debug.
- **Measured on linux-box** (2026-09-26, 4 threads, the production image with a real photo): pending to ready 7.1 s cold (2.9 s model load, 3.8 s inference; the boot's checksum took 0.5 s), 3.6 s warm; model process peak RSS 2.9 to 3.3 GB, container 1.6 GB while the model stays loaded. The image grew 66 MB (onnxruntime-node, linux-x64 only). `test/integration/cutout-model.spec.ts` measures it with the real model when `MODELS_PATH` (or `./models`) holds it, and is skipped otherwise (CI never downloads 940 MB).

### Wardrobe

`src/web/wardrobe/` (on Drizzle since 2026-09-26): `routes.tsx`, `render-form.tsx` (the garment form page, shared with the link import), `queries.ts` (plain rows), `writes.ts` (the photo-aware writes), `validation.ts`, `garment.ts` (the category and size rules the outfit builder shares), `urls.ts`, `link-import/` (see Link import), and the pages (`wardrobe-page.tsx`, `garment-page.tsx`, `garment-form.tsx`, `wardrobe-tabs.tsx`: the Garments/Capsules/Wishlist tabs), `status.ts` (`inCloset` and the status writer; see Wishlist), `destination.ts` (a new garment's closet or wishlist destination). Every route takes `?ownerId=` for a shared wardrobe and resolves it once through `authorizeWardrobe` (`src/web/sharing/access.ts`, over `resolveWardrobeAccess`; the capsule routes use it too): reads need a view, writes a MANAGE share or ownership, archive and delete ownership, a clone only a view (it lands in the requester's own wardrobe). A garment outside the addressed wardrobe is a 404 like a missing id.

- **Routes**: `GET /wardrobe` (the page, or `#wardrobe-main` alone to an htmx fragment request, with `Vary`), `GET /wardrobe/tiles` (the next grid page; always a fragment), `GET /wardrobe/new`, `POST /wardrobe/properties-fragment` (the form's properties after a category, type or weight change; see Properties), `POST /wardrobe/bulk` (select mode's "Set…"; see Properties), `GET /wardrobe/tag` and `POST /wardrobe/:id/tag` (tagging mode; see Tagging mode), `GET /wardrobe/:id`, `GET /wardrobe/:id/edit`, `GET|POST /wardrobe/:id/clone`, `POST /wardrobe`, `POST /wardrobe/:id` (every field; a cleared one is NULL), `POST /wardrobe/:id/photo` (multipart `photo`, queued for its cutout; a `nobgPhoto` part from an old cached page is ignored; `HX-Redirect` to `?photoSaved=1`), `POST /wardrobe/:id/nobg` (the mask editor's fetch, answers `{ version }`; the `edit` event), `GET /wardrobe/:id/cutout` (the photo fragment the pending page polls) and `POST /wardrobe/:id/cutout/retry` (native post, 303 back), `POST /wardrobe/:id/archive` and `/restore` (each names its move: a status that does not take it is a 409, never the opposite move the old toggle made) and `DELETE /wardrobe/:id` (`navigateTo` the grid, or the wishlist for a wishlist item; owner only); `GET /wardrobe/new?to=wishlist[&replaces=<id>]` (the wishlist's form; see Wishlist), `POST /wardrobe/:id/condition` (the garment page's condition control, an `AutosaveForm`, owner and MANAGE; answers its status line, a plain post 303). The wear, wash and away posts are the wears plugin's (Wears and washes). Adding from a link (`link-import/routes.tsx`, its own plugin; owner or MANAGE): `GET /wardrobe/new/from-link` (the link page; also the manifest's `share_target`, which sends `title`, `text`, `url`), `POST /wardrobe/new/from-link` (fetch, then the garment form prefilled, 200), `POST /wardrobe/new/from-link/photo` (another of the page's photos, or none; answers the photo slot). `POST /wardrobe` takes the form's `linkPhoto`.
- **The grid is keyset-paged**: `GRID_PAGE_SIZE` (48) tiles newest first, `id < before` for the next page, one statement per page that reads only what a tile shows (id, name, category, status, photo name and version). The last tile is followed by a sentinel (`hx-trigger="revealed"`, `hx-swap="outerHTML"`) that fetches `/wardrobe/tiles` with the same filters and replaces itself with the next page and its own sentinel. Filtering and searching swap `#wardrobe-main` and so start at page one; the result count is a separate `count(*)` over the same filters. Indexes: `(owner_id, status, id desc)` and `(owner_id, category, id desc)`, also the owner foreign key's; at household size the planner often prefers a backward primary-key scan with a filter, which is as fast (under 0.3 ms at 1,500). A new sort order needs its own cursor and index.
- **Care filters and badges** (#7): `?needsWash=true` (a copy needs a wash; the owner's own wardrobe only, `gridSearch` drops it on a share, and the modal does not offer it there) and `?attention=true` (condition not good), checkboxes in the modal's Care group. Tiles carry `quantity` ("×3") and `condition` for everyone, and `care` (dirty copies, away) only when `gridPage(..., { ownerView })` is the owner's: the correlated wear count is not even computed for a share. The owner's grid shows "N garments need a wash · Laundry" (`countNeedingWash`).
- **Capsule filter** (`?capsule=<id>`, #8): members only (`inCapsule`, `src/web/capsules/queries.ts`); a pill with its name, a Capsule group in the filter modal, carried by every link through `GridSearch`. Not an id is a 400, not one of the addressed wardrobe's capsules a 404.
- **Property filters**: `type` (only with its category: `gridSearch` drops a type the chosen category lacks, so dropping the category pill drops it too), `warmth`, `formality` and `material` (`materials @> array[...]`, as the colour's `colors @> array[...]`); the scales and the material are 400 outside their sets, like a colour. No GIN index on either array: the owner's grid index narrows to one wardrobe (hundreds of rows) and the containment is a filter over those, as the other property filters are. The filter modal offers only values the wardrobe holds (`filterOptions`, one statement; materials through an `unnest` subquery). `GridSearch`'s keys are the query parameters' names, so `searchParams(search)` is the whole list: links, the sentinel, the search form's hidden inputs and the bulk form's action all spread it, and a new filter needs no second list.
- **Select mode and bulk edit** (`?select=1`, owner and MANAGE only): tiles become checkboxes (`SelectTile`, `name="ids"`) inside one native-post `#bulk-form`; the sentinel asks `/wardrobe/tiles?select=1`, so later pages arrive as checkboxes inside the same form. "Set…" opens `#bulk-dialog`, which sits outside the form (forms cannot nest; the backdrop is a dialog form) and joins it through `form="bulk-form"`: daisyUI radio tabs whose radio is the posted `property`, each tab's chips that property's field. `POST /wardrobe/bulk` (`bulkSetProperty`, one transaction, rows locked) sets it on the selected garments of the addressed wardrobe whose role has it, ignores other ids, adds a material rather than replacing the set (type and weight are per garment, not bulk), and answers 303 to the same filters with `bulkUpdated`/`bulkSkipped` for the toast (`SavedToast` + `StripFlags`, `src/web/layout/parts.tsx`, which the garment page's saved toasts use too). **The capsule picker** is the same select mode (`?pick=<capsuleId>`, owner and MANAGE; a viewer gets the plain grid): `SelectForm` with the capsule's members pre-checked and a hidden `shown` per tile, posting to `POST /capsules/:id/garments` (see Capsules); no bulk dialog, no filter bar, Cancel back to the capsule.
- **Tagging mode** (`/wardrobe/tag`, owner and MANAGE; `tag-page.tsx`): one card at a time for garments that still need their type (where the category has types), warmth (where the role has one) or formality (`needsTags` in `queries.ts`, archived left out), newest first; the wardrobe shows a "N garments need details" prompt while any do. The card's chips are one `AutosaveForm` posted on every change to `POST /wardrobe/:id/tag`, which saves at once and answers the chips as saved (`#tag-fields`, never the form) and the count left out of band: the tapped values replace the stored ones, and a new type (not the stored one posted again) brings its presets into properties still unset or still at the **stored** type's presets (`readTags`: `applyPresets` from the stored type, as the form uses its hidden `presetType`). The first tag has no source, so it only fills what is unset and never overwrites what the garment form set; a second type tap moves what the first type filled (the card saves every tap, so without the stored type as the source the first type's presets would stick). Next is the form's submit button (`next=1`): it saves what the card holds (a tap still waiting in the form's queue rides along); like every tap it writes only the fields that differ from the stored garment (`readTags`), so Next on a card left alone writes nothing; and answers the card after this garment (`HX-Retarget: #tag-card`), so a garment left alone waits for the next pass. `GET /wardrobe/tag?before=<id>` still answers the card to pages cached with the old Next link.
- **Search** is `ILIKE` on name, notes and brand with the keyword's `%`, `_` and `\` escaped (`containsPattern`). The colour filter (`colors @> array[<colour>]`) must be a built-in colour (else 400).
- **The form is validated in two layers** (`validation.ts`): TypeBox caps shape and length (a 400 error page; the inputs carry the same `maxlength`), then `readGarmentForm` re-renders the form with a 400 and messages for a blank category, a colour outside `GARMENT_COLORS` or a date that is not one. Categories are stored trimmed and lower case (the filter value and the builder's key), one-line fields trimmed, blank fields NULL, sizes normalized (`XL` is `X-Large`). The date field keeps its historical name `dateAquired` (cached pages post it); the column is `acquired_on date`.
- **Colours are a fixed set** (`GARMENT_COLORS`, `src/wardrobe/properties.ts` since #34, so the schema's plan and style checks can list them; each has a `.ms-swatch--<name>` class). **`garment.colors` is a `text[]` set** (#28), one model with `materials` and `plan_item.colors`: in `GARMENT_COLORS` order, each once, null for none (never an empty array), checked by `garment_colors_check`; `readColors` (`validation.ts`) is the one writer's normalisation, and readers take `colors ?? []`, never a string to split. `drizzle/0023_garment_colors.sql` converted the comma-joined `color` column (trimmed, lower case, blanks dropped, reordered, duplicates dropped) after aborting the boot, naming the rows, on any item outside the set. The form's field is still `color` (one per checked box), so forms the installed app cached post what they always did and need no marker; the MCP tools' output was already `colors: string[]`. `public/js/color-multiselect.js` only mirrors the server-rendered checkboxes as pills, built with `createElement`/`textContent`: a stored colour rendered through `innerHTML` was a stored XSS (audit2-correctness H5), and free-text colours are gone with it.
- **Properties** (#12; plan section 6): `type`, `warmth` (1-5), `formality` (1-4), `materials` (`text[]`, a set, null for none), `pattern`, `fit`, `sleeve`, `length`, `fabric_weight` (gsm, entered in oz or gsm; 6 oz is 203) and `water_resistant`, all optional, each with a check constraint listing `src/wardrobe/properties.ts`'s values. The form renders only what the category's role has (`propertyApplies`: no sleeve on shoes; a custom category gets the general ones and no type) and a save stores null for the rest, so recategorising drops what no longer applies. Type, warmth and weight sit beside the category; the rest in the collapsed "More details". Changing the category or anything in either block posts the form to `POST /wardrobe/properties-fragment` (reads and writes nothing; the triggers are `autosaveAttributes`, see Gotchas), which answers both blocks' contents (`#garment-props-main`'s in place, `#garment-props-more`'s out of band; never the blocks, which carry the triggers) with **presets filled only where the user has not chosen**: the form carries hidden `presetCategory`/`presetType`/`presetWeight` (where the shown presets came from), and `applyPresets` moves a value to the new preset only when it is unset or still equals the old one. A heavier fabric of the same type is warmer (`weightSteps`: a 6 oz tee is warmth 3). Labels are the catalog's `property.<name>.<value>` strings through `tKey` (`labels.ts`; `labels.spec.ts` proves every value has one).
- **Product link and price** (`source_url` text, `price` numeric(10,2); added for the seed and link import #6): optional fields in "More details", read by `readSourceUrl` (an absolute http(s) URL, stored as the parser writes it; anything else is a message, so a `javascript:` link never reaches the page) and `readPrice` (`$1,299` and `49.9` read as `1299.00` and `49.90`; never negative), both backed by check constraints. The garment page shows the price (`priceLabel`: US dollars, the household's one currency) and a "View product" link with `target="_blank" rel="noopener noreferrer"`. A clone keeps both.
- **Link import** (#6, `link-import/`: `routes.tsx`, `import.ts` the fetch and the pending photo, `prefill.ts` the form values, `link-page.tsx`, `photo-choice.tsx`, and the extractor): `extractProduct(html, pageUrl)` (`extract.ts`, pure) turns a product page into form prefills: schema.org Product JSON-LD (also inside `@graph`, arrays, a WebPage's `mainEntity`, a ProductGroup's variants), then Open Graph and `product:` tags, then `<title>`, each field from the first source that has it; price as a decimal string with its ISO currency; up to 8 image candidates, absolute (against `<base href>`), http(s) only, each once. `guess.ts` maps words to the form's values: colours onto `GARMENT_COLORS` ("navy" is blue), category and type from the name (the phrase that ends last wins: "shirt dress" is a dress), materials, a stated weight ("240 gsm", "14 oz") to `fabricWeight`, and "heavyweight"/"lightweight" without a number to the type's weight-step warmth. `html.ts` is a linear tag scanner, not a parser: the page is a stranger's, so nothing may throw, backtrack or recurse on it (`extract.spec.ts` feeds it broken and hostile pages).
  - **The flow**: "Add from a link" on the new garment form (or Android's share sheet) opens the link page; it fetches nothing until Fetch (a GET never writes). `importLink` (`import.ts`) fetches with `accept: ['html', 'image']`: an image is stored as the **pending photo**; a page goes through `extractProduct`, then up to `MAX_PHOTO_CHOICES` (6) of its image candidates are fetched together, each turned into a small WebP preview in memory (`Photos.preview`), and the first readable one stored as the pending photo. `importedForm` (`prefill.ts`, pure) makes the form values: the category's presets fill what the page did not say (as `withPresets`), a stated weight shows in gsm, the price only when in dollars or without a currency (else a notice names it), the product link is the link as given. The answer is the ordinary new-garment form (posting to `POST /wardrobe`) with notices, the pending photo (hidden `linkPhoto` plus its thumb) and, for two or more readable candidates, the choices as buttons with `data:` previews. A tap posts `url` and the current `linkPhoto` (`hx-params`) to the photo route, which stores the pick and discards the photo it replaces. A page with nothing extractable opens the form with the link kept and a message. `link-import.spec.ts` serves fixture pages from 127.0.0.2 (`test/integration/link-sites.ts`).
  - **A pending photo** is bytes without a `file` row plus a `pending_photo` row naming the user who fetched it (a MANAGE grantee's import is theirs until saved), recorded by `storePhoto` (`import.ts`) with the per-user cap (see Images). The save claims it: `createGarmentWithLinkPhoto` (`writes.ts`) takes the pending row (the requester's only), inserts the `file` row (queued for its cutout, owned by the wardrobe's owner) and the garment in one transaction, and refuses (the form again, "no longer available") a name with no pending row of the requester's, no bytes, or a `file` row already. `discardLinkPhoto` deletes only the requester's own pending photo. Nothing reaches `garment` or `file` before the save; reconciliation removes a pending photo a day old with its row, outside the deletion guard.
  - **Memory**: one import holds up to 6 fetched images of up to 15 MB at once, about 90 MB transient, plus their preview decodes. `LINK_IMPORT_LIMIT` bounds one user's rate; concurrent users multiply it.
- **Photo writes** (`writes.ts`): the garment is looked up before a multipart body is read, so a refused upload stores nothing; `Photos.storeUploadParts` writes the bytes; `commitWithPhoto` inserts the `file` row with the garment write in one transaction and deletes the new bytes if it fails; replaced or deleted photos are unlinked after commit.

### Wishlist

`src/wardrobe/status.ts`, `src/web/wardrobe/status.ts`, `src/web/wishlist/` (#18, slice 18a; plan section 11). A wishlist item is a garment with `status = 'wishlist'`: same table, form, photo, link import and sharing as any garment, and out of every closet read.

- **The status is a state machine.** `garment.status` (`wishlist`, `closet`, `archived`; a check constraint) replaced `archived boolean` in `drizzle/0014_garment_status.sql` (true to archived, false to closet; `garment-status-migration.spec.ts`). Transitions are events, each with one edge: `buy` wishlist to closet, `archive` closet to archived, `restore` archived to closet (`garmentStatusTransition`, pure, `status.spec.ts` covers all nine pairs). Refused on purpose: wishlist to archived (dropping a wishlist item is a delete: it has no history to keep), anything to wishlist (wanting another is a new item: clone or "Find a replacement"), and self-moves. A garment is inserted with an entry status (`insertGarment`'s `EntryStatus`: closet or wishlist; a clone of a wishlist item lands on the requester's wishlist, anything else in their closet, `statusOfClone`) and changed afterwards **only by `setGarmentStatus`** (row locked, the machine asked, a purchase's day and price written with it): archive, restore, "Bought it" (`buyGarment`, which archives the replaced garment in the same transaction only when asked) and the seed.
- **`inCloset` is the one predicate of every closet read** (`src/web/wardrobe/status.ts`, with `onWishlist`, `ownedGarment` = closet or archived, and `inScope` for `GridFilters.scope`): the grid (`ownedGarment` with "Show archived"), its filter choices, the builder's cycles, capsules' counts, strips and pages, tagging, laundry and the wash counts, `availableGarment`/`isAvailable`, the MCP tools' closet reads, insights (#17). Writes that may only name owned garments filter by `ownedGarment`: outfit slots (`insertSlots`), capsule membership (`changeMembership`), `markWashed`, `setAway`; `setWoreToday` answers `'wishlist'`; the wear routes answer a wishlist item 409. The outfit generator (#9) reads `availableGarment`, which includes it; "Goes with my closet" (#18b) reads `closetGarments` (`inCloset`) and locks the wishlist item beside it (see below). `wishlist.spec.ts` proves an item is absent from each read.
- **Replacing**: `garment.replaces_garment_id` (nullable, `ON DELETE SET NULL`, not itself by a check), kept after "Bought it" as the record of what the purchase replaced. The same-owner rule is the writers': `replacementOf` (`src/web/wardrobe/queries.ts`) stores the id through a subquery in the insert or update itself, only when it names a garment of the same owner that is owned now or once, else null. It is read from the form only beside its marker `wishlist=1` (Gotchas). A garment marked `replace_soon` shows "Find a replacement" (owner and MANAGE) to `/wardrobe/new?to=wishlist&replaces=<id>`, prefilled from it (`destinationValues`: category, type, properties, brand, colours, size; not its name, notes, dates, price or care), and lists the wishlist items that would replace it.
- **Routes**: `GET /wardrobe/wishlist` (the Wardrobe's Wishlist tab in `wardrobe-tabs.tsx`; under `/wardrobe`, so `sections.ts` already marks it; unpaged, a wishlist is a handful), `GET|POST /wardrobe/:id/bought` (the day, today in `APP_TIMEZONE`, and the price paid, the listed one, prefilled; a checkbox to archive the replaced garment when it is still in the closet and the requester is its owner, unchecked; a native post re-rendered 400 on a bad date or price; 303 to the garment with `?bought=1`; an item no longer on the wishlist is a 409, its form a 302 to the garment). New items come from the garment form (`GET /wardrobe/new?to=wishlist`, posting `to=wishlist`; no care fields or acquired date on a wishlist form) and from the link import, which carries `?to=wishlist&replaces=` from the link page to the form (`resolveDestination`, `src/web/wardrobe/destination.ts`; the share target stays the closet).
- **Shared like the rest of the wardrobe** (owner decision on #18): a VIEW grantee reads the owner's wishlist (gifting; the owner reading a sibling's), a MANAGE grantee adds, edits and buys, only the owner archives what a purchase replaces (a grantee asking is a 403) and deletes an item. Matrix rows in `authorization.spec.ts`.
- **"Goes with my closet" (#18b; `src/wardrobe/goes-with.ts` pure, `goesWithCloset` in `src/web/gallery/ideas.ts`, `gallery/goes-with.tsx`)**: a wishlist item's page judges it against the closet, **the owner's alone** (it reads their closet and clashes, like ideas; a grantee who reads the item never gets it, and `goes_with_closet` refuses another's item: matrix rows in `authorization.spec.ts`, `mcp-seed.spec.ts`). The generator with the item `locked` (never in a pool, so ideas, Today and picks cannot draw it: `wishlistGarments` is the only read that hands one to the generator) over `closetGarments`: **the whole closet**, dirty and away included (a purchase is judged against what is owned, not today's laundry), **no weather** (worn across seasons; so no layer is drawn and each closet layer is checked on its own, locked with the item), **the item's own formality as the range** (the best few are those dressed at its level; the count still takes every outfit the hard rules allow), **no rotation** (idle days nulled: uniform draws). One search asks for a page as large as `MAX_DRAWS`, so it returns every distinct outfit it met: the count is exact below `OUTFIT_COUNT_CAP` (50) and "50+" past it; the best 3 as `OutfitCollage` cards (display only: no form, `pickIdea` takes closet garments; "Bought it" changes that); per role it is worn with, "k of n" and the best 3 partners (at its formality, then in the most outfits), layers always asked ("No layer goes with it"); **near-duplicates** (`nearDuplicates`: same category, same type, same colour set, not empty) warn "do I need this?", except the garment it replaces, shown like for like. Seeded by the item's id. The shopping list's candidate cards show the count as a chip loaded when it scrolls into view (`OutfitCountSlot`, `hx-trigger="revealed"`, from `GET /wardrobe/:id/outfit-count`: `goesWithCount`, the owner's own wishlist item, else a 404; always a fragment): three statements and one search, 4 to 8 ms warm and about 20 ms cold over Theo's closet. Not inline, on purpose: the list's worst case would be its items (a plan's are unbounded) × `MAX_CANDIDATES_PER_ITEM` (5) × up to ~20 ms, already about 2 s at 20 items, past the ~500 ms a page may take; lazy, the page costs what the list costs and each chip pays for itself once seen. Theo's merino (replaces T21), padded jacket and Allbirds (twin of the Vejas) are the demo (`34-demo-goes-with`). ~15-35 ms over his 80 garments, so it renders inline; the page logs one debug line.
- **Plans' part (#34b)**: on the owner's own wishlist each card names the plan items it is a candidate for, with "For plan item…", and the header links the shopping list; the owner's "Bought it" shows what the purchase does to those items and takes their follow-ups (`adjustItems`, `removeCandidates`; `buyCandidate`, see Wardrobe plans). A grantee sees none of it and asking for a follow-up is a 403, like the archive.

### Wardrobe plans

`src/wardrobe/plans.ts`, `src/wardrobe/shopping.ts`, `src/wardrobe/style.ts`, `src/web/plans/`, `src/web/mcp/tools/plans.ts` and `shopping.ts` (#34, slices 34a and 34b; plan section 15). What the wardrobe should be, and what the closet lacks. **The owner's own, like outfits** (owner decision on #34): no route takes `?ownerId=`, another user's plan or item is a 404, shares never reach plans or the style profile. Matrix rows in `authorization.spec.ts`.

- **Tables** (`drizzle/0016_wardrobe_plans.sql`): `style_profile` (one per user: `styles` and `palette` `text[]` sets, `budget` band, notes; its week's rhythm is derived from the week template, #16, see Weekly auto-plan: 34a's `style_rhythm` counts were replaced by it in `0022`); `wardrobe_plan` (owner, name unique per owner in any case, notes, `active`: `wardrobe_plan_owner_id_active_unique` keeps one per owner); `plan_item` (category, optional type, `colors` and `materials` sets, warmth and formality ranges as min/max pairs, quantity, priority, budget per piece, note, `proposed`). Every value set is a check constraint from `properties.ts`/`style.ts`, as on `garment`. **No home city of its own**: that is the weather's (`user_weather`, #14); the style page shows it read-only (`findWeatherSettings`, with a link to Profile › Weather, nothing when `WEATHER_ENABLED` is off) and never copies it.
- **Which garments fulfil an item is never stored.** `matchPlan` (pure, `plans.spec.ts`) derives it on every read against `inCloset` garments: same category, the item's type if named, every colour and material it names, warmth and formality inside its ranges; copies count toward the quantity (owned, partly, missing). One garment fulfils one item with all its copies; greedy and deterministic (fewest candidates first, then priority, then id; closest garment first). **`replace_soon` never fulfils** (it is the gap to refill, reason `replace-soon`); `needs_repair` does, flagged. `planGaps`/`allPlanGaps` (`gaps.ts`) read items and the closet in two statements and run it; the page and the MCP tools share them.
- **One writer each** (`queries.ts`): `createPlan` (with items; active when the owner has none), `updatePlan`, `deletePlan`, `setActivePlan` (the old one cleared first). **Which plan is active is decided under `lockOwner`** (`src/web/auth/queries.ts`: the owner's `user` row, `FOR NO KEY UPDATE`; the gallery's pick uses it too): locking the plans would not do, because a user's first two plans made at once (a double tap) have no plan row to lock and would both take the one-active index; `plans.spec.ts` interleaves two such transactions. `insertItems`, `updateItem` (whole; `proposed` says who wrote it), `acceptItem`, `deleteItem`, `saveStyleProfile` (upsert). Forms read through `readPlanForm`, `readPlanItemForm`, `readStyleProfileForm` (`validation.ts`), which the MCP tools and the seed post through too.
- **The agent proposes, the owner decides.** `propose_plan_item` inserts `proposed`; `update_plan_item` leaves the item `proposed` again. A proposed item shows apart on the gap view and is left out of matching until the owner accepts it (Accept, or saving the item form) or dismisses it (a delete).
- **Routes**: `GET /wardrobe/plans` (the list, active first with its tally; "start from a wardrobe"), `GET|POST /wardrobe/plans/new` / `POST /wardrobe/plans`, `POST /wardrobe/plans/from-wardrobe` (`ownerId` of a wardrobe the requester can view, `authorizeWardrobe`: the closet grouped into items by `planItemsFromWardrobe`, as a new plan of the requester's), `GET /wardrobe/plans/:id` (the gap view: missing, partly, owned, the proposals first), `GET /wardrobe/plans/:id/edit`, `POST /wardrobe/plans/:id`, `DELETE /wardrobe/plans/:id` (`navigateTo` the list), `POST /wardrobe/plans/:id/activate` and `/duplicate`, `GET /wardrobe/plans/:id/items/new`, `POST /wardrobe/plans/:id/items`, `GET .../items/:itemId/edit`, `POST .../items/:itemId`, `POST .../items/:itemId/accept`, `DELETE .../items/:itemId`, `GET|POST /auth/profile/style`. Forms are `PostForm`s (400 re-renders); the plan's ⋯ menu submits hidden forms through the `form` attribute. The Wardrobe header's ⋯ menu (`WardrobeMenu`, `wardrobe-page.tsx`) links Plans, the shopping list and Insights; the Profile links the style profile.
- **Candidates (34b)**: a plan item's candidate products are **wishlist garments**, linked in `plan_item_candidate` (`(plan_item_id, garment_id)` primary key, both cascade, index on `garment_id`; `drizzle/0017_plan_item_candidate.sql`). A link, not a `plan_item_id` column on the garment: one product can stand for the same item in two plans (a duplicate copies the links), and the wishlist is shared with MANAGE grantees while plans are not, so no garment row a grantee reads or edits carries plan data. **One writer**, `changeCandidates` (`candidates.ts`, a Queryable, both sides locked `FOR SHARE`, `changeMembership`'s shape): only items of the owner's plans and garments of their wardrobe, and only wishlist garments are added. **At most `MAX_CANDIDATES_PER_ITEM` (5) per item**, a curated few to choose between (and what bounds a candidate's cost on the shopping list, #18b): an add past it throws `TooManyCandidates` (a 400 `HttpError`) before anything is written, counted under `lockOwner` taken first in the transaction, so two adds at once cannot both pass (`candidate-cap.spec.ts` holds one open while the other waits). Only candidates still on the wishlist count (a bought one frees its place), and only an item that gains one is judged, so an item past the cap from before (none could be: the cap came with #18b, right after 34b) keeps its links and may drop some. The pickers re-render their form 400 with the reason and what was ticked; the garment form's and the link import's `planItem` are refused ahead by `requireCandidateRoom` (in `resolveCandidateFor`), and the writer's throw rolls back a garment saved with the link; `add_candidate` answers the error (by url before the page is fetched). Readers (`candidatesOfPlan`, `candidatesOfItems`, `candidaciesOf`) go through `onWishlist`, so a bought candidate's link stops mattering on its own. Added from the item (`GET|POST .../items/:itemId/candidates`: a link or a photo through the wishlist's own add carrying `planItem`, or ticking what is on the wishlist; the form posts `shown`, the capsule picker's rule) and from the wishlist item (`GET|POST /wardrobe/:id/plan-items`). `planItem` on the new garment form and the link import (`DestinationQuery`, `GarmentBody`) is resolved by `resolveCandidateFor` (the requester's own item in their own wardrobe, else a 404 before anything is stored) and linked in the garment's own transaction (`WithGarment`, `createGarment`/`createGarmentWithLinkPhoto`). **A candidate link is not a proposal**: it changes nothing the plan asks for and counts for nothing (matching reads the closet), so `add_candidate` writes it as the owner's form would.
- **The shopping list** (`GET /wardrobe/shopping[?plan=]`, `shopping-page.tsx`, `planShoppingList`): the active plan's missing and partly items (another plan's with `?plan=`), highest priority first, then missing before partly; each with the copies to buy, the budget per piece and its candidates (photo, name, price, product link, "Bought it"), matching ones first, then within budget, over, unpriced, cheapest; a candidate that is not the kind the item asks for says how ("Doesn't match the item: blue vs black", `targetDifferences` in words by `differencesText`). The totals (`shoppingTotals`): pieces, the budget over items that have one, and the cheapest matching priced candidates. Linked from the Wardrobe's ⋯ menu, the plans list, the gap view and the wishlist.
- **"Bought it" for a plan (34b; `purchase.ts`, the rule in full there)**: buying is the wishlist's `buy` (`buyGarment`, `setGarmentStatus`); matching being derived, the item becomes owned (or partly) by itself **when the garment is the kind the item asks for**. The owner's Bought it page shows each item the garment is a candidate for (`planPurchases`): that it fulfils it (the status after, `matchPlan` with the purchase in the closet), or that it does not match ("This doesn't match the plan item: blue vs black") with "Change the item to match" **unticked** (`fitTargetTo`: only what differs; an item it matches is never rewritten); and the item's other candidates offered for removal from the wishlist (a delete), ticked only when the purchase leaves the item owned and the candidate stands for nothing else. `buyCandidate` does the buy and the follow-ups in one transaction (anything posted outside the garment's own candidacies is ignored) and unlinks removed photos after the commit.
- **Comparing two plans** (`GET /wardrobe/plans/compare[?a=&b=]`, `compare-page.tsx`; `planComparison`, `comparePlans`): accepted items paired by kind (category, type and colour set), what B adds and drops, pairs whose quantity, priority or details changed, a count of the same, each with its status in its own plan. A defaults to the active plan, B to the next; fewer than two plans shows why.
- **Routes (34b)**: `GET /wardrobe/shopping`, `GET /wardrobe/plans/compare`, `GET|POST /wardrobe/plans/:id/items/:itemId/candidates` (`returnTo` through `safeReturnTo`), `GET|POST /wardrobe/:id/plan-items` (the owner's own wishlist item; not on the wishlist: a 302 to the garment, a 409 to the post), and `POST /wardrobe/:id/bought`'s `adjustItems`/`removeCandidates` (`src/web/plans/shopping-routes.tsx`; the lookups by path id in `require.ts`).

### Capsules

`src/web/capsules/` (#8, plan section 2): a capsule is a named subset of one wardrobe's garments (office, weekend, a trip's pool). **The closet is implicit**, never a row: every garment in the closet (`inCloset`), what every page shows without a capsule (the list shows it first, linking to the grid). Tables `capsule` (`owner_id`, `name` text not null and trimmed, one per owner in any case through `capsule_owner_id_lower_name_unique` on `(owner_id, lower(name))`, `notes`, `created_at`) and `capsule_garment` (`(capsule_id, garment_id)` primary key, both cascade, index on `garment_id`), `drizzle/0009_capsules.sql`.

- **Part of the shared wardrobe** (owner decision on #8; the plan said private, the owner overrode it): every route takes `?ownerId=` and goes through `authorizeWardrobe`. A VIEW grantee lists and opens the grantor's capsules and filters the grid by one; a MANAGE grantee also changes membership (picker, toggles); only the owner creates, renames and deletes. A capsule outside the addressed wardrobe is a 404 (`capsuleNotFound`), a refused change on a visible one a 403. The matrix rows are in `authorization.spec.ts`.
- **Routes**: `GET /capsules` (the wardrobe page's Capsules tab: the closet card, then the capsules by name with counts and a strip of their newest four), `GET /capsules/new`, `POST /capsules` (303 to the capsule, `?created=1`), `GET /capsules/:id` (its members in the closet as the grid's tiles and keyset pages; Choose garments, Filter the wardrobe, Build an outfit), `GET /capsules/:id/edit`, `POST /capsules/:id` (rename and notes; a blank name, or one the owner's other capsule has in any case, re-renders the form 400: `createCapsule`/`updateCapsule` answer the index's unique violation as `'name-taken'`, in a savepoint so the seed's transaction survives), `DELETE /capsules/:id` (`navigateTo` the list; the garments stay), `POST /capsules/:id/garments` (the picker's Save, 303 back with `added`/`removed` for the toast), `POST /wardrobe/:id/capsules` (the garment page's "In capsules" toggles, an `AutosaveForm` that answers its status line; registered by the capsules plugin).
- **One writer**, `changeMembership` (a Queryable, one transaction, both sides locked `FOR SHARE`): removes the pairings in `remove`, then adds those in `add`; ids outside the wardrobe are dropped. The picker and the toggles post what they **showed** (`shown`) beside what is checked, and only shown-and-unchecked pairings leave: members on pages never scrolled to, filtered out or archived, and capsules made meanwhile, are left alone.
- **Archived garments keep their membership** and are left out of every capsule read (counts, strips, the capsule page, the filter, the picker), like everywhere else.
- **Building from a capsule**: `/outfits/new?capsule=` (the requester's own capsules only; outfits are private) cycles every row through the capsule's garments; the rows carry `data-capsule` and the row fragment takes `?capsule=`. New builds only: the edit form cycles the whole closet. The outfit gallery (#9) plugs in the same way: `/outfits/ideas?capsule=` draws its pool through `inCapsule`, and the capsule page's "Swipe outfits" (the owner's) opens it.

### Wears and washes

`src/web/wears/` and `src/wardrobe/availability.ts` (#7, plan section 1). **The owner's own records, like outfits and the calendar**: wears, washes and away are never shown to or changed by a grantee (the garment routes answer a grantee 403 with `?ownerId=`, 404 without; the grid computes no wash state for a share; `/laundry` ignores `?ownerId=`). A grantee sees what are garment properties: `quantity` and `condition` (which a MANAGE grantee may set).

- **`garment_wear`** (`drizzle/0011_wears_washes.sql`): one row per (calendar entry, garment) when the entry is marked worn, or one per (garment, day) for "Wore today" (`outfit_calendar_id` null; `garment_wear_garment_id_day_single_unique` keeps it to one a day). **Counts are distinct days**, never rows: two entries on one day are one wear. Deleting a garment or its owner takes its wears; archiving keeps them.
- **Deleting an entry and deleting an outfit differ on purpose.** Deleting a calendar entry (`deleteEntry`, the chip's ×) removes exactly its wears, like unmarking: the user says the entry was wrong. Deleting an outfit keeps the days it was worn: `deleteOutfit` calls `detachOutfitWears` in its transaction (the outfit and its entries locked) before the delete, which turns each entry wear into a day-level wear (`outfit_calendar_id` null; where the garment already has one that day, that one stays). Without it `outfit_calendar`'s cascade would take the entries and `garment_wear`'s cascade their wears: history erased by tidying the outfit list. The same rule holds for the entries' outfit selfies (#19): deleting the entry deletes its selfie (row, then bytes after commit); deleting the outfit keeps each one as a look on its day (`selfie.outfit_calendar_id` goes null by its foreign key; see Outfit selfies). "Wore today"'s undo deletes only today's day-level wear, so a kept wear from another day cannot be undone; one kept today reads as "Wore today" and its undo is today's to make.
- **One writer each** (`src/web/wears/queries.ts`): `setEntryWorn` (the calendar pill and the seed; the entry locked, one transaction: marking snapshots the outfit's garments of the owner as they are now, so **editing an outfit never changes past wears**; unmarking deletes exactly that entry's rows; an explicit `worn`, absent from pills cached before it, toggles; a day after `APP_TIMEZONE`'s today is refused, 409, and the calendar shows no pill there), `setWoreToday` (and its same-day undo), `markWashed` (`last_washed_on` = today; the garment page's Washed, `/laundry`'s batch, the seed's Sundays), `setAway`. `insertEntry` creates entries unworn: nothing else sets `worn_at`.
- **The rules** (`src/wardrobe/availability.ts`, pure, `availability.spec.ts`): wears since the wash are days after `last_washed_on` (a wear on the wash day counts before it); the limit is `wash_after_wears` or the role's default (top and one-piece 1, bottom 3, layer 10, footwear, accessory, bag and none never; `NEVER_WASH` (0) is an explicit never, as null is "the default"); **dirty copies = floor(wears / limit), capped at the quantity**. The plan wrote ceil, which marks jeans (limit 3) dirty after one wear against its own threshold rule; floor is that rule per copy and equals ceil at limit 1. "Needs a wash" (laundry, filter, badges) is a dirty copy; **available** is in the closet (`inCloset`: not archived, not a wishlist item), not away and a clean copy left.
- **The generator-facing predicate**: `availableGarment()` (SQL condition, `src/web/wears/queries.ts`) and `isAvailable()` (pure, `availability.ts`) are the same rule; use one of them, never a third. `wears.spec.ts` checks the SQL forms (`dirtyCopiesSql`, `availableGarment`) against the pure ones over a case table. **Condition never counts**: `needs_repair` is still in the closet and worn; `away: repair` is physically at the shop.
- **Routes** (wears plugin): `POST /wardrobe/:id/wear` (`worn=1|0`), `/washed`, `/away` (`away` '' | lent | repair, `awayNote`): to htmx, wear and washed answer `#garment-wear-status` (the section without "where it is") and away, an `AutosaveForm`, its status line; a plain post 303 to the garment; `GET /laundry` (what needs a wash, checked, then what was worn but is not due, unchecked; archived and away left out; one `PostForm`) and `POST /laundry` (`ids`, others' ignored; 303 `?washed=N` for the toast).
- **Garment form**: quantity (1-30), "Wash after" and condition + note, guarded by their own marker `care=1` (Gotchas). The note is kept only with a problem (a check constraint agrees); `away_note` only with `away`.
- **Offline**: these writes and the calendar pill carry `data-needs-network`; while offline or reconnecting `connectivity.js` (`guardWrites`, on every state change and swap) sets the real `disabled` and `aria-disabled` on their controls, marked `data-offline-disabled` so reconnecting re-enables only those and never a control disabled for its own reason, and `main.css` dims them through `data-connectivity` on `<html>` (the banner says why). Any new write can opt in the same way (`test/wears.spec.ts` covers keyboard and restore). A page that needs to say what offline means for it adds an element with `data-offline-note`, hidden online by `main.css` and shown offline or reconnecting (the gallery's "picking needs a connection").
- **Backfill**: `0011` inserted the wears of every entry already marked worn from its outfit's slots at migration time (the only record), owner-checked, dated the entry's day (`wears-migration.spec.ts`).

### Insights

`src/wardrobe/insights.ts` (pure), `src/web/insights/`, `src/web/mcp/tools/insights.ts` (#17, plan section 10). How the closet is actually used, computed on every request from the wear log; nothing stored. **The owner's own, like wears**: `GET /wardrobe/insights[?unworn=30|90|180]` (in the Wardrobe's ⋯ menu beside Plans and the shopping list; under `/wardrobe`, so the dock marks Wardrobe) ignores `?ownerId=`, and a share never reaches it (matrix row in `authorization.spec.ts`). `?unworn=` is navigation state: anything else is 90, never a 400.

- **Two statements** (`queries.ts`, run together by `readInsights`, which the page and `wardrobe_stats` share): `insightGarments`, one row per garment in the closet (`inCloset`) with its wear days ever, in the last year, the last day worn, and days since it and since `acquired_on` (Postgres `date - date` against the household's today, so the pure side does no date arithmetic); and `wornPairs`, the self-join of one year's distinct (garment, day) pairs, at most 5. `wardrobeInsights` computes everything else from those rows. The page is the owner row plus these two (`recordQueries` in `insights.spec.ts` and `insights-seed.spec.ts`): **a new figure is computed from the rows in `insights.ts`, not a new query**, unless it needs data the rows lack.
- **Definitions** (`insights.ts` states them; the specs pin each on a known closet): the closet is `inCloset` garments, each counted once whatever its quantity (worn when any copy was); wears are distinct days. *Worn in the last N days* (30, 90, 365): a wear today or in the N - 1 days before. *Unworn in N days* (30, 90, 180): never worn or last worn N days ago or more, among garments owned at least N days (no `acquired_on` counts as owned long enough), never worn first, then the longest since; each with "Style this" (`styleThisUrl`, `urls.ts`: the gallery's `/outfits/ideas?with=`, as on the garment page). *Most worn*: by wear days ever, ties the most recent first. *Least worn*: among garments owned `LEAST_WORN_MIN_OWNED_DAYS` (90) or more, leaving out the most worn. *Cost per wear*: `price` is per piece and, after "Bought it", the price paid (it overwrites the listed one), so the cost is price × quantity, divided by wear days, in cents rounded to the cent; no price is left out (counted), 0 wears is "not worn yet" and never divided; best is the cheaper half at most (up to 5), worst the dearer half, so no garment is in both. *Pairs*: two closet garments worn on the same day (whichever entries held them) on at least 2 days of the last year. *Colours*: each colour's share of the closet's garments and of the last year's wear days, a garment in k colours counting 1/k to each (strips of `.ms-swatch--<colour>` segments grown by `flex-grow`). *Categories and brands*: garments, pieces (quantity), share of the closet and of the year's wear days; brands grouped regardless of case and spaces under the first-added garment's spelling, 8 named and the rest summed. *Condition*: needs_repair and replace_soon counts, linking to the grid's "Needs attention" filter (`?attention=true`).
- **Seed**: Theo's 13 weeks give every figure a real answer (`insights-seed.spec.ts`, the clock pinned to the anchor); Dana's untagged closet has no wears (the "nothing worn yet" note); Riley's is the empty state.
- **Logs**: the route logs one debug line per read (`Insights for user 3: 80 garment(s), 5 pair(s), unworn 90 days in 12 ms`); the request line is the root hook's.

### Calendar

`src/web/calendar/` (ported to plain Fastify and Drizzle 2026-09-26). A calendar day is a plain date: `outfit_calendar.day` is a Postgres `date`, a `'YYYY-MM-DD'` string in TypeScript from the row through the URL and back, and all arithmetic is on day numbers in `calendar-date.ts`. No JS `Date` represents a calendar day: stepping an instant by 24 h or with local-time setters mislabels days as soon as a zone observes DST. The one conversion from an instant is `todayIn(APP_TIMEZONE, now)`: "today" (the highlight, the default week, the month links) is the household's date in `APP_TIMEZONE` (IANA name, default `America/New_York`, checked at boot), never UTC and never the container's zone. Weeks run Sunday to Saturday. `calendar-view.ts` builds the page model from plain dates (pure, unit-tested in New York time).

- **Routes**: `GET /calendar[?week=YYYY-MM-DD][&calMonth=YYYY-MM]` (a missing or malformed value falls back to the current week / the week's month: navigation state, never a 400); `GET /calendar/plan?for=day:D&occasion=O[&replace=E]` (the plan page, below; a missing or malformed destination is today, all day; a `replace` that is not the user's entry there plans one more); `POST /calendar` (`date`, `outfitId`, optional `occasion` (all day without one, as pages cached before #13 post it), `week` and `replace` (an entry id: change that entry's outfit, below); 204 to htmx, else 302 to the week; malformed input, an unknown occasion included, is a 400); `POST /calendar/:id/delete` (`navigateTo` the week to htmx, else 303) and `/worn` (the pill fragment to htmx, else 303), whose body is optional and only picks the redirect: the week, or `returnTo` through `safeReturnTo` (Today's "Wore it" and its undo come back to `/`). Entries are the signed-in user's own: 404 for no such entry and for someone else's.
- **Scheduling is idempotent**: `UNIQUE (owner_id, day, outfit_id)`, and the one writer, `insertEntry` (`src/web/calendar/queries.ts`, taking a `Queryable`), inserts with `ON CONFLICT DO NOTHING`: POST /calendar through `scheduleOutfit` (ownership check first), the outfit form inside its save transaction, the gallery's pick (and through it "Plan my week", `planned_by` 'auto', see Weekly auto-plan), the seed. The unique index leads with `(owner_id, day)`, so it is also the index of the week query and of the owner foreign key.
- **Occasions** (#13, plan section 8): `outfit_calendar.occasion` (text, default and check constraint from `src/wardrobe/occasions.ts`; `drizzle/0013_outfit_calendar_occasion.sql` made every existing entry all day) is the part of the day an entry is for: `all-day`, `workout`, `work`, `daytime`, `evening`, `night-out`, in that display order (all day frames the day, the rest by when their windows start). `OCCASION_HINTS` gives each a weather window (hours in `APP_TIMEZONE`, e.g. work 8 to 18, evening 18 to 23) and a formality range on the garment scale (work 3 to 4, workout 1): the one place #14's weather and #9's generator read them from. **Several outfits a day are separate entries; the same outfit is on a day once**, whatever the occasion (the unique key did not change): planning it again for another occasion inserts nothing and keeps the first occasion, so an edit form re-saved with the picker at its default never moves an evening entry to all day. There is no "change an entry's occasion" write yet: delete the entry and plan it again. Labels are the catalog's `occasion.<value>` (`occasionLabel`, `src/web/calendar/labels.ts`, with the day and month names).
- **Changing an entry's outfit** (#69): `replaceEntryOutfit` (`replace.ts`), the one replace write, reached from POST /calendar's `replace` (the plan page's saved outfits), the gallery's pick with `replace` (Today's Change, the plan page's ideas) and `schedule_outfit`'s `replaceEntryId`. One transaction under `lockOwner`: the entry (the owner's, on that day and, when given, that occasion; else 404) locked, then the outfit (a saved one, `ownsOutfit`, or an idea through `pickIdea` without a plan), then `setEntryOutfit` (the entry keeps its id, day and occasion). The rules: **a worn entry is refused** (409 saying to add another outfit: it is the record of that day and its wears are that outfit's; Change is offered on unworn entries only); **its selfie is kept as a look on its day** (`detachEntrySelfie`: the photo shows the old outfit, the #19 rule for a deleted outfit); **the entry becomes the person's** (`planned_by` 'user'); **an outfit "Plan my week" created for it** goes once nothing holds it (`removeUnheldOutfits`, Undo's rule: no entry and no trip, `outfitIsHeld`), only while the entry was still `auto`; **the new outfit already on that day** is refused (409, naming its occasion: the unique key). Idempotent: a double tap's second request waits on the owner lock and finds the entry holding the outfit (`unchanged`; the pick's redirect says "Already saved"). Logs (context `Web`): `Calendar entry <id> (<day> <occasion>) changed by user <id>: outfit <a> -> [new ]outfit <b>[, selfie <id> kept as a look][, planner's outfit <a> removed]`, `... already holds outfit <id> ...; nothing changed`, `... not changed for user <id>: <reason>`. `test/integration/replace-entry.spec.ts`.
- **The page**: a day stacks its entries in occasion order (`buildCalendarView` sorts; `findEntries` reads by day and id) through **`OccasionRow`** (`occasion-row.tsx`: the label, Change (the plan page with `&replace=`, unworn entries only, #69), the outfit chip with its edit link and ×, the worn pill), the one way the week draws an entry: the redesign's week agenda (R6) reuses it. Today (#15) draws its entries larger (the collage) but writes through the same worn route. Each day ends with "+ Plan" (empty) or "+ Another outfit", a link to the plan page, which is also the marker the specs split day columns on (`test/integration/calendar-page.ts`).
- **The plan page** (`plan-page.tsx`): the occasion as chip links (the choice lives in the URL), "Choose from ideas" (the gallery's Ideas with the same `?for=`, #9), "Build a new outfit" (the builder with the same `?for=`), and the saved outfits as buttons of one native `PostForm` to POST /calendar (`data-needs-network`); an outfit already on the day is disabled, saying for which occasion. The redesign's "+ Plan" sheet (R6) is this content. With `&replace=` of an unworn entry it is "Change outfit" (#69): no occasion chips (the entry's), no "Build a new outfit" (the builder adds), ideas and saved outfits carrying `replace`; for a worn entry it plans another and says why.
- **`OutfitDestination`** (`src/web/outfits/destination.ts`, pure, unit-tested) is the one parser of `?for=day:YYYY-MM-DD&occasion=O[&replace=E]` (`parseDestination`, lenient: anything malformed is `none`, an unknown occasion all day, a malformed `replace` dropped) and its writer (`destinationQuery`). `replace` (#69, a day's only) names the entry a choice takes the place of; the writes check it (`replaceEntryOutfit`), the builder ignores it. The plan page and the builder read it; Styling (#42), Ideas (#9) and Today (#15) import it. Trips (#10) are `for=trip:ID[:YYYY-MM-DD][&occasion=O]` (no occasion is not all day there: a trip outfit may have none); `destinationTarget` writes the `for` value alone for a write's hidden field, and the builder treats a trip as no destination (trips add saved outfits).
- **Worn** is `setEntryWorn` (`src/web/wears/queries.ts`): the entry's `worn_at` and its wear rows change together (Wears and washes). Days after today have no pill and are refused. **"Wearing this"** for a whole outfit off the calendar (Today's "Wear this", a trip's "Wearing this today") is `wearOutfitOn` (`queries.ts`): planned on the day through `insertEntry` and marked worn, one transaction, idempotent.
- **Tabs**: `CalendarTabs` (Week, Trips), static like the Outfits tabs (`/calendar` is a stale-while-revalidate tab root).
- **Selfies** (#19): each row (`OccasionRow`) shows its entry's selfie, or on today and before the camera and the library to take one (which marks it worn); a day also shows the looks kept after their outfit was deleted (`DayLooks`, read by `detachedLooks`). Deleting an entry goes through `removeEntry` (`writes.ts`), which unlinks its selfie after commit. See Outfit selfies.

### Trips

`src/wardrobe/packing.ts` (pure) and `src/web/trips/` (#10; plan section 4, the redesign's "Calendar › Trips"). A trip is **a standalone list of outfits** for some days away (owner decision: not a date range over the calendar) and the packing list derived from them. **The owner's own, like outfits**: no route takes `?ownerId=`, another user's trip, trip outfit or extra is a 404 with nothing written, shares never reach it (matrix rows in `authorization.spec.ts`, a gallery pick for someone else's trip included).

- **Tables** (`drizzle/0024_trips.sql`): `trip` (owner, name, `destination` text, `latitude`/`longitude` rounded like the weather home and only with a destination (`trip_location_check`), `starts_on`/`ends_on` dates, at most `MAX_TRIP_DAYS` (60) by the form, notes); `trip_outfit` (trip, outfit, optional `day` and `occasion`, OCCASIONS by a check: the same outfit once a day, or once without a day, by two partial unique indexes, so adding again is `on conflict do nothing` and keeps the first occasion, the calendar's rule); `trip_item` (the extras: label once per trip in any case, `packed`); `trip_garment_packed` (trip, garment: a row means packed). All cascade with the trip; `trip_outfit` with its outfit, the mark with its garment.
- **The packing list is derived, never stored** (`packingList`, pure, `packing.spec.ts`; read by `tripModel`, `model.ts`, five statements): the distinct garments of the trip's outfits, grouped by role top to toe. **Copies needed**: a garment is worn once a day whatever the occasions (Day 2's daytime and dinner jeans are one wear), an outfit without a day is a wear of its own (`tripWears`); nothing is washed on the trip, so with a wash limit k the trip needs `ceil(wears / k)` copies, one for what is never washed (`copiesNeeded`); what can be packed is that up to the quantity owned. **Warnings**, only while the trip is ahead or on (a finished trip's list is a record): `too-few` (the trip needs more than owned), `wash` (up to departure: fewer clean copies now than to pack, from `availability.ts`'s rules and `wearsSinceWashSql`), `away`, `archived`.

Every writer that can take a garment off a trip's list prunes the marks it orphans in its own transaction (`prunePacked`, `packed.ts`): `removeTripOutfit`, `updateOutfit` and `deleteOutfit` (`src/web/outfits/queries.ts`, through `tripsOfOutfit`), and `setPacked` itself; a garment that comes back comes back unpacked. The reads join through the list, so a mark left by a race (an outfit edit beside a packing tap) never shows and goes at the trip's next write.
- **One writer each** (`queries.ts`, every write under the trip's row lock, `lockTrip`, taken before any other): `createTrip`, `updateTrip` (a new destination name clears the location it no longer describes; outfits on days the new dates leave out move to "Any day", one row each, so `day` is always one of the trip's days), `setTripDestination`, `deleteTrip`, `addTripOutfit` (a day outside the trip is refused), `pickForTrip` (the gallery's pick and `plan_trip_outfit` with garments: `pickIdea` then the trip, one transaction, trip lock before `lockOwner`), `removeTripOutfit`, `addTripItems`, `copyTripItems` (another trip's labels, unpacked, those already there skipped, so twice adds nothing), `setItemsPacked`, `removeTripItem`; `setPacked` (`packed.ts`: only garments on the list are marked). The form reads through `readTripForm` (`validation.ts`), which the seed posts through too.
- **"Wearing this today"** (`POST /trips/:id/outfits/:tripOutfitId/wear`, while the trip is on, else 409): the calendar's writers, `wearOutfitOn` (`src/web/calendar/queries.ts`: `insertEntry` for today and the trip outfit's occasion, all day without one, then `setEntryWorn`, one transaction, idempotent), which Today's "Wear this" (`wearIdea`) uses too. The trip page says "Worn today" for an outfit with a worn entry today.
- **The destination's forecast** (`forecast.ts`, `tripForecast`): the weather's own service and cache (`forecastFor`) at the trip's rounded location, for its days the 16-day forecast reaches, each with what it asks of an all-day outfit (the person's offset); later days say from when their forecast arrives (climate normals stay deferred, #14's hook in `open-meteo.ts`); nothing is fetched for a trip without a located destination, one that is over, or one that starts past the forecast. Located through the weather's geocoding search on the trip page (`/trips/:id/places`, `WEATHER_SEARCH_LIMIT`, `secretPath`), set by `POST /trips/:id/destination`. **Weather-aware ideas**: the gallery with `for=trip:ID[:day]` passes the destination as `IdeasInput.place` (`ideasFor`), so a trip day's ideas match its weather (none, never home's, while the destination is not located). Pages never render the forecast themselves: `GET /trips/:id/weather` is a fragment the page loads.
- **Routes** (`routes.tsx`): `GET /trips` (the Calendar's Trips tab, `CalendarTabs`; `sections.ts` marks `/trips` as Calendar), `GET /trips/new`, `POST /trips` (303 `?created=1`), `GET /trips/:id` (days with their outfits in occasion order and "Any day", each with Ideas and "+ Add"; the packing list and the extras as `AutosaveForm`s posting the checked and `shown` ids, answering the status line and the summary out of band; notes), `GET /trips/:id/edit`, `POST /trips/:id`, `DELETE /trips/:id` (`navigateTo` the list; the outfits stay), `GET /trips/:id/outfits/new?day=&occasion=` (the calendar plan page's shape: day and occasion chips, Ideas, the saved outfits as `SavedOutfitButton`s), `POST /trips/:id/outfits`, `POST /trips/:id/outfits/:tripOutfitId/delete` and `/wear`, `POST /trips/:id/packed`, `POST /trips/:id/items`, `/items/packed`, `/items/:itemId/delete`, `/items/copy`; with `WEATHER_ENABLED` only, `GET /trips/:id/weather`, `GET /trips/:id/places?q=` and `POST /trips/:id/destination`. ### Outfit selfies

`src/web/selfies/` (#19; plan section 13): a mirror photo as the record of what was worn. **The owner's own, like the calendar**: every query is scoped to the owner, another user's entry, selfie or photo name is a 404, and nothing reaches a grantee, the share page, Open Graph or another user's MCP tools.

### Weather

`src/weather/` (pure) and `src/web/weather/` (#14, plan section 7). **`WEATHER_ENABLED=false`** (default true): `createApp()` builds no service, so there is no `/weather` route (404), no weather on any page or in the profile, no MCP weather tool, and the seed stores no location: nothing is fetched and no location is stored (`weather.spec.ts`, "weather off").

- **Location** (`user_weather`, `drizzle/0015_weather.sql`; a row once the user sets something, cascading with the user): a **home** city picked from the geocoding search (`home_name`, `home_latitude`, `home_longitude`) and the installed app's **"Use my location"** (`here_*`, `here_located_at`), which stands in for home for `HERE_FRESH_HOURS` (12), then home again. Every coordinate is rounded to 2 decimals (about 1 km) by `roundedLocation` (`src/weather/location.ts`) before it is stored, used as the cache key or sent; the phone rounds too (`public/js/locate.js`), so its precise position never leaves it. Check constraints keep each group whole and on the globe. One writer per group (`queries.ts`).
- **Provider: Open-Meteo, from the server only** (`open-meteo.ts`): the forecast (16 days: hourly apparent temperature, chance of precipitation and weather code; daily high, low, code) requested with `timezone=APP_TIMEZONE`, so its days are calendar days and its hours the occasions' hours (`OCCASION_HINTS`, which are APP_TIMEZONE hours; the phone's location in another zone reads in the household's); the geocoding search for the city. Through the outbound fetcher with `hosts` (Request security, Outbound fetches); the request carries the rounded coordinates (or the typed city) and nothing about the user. Answers are checked against TypeBox schemas before use. **Climate normals** past 16 days are deferred (the hook is in `open-meteo.ts`): the calendar shows nothing past the forecast.
- **Cache** (`weather_forecast`, `service.ts`): one row per rounded location, no user id: the last good forecast (normalized, `jsonb`), `fetched_at`, `attempted_at`. Fresh for an hour; a failed refresh keeps the last good answer and waits 10 minutes before asking again; one lookup per location at a time per process (the single-flight covers the cache read too: an ask that read the stale row just before another's refresh saved would fetch again). **A table, not memory** (the plan said memory): the hourly autoupdate and restarts start warm, two servers in an overlapping deploy share it, and the last good answer outlives a restart while Open-Meteo is down. No background refresh or timer: the asking request waits for at most one bounded fetch.
- **Where it shows** (`views.tsx`, the redesign's one `WeatherLine` and one `WeatherDay`): `WeatherSlot` in the page header (the wardrobe, above and outside `#wardrobe-main` so filtering never reloads it, and not in select mode or the picker; the calendar, above the week; Today, under the date) loads `GET /weather/summary` once in place (`hx-trigger="load"`, its own `hx-indicator`): today's line (icon, low to high in the user's unit, "rain from 3 pm", "take a layer", the place and "as of 8:31 PM") or, without a location, the link to set one; with `?from=&to=` the calendar's day chips arrive out of band into each day's `WeatherDaySlot`. **Pages never render the forecast themselves**: a tab root must render byte for byte the same while nothing changes (PWA, stale-while-revalidate), and an hourly forecast would mark it changed. Offline the worker answers the fragment from its cache (`url|hx`) and "as of" says how old it is (`test/weather.spec.ts`). The settings are `WeatherSettings`, a section of the profile (the redesign's Profile slots it in unchanged).
- **Matching** (`src/weather/match.ts`, pure, `match.spec.ts` across seasons and occasions; for the generator #9, Today #15 and the MCP tools): `weatherNeeds(day, occasion, offset)` reads the occasion's window, its feels-like range plus the personal offset, and sets targets: the **torso** (top or one-piece plus layer, combined 1 to 9: one step per 4 °C down from 26 °C; a tee is 2, a tee under a jacket 5, a sweater under a parka 9) and **legs and feet** (one garment, 1 to 5); **a layer** when the window's coolest and warmest hours are two torso steps apart (then the outfit is judged with the layer at the coolest hours and without it at the warmest; a swing inside the heat asks for nothing); **rain** when an hour of the window reaches 50 %, wanting a water-resistant layer, footwear or accessory (a bag's does not count). `assessOutfit(needs, garments)` lists the problems and a score (0 fits) and judges only the parts an outfit has; `matchGarment` counts an unknown warmth as the type's preset (its weight step included), else the role's usual. Availability (`isAvailable`) is a separate question: filter, then match.
- **Personal offset and units** (`temperature.ts`): °C added to every feels-like, within ±5, moved half a degree by "I was too warm" / "I was too cold" on the profile (`nudgeTemperatureOffset`, one SQL statement so quick taps all count; the writer #9's "say why not" calls). Everything is computed and stored in °C; `temperature_unit` (°F by default, for the NYC household; the constant and the migration default must agree) is only how the user reads it.
- **Routes** (session; `weather/routes.tsx`): `GET /weather/summary[?from=&to=]` (always a fragment; both or neither, at most 42 days, else 400), `GET /weather/places?q=` (2 to 100 characters; `WEATHER_SEARCH_LIMIT`, 20 a minute per user; `secretPath`, so the request log never shows the typed city; a failed search is a 200 message so htmx shows it), `POST /weather/home`, `/home/clear`, `/here`, `/here/clear`, `/unit`, `/feedback`, `/offset/reset` (htmx: the part of the section each changed, never the whole, which holds the unit's `AutosaveForm`: the location forms `#weather-location`, the feedback `#weather-offset`, the unit its status line and the offset out of band; a plain post: 303 to `/auth/profile#weather`; `data-needs-network`).
- **Logs** (context `Weather`): `Forecast for 40.69,-73.98: 16 days in 120 ms`, a failure with its reason and what is served instead, `Place search: 1 result(s) in 80 ms`: the rounded location, never the user or the query. The settings routes log the user (context `Web`), never a location; the fetcher's line names the host only.
- **Trips (#10)**: a trip's forecast is its destination through the same geocoding and `forecastFor`, for its days within the 16 days (`tripForecast`; see Trips); `ideasFor` takes the destination as `place`. `get_weather` stays the user's own location; `get_trip` carries the trip's.
- **Tests never call Open-Meteo**: `test/support/weather-stub.ts` (an HTTP server on 127.0.0.2, admitted by the weather fetcher's own policy) serves the seed's simulated New York weather from today in the requested zone. The harness runs with `WEATHER_ENABLED=false` and refuses to boot a spec that turns it on without the stub; the e2e test server always starts it.

### Outfits

`src/web/outfits/` (ported to plain Fastify and Drizzle 2026-09-26). Outfits are private: every query is scoped to the signed-in owner, shares never reach them, `?ownerId=` is ignored, and another user's outfit id is a 404.

- **Composition is `outfit_slot`** and nothing else: `(outfit_id, position)` primary key, `category` text, `garment_id` nullable (`ON DELETE SET NULL`: deleting a garment empties its slot). One row per builder row in the order the user left them; an empty slot is a row kept without a garment. `drizzle/0002_outfit_slot.sql` built it from the old `outfit.slots` JSON and `outfit_garments` pivot and aborts the boot if the two disagree for any outfit (compared as garment sets, owner-checked). A slot only ever names a garment of the outfit's owner: the save looks the posted ids up and stores any other as an empty slot. Archived garments stay in outfits.
- **Pages read slots by position**: the list (newest outfit first), the outfit page and the calendar chips go through `db.query` with `slots` ordered by `position`, one statement for all outfits with their garments and thumbs.
- **The builder** (`builder.ts`, pure, unit-tested): a row cycles through its category: position 0 is "no garment", 1..count the owner's closet garments (`inCloset`) of that category newest first, wrapping through 0. The server computes both neighbours (`data-prev-index`, `data-next-index`; the swipe in `public/js/outfit-builder.js` only reads them; rows are `touch-pan-y`, so its touch listeners are passive). `/outfits/new` reads one row per category (newest garment plus count, a window query), `GET /outfits/row-fragment?category=&index=` reads the count and the one garment at that offset (a missing index is 1, an out-of-range one is clamped, a missing or blank category is a 400). The edit form reads the saved slots with, per slot, its category's count and how many are newer; a garment outside the cycle (archived, or recategorised since) is shown marked, with `index` null and arrows to its neighbours by age, and cannot be stepped back to. Rows show the `thumb` variant; the detail dialog takes the `nobg` URL from a data attribute and loads it only when opened. An outfit saved with no rows edits like a new build. `?capsule=` on a new build restricts every cycle to that capsule's garments (see Capsules).
- **Saving** (POST /outfits, POST /outfits/:id): `category` and `garmentId` arrive one pair per row, in document order (a single row as scalars, which ajv's `coerceTypes: 'array'` turns into arrays); unequal counts are a 400. `scheduleDate` and `returnToWeek` are `''` or a real date (else 400). The outfit, its slots (replaced whole) and the calendar entry commit in one `db.transaction`; an update locks the outfit row (`FOR UPDATE`) so two saves cannot collide on the slot key. An update without `name`/`notes` leaves them; blank ones are stored as null ("Untitled Outfit"). Both are `text` columns since `0005`; the caps are the form's (`OUTFIT_NAME_MAX` 255, `OUTFIT_NOTES_MAX` 4000 in `form-page.tsx`, shared by the inputs' `maxlength` and the route schema, a longer post is a 400). The redirect goes back to `/calendar?week=` when `returnTo` is `/calendar`, else to the outfit. "Add to calendar" is the date plus an occasion select (`scheduleOccasion`, all day when absent: forms cached before #13); `/outfits/new?for=day:D&occasion=O` (the plan page) prefills both, and `?scheduleDate=` (calendar links cached before #13) still prefills the day as all day. The outfit list card's calendar dropdown posts an `occasion` too (R5 removes that dropdown).

### Outfit gallery

`src/wardrobe/generator.ts` (pure) and `src/web/gallery/` (#9; plan section 3, redesign section 1). The model: **the gallery chooses whole outfits** (Ideas and Saved, the Outfits page's tabs); composing row by row is Styling (#42, later); **the generator is the one source of suggestions**, reached only through `ideasFor` (`ideas.ts`): the Ideas tab, `suggest_outfits` and Today (#15: today's all-day ideas, 3 a page, through `todayIdeas`), then Styling's Shuffle (#42: its locked rows as `locked`); and its sibling `goesWithCloset` (#18b, see Wishlist: the whole closet with a wishlist item locked). Private like outfits: the signed-in user's garments, capsules and outfits; `?ownerId=` is not read. The tabs' labels are catalog strings only (`gallery.TAB_*`): the dock and naming (#43) are still the owner's call, and Ideas lives inside the current Outfits page (`outfit-tabs.tsx`, static, so `/outfits` stays byte-stable for the service worker).

- **The generator** (`generateIdeas`, generic over the caller's garment type so ideas hand back the pool's objects; `generator.spec.ts`): templates top + bottom + footwear or one-piece + footwear (footwear only when the closet has any; each weighted by its anchor garments), a layer only when the weather asks (the option with the best score, then no layer, then the most rested). **The pool is the caller's**: `ideaPool` reads `availableGarment()` (in the closet, not away, a clean copy left) and `inCapsule`; the generator never widens it, draws only layer, one-piece, top, bottom and footwear, and lets locked garments (any role, clean or not) ride along. Rotation: each role is drawn weighted by days since its last wear day (`1 + min(idle, 60) / 10`; never worn is the cap), so the least recently worn come up most. **Hard rules** (never relaxed): at most two colours beyond the neutrals (`neutralFor(role, color)`, the one place: black, white, grey, beige and brown on anything, and **blue on bottoms**, owner's rule from the #9 review: jeans and navy chinos go with anything, so a blue top or layer counts as a colour and blue trousers do not; a colour counts once however many garments carry it) and one patterned garment (anything but solid, or the colour `pattern`); no pair in `generator_avoid`; no combination equal to a saved outfit, compared on the drawn roles (a saved outfit with a belt still counts); every locked garment in every idea. **Soft rules, a score**: `assessOutfit` against the day's `weatherNeeds` (the occasion's window, the personal offset) plus one per formality step outside `OCCASION_HINTS`' range; ideas scoring 0 come first in draw order, then, once the draws run out, the near misses best first, each with its problems named (`IdeaProblem`).
- **Seeded and paged, never materialized**: the draws are `seededRandom('generator', GENERATOR_VERSION, seed)`; a page asks for `offset + limit + 1` fitting ideas and stops drawing once it has them, else spends all `MAX_DRAWS` (2000) and appends the sorted near misses. The fitting list is a prefix-stable sequence, so page 1 never changes when page 3 is read, and the same (pool, seed, page) is the same page. A base is judged deterministically (its layer included), so it is one idea however often it is drawn. The day's seed (`dailySeed(today)`) opens the gallery; Shuffle is `shuffledSeed(seed)`; both are seeded too (no `Math.random` or `Date.now` anywhere in the data path).
- **Routes** (`routes.tsx`, own plugin): `GET /outfits/ideas[?for=day:D&occasion=O][&capsule=][&with=][&seed=][&page=]` (the page), `GET /outfits/ideas/more?...&page=N` (the strip's next cards and sentinel, always a fragment), `POST /outfits/ideas/pick` (native `PostForm`: `garmentId` × n plus the destination; 303 to the week for a day, else to the new outfit; with `replace` the idea takes that entry's place through `replaceEntryOutfit`, #69, and `replace` without a day is a 400), `POST /outfits/ideas/feedback` (too warm / too cold, through the weather's `nudgeTemperatureOffset`; 404 without `WEATHER_ENABLED`; 303 back to the same gallery), `POST /outfits/ideas/avoid` ("Clashes": `garmentId` × 2; htmx answers 200 empty and the card is swapped away with `hx-swap="delete"`, a plain post 303 back), `POST /outfits/ideas/allow` (the garment page's undo; 303 to the first garment). `?for=`/`?occasion=` are navigation state through `parseDestination` (none: today, all day, and a pick just saves), `?seed=`/`?page=` fall back to the day's seed and page 1; `?capsule=`/`?with=` name data: not an id 400, not the user's own capsule or closet garment 404. A write's `for` is data: a malformed day is a 400 (it must read back as posted, `destinationTarget`). `for=trip:ID[:day]` (#10) names the owner's trip (else a 404; a day that is not one of its days is dropped for the trip's day): its ideas use the destination's forecast and its pick is `pickForTrip`, 303 to the trip (`?picked=1`).

The forecast is read only for days it covers (today to 15 days ahead). **Offline**: the cards the worker cached show; every write is `data-needs-network`; a `data-offline-note` says picking needs a connection.
- **Entry points**: the calendar's plan page ("Choose from ideas" with its `?for=`), a closet garment's "Style this" (`?with=`, the owner's), a capsule's "Swipe outfits" (`?capsule=`, the owner's), the Saved tab.

### Web Push

`src/web/push/` (rebuilt 2026-09-26; the old module never delivered anything, audit A1). Registered only when `PWA_ENABLED` (`WebConfig.vapid`); without it `/push/*` is a 404, the profile shows no controls and nothing is scheduled. What it is for (#5, decided 2026-09-26, built in #15): a morning "Today's outfit" and an evening "What did you wear?" reminder, **opt-in per device**, besides the profile's test send; the week's re-plan (#16) tells the devices with the morning reminder on what it swapped (see Weekly auto-plan). A shared wardrobe notifies nobody else: reminders are about the person's own day.

- **Routes** (session required; fetches get the 401): `GET /push/vapid-public-key` (text), `POST /push/subscribe` (the browser's `PushSubscription.toJSON()`: https endpoint up to 2048 chars, base64url `p256dh` of 65 bytes and `auth` of 16, else 400; 204), `POST /push/unsubscribe` (`{ endpoint }`, deletes only the caller's row; 204 either way), `POST /push/test` (htmx button, always a 200 fragment saying how many devices it reached, failed or removed).
- **`user_device` is keyed by endpoint** (`UNIQUE`, text) and written only by `upsertDevice` (`INSERT ... ON CONFLICT (push_endpoint) DO UPDATE`): renewed keys update the row, and the same browser signed in as someone else moves it to that user. Keys are columns (`key_p256dh`, `key_auth`), not JSON.
- **One sender** (`createPushSender`, `sender.ts`, built once by `createApp()` when `PWA_ENABLED`, context `Push`, handed to the routes as `WebOptions.push` and to `server.ts`): `sendToUser(userId, payload, { ttlSeconds })` (or `sendToDevices(userId, deviceIds, ...)`, a reminder's devices only) sends to every device of the user in parallel with web-push (aes128gcm, VAPID passed per request, 10 s socket timeout), deletes a device on 404/410, logs any other failure with the device id and never throws for a device. Endpoints are capability URLs: never log them (a `WebPushError` carries one). The VAPID keys and `SITE_URL` (must be https, web-push's rule) are validated when the sender is created, so a bad config fails the boot.
- **The payload is `PushPayload` (`payload.ts`: `title`, `body`, `url`, optional `tag`)**, imported by both the sender and the service worker; `parsePushPayload` is the worker's check. `notificationclick` opens `notificationTarget(url)` (same origin only, else `/`): focuses a window already on it, else navigates the first open window, else opens one.
- **Client** (`public/js/push.js`, imported by `pwa.js` only on pages the layout marks `data-signed-in` on `<html>`: the cookie is httpOnly, so no script can tell): `syncSubscription()` re-sends an existing subscription once per document (keeps keys current, moves the device to whoever is signed in); `<push-settings>` on the profile (`settings.tsx` renders every state's text hidden, the element shows one: checking, on, off, blocked, unsupported, install, error). Permission is only ever requested by `pushManager.subscribe()` as the first await of the enable tap (iOS drops the gesture across other awaits; the registration and key are fetched beforehand). iOS/iPadOS has push only in the Home Screen app (16.4+): a Safari tab has no `PushManager` and `navigator.standalone === false`, which is the "install" state.
- **Signing out drops the subscription** in the service worker (with the page cache); the row goes on the next send's 410 or with the account.
- **Reminders, per device** (`user_device.morning_reminder`, `evening_reminder`: minutes after midnight in `APP_TIMEZONE`, null when off; `reminders_set_at`; `drizzle/0019_push_reminders.sql`). The times are quarter hours in `REMINDER_WINDOWS` (morning 05:00-11:00, evening 17:00-23:00; `src/push/reminders.ts`, which the check constraints are built from): away from midnight and from the 01:00-03:00 hours US and EU DST changes skip or repeat. Only the browser knows which device it is (its subscription's endpoint), so `<push-settings>`, once on, posts it (`POST /push/reminders/form`, a POST though it reads: the endpoint is a capability URL and never goes in a logged URL) and htmx swaps the form into `#push-reminders`; every change posts `POST /push/reminders` (`endpoint`, `morningOn` + `morning`, `eveningOn` + `evening`; a time off the choices is a 400; another user's endpoint changes nothing and says to turn notifications on), which answers **only the status line** (`ReminderStatus`), never the form: the form is an `AutosaveForm` (Gotchas), in order and whole each time, in the slot `#push-reminders` push.js loads it into. One writer, `saveReminderSettings`, stamps `reminders_set_at`. `upsertDevice` clears a device's reminders when the browser signs in as someone else.
- **The scheduler** (`src/web/push/reminders.ts`, `sendDueReminders(deps, now)`): `server.ts` runs it every minute (`scheduleMinutely`, a second past the minute) and prunes claims of past days nightly; **`createApp()` never schedules it, so the integration harness and the CLIs send nothing** (a spec calls it with the instant it wants). A run: `dueReminders` (pure) lists each device's reminder whose wall-clock time today (`instantAt`, so 07:30 stays 07:30 on both DST days) has come, came after `reminders_set_at` (a device that turns one on after its time today gets it tomorrow) and is at most `LATE_LIMIT_MINUTES` (30) ago (a restart across its minute catches up; a server down for hours never sends a morning reminder at noon); `claimReminders` inserts them into `push_reminder` (`(device_id, kind, day)` primary key) with `ON CONFLICT DO NOTHING RETURNING` in one statement, and only what it inserted is this run's to send. **Two servers overlapping in a deploy** both find a reminder due and both insert; Postgres makes the second wait on the first's key and skip it, so each goes out once (`push-reminders.spec.ts` runs two servers' runs at once for 20 minutes' worth). The claim comes before the send: a crash between them loses a reminder rather than sending it twice. It raises no unique violation, so it names no `UniqueConstraint`. Then per person and kind, from `todayFor` (the page's model): **morning** "Today's outfit", the weather line as text (`weatherLineText`) and the planned outfits (`Work: Navy suit · Evening: Summer date`), with the top idea first while nothing dresses the day; **evening** "What did you wear?", naming what is planned, and **skipped when anything is marked worn today** (claimed all the same: it is decided at its minute). Both open Today (`url: '/'`), tagged `today-morning`/`today-evening` (a later one replaces an unread one), TTL 3 h and 1 h (never the next day).
- **Logs** (context `Push`): `Push reminders runs every minute`, one line per run that claimed something (`Reminders at <instant>: N claimed of M due, S sent, K skipped, F failed`), a skipped evening per user, the sender's per-user line, the prune. The settings route logs the user and device id (context `Web`), never the endpoint.
- **Manual check** (CI has no push service): on an installed phone, Profile, enable notifications, turn the morning reminder on at the next quarter hour; it arrives at that minute and opens Today; mark something worn and set the evening one: nothing arrives.

### MCP server

`src/web/mcp/` (#33; plan section 14): the owner's own Claude (Code, Desktop) works on the wardrobe through MCP. `POST /mcp` is a Streamable HTTP endpoint on the official `@modelcontextprotocol/sdk` in **stateless** mode: a `McpServer` and a `WebStandardStreamableHTTPServerTransport` per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`: JSON answers, no SSE, no `Mcp-Session-Id`), fed a Web `Request` built from the Fastify request and the body Fastify already parsed, its `Response` copied onto the reply, so the root hooks (security headers, the request log line, compression) apply as to any route. `GET` and `DELETE /mcp` are 405. Tool inputs are zod (`zod/v4`, the SDK's schema language; the only zod in the app).

- **Auth: personal access tokens** (`src/web/auth/personal-tokens.ts`, table `personal_access_token`, `drizzle/0012_personal_access_token.sql`): `closet_` plus 32 random bytes in base64url, stored as its SHA-256 (hex, `personal_access_token_token_hash_unique`) with an 11-character display prefix; `created_at`, `last_used_at` (written at most once a minute), `revoked_at` (revoked rows stay, hidden from the list). At most `MAX_ACTIVE_TOKENS` (20) in force per user. Created, listed and revoked at `/auth/tokens` ("Agent Access" on the profile; native-post `PostForm`s). **Creating needs the current password** (`currentPassword`, checked with `verifyPassword` like change-password; the step-up rule, Stack Auth): a wrong one re-renders the form 400 with the field's message and the name kept, the password never echoed or logged; a missing one is a schema 400; every attempt counts against `ACCOUNT_LIMIT`. A created token is answered once in the page, `Cache-Control: no-store`, beside the `claude mcp add` command. Revoking needs no password (it only narrows access); `POST /auth/tokens/:id/revoke` is a 404 for anyone else's. A new password revokes them all. The endpoint's own preValidation hook reads `Authorization: Bearer` (never the cookie) into `request.accessToken`; a missing, malformed, unknown or revoked token is the same bare 401 with `WWW-Authenticate: Bearer realm="closet"`.
- **An API route, not a page: `config: { bearer: true }`** (declared in `require-session.ts`). Three places honour it: the root preValidation hook skips the session and the page context (so its errors are JSON, as on a static path), `requireSession` lets it through, and the same-origin hook accepts it without Origin (Request security, CSRF). `secretPath` is set too, so the request log shows `/mcp` even if a client put a token in the query string.
- **A token acts exactly as its user.** Every tool resolves the wardrobe it addresses (`ownerId`, from `list_shared_wardrobes`) through the same `authorizeWardrobe` as a page's `?ownerId=` (`wardrobeFor`, `tool.ts`), and calls the pages' own query and write functions: no SQL of its own for a write. Refusals are `HttpError`s as in a route and answer a tool error with the page's message (`Wardrobe not found`, `Forbidden`, `Garment not found`); anything else is logged with its stack and answered without detail.
- **Tools** (`tools/`): read `search_garments` (the grid's filters through `garmentSummaries`, which shares `gridWhere`; a type needs its category; `needsWash` on a shared wardrobe is a 403, where the grid silently drops it), `get_garment` (no photo; its status; the owner's wears and washes only on their own), `list_wishlist` (`wishlistItems`: price, link, what each replaces; search_garments never lists the wishlist), `list_capsules`, `get_capsule`, `list_outfits`, `get_outfit`, `get_calendar` (up to 62 days, the household's days; each entry's `selfie: true|false`, never the image, #19), `laundry_status`, `wardrobe_stats` (`tools/insights.ts`: the insights page's figures through the same `readInsights`, the caller's own, `unwornDays` 30, 90 or 180), `list_shared_wardrobes` (the first name, never an email), `compare_with_shared_wardrobe` (`compare.ts`, pure: the closet vs a shared one by role and type, gaps with brands, colours, prices and links); ### Config

`loadConfig()` (`src/config.ts`) is the only reader of `process.env`: one TypeBox schema declares every variable with its default and rule, the values are merged from `.env` under `.env.local` under the real environment (the environment wins), booleans and numbers are converted only when they spell one exactly, and anything wrong stops the boot with every offending key named, never its value (`ConfigError`); `APP_TIMEZONE` must be an IANA zone and `PUBLIC_VAPID_KEY`/`PRIVATE_VAPID_KEY` are required with `PWA_ENABLED`. Secrets have no default: `ACCESS_TOKEN_SECRET` is required and at least 32 characters (the old `ChangeMe!` default let anyone who read the repo mint a session for any user id; the refusal says `openssl rand -hex 32`), and the database credentials are required too. Every process that boots the server passes one: the integration harness (`BASE_ENV`), `playwright.config.ts` (a random one unless the environment has it), the load test (random), CI and nightly (a CI-only value), `.env.local` for development. The result is a typed `Config` with the env names as keys (`config.DATABASE_HOST`), handed to `createApp()` and the CLIs, which pass slices on (`dbConfig`, `photosConfig`, `WebConfig`). `.env` is committed and holds public defaults; `.env.local` is gitignored and is for local development only. **The Docker image bakes `.env` and never sees `.env.local`**, so production configuration is real container environment variables, nothing else.

### Logging

`createLogger(config)` (`src/logger.ts`) is the process's pino logger: LOG_LEVEL for both outputs, pino-pretty in a worker thread to stdout and to `DATA_PATH/app.log` (flushed on exit), `cookie`, `authorization` and `set-cookie` redacted wherever a `req`/`res` is logged. Every module takes a child named for it (`logger.child({ context: 'Photos' })`; contexts: Bootstrap, Migrations, Db, Photos, Cutout, CutoutModel, Security, RateLimit, Session, OutboundFetch, Weather, Push, WeekPlan, Web, Http, Fastify, Mcp, Reconciliation, SetPassword, Seed), so lines are filterable in app.log and Loki. Fastify gets the `Fastify` child (its own startup and internal warnings) with its request logging off: the root onResponse hook writes the one header-free line per request, skipping static paths.

### PWA and the service worker

`public/sw.js` is a build artifact. Edit `views/assets/src-sw.ts` and run `npm run generate:sw`: esbuild bundles and minifies it with `process.env.NODE_ENV` defined as `"production"`, which strips Workbox's development logging and assertions (130 KB to 30 KB), then Workbox injects the precache manifest from `workbox-config.js` globs. Every `workbox-*` module the worker imports is a declared devDependency. The worker's only console output is its own `[sw]` lines. Service workers and Web Push require a secure context, which is why production is served over HTTPS (see Deployment).

Delivery model (audit fixes, see `src-sw.ts`, `public/js/pwa.js`, `public/js/connectivity.js`):

- **Static cache key.** Every first-party static URL carries `?v=<appVersion>` (the layout, the importmap, the garment page's module import). `appVersion` is `src/build-info.ts`: package.json version plus the commit (or build time) from `public/build.json`, which `scripts/write-build-info.ts` writes during `npm run build`. `app.ts` serves `/modules`, `/js`, `/vendor`, `/assets` and `bundle.css` as `public, max-age=31536000, immutable`, so **the key is the only thing that rolls the cache**: `npm version`, a new commit in a built tree, or `GIT_SHA` passed to the Docker build all change it; a build with none of those still gets a unique timestamp. `sw.js` and `manifest.json` stay `no-cache`. `NODE_ENV=development` turns the immutable policy off so `tailwind --watch` output shows on a plain reload.
- **Service worker strategies.** public/ files are precached by content hash (`?v` ignored on match). The tab roots opened as a document are stale-while-revalidate (below); every other navigation and every htmx request is NetworkFirst (3 s timeout). Both page strategies share one cache, `pages-v2`, and one plugin list; navigation preload is on, so a navigation's request starts while a cold worker boots and both answer or revalidate with the preload response (every GET navigation must stay routed to one of them, or the preload is wasted); fragments are keyed `url|hx` by `src/htmx/fragment-request.ts`, which the server uses for the same decision. A followed redirect is not stored under the URL that redirected. Versioned scripts are StaleWhileRevalidate (`assets-v1`; `/vendor/` is precached as well, being under public/), `/file/**` images CacheFirst (`images-v1`, 500 entries, 30 days). Unmatched requests (other POSTs, `/healthz`) bypass the worker, and so does every request to `/mcp`, navigations included (`bypassesWorker`, `page-cache.ts`; the one GET navigation deliberately left unrouted). On activate the worker deletes retired caches (`RETIRED_CACHES`: the in-browser model's, up to ~42 MB on a phone that used it, and `pages-v1`, whose pages were neither stamped nor owned).
- **Stale-while-revalidate tab roots** (issue #2). `/wardrobe`, `/outfits` and `/calendar` (`OPENS_STALE`, `page-cache.ts`: every dock tab but Today, which is network first, see Today), exactly (no query), loaded as a document (the app opening, a reload, pull to refresh) are answered from the page cache at once while the worker fetches the page again (`StaleTabRoot` in `src-sw.ts`, `servesStaleWhileRevalidate` in `src/web/page-cache.ts`); without a cached copy, or with one stored before this worker activated (an older build rendered its `<head>`, whose importmap must not meet this build's precached scripts), they are NetworkFirst. In-app taps stay NetworkFirst on purpose: they follow the user's own writes (an archive lands on `/wardrobe` through `HX-Location`), which must show at once; the cold open is where the wait was. The revalidation compares the server's body with the cached one (`revalidationOutcome`: current, updated, signed-out, account-changed, failed), so **a tab root must render byte for byte the same while nothing changes** (`delivery.spec.ts` checks it): no timestamps, nonces or random ids in those pages. There are no `updated_at` columns and none are needed: the freshness shown is the copy's age, not the data's.
- **Freshness stamp and indicator.** Every copy the worker stores carries `X-SW-Cached-At` (epoch ms, the device's clock), so any response served from the cache says when it arrived. `public/js/freshness.js` (started by `pwa.js`) tracks the display on screen: a document asks the worker how it was served (`PAGE_FRESHNESS` over a `MessageChannel`: fresh, or cached with the stamp and then the revalidation's outcome); an htmx swap reads the stamp from its own response; htmx history restores reuse the stamp kept on `#freshness` in the snapshot. A cached copy a minute old or more shows "Updated 3 minutes ago" (`#freshness` in the navbar, `public/js/age-label.js`, unit-tested in `src/web/layout/age-label.spec.ts`), after a 1 s grace while a revalidation is in flight so an online open never flashes it. **When the server's page differs it is swapped in only if the page is untouched** (no tap, key or wheel yet, scrolled to the top, no dialog open); otherwise a persistent toast offers it ("Newer version of this page", Refresh), so content never moves under a thumb or a half-typed form. Signed-out or account-changed reloads the page (the worker has dropped every page). Back online (`connectivity:change`), a cached display asks the worker to revalidate it (`REVALIDATE_PAGE`), with the same handling. The new page arrives in the worker's answer and is swapped with `htmx.swap` (no second fetch).
- **Page cache ownership.** The cache holds one account's pages; no page is ever served to a session it was not rendered for. The worker cannot read the httpOnly cookie, so: (1) a POST to `/auth/login`, `/auth/register`, `/auth/logout` or `/auth/delete-account` that answers with a redirect drops the cache before the redirect is answered (sign-out also drops the push subscription); (2) every HTML answer names its account (`X-Page-Account`, the user id, set by `send()` in `src/web/render.ts`; absent signed out), and the worker drops the whole cache before storing a page for an account other than the recorded owner (`claimPageCache`; the owner and the activation time are records in the cache under off-origin `page-cache.invalid` keys, so a drop takes them too); (3) a tab root whose revalidation comes back signed out or for another account drops the cache and reloads the page. (1) covers every sign-in made in the app; (2) and (3) are the backstop for one the worker never saw (only possible from outside the page, as `page.request` in a spec): the first page of the new session empties the cache, and at worst a tab root opened straight after shows the old copy until its revalidation lands and reloads it. `test/stale-pages.spec.ts` covers all three.
- **Updates.** The worker does not `skipWaiting()` on install. `pwa.js` shows an "Update available: Reload" toast on `waiting`, posts `SKIP_WAITING` on tap, and reloads on `controlling`. Never force a reload.
- **Connectivity.** `connectivity.js` probes `GET /healthz` (204, `no-store`, skips the session hook) every 30 s while visible, on every `htmx:sendError`/`responseError`, and every 5 s while offline; it drives `#connectivity-banner` in `src/web/layout/app-status.tsx` and dispatches `connectivity:change` on the document (freshness.js revalidates a cached display on it). `navigator.onLine` is only a hint.
- **Per navigation, only the body.** A boosted navigation swaps the body and nothing else should run again: `pwa.js` sits in the head; the install dialog (below) is mounted once on `<html>`, outside the swapped body (in the body every navigation re-mounted it and re-fetched `/manifest.json`); pull to refresh (iOS standalone only) is rebound when the body is swapped, not on fragment swaps. The htmx config has no view transitions (taps are dropped while one runs) and keeps 3 history snapshots (`layout.tsx` has the measurements). Tap feedback: the body's inherited `hx-indicator="#loading, closest a"` lights the navbar spinner for every request and marks the tapped link `htmx-request` (`main.css` dims it and its card).
- **Install dialog** (issues #4, #48). `<pwa-install>` (`@khmyznikov/pwa-install` 0.7) costs whoever mounts it the bundle (160 KB, 45 KB compressed; 0.5.8 was 100/30 KB but read `/manifest.json` twice when handed the prompt event), `/manifest.json` once and the manifest's first icon, so `pwa.js` imports it only on a load that can offer an install: never standalone (`display-mode: standalone`, or `navigator.standalone` on iOS); in Chromium only on `beforeinstallprompt` (installable, not installed); in a browser without that event only on the platforms the element has instructions for (`manualInstallPlatform`: iPhone and iPad, Safari on macOS, Android), so never in desktop Firefox. The element shows itself; there is no install button in the app. It shows the manifest's `icons[0]` (fetching no other), so the manifest lists the small rasters smallest first (`src/web/app-icon.ts`: `icon-192.png`, 5 KB, and `icon-512.png`, from `npm run generate:icons`); the 1000 px `ICON_NAME` (45 KB) is only for Open Graph and the watermark, and the apple-touch-icon (which Firefox also fetches on every cold load) is the 192 px one. On Chromium 155+ 0.7 installs through the Web Install API (`navigator.install()`, the manifest's `id`) and keeps the prompt event as its fallback. **No screenshots** (owner decision): the manifest has none, the element gets `disable-screenshots`, and `public/assets/screenshots/` is gone. Nothing under `public/assets/` is precached (`workbox-config.js`): no page renders the icon (the OS reads it at install, link previews and the dialog online), and precaching it cost every fresh install 45 KB. `test/install-dialog.spec.ts` proves a cold load of the installed app (Android and iPhone) fetches no icon, no dialog and the manifest at most once, desktop Firefox loads nothing, the Chrome dialog fetches the manifest exactly once (the browser's own read, which the element's `getInstalledRelatedApps()` triggers in headless Chromium, is told apart by resource type) and only the 192 px icon, and the Chrome and iPhone dialogs still work; Chromium stands in for Safari (user agent, `navigator.platform`, no `BeforeInstallPromptEvent`) and the spec dispatches the `beforeinstallprompt` headless Chromium never fires.
- **Page-only libraries** (the outfit builder's script and sortablejs on the outfit form; on the garment page `mask-editor` and `photo-input`) load from the page that needs them, as ES modules through the importmap (`src/web/layout/layout.tsx`) so boosted navigations cannot race a global. sortablejs ships its ESM build unminified (119 KB) and its minified build only as UMD, so `npm run generate:vendor` (part of `generate`, `start:dev`, and the integration project's globalSetup) has esbuild bundle and minify its default export from `views/assets/sortable.js` into `public/vendor/sortable.min.js` (37 KB, gitignored), which the importmap maps `sortablejs` to; the package directory is not served. A future page-only library whose package ships no minified ESM goes the same way. The outfit form imports `outfit-builder` from an inline module (a fixed string through `dangerouslySetInnerHTML`, `src/web/outfits/form-page.tsx`) that calls `initOutfitBuilder` for this visit's list: a `<script type="module" src>` runs once per document, so it would not run again when a boosted navigation returns to the page. The module registers its delegated listeners on the document once, at evaluation; an inline module registers its own on an element of the page (the outfit list's schedule toast), never on the document, or every visit would add another. No page loads a background-removal model or WASM (`pwa.spec.ts` asserts none is ever requested, through a whole upload). The mask editor's pencil is wired by a listener delegated on `#garment-photo-slot` that reads its URLs from the button's data attributes at the tap, because the cutout polling swaps the button.
- **Wardrobe fragment.** `GET /wardrobe` with a fragment request (`HX-Request` without `HX-Boosted`/history restore) returns `WardrobeMain` (`#wardrobe-main`) with `Vary`; the filter bar, the search form, the filter modal's own GET form and a grantee's wardrobe switcher (`ownerId`, `''` for their own) target `#wardrobe-main` with `hx-push-url`, so filtering or switching wardrobe never re-renders navbar and dock. The grid's later pages come from `GET /wardrobe/tiles`, always htmx requests, so the worker caches each under its own `url|hx` key; offline, the pages already scrolled through are what the cache has.

## Conventions

Upstream rules we keep (from `.github/prompts/boilerplate.prompt.md`), plus ours:

- **Server owns the HTML.** Reach for htmx attributes first (`hx-get` on a form of its own, `hx-include`, the `form` attribute, a GET form that works without script), then CSS, then a one-line inline handler (`onclick`, `onsubmit`; the CSP allows inline script) with data from `data-*` attributes, never spliced in. A behavior bigger than a line lives in a module in `public/js/` loaded by the page that uses it, and needs a reason stated in the PR. `_hyperscript` (172 KB, the largest script in the shell) was removed on 2026-09-26: its 13 attributes were each a few lines of this; `pages.ts` fails a page with an `_=` attribute.
- **Locality of behavior.** Keep view logic beside its markup. Extract only when reused.
- **Every user-facing string goes through i18n.** `t('KEY')` (or `tHtml` for the few with markup) from `src/web/i18n.ts`; add the key to `src/i18n/en/lang.json`, the only catalog.
- **daisyUI components, not bespoke CSS.** Theme through daisyUI tokens. No hardcoded colors in templates.
- **No runtime CDN imports.** Every client dependency is an npm package served by the `@fastify/static` registrations in `app.ts` (`registerStaticAssets`), from node_modules or, when the package ships no minified ES module, minified from it at build into `public/vendor/` (`npm run generate:vendor`). The installed PWA must boot with zero external requests: no preconnect, and the CSP names no other origin (`delivery.spec.ts` checks both).
- **Config via `loadConfig()`**, never `process.env` anywhere else in `src/`. New env vars: a schema entry in `src/config.ts` with a default (a secret gets none: required, with a minimum), a row in the README configuration table. `APP_TIMEZONE` (default `America/New_York`) is the household's zone for everything that asks "what day is it" (the calendar today); an unknown zone name fails the boot.
- **One database: Postgres.** Every tier (integration, Playwright, load test, CI) runs on Postgres. Do not reintroduce a second driver for test speed: the scratch-database harness is as fast as in-memory SQLite was.
- **Cookies stay `Secure`-less.** The `.box` name is HTTP by design (Tailscale encrypts). Adding `secure: true` to `setSessionCookie` (`src/web/auth/session.ts`) makes login silently never stick over `http://closet.box`. `SameSite=Lax` is set and must stay (CSRF). If a secure cookie is ever wanted it must be driven by a `COOKIE_SECURE` env var defaulting to false.
- **Offline-first UX per `frontend-pwa.md`.** Reads render from cache with a freshness indicator, writes that cannot reach the server are disabled with an explanation, never silently dropped. Connectivity detection is active (heartbeat), not `navigator.onLine`.
- **Logging**: use the pino child the module was given (`logger.child({ context })` in `createApp()`). Log at operation boundaries with garment/outfit IDs and user IDs; errors as `logger.error({ err }, message)`. Nothing inside template rendering or loops.

## Changing the schema

`src/db/schema.ts` is the schema; `drizzle/` holds the migrations drizzle-kit generates from it. The server migrates on every boot (`createApp()`, before the pool opens and before anything queries), so a deploy is the migration. The CLIs never migrate: `requireCurrentSchema` refuses a database behind the build (`SchemaBehindError`, exit 1).

1. Edit `src/db/schema.ts`. Name new indexes and constraints the way the existing ones are (`<table>_<column>_index`, `_unique`, `_foreign`; MikroORM's names, kept). Every foreign key column gets an explicit `index()`, or leads a composite index or unique constraint (as `outfit_calendar.owner_id`): Postgres does not index them on its own. A composite name lists its columns in order (`outfit_calendar_owner_id_day_outfit_id_unique`).
2. `npx drizzle-kit generate --name <what-changed>` writes `drizzle/NNNN_<name>.sql` and `meta/NNNN_snapshot.json` from the diff against the last snapshot. Read the SQL: a rename it cannot tell from drop + add makes it prompt (run it in a terminal), and data fixes (backfills, deletes before `SET NOT NULL`) are hand-added to the generated file.
3. `npm run test:int`: `test/integration/migrations.spec.ts` asserts that drizzle-kit's `pushSchema` finds nothing to change after boot (a schema edit without its migration fails there, naming the missing statement) and lists the index names queries rely on.
4. Never edit or delete a migration that has shipped. Drizzle applies every file whose journal `when` is newer than the last row in `drizzle.__drizzle_migrations` and never re-checks hashes, so an edited file silently diverges from production.

**Pending migrations run in one transaction, all files together** (drizzle-orm's migrator). A failed batch leaves nothing behind, and `CREATE INDEX CONCURRENTLY` cannot run inside it. The tables are household-sized, so a plain `CREATE INDEX` holds its write lock for milliseconds; if a table ever grows to where that matters, build the index in a non-transactional step added to `runMigrations` after `migrate()` (under the same lock), not in a migration file.

**How `src/db/migrate.ts` adopts a MikroORM-era database** (production's first Drizzle boot). All of it runs on one connection holding `pg_advisory_lock(hashtext('closet:migrations'))`, so two servers on one database (an overlapping deploy) never migrate at once; the second waits, then finds nothing to do.

- `mikro_orm_migrations` exists: its rows must include `LAST_LEGACY_MIGRATION` (`Migration20260926021506`, the newest file in `test/support/legacy-migrations/`), or boot fails with `LegacyMigrationsIncompleteError` (boot a pre-Drizzle build once to finish them). Then, if `drizzle.__drizzle_migrations` has no row for the baseline (`drizzle/0000_baseline.sql`, the full schema as MikroORM left it), the runner inserts the row drizzle's migrator would have written (hash and `created_at` from drizzle-orm's own `readMigrationFiles`) without running the SQL.
- No `mikro_orm_migrations`: a fresh database; the baseline runs like any migration.
- Then drizzle's `migrate()` applies anything newer. The log says which: baseline recorded, `Applied N Drizzle migration(s)`, or `Schema up to date`.
- `mikro_orm_migrations` stays in legacy databases (hidden from drizzle-kit by `tablesFilter`). MikroORM is gone from the app; once production is known to be past the baseline, the legacy check, `test/support/legacy-migrations*` and the three `@mikro-orm/*` devDependencies go too.

## Gotchas

- **`prettier --write` on a directory formats the persona bibles too.** `src/seed/personas/*.md` are the seed's data; prettier re-pads their tables and the seed stops parsing (`persona.spec.ts` fails with "not a garment"). Format `"{src,test,scripts}/**/*.{ts,tsx}"` (`npm run format`), never a bare directory.
- **A numeric column's default is written as SQL** (``.default(sql`'0'`)``, `user_weather.temperature_offset`): Postgres reads a numeric default back as the literal `'0'`, so a plain `.default(0)` shows as drift in `migrations.spec.ts`.
- **Weather is off in the integration harness.** `BASE_ENV` sets `WEATHER_ENABLED=false`; a spec that turns it on must pass `weather: (await startWeatherStub()).options`, or `createTestApp` refuses to boot (a spec must never reach Open-Meteo). The e2e test server always serves the stand-in.
- **The weather's days and hours are the household's, not the location's.** The forecast is requested in `APP_TIMEZONE`, so "today", the calendar's chips and the occasion windows line up; derive them with `todayIn`/`hourIn`, never `toISOString()` or UTC getters. The integration spec pins the clock (`vi.useFakeTimers({ toFake: ['Date'] })`) at 00:30 UTC on a Sunday, still Saturday evening in New York.

- **The persona bibles are data, and the image carries them.** `src/seed/personas/*.md` are read at seed time (tsc does not copy Markdown), so `docker/Dockerfile` copies them into the runtime image; a renamed column, a short row or a value the garment form would drop fails the seed (and `persona.spec.ts`) with the bible and row named. Edit a table, not the code, to change what a persona owns or wears.
- **`ci.yml`'s `publish` job pushes `:latest` and `sha-<7>` only after `check` and `e2e` pass** (and semver tags on `v*` tags from `tag-release.yml`), amd64 only, GHCR only. Until 2026-09-25 publishing was a separate workflow racing CI, so a red run still deployed. Docs-only pushes to main (`docs/**`, `*.md`) skip CI and publish entirely; pull requests always run both jobs, docs-only ones included, because branch protection requires them. Merging to main is deploying: the homelab autoupdater redeploys within the hour. The browser job runs with the PWA on, as production does; specs sign in through `test/support/e2e-session.ts`. Load test and Lighthouse run nightly (`nightly.yml`).
- **A capsule only ever holds its owner's garments, and the capsule filter relies on it.** `inCapsule` is applied without checking whose capsule it is (the tiles sentinel, the builder's row fragment): on another wardrobe it matches nothing because `changeMembership` drops every garment of another owner. A second writer of `capsule_garment`, or anything that moves a garment between owners, must keep that, or `?capsule=` starts showing another wardrobe's garments. Pages that render a capsule's name still look it up in the addressed wardrobe (404).
- **Adding an occasion is a migration.** `outfit_calendar_occasion_check`, `week_template_occasion_check` and `trip_outfit_occasion_check` list `src/wardrobe/occasions.ts`'s `OCCASIONS`, so a new one fails every insert until `npx drizzle-kit generate` recreates the constraint; add its `occasion.<value>` string (a missing one is a type error). The display order is the array's order: reordering it is code only.
- **Wears count days, not entries, and every new wear count must too.** With several outfits a day, one garment has a `garment_wear` row per worn entry that held it (so unmarking one entry removes exactly its rows); every count and wash rule is `count(distinct day)` (`wearsSinceWashSql`, `wearSummary`, `availability.ts`, insights' `insightGarments` and `wornPairs`). A new query that counts rows would count "office then dinner, same shoes" twice (`wears.spec.ts` has that case).
- **Adding a property value, a garment type, a colour or a style is a migration.** The check constraints (`garment`'s, and `plan_item`'s and `style_profile`'s, #34) list `src/wardrobe/properties.ts`'s and `style.ts`'s sets, so a new value there fails every insert until `npx drizzle-kit generate` recreates the constraint; add its `property.<name>.<value>` string too (`labels.spec.ts` fails without it). Removing a value needs a data step for rows that hold it.
- **A garment form without properties must not clear them.** An edit writes every field, and a form the installed app cached before properties existed posts none. Every form that renders them posts `props=1` (a hidden field in `PropertiesMain`); `readGarmentForm` reads and writes properties only with it (`garment-properties.spec.ts` saves an old-shaped form over a tagged garment). The product link and price have their own marker, `product=1` (a hidden field beside them in "More details"), because forms cached between the two post `props=1` without them (`garment-product.spec.ts`). The care fields (quantity, wash after, condition, #7) have `care=1`. A new garment field that old cached forms lack needs the same care: a marker of its own, posted beside the fields it guards.
- **Suggestions come from the generator, through `ideasFor`, and its randomness is seeded.** A new surface that suggests outfits (Today #15, Styling's Shuffle #42) calls `ideasFor` (or `generateIdeas` with a pool from `ideaPool`; "Goes with my closet" #18b is one other pool, `closetGarments`, with its item only ever `locked`, and the week planner #16 the other, `weekPool`: dirty garments included, judged per day by `cleanCopies` with the week's own wears), never a query of its own, or the availability, colour, clash and duplicate rules fork. Nothing in its data path may use `Math.random` or the clock: a gallery page is a function of (pool as a set, seed, page), and the sentinel's page 2 must continue page 1. The pool is a query's rows, whose order Postgres never promises without ORDER BY (it follows the heap and the plan: a reseed, an update or an index choice reorders them), so `generateIdeas` orders each role by id before it draws by position; a planned week that differed after `--reset` was this (#16). A new seeded path that draws by position does the same, never trusting row order. Bump `GENERATOR_VERSION` to reshuffle every seed on purpose.
- **A sentinel inside a scroll container triggers on `intersect`, and a delete swap needs a 200.** htmx's `revealed` listens to the window's scroll, so a sentinel at the end of a horizontal strip (the gallery) never fires with it; `intersect` uses an IntersectionObserver, which sees the container's clipping. htmx swaps nothing on a 204, so a write whose answer removes its element (`hx-swap="delete"`, the gallery's "Clashes") answers 200 with an empty body.
- **Postgres' `least()` and `greatest()` ignore NULL arguments.** `least(quantity, wears / null)` is the quantity, not null, so a garment that never needs a wash came out fully dirty until the SQL wash rule (`dirtyCopiesSql`) used a CASE; `wears.spec.ts`'s SQL-against-TypeScript case table caught it. Compare any SQL form of a pure rule against the rule the same way.
- **Never delete an outfit with a plain `DELETE`.** `outfit_calendar.outfit_id` and `garment_wear.outfit_calendar_id` both cascade, so it erases every wear of the days the outfit was worn. Go through `deleteOutfit`, which detaches them first (`detachOutfitWears`; Wears and washes). Deleting one calendar entry does cascade its wears, deliberately; account deletion takes everything. A new path that deletes outfits or calendar entries in bulk must choose between the two on purpose; `wears.spec.ts` covers both.
- **"Delete the outfit once nothing holds it" asks one predicate, `outfitIsHeld`** (`src/web/outfits/references.ts`: a calendar entry on any day, worn or not, and a trip's `trip_outfit`), like `photoIsReferenced` for photos. `deleteOutfit` cascades every holder, so a holder missing from the list is a row silently deleted with the outfit: until #69's review, `removeUnheldOutfits` (Undo, the daily re-plan's swap, Change) asked only `outfit_calendar` and took planner-made outfits off the trips that held them, packing lists included. A new table with an `outfit_id` joins the predicate in the same change. `removeUnheldOutfits` locks the outfits (`FOR UPDATE`) before asking, so a holder being inserted meanwhile either committed first and is seen, or waits and fails on the deleted outfit's foreign key; never a silent cascade. `replace-entry.spec.ts` and `week-plan.spec.ts` hold a planner-made outfit on a trip through each of the three paths.
- **A garment's status changes only through `setGarmentStatus`, and closet reads only through `inCloset`.** A new query that lists "the wardrobe" without the predicate shows wishlist items (things not owned) in the closet, the builder or laundry; one that writes `garment.status` directly skips the machine's refusals. `insertGarment` takes an entry status (closet or wishlist, never archived). The grid's `?archived=true` is the URL contract kept from before the status; internally it is `scope: 'owned'`.
- **A wishlist form's `replaces` has its own marker, `wishlist=1`.** Closet forms and forms cached before #18 post neither and must leave the stored replacement alone (the product, care and props markers' rule). The replacement is stored only through `replacementOf`, which is where the same-owner rule lives: a second writer of `replaces_garment_id` must go through it.
- **A plan item never names a garment, and matching must stay derived.** Which garments fulfil an item is computed on every read (`matchPlan` over `inCloset`), so a purchase, an archive or a retag moves the gap view with nothing to update. A stored link (the issue's `plan_item_garment`) would need every garment writer to keep it in step; add one only as an explicit owner's pin, never as a cache. A new reader of a plan's gaps goes through `planGaps`, and proposed items stay out of matching.
- **A candidate link is read only through `onWishlist`, and is never a fulfilment.** `plan_item_candidate` keeps a bought garment's link (it stops mattering; nothing deletes it on buy, so a grantee's purchase never writes the owner's plans). A new reader that joins the table without `onWishlist` would list closet garments as things to buy; one that counts links toward an item would break derived matching (the gotcha above). Writes go through `changeCandidates`, where the same-owner and wishlist-only rules live.
- **A writer that can take a garment off a trip's packing list prunes its packed marks** (`prunePacked`, `src/web/trips/packed.ts`, in the same transaction). The list is derived from the trip's outfits' slots, so today that is removing a trip outfit, editing an outfit's slots and deleting an outfit (`tripsOfOutfit` first: `trip_outfit` cascades). A new path that changes slots or trip outfits (Styling's save, #42; a bulk outfit delete) must call it too, or a garment that comes back to the list comes back already packed.
- **A unique violation is answered only for the constraint the caller names.** `isUniqueViolation(error, constraint)` (`src/db/errors.ts`) takes the constraint (`UniqueConstraint`: the names are constants beside their indexes in `schema.ts`) and is false for any other, so the caller rethrows. Matching any `23505` once turned the plans' one-active race into "a plan with this name already exists". A new writer that answers a violation with a message adds its constraint to `UniqueConstraint`.
- **Condition is not availability, and `away: repair` is not `needs_repair`.** Condition (good, needs_repair, replace_soon) is a garment property anyone who can edit sets; it never feeds `availableGarment`/`isAvailable`. Away (lent, repair) is the owner's record that the garment is physically elsewhere, and does. Do not merge the two.
- **Upstream references are limited to attribution.** The only permitted mentions of the upstream project are the attribution link in the About page and README and code comments citing upstream issues or PRs. Any other occurrence of the upstream company or project name (assets, links, config defaults, CI values, marketing copy) is a rebrand regression; grep for it before a PR.
- **`npm install <package>` does not run the project's own `postinstall`**, so `patch-package` never applies `patches/` to a fresh `node_modules` built that way, and the drift test fails in drizzle-kit ("there is no parameter $1"). After adding a dependency to a new worktree, run `npx patch-package` (or `npm ci`, which does run it).
- **`/.well-known/*` answers `{}` to anything** (`src/web/shell/routes.tsx`, to keep browser and tool probes out of the error log). An MCP client refused with a 401 may look for OAuth metadata there (`/.well-known/oauth-protected-resource`) and gets an empty object: harmless, since `/mcp` offers no OAuth, but its error can read oddly. Real OAuth for `/mcp` would need real documents there.
- **`@fastify/rate-limit`'s `createRateLimit()` answers `isAllowed: true` only for the allow list.** A counted request is `isAllowed: false` whatever its count; over the limit is `isExceeded`. `/mcp`'s link import budget reads both (`src/web/mcp/routes.ts`).
- **Regenerate `package-lock.json` only with Node 22 / npm 10** (`nvm use`, or `docker run --rm -v $PWD:/app -w /app node:22 npm install --package-lock-only`). npm 11 prunes nested entries that npm 10's `npm ci` in the Docker build then reports as missing, so the image build fails while local installs look fine.
- **pgvault-dev runs Postgres 18; production and CI run 17.** Features new in 18 pass locally and fail in CI.
- **`precommit:full` is minutes long** (Lighthouse and load test included); CI runs those two nightly, not per push.
- **Playwright serves whatever is on :3000** (or on `PORT`, which `playwright.config.ts`'s `baseURL`, the spec's `APP_ORIGIN` and the started server all follow: `PORT=3107` runs a worktree's specs beside another's). Its webServer is `npm run start:test` (`test/support/test-server.ts`): the existing build (the npm scripts build first; it imports `dist/`, so a stale or missing build is what runs) served by `serve()` with a stub cutout runner (3 s a photo), so an upload goes pending and its cutout arrives without the model. `reuseExistingServer` is on outside CI, so a running `start:dev`/`start:prod` is tested instead, with the real model on uploads. Stop it before `verify:push`.
- **The integration harness configures the app explicitly.** `createTestApp(overrides)` builds `Config` with `loadConfig({ env: { ...BASE_ENV, ...database, DATA_PATH, ...overrides }, envFiles: [] })`: neither the process environment nor `.env.local` reaches a spec, and different overrides in one file are fine. Its logger writes JSON lines into `t.logs` (LOG_LEVEL `debug`, nothing on the console); `{ appLog: true }` gives the real stdout + `app.log` outputs instead (file-route.spec.ts reads app.log). Vitest runs every file in its own child process (the default `forks` pool with `isolate`), which keeps one file's app, rate-limit counters and mocks out of the next: never set `isolate: false` or `pool: 'threads'` on the integration project.
- **The integration harness is signed in by default.** `createTestApp` registers `owner@example.com` at boot and `t.inject` sends that session (`t.owner.cookie`) unless the request has its own `cookie` header or passes `anonymous: true`. A test about signed-out behavior must say `anonymous: true`; one that forgets asserts on the owner's view.
- **`config: { public: true }` is the only way past the session gate, and static paths never have a session.** The root preValidation hook in `app.ts` skips `static-prefixes.ts` paths, so a route under one (`/file/**`, `/healthz`, `/manifest.json`) always sees `req.auth` and `reply.locals` undefined and must be public, or it answers every request with a login redirect. `sessionUserId()` on a public route throws: a public handler reads `req.auth` itself if it cares (the invite landing page).
- **htmx does not swap 4xx/5xx responses** (its default `responseHandling`), boosted or not, and a boosted form's events fire on the body, not the form. A form whose refusal re-renders with a 4xx must be a native post (`hx-boost="false"`, as every form in `src/web/auth/`: `PostForm`), or the user sees nothing. Native posts are also what makes browsers offer to save a password: a boosted registration let Firefox generate one and never save it, locking the owner out. Enforced: `expectNativePostForms` in `test/integration/pages.ts` fails any rendered page with a `<form method="post">` that is still boosted; in JSX use `PostForm` (`src/web/auth/form.tsx`), the only native-post form component. It caught three on 2026-09-26: the outfit save form, the garment form and the share revoke/leave buttons. **Every `PostForm` submits once** (`data-submit-once`, `public/js/submit-once.js`, loaded by the layout on every page): a second submit while the first is in flight is cancelled, and the form's buttons (and those joined by `form=`) are disabled a tick after the submit (disabling the submitter in the submit event drops its `name=value` from the post), marked `submitDisabled` so only those are re-enabled: on a back/forward-cache return (`pageshow` persisted) and on an htmx request error. A control the offline guard or the page disabled is left alone. The server stays the guard where a duplicate matters (`pickIdea`); `test/gallery.spec.ts` taps twice during a slow post and counts one.
- **The dock stacks above every page, and its active tab comes from one route table.** `.dock` is z-index 900 in `main.css` (daisyUI gives it 1, so the outfit card's `relative z-10` calendar button drew over it); page content stays at z-20 or below and the navbar, whose drawer must cover the dock, is 1000. A bar fixed above the dock uses `bottom-dock` (`--spacing-dock` in `main.css`: the dock's height with the safe area). A tab is lit on every page of its section: `sectionOf` (`src/web/layout/sections.ts`) maps the request path, whole segments (`/capsules/*` is Wardrobe, `/wardrobe-share` is nothing). A new top-level route shows no tab until it is added there. `DOCK_TABS` is which sections the dock shows, in order; `SECTION_HOME` (the tabs' links) minus Today is the service worker's stale-while-revalidate tab roots (`OPENS_STALE`, `page-cache.ts`): a new tab root must render byte for byte the same while nothing changes, or be left out of it on purpose like Today. `test/dock.spec.ts` probes the dock at 390 px on each page with floating controls.
- **A page's `<main>` needs `w-full` beside `max-w-* mx-auto`.** The body is `flex flex-col`, and a flex item with auto margins does not stretch: it sizes to its content, capped by the max width. A horizontal scroll strip (its max-content is every card) then widened the garment page to 512 px on a 390 px phone (#18b); short content made pages narrower than the screen. Every such `<main>` carries `w-full` since; the gallery's `sm:mx-auto` only applies past the phone.
- **htmx reads only the first `<meta name="htmx-config">`.** Keep the config in one JSON object. `disableInheritance` is on, so any attribute that must reach descendants needs `hx-inherit` on the ancestor (the body has `hx-inherit="hx-boost hx-indicator"`; without it no link is boosted and no tap shows feedback). An element with its own `hx-indicator` replaces the inherited one, so the tapped link is no longer marked.
- **`public/build.json` lingers after `npm run build`.** `start:dev` then serves assets with that build's cache key; set `NODE_ENV=development` in `.env.local` (caching off) or delete the file if styles look stale.
- **Indexes and constraints are declared in `src/db/schema.ts`, never only in a migration file.** `drizzle-kit generate` diffs snapshots, not the database, so DDL hand-added to a migration is invisible to every later diff and the drift test reports it. Postgres does not index foreign keys on its own. `test/integration/migrations.spec.ts` lists the expected index names.
- **`patches/drizzle-kit+0.31.11.dev.patch` fixes `pushSchema` (`drizzle-kit/api`), which the drift test depends on.** Unpatched, its Postgres introspection drops query parameters (the composite primary key lookup fails with "there is no parameter $1") and reads a composite constraint's columns in no particular order, so `outfit_garments_pkey` and `wardrobe_share_grantor_id_grantee_id_unique` show up as drift. The CLI (`drizzle-kit pull`) shares the unordered query: check column order in anything it emits. The `.dev.patch` suffix is what makes patch-package skip it under `npm ci --omit=dev` (the Docker runtime stage); a plain `.patch` for a devDependency errors there and only passes while `CI` is unset. Re-check both bugs before bumping drizzle-kit; a version bump drops the patch.
- **`pg` is pinned to the exact version `@mikro-orm/postgresql` pins** (8.20.0), so there is one node-postgres copy: the app's, and the legacy-database helper's (a devDependency now). Bump them together until the helper goes.
- **The drift check ignores one legacy statement.** `tablesFilter` hides `mikro_orm_migrations` from drizzle-kit but not its serial sequence, which introspects as a standalone sequence that push would drop; `test/support/schema-drift.ts` filters exactly that `DROP SEQUENCE`. `drizzle-kit pull` against a legacy database emits a `pgSequence` for it: delete it, never add it to the schema.
- **Photo bytes are written before any row, and rows commit together.** `Photos.storeUpload` / `copy` write the files and return a `NewPhotoRow` without inserting it; the caller inserts it with `insertPhotoRow(tx, row)` inside the transaction that points a garment at it and calls `deleteVariants` if that transaction fails (`commitWithPhoto`, `src/web/wardrobe/writes.ts`). Garment deletion and photo replacement delete the `file` row in the same transaction and unlink after commit. Nothing in `src/web/files` inserts or deletes a `file` row; it only changes `version` and the cutout columns, through `applyCutoutEvent`.
- **The DB cascade deletes rows, never bytes.** `deleteRule: 'cascade'` on `File.createdBy` and `Garment.owner` drops the rows when a user goes, but only `Photos.deleteVariants` removes the files. Every path that removes a `file` row (`removeGarment`, photo replacement, `POST /auth/delete-account`) must unlink through `Photos` after commit; account deletion also deletes the user's `pending_photo` rows in its transaction and unlinks those bytes (the cascade would leave them unexplained); the cascade is the safety net and `reconcileStorage` (`src/maintenance/reconcile.ts`: nightly, or `npm run maintenance:reconcile`) is the backstop that deletes photo sets and rows older than a day that nothing references. Outfits own no files; **a calendar entry owns its outfit selfie** (#19): deleting the entry deletes the selfie's `file` row in its transaction and unlinks after commit (`removeEntry`); deleting the outfit keeps the selfie as a look (`selfie.outfit_calendar_id` set null). **What "references" a photo is one list, `photoIsReferenced`** (`src/web/files/references.ts`: `garment.photo_id` and `selfie.photo_id`): a new table with a photo column must join it, or reconciliation deletes each of its photos the night after it is stored (`reconcile.spec.ts` proves selfies survive).
- **HEIC uploads are buffered.** sharp's libvips has no HEIC decoder, so `image/heic`, `image/heif` and an `application/octet-stream` named `.heic`/`.heif` are read whole (capped by `MAX_HEIC_BYTES`, 413 past it), their dimensions checked against `MAX_INPUT_PIXELS`, and decoded with heic-decode to raw RGBA that sharp reads as `raw` input (no JPEG round trip). libheif applies the container's rotation while decoding and raw pixels carry no EXIF, so HEIC photos are stored as decoded. Chrome/Android cannot decode HEIC in a canvas: `photo-input.js` leaves such a file as it is (no downscale) and the form submits the original; the server decodes it and makes the cutout.
- **All user-supplied URL fetches go through `outbound-fetch`.** Never `fetch()`, `http.get` or an HTTP library on a URL a user typed, pasted, shared or that a fetched page named (an image candidate, a redirect): linux-box reaches the NAS, pgvault and the router, and a check of the URL's name followed by a normal request is open to DNS rebinding (the socket resolves again). `createOutboundFetcher` checks every resolved address and pins the connection to it (Request security, Outbound fetches). Its `destinations` and `resolve` options exist for the specs only; production passes neither. The spec stands in for the internet with the loopback alias `127.0.0.2`, which Linux routes (all of 127/8 is `lo`) and macOS does not without `sudo ifconfig lo0 alias 127.0.0.2`.
- **A link import's `linkPhoto` is a name the client sent: the `pending_photo` row is the capability, not the name.** Claiming (`createGarmentWithLinkPhoto`) and discarding (`discardLinkPhoto`) both require a pending row for that name **and the requesting user**, so knowing another user's pending name (or a saved photo's) gets nothing. `commitWithPhoto` deletes the new bytes when its transaction fails, which is right only for bytes the same request wrote: the claim never deletes bytes, and the discard deletes them only after taking its own pending row. Both also take `lockPhotoName` (`src/web/files/queries.ts`, a transaction advisory lock on the name) and check that no `file` row exists; the pending row's delete orders a save, a discard, an eviction and reconciliation, so exactly one of them wins.
- **Abandoned link imports must never reach reconciliation's guard.** The guard refuses a whole run past 25 unexplained photo sets (or a fifth of them), and at 10 imports a minute one person browsing without saving passes that in a day; then nothing is cleaned, legitimate orphans included. So every stored pending photo has a `pending_photo` row: reconciliation deletes day-old ones (row and bytes) in a pass of its own before the plan, reports them as `pendingPhotosDeleted` apart from the guard's count, leaves younger ones out of the plan, and deletes pending rows whose bytes are gone (`pendingRowsWithoutFiles`). The guard keeps its thresholds for what nothing explains. A new feature that stores bytes ahead of their `file` row needs the same: a row that explains them, or it jams the nightly clean-up.
- **Link import's photo choices are never stored.** Only the pick is: the candidates are previews inline as `data:` URLs (the CSP's `img-src` allows `data:` and no other origin, which is also why remote images cannot simply be shown), and the photo a pick replaces is discarded at once. With the per-user cap of 10 pending photos, one user can never hold more than 10 stored imports.
- **The share target is a GET that fetches nothing.** Android opens `/wardrobe/new/from-link?title=&text=&url=` (the link arrives in either `url` or `text`; `linkIn` takes the first http(s) link). Fetching stores a pending photo, and a GET never writes; a POST share target would also need its Origin to pass the same-origin check. The person taps Fetch.
- **`/file/**` serves from DATA_PATH, which also holds `app.log`.** The route accepts only a photo base name as `parseStoredName` defines it (the same rule reconciliation uses); a looser "safe characters" regex served `/file/app.log`, session cookies included, on the public hostname until 2026-09-25. Never add a second definition of a stored name. `test/integration/file-route.spec.ts` covers it. **Public by name is only for photos a share may show**: an outfit selfie's name is a 404 there (`isPrivatePhoto`) and its share id makes no preview; a new kind of private photo gets its own session-checked route (as `/selfies/*`) and joins `isPrivatePhoto`.
- **Drizzle writes a SQL field's columns without their table in a single-table select.** `db.select({ x: sql\`... ${other.col} = ${file.id} ...\` }).from(file)` renders `"col" = "id"`, so a correlated subquery compares the subquery table's own columns (`garment.photo_id = garment.id`) and silently answers wrong. `photoIsReferenced` is an uncorrelated `IN (... union all ...)` for that reason; in a `where` or a joined select the columns keep their tables.
- **An `sr-only` input escapes a scroll container.** It is absolutely positioned, so without a positioned ancestor its containing block is the page: file inputs inside the outfit page's horizontal Worn strip widened the whole page to the strip's scroll width (1078 px at 390). The label that wraps one is `relative` (`SelfieUpload`).
- **The request log never holds a credential and skips static paths.** One line per request from the root onResponse hook (`GET /wardrobe 200 3.1ms`, context `Http`): method, `loggableUrl`, status, time, never headers. The session cookie is a year-long bearer credential and the logs reach `app.log` and Loki; the logger also redacts `cookie`, `authorization` and `set-cookie` under any logged `req`/`res` (`src/logger.spec.ts`). Fastify's own request logging stays off (`LogController({ disableRequestLogging: true })`): it would log every thumbnail and heartbeat.
- **`PhotoStorage.store` must be atomic.** A variant is read (the thumb writer, `/file/**`) while another write may replace it (a cutout job or mask save rewriting the cutout and thumb); storage writes to `DATA_PATH/.incoming/` and renames. Writing to the final name made every real photo+cutout upload fail with 500 when the browser still uploaded its cutout beside the photo: the thumb step read a half-written cutout. Boot removes `.incoming` entries older than an hour, never fresh ones (the reconcile CLI boots beside a live server). A cutout of an existing photo (`writeCutout`: mask edit, server job) rewrites the thumb before the row takes the new version.
- **Cutout bytes are written under the row lock, after the state machine accepted.** `Photos.writeCutout` locks the `file` row, and `applyCutoutEvent` runs its `effect` (nobg and thumb) only for an accepted event, before writing the row. Writing first and checking after would let a late job result overwrite a mask the user saved meanwhile. The slow parts (encoding the upload, composing the model's cutout) happen before the lock. `test/integration/cutout-queue.spec.ts` edits, replaces and bumps a photo while a job runs.
- **onnxruntime-node**: `.npmrc` sets `onnxruntime-node-install-cuda=skip` (its postinstall otherwise downloads 300+ MB of CUDA/TensorRT providers on linux-x64; the Dockerfile copies `.npmrc` into both stages), and the runtime image deletes the darwin, win32 and linux-arm64 binaries. It is pinned (1.21.0, what the benchmark measured): bump it deliberately and rerun `cutout-model.spec.ts` with the real model. `src/cutout/child.ts` imports nothing from `src/` at runtime (types only): in the tests it runs as TypeScript under Node's type stripping, where a relative import would need an extension.
- **sharp orders a pipeline's operations itself.** `composeCutout` joins the alpha (`joinChannel`), reads the RGBA back, and only then pads (`extend`) in a second pipeline; a single-channel raw mask needs `extractChannel(0)` after `resize` or sharp emits it as 3-channel sRGB (the benchmark's traps).
- **Pipelines started inside a multipart `for await` loop must be armed with a no-op catch at creation.** `Photos.storeUploadParts` starts the photo's pipeline without awaiting it (an unconsumed part hangs busboy; later parts, such as an old page's `nobgPhoto`, are drained) and the caller awaits it after the loop; a rejection while later parts are still being read (an undecodable HEIC/JPEG) was an unhandled rejection that exited the process with an empty reply. `startPipeline()` attaches the catch and returns the same promise, so the real error still surfaces from the await. `test/integration/heic.spec.ts` records `unhandledRejection` and asserts the app answers the next request. Node's default (crash loudly) is kept on purpose; do not add a process-level handler.
- **Reconciliation refuses wholesale deletions.** It deletes photo sets whose `file` row is gone, so a database that lost its rows (a restore, the wrong `DATABASE_*`) would have it wipe every photo. `guardRefusal` (`src/maintenance/reconcile.ts`) stops a run that would delete anything while the file table is empty and storage holds photos, more than 25 sets, or (above 5 sets) more than a fifth of the stored ones: it logs a warning, deletes nothing, reports `refused`, and the CLI exits 3. `--force` is the operator's override after a `--dry-run`. `test/integration/reconcile-guard.spec.ts` covers each rule. Link imports' pending photos are explained, not counted (see the link import gotcha above; `link-import.spec.ts` reconciles 27 abandoned imports and then a real mismatch).
- **Only the server schedules the nightly reconciliation, the push reminders and the week's re-plan.** `serve()` (`server.ts`) starts `scheduleNightly` (03:00 in `APP_TIMEZONE`, recomputed after every run, never overlapping) when `MAINTENANCE_ENABLED`, with `PWA_ENABLED` the reminders' `scheduleMinutely`, and with `WEATHER_ENABLED` the re-plan's (each stopped at `preClose`, waiting for a run in flight, before the pool ends); `createApp()` does neither, so the integration harness and the CLIs never hold a timer or send a notification. A spec runs one minute's reminders with `sendDueReminders(deps, now)`.
- **An auto entry is the planner's only until someone touches it.** `outfit_calendar.planned_by` is what keeps the daily re-plan and Undo off a person's choice (#16): a new writer that edits an entry (its outfit, its occasion, worn) must set it to `user` in the same transaction, as `setEntryWorn`, `updateOutfit` and `setEntryOutfit` do, or the next morning's re-plan may swap out what they chose. Only the planner writes `auto` (through `pickIdea`'s `plannedBy`), and a new reader of "the planner's entries" filters `planned_by = 'auto'` rather than joining `week_plan_entry` alone (that row stays, as provenance, after the person takes the entry over).
- **A push reminder is claimed before it is sent, and claimed once.** `push_reminder`'s primary key (device, kind, day) is the only thing standing between two overlapping servers and a double notification; a new kind of scheduled send claims the same way (an insert that lands, `ON CONFLICT DO NOTHING RETURNING`), never "check, then send". A reminder's time is a wall-clock minute in `APP_TIMEZONE`, turned into an instant per day with `instantAt`; never add 24 h to yesterday's instant (DST).
- **Every form or control saved on change is built by `src/web/autosave.tsx`** (`AutosaveForm`, or `autosaveAttributes` for controls inside a larger form), never by hand with `hx-trigger="change"`: `expectAutosaveControls` (`test/integration/pages.ts`) fails a page with one. In htmx 2 a change made while the form's save is in flight is queued on the element that issued it and re-issued after the answer is swapped in, reading the form then; an answer that replaced that element (`outerHTML` on the section) silently dropped the queued save, and one that re-rendered the controls put back what the person had changed since (found on the push reminders' form, #15). The helper sets one queue per form, latest last (`hx-sync="closest form:queue last"`), posts the whole form each time, and answers the status line (`AutosaveSaved`) or, where the server must redraw controls (tagging's presets, the garment form's properties), a region's contents, never the element that posts; `public/js/autosave.js` (every page) drops an answer overtaken by an edit, whose own queued save lands instead. So every control in a redrawn region must itself post on change, and **no other swap may replace an autosave form** (its queued save would die with it): sibling writes answer regions beside it (the wear section's `#garment-wear-status`, the weather's `#weather-location` and `#weather-offset`). `test/autosave.spec.ts` changes each family several times on a slow network.
- **`@fastify/static` 10 applies `setHeaders` after `send`'s own Cache-Control**, passing the `FastifyReply` (`reply.header()`), which is what makes the per-file policy in `registerStaticAssets` (`app.ts`) work; before 10 it was the raw response and `send` overwrote it. `test/integration/delivery.spec.ts` asserts the headers.
- **`test/support/legacy-migrations.ts` loads the MikroORM migrations through `dynamicImportProvider`.** MikroORM's default is an `import()` inside `node_modules`, which Vitest does not intercept: Node then loads the migration `.ts` itself with type stripping, outside Vitest's resolution. The provider's `import()` sits in our file, so Vitest's module runner handles it. The frozen migrations import nothing from `src/` (Migration20260925182919 keeps its own copy of the colour list: its ordinals are positions in the enum as it was).
- **Vitest runs a function returned from `beforeEach`/`beforeAll` as that hook's cleanup.** `beforeEach(() => mock.mockReset())` returns the mock, so Vitest calls it after every test; with `mockRejectedValue` set, the test fails with the mock's rejection. Brace hook bodies that return anything. Jest ignored the return value.
- **`vi.mock` factories return the module namespace.** Mocking a CommonJS default export is `vi.mock('heic-decode', () => ({ default: { all: vi.fn() } }))`, and `vi.mocked(heicDecode.all)` types it; Jest's `() => jest.fn()` shape throws ("is not returning an object"). `vi.mock` is hoisted like `jest.mock`.
- **"Today" always comes from `todayIn(APP_TIMEZONE, now)`, in app code and in tests.** Never `new Date().toISOString().slice(0, 10)`, `toLocaleDateString` or a UTC getter: from 19:00 or 20:00 in New York until midnight that is tomorrow's date, on Saturday evening next week's, and a day after today cannot be marked worn (409). main went red at 00:01 UTC on Sunday 27 Sep 2026 because the authorization matrix planned its fixture entry on UTC's today; the same PR had passed before midnight UTC. Routes and tools call `todayIn(config.timeZone, new Date())` / `todayIn(ctx.timeZone, ...)`; integration specs use `t.today()` (the harness's app zone, read at the call so a faked Date moves it); Playwright specs use `householdToday()` (`test/support/household-today.ts`, the server's `loadConfig()` zone). ESLint's `no-restricted-syntax` refuses `toISOString().slice/substring/split` and `toLocaleDateString` in `src/`, `test/` and `scripts/`. `test/integration/today.spec.ts` pins the clock (`vi.useFakeTimers({ toFake: ['Date'] })`) where UTC and the household disagree: a UTC Sunday that is Saturday evening in New York, UTC midnight on a month boundary, the week and month turning on the day DST ends, New Year's Eve, and Auckland (ahead of UTC); it covers the calendar week and highlight, the plan page, worn and its 409, Wore today, Washed, laundry, "Bought it"'s purchase day, Today (#15: its plan, "Wear this", `get_today`) and the MCP tools. A new "today" consumer gets a row there.
- **The calendar's unit specs (`src/web/calendar/*.spec.ts`) run in America/New_York through their own project**, `unit-new-york` in `vitest.config.ts` (`env: { TZ }`, `pool: 'forks'`), to prove the date logic ignores the process's zone. Vitest assigns `env` to the worker's real `process.env` before importing the spec, and Node reloads the zone on that assignment in a child process; worker threads keep the parent's zone, so the project must stay on forks. Each spec's first test asserts the offset. Another spec that needs a zone gets its own project the same way; it stays under `npm test` if its name starts with `unit`.
- **Vitest is pinned to `~4.0`.** Vitest 4.1 depends on Vite 8, whose optional peer chain (`@vitejs/devtools` back to `vitest`) crashes npm 10's resolver with "Cannot read properties of null (reading 'edgesOut')", and npm 11 lockfiles break the Docker build (see the lockfile gotcha). Bump only when `npx -y npm@10 install -D vitest@<new>` resolves, and prove the lockfile with `npm ci --dry-run` on npm 10.
- **hono/jsx types an element as its rendered string.** At runtime `<Page />` is a node whose `toString()` renders it and returns a Promise once any component is async; `String(<Page />)` can silently be `[object Promise]`. Render only through `renderToString`/`renderPage`/`renderFragment` (`src/web/render.ts`), which await it.
- **An async Fastify hook that answers must `return reply`.** `requireSession` returns `reply.redirect(...)`; sending without returning lets the handler run and send again. A hook that does no async work takes Fastify's `done` callback instead (`@typescript-eslint/require-await` rejects an `async` one without an `await`).
- **Errors before the root preValidation hook have no page context.** A body that fails to parse reaches the error handler with `reply.locals` unset, as does anything on a static path (the hook skips them), so both answer `{ statusCode, message }` with the right status instead of the page. A schema validation failure comes after the hook and gets the 400 page. The hook must stay at preValidation (not preHandler): validation runs between the two.
- **A Fastify plugin inherits only what its parent had when it was registered**: hooks, content-type parsers, decorators, the error handler. `createApp()` therefore registers every root piece (same-origin hook, rate-limit plugin, session hook, security headers, request log, cookie, compression, `@fastify/formbody`, multipart, the error handler) before `webPlugin`; one registered after it silently never applies to the routes (a form parser added late makes every urlencoded post a 415). The not-found handler is set at the root and runs the root hooks too, which is why a 404 page shows who is signed in.
- **An index that mixes a column and an expression must write the column as an expression too.** drizzle-kit's introspection (the drift test's `pushSchema`) marks every column of an index with any expression as an expression, so `capsule_owner_id_lower_name_unique` declared with `table.ownerId` as a plain column beside `lower(name)` read back as drift (drop and recreate). It declares `owner_id` as the expression ``sql`${table.ownerId}` `` instead, which generates the same SQL.
- **drizzle-kit does not emit a type change on a column it renames.** `0001_calendar_day.sql` renames `date` to `day` and changes timestamptz to date; the generated file had only the rename, and the `ALTER COLUMN ... TYPE ... USING` was added by hand. The drift test catches a missing statement; the rename prompt needs a TTY (drive it from a terminal, not a pipe). Without one (an agent), as for `0003_user_device_push.sql`: write the SQL in drizzle-kit's form (`--> statement-breakpoint` between statements), build the snapshot with drizzle-kit's own `generateDrizzleJson(schema, previousSnapshotId)` from `drizzle-kit/api`, add the journal entry, and prove it with a second `npx drizzle-kit generate` ("No schema changes") plus the drift test. For `0004_garment_web.sql` (a rename among many other changes) drizzle-kit generated everything with the column still under its old name in the schema, then the rename, its `USING` and the data guards were written in and the snapshot rebuilt from the real schema.
- **Playwright's default Chromium (the headless shell) reports `Notification.permission` as `'denied'`** even after `grantPermissions(['notifications'])` (the Permissions API says `'granted'`), so the profile's push controls read "blocked". `test/push-settings.spec.ts` runs on the full Chromium build (`test.use({ channel: 'chromium' })`, installed by `playwright install chromium`). Headless Chromium has no push service either: that spec stubs `PushManager` in the page and lets everything server-side run for real.
- **A migration that changes data asserts its assumptions and aborts.** `0001_calendar_day.sql` raises (so the whole batch rolls back and the boot fails with `MigrationFailedError` naming the reason) if any calendar value is not UTC midnight or any row has notes, rather than shift a day or drop text. Do the same for any conversion whose correctness depends on what the data looks like.
- **The CLIs never migrate.** `runCli` (`src/maintenance/cli.ts`) checks `requireCurrentSchema` first and exits 1 with "The database is N migration(s) behind this build. Start the server..." when the image is newer than the database. A recovery tool run beside a live server must not change the schema under it (until 2026-09-26 they booted the whole app, migrations included). `test/integration/migration-runner.spec.ts` covers the check.
- **Scratch databases are named with their creation time** (`closet_it_<base36 seconds>_<hex>`). A killed test run (`npm run check` stops the tests when another check fails) never drops its databases; the integration project's globalSetup (`test/support/sweep-scratch-databases.ts`) drops idle ones older than an hour, never with FORCE, and leaves names it cannot date.
- **Vitest does not type-check.** It compiles with esbuild, which strips types; `npm run typecheck` (the root `tsconfig.json`: `src/`, `test/`, `scripts/`, the configs; no test globals, so a helper that calls `expect` without importing it fails here) and `npm run build` (`tsc -p tsconfig.build.json`, `src/` only) do. The service worker has its own `views/assets/tsconfig.json` (WebWorker lib, strict) because it runs in a worker scope. It was 790 errors until 2026-09-25, one of them a live 500 (a misspelled MikroORM exception import is `undefined` at runtime, so `instanceof` threw).

- Behavior assertions go in `test/integration/` first: a spec that boots the real app and checks the HTML, headers, rows and files is the default proof that a change works, and it runs in seconds without a build or a browser. - **Changes land through pull requests** (owner decision, 2026-09-26). `main` is protected: the `format, lint, types, unit + integration` and `browser (production config)` checks must pass, and the branch must be up to date with `main` (strict), which is what catches two parallel branches that each pass alone (a duplicate migration number, conflicting edits). - **Migrations and parallel branches:** two branches that each generate `NNNN` collide in `drizzle/meta/_journal.json`.
