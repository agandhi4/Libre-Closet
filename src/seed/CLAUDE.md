# Seed personas

`npm run seed` (#32; `src/seed/`) writes three personas, each an archetype the app must look right for, so every feature can be seen and judged with real data: locally, in CI's screenshots, and as a demo login on production. **Personas are stories, not random rows**: each has a character bible, `src/seed/personas/<name>.md`, and the bible's tables **are** the seed's data (`bible.ts`, `persona.ts` read them at seed time); its history is simulated from them day by day (`simulate.ts`).

- **Through the app's writers**: every garment is posted through the garment form's schema and `readGarmentForm` (a value the form would drop is a `BibleError`, before anything is written), then `insertGarment`, `createOutfit`, `createCapsule` and `changeMembership` (the bible's Capsules table), `insertEntry` (with the worn instant: 21:00 of the day in `APP_TIMEZONE`, `instantAt`), ``setGarmentStatus` (the Archived table's archive; wishlist items are inserted with status `wishlist` after the owned garments)`, `saveStyleProfile`, `createPlan`, `insertItems`, `changeCandidates`and`setActivePlan`(the bible's Style profile and`Plan: <name> (active)`tables, through the forms' readers),`saveWeekTemplate`and`planMyWeek`(the week table as a template through its form, and the planned week, #16; the plan table's`Candidates`column names Wishlist ids),`createInvite`/`acceptInvite`, `setEntrySelfie`(the selfies, their art stored before the transaction like the garments'),`readTripForm`, `createTrip`, `setTripDestination`, `addTripOutfit`, `addTripItems`, `setItemsPacked`and`setPacked`(the Trips tables, their dates moved with the Events),`deleteAccount` (`src/web/auth/account.ts`, shared with the profile's deletion). No SQL of its own.
- **Photos are generated art** (owner, 2026-09-26): `art.ts` draws each garment's type as a flat-lay SVG in its colours and pattern (a shade from the name: "navy", "olive", "raw"); sharp renders it and `Photos.storeImage(..., { alphaIsCutout: true })` stores it: the original on white, the art's transparency as the cutout, the row `ready` (nothing queued). No image files in the repo. Every type in `properties.ts` has a shape (`art.spec.ts`).
- **One transaction per persona**: bytes first, then every row; a failure deletes the bytes (the commit contract, Gotchas). So a persona's user existing means it is complete: `npm run seed` leaves an existing persona alone, `--reset` removes and rewrites it, `--remove` deletes the account (rows cascade, files through `Photos`; reconciliation finds nothing). `test/integration/seed.spec.ts` proves each, and that two seeds are identical.
- **Weather** (#14): the Account table's `Weather home`, `Weather location` (rounded) and `Temperature unit` rows go through the weather's writers (`setHome`, `setTemperatureUnit`) when `WEATHER_ENABLED`. `weather.ts`'s simulated days are also forecasts (`forecastDayOf`: hourly feels-like in °C, rain spells), which is what the tests' Open-Meteo stand-in serves, so the demo's planned week shows the weather it was drawn for; `weather.spec.ts` holds each band to a range of the matching's torso target, rising band by band.
- **Deterministic**: `random.ts` streams keyed by (persona, subsystem, day), never `Math.random`; the same `--anchor` gives the same rows and photo bytes. The bibles are written for the reference anchor Saturday 2026-09-26; seeding at another anchor (default: today in `APP_TIMEZONE`) shifts acquisitions by whole weeks and events by whole 52-week years (they keep their season), and the weather (`weather.ts`: NYC normals, an AR(1) anomaly, rain odds) follows the real dates, so a January seed dresses for January.
- **Every input is checked before the first write** (#119): the bibles, `--share-with` (an existing account, none of the personas being seeded) and the `--password-stdin` password (the app's rules), all before `--reset` or `--remove` deletes anything; a refusal (exit 1) leaves every persona as it was.
- **Credentials**: printed once. Random unless `--password-stdin` (development and CI pipe `Closet-demo-1`; `--remove` reads none). `--share-with <email>` gives an existing account a VIEW of each persona seeded in the run (production: the owner sees Demo in the wardrobe switcher and can Clone pieces). `--token` also prints a personal access token per persona (named `npm run seed`), for an MCP client acting as Theo; it is created after the persona's transaction, so an already-seeded persona gets one too, and `--reset`/`--remove` take it with the account. `test/integration/mcp-seed.spec.ts` drives the tools over the seeded personas.
- **CI screenshots**: the e2e job runs `test/screenshots.spec.ts` with `SEED_SCREENSHOTS=1`: it seeds all three personas (anchor 2026-09-26, `--reset`, so a retry or a second run on one database starts from the same rows) into the job's database and saves 390 px shots of the wardrobe, filters, garment page and form, select mode, outfits, Styling and its Save sheet, calendar history and planned week, a three-outfit day and the plan page (and fresh's), shares, capsules (list, a capsule, the picker), the laundry page, a garment with wears and the wash and attention filters, sparse's grid and tagging, and Theo's wishlist (the tab, an item, Bought it, the replace-soon merino, "Goes with my closet" on the Allbirds), his plans, gap view, style profile, shopping list and Bought it for a plan item, the outfit gallery (Ideas at a fixed seed, Ideas for a planned evening from the plan page, "Style this" on the olive chinos), his insights (measured from the run's real today, so they age with the history) and an unworn garment's "Style this", sparse's insights without a wear, fresh's empty states (laundry, wishlist, plans, the shopping list, Ideas, insights and Today included), his outfit selfies (#19: a week of them on the calendar, one opened, an outfit's Worn strip), and last, Theo re-seeded with the real today as his anchor (Today's date is the server's), his Today and the profile's notifications with a device's reminders (PushManager and the permission stubbed, `test/support/push-stub.ts`), his week template and tomorrow's week as "Plan my week" filled it (#16); his sizes (#24: Profile › Sizes, its editor, an Allbirds wishlist item's note and its form's hint, and fresh's empty editor, shots 75-79), his trips (#10: the list, the Austin conference's page with its packing list, its add page) and fresh's empty Trips, the calendar's month of August (70, with a dark twin), the planned week's "+ Plan" sheet (71, the viewport alone) and fresh's empty month (72), the outfit page's Plan sheet (73) and the Saved tab picking for a day (74), uploaded as the `screenshots-390px` artifact and linked from the run summary. The seed runs inside the spec because the server Playwright starts is what migrates the database. Dark-mode twins (`colorScheme: 'dark'`) of shots 01, 03, 06, 07, 08 and 10 are saved as `<name>-dark`, taken before Theo is re-seeded so they show the same data as their light twins. **Each test owns its data** (#103): the file is serial, so a failure retries it whole in a fresh worker whose `beforeAll` resets the personas; the tests that change Theo (the re-seed, the photo adds) come last; a page is reached by its exact name, never as the first tile of a search (`?keyword=raw` finds the Iron Rangers first: their notes say "with the raw denim").
- **Every later feature extends the seed** (the rule for every feature issue): make the feature show up in demo by extending the **simulation**, not by adding rows beside it (wears and washes #7: its worn entries go through `setEntryWorn`, its Sundays through `markWashed`, the Laundry table becomes each garment's "Wash after" and the simulation judges clean by the app's own rules, the Condition and Away tables are garment form fields and `setAway`; trips #10: the Austin conference, done; occasions #13: the week table's `Calendar` and `Workout` columns and the evenings' occasions, done), add what it needs to the bibles' tables, and consider all three personas: what Riley sees empty, what Dana's untagged closet does. `demo.md`'s "What later features add" lists the plan.

## Commands

```
echo Closet-demo-1 | npm run seed -- --persona all --password-stdin [--reset | --remove] [--anchor YYYY-MM-DD] [--token]
                              # the seed personas (see Seed personas), from dist/ (build first; the server
                              # must have migrated the database). Without --password-stdin a random password
                              # is printed once. On linux-box: docker exec closet npm run seed -- --persona demo
                              # --share-with <owner email>
```

## Layout

```
  seed/                The seed personas (see Seed personas): personas/<name>.md (the character bibles,
                       which are the seed's data), bible.ts + persona.ts (their tables, checked through
                       the garment form), simulate.ts + weather.ts + random.ts (the history, pure and
                       deterministic; random.ts keys src/random.ts's streams by SEED_VERSION), art.ts (the generated garment photos), selfie-art.ts (the generated outfit selfies), seed.ts (the writes, the
                       command), seed.cli.ts (`npm run seed`)
```

## Gotchas

- **The persona bibles are data, and the image carries them.** `src/seed/personas/*.md` are read at seed time (tsc does not copy Markdown), so `docker/Dockerfile` copies them into the runtime image; a renamed column, a short row or a value the garment form would drop fails the seed (and `persona.spec.ts`) with the bible and row named. Edit a table, not the code, to change what a persona owns or wears.
