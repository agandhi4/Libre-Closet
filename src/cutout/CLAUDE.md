# Background removal

The server makes every photo's cutout: the photo form posts the photo alone and the upload queues it. Built 2026-09-26 for the move to linux-box (a Ryzen 7 8845HS; `docs/audits/2026-09-25-program2/bg-removal-benchmark.md` chose the model); the in-browser path (`@imgly/background-removal`, `onnxruntime-web`, `/bg-removal-models`, `background-removal.js`) and the `CUTOUT_MODE` switch were deleted the same day. A page the installed app cached before that still posts the browser's cutout (`nobgPhoto`) with the photo: `Photos.storeUploadParts` drains and ignores it (logged, context `Photos`) and the photo is queued like any other; the upload route accepts two files for it (`cutout-upload.spec.ts`). A leftover `CUTOUT_MODE` in an env file is ignored.

- **The state machine** (`src/cutout/state.ts`) is the one place that decides a cutout's state: `none -> pending` (request: every upload; `none` is left only on photos stored before 2026-09-26, whose cutout the browser made), `pending -> pending` (start: attempts + 1, the job's photo version recorded, the row leased to the worker; release: a job cut short by shutdown frees its own lease), `pending -> ready | failed` (succeed/fail, accepted only while pending and on the photo version the job started for), `failed -> pending` (retry: "Try again", the nightly retry; a pending row is queued or running already, so a retry of it is refused and a running job keeps its result: #45), `any -> edited` (edit: the mask editor, which always wins), except `unwanted`: an outfit selfie keeps its background, so it is stored `unwanted` (`initialCutoutState('unwanted')`, by `setEntrySelfie`) and no event applies to it, request and edit included, so no job, backfill of `none` rows or mask ever cuts the person out of the room (and, never pending, it is never claimed or leased). Every event but start leaves the row without a lease. The columns (`file.cutout_status`, `cutout_attempts`, `cutout_job_version`, `cutout_requested_at`, `cutout_worker`, `cutout_started_at`, `variant_key`; a check constraint on the status, `file_cutout_lease_check`: both lease columns or neither, and only on a pending row, and `file_variant_key_check`: a key only on a ready or edited row) are written only by `applyCutoutEvent` (`src/cutout/queries.ts`) under the row's `FOR UPDATE` lock. A new row starts through `initialCutoutState` (upload: `pending`; clone: the source's status; rotate, #199: `edited` with the mask turned along, else `pending`, so a user's mask survives a turn and a model cutout is re-made for the turned photo). `src/cutout/state.spec.ts` covers every edge.
- **The queue** (`CutoutQueue`, `queue.ts`) is the pending rows no live lease holds, oldest `cutout_requested_at` first, one at a time (`claimNextCutout`, `SKIP LOCKED`; see Across servers). Before each claim it waits for the runner's model (`CutoutRunner.ready`), so no lease is held through a first boot's download; while the model cannot be had (a failed download, a refused checksum) it claims nothing, logs `Cutout queue cannot run the model (...)`, and tries again every 5 min, so photos wait pending rather than fail for an ops problem. `createApp()` builds it for every app and stops it on close; only `serve()` (`server.ts`) starts it, with the runner it is given (`main.ts`: the `ModelRunner`; `test/support/test-server.ts`: a stub that answers in 3 s), so the harness and the CLIs never run jobs (a spec starts it with a fake runner: `fakeRunner()` in `test/integration/cutouts.ts`, then `t.cutouts.whenIdle()`, which only a look that starts after the call answers: one already in flight may predate the spec's last write). **It looks for work four ways**: a write in this process wakes it (`cutouts.wake()`); every write that makes a row pending, in any process (a CLI such as the seed, a second server during an overlapping deploy), sends `NOTIFY closet_cutout_queued` inside its transaction, so it is delivered only on commit (`notifyCutoutQueued`, called by `applyCutoutEvent` for request, retry and release and by `insertPhotoRow` for a pending row; a new writer of pending rows goes through one of them), and the listener wakes the queue; at start it resumes whatever is pending (a restart loses nothing); and while idle it polls every `CUTOUT_POLL_SECONDS` (default 60), one indexed claim, never while a job runs. A poll that finds work logs `Cutout poll found photo <id> (<name prefix>) pending without a notification`: a lost notification or a listener that was down (or a lapsed lease: the poll is what finds one). A job cut short by shutdown stays pending and releases its lease, so the next start or another server runs it at once. The nightly retry (`retryFailedCutouts`, scheduled by `server.ts` at 03:00) requeues failed rows under `MAX_CUTOUT_ATTEMPTS` (3); "Try again" has no cap.
- **The listener** (`CutoutListener`, `listener.ts`) is one dedicated `pg` Client outside the pool (LISTEN belongs to a session; a pooled client serves other queries), opened by the queue's `start()` and ended by its `stop()`, so the harness and the CLIs never hold one. It connects with the pool's settings (`connectionOptions(dbConfig)`), as `application_name` `closet-cutout-listener` (find it in `pg_stat_activity`), with TCP keepalive and a 10 s connect timeout. A dropped connection is reopened with backoff (1 s, doubling to 60 s, reset once listening), and every (re)connect wakes the queue, because notifications sent while it was down are lost. **Pool budget**: a server with its queue running holds the pool's 10 connections plus this one on pgvault. `test/integration/cutout-notify.spec.ts` covers a row inserted through a second connection, the poll, `pg_terminate_backend` and the reconnect, and shutdown.
- **Stopping is bounded and cannot lose its signal.** Each `start()` gets its own `AbortController`; the loop, its sleeps and a job's cancellation all watch that signal, so a `stop()` that lands while a claim is in flight still ends the loop (a plain `stopping` flag plus waking a sleep lost that wake-up and slept a whole poll interval: the intermittent CI hang of 2026-09-26, PR #51). `stop()` always resolves: the listener owns its socket (pg's `stream` option) and destroys it if a clean close takes over 5 s (a database that stopped answering), and the runner's close plus the loop's end get 10 s (`settlesWithin`, `deadline.ts`), after which it logs a warning and returns, leaving a running job pending under its lease (it may yet finish; releasing it could start a second run beside it), which lapses. It never rejects (a failed runner close is logged), so the app still ends the pool. Any new wait inside the loop must take the `halt` signal.
- **Across servers a photo is run once and written once: a lease** (#45, `drizzle/0021_cutout_lease.sql`). A started job stays `pending` (a crashed server's job must stay claimable), so the claim's own statement also leases the row: `start` sets `cutout_worker` (the queue's worker id, `<host>:<pid>:<8 hex>`, new per `start()`, logged as `Cutout queue started as worker ...`) and `cutout_started_at` (the database's `now()`, so the servers' clocks never matter). `claimNextCutout` skips a row whose lease is younger than `CUTOUT_LEASE_MS` (`queries.ts`: 5 min, five times the model's 60 s kill; a job is the decode, that one bounded model run and the write, and the model file is readied before the claim), so during an overlapping deploy `SKIP LOCKED` keeps the servers apart while one claims and the lease while it runs. Succeed, fail and edit clear the lease with the status; a shutdown releases it (`release`, only the worker's own: a lease that lapsed and was taken since is left alone), and so does a result refused as `stale` on a still-pending row. **A crash** leaves the lease to lapse: after 5 min the next claim (the poll, a start, a notification) takes the row over and logs `Cutout lease of worker <id> lapsed after 5 min; running ... again` at warn. Why a lease and not a per-photo advisory lock: it is visible in the data (`select file_name, cutout_worker, cutout_started_at from file where cutout_worker is not null`), survives the listener's or the pool's connection drops, and costs no connection per job beside the listener's. The state machine still keeps the first result should two runs ever meet (a job that outlived its lease): `Cutout discarded (not-allowed)`. `cutout-notify.spec.ts` runs two servers on one pending photo and on eight (the runner called once per photo); `cutout-queue.spec.ts` covers a live lease skipped, a lapsed one taken, the shutdown release and "Try again" mid-job.
- **The runner** (`runner.ts`) runs the model in a forked child (`child.ts`), not a worker thread: onnxruntime cannot be interrupted, so the 60 s limit per image kills the process; an idle process exits after 15 min and returns its ~3 GB; an OOM kill takes the child, not the server. CPU only, `enableCpuMemArena: false`, `CUTOUT_THREADS` intra-op threads (default 4). Pixels travel over IPC with `serialization: 'advanced'`.
- **The model** (`model.ts`, `BIREFNET_512`) is not in the image: `CutoutModel.ready()` downloads it into `MODELS_PATH` (a local volume, not NFS) from a revision-pinned Hugging Face URL, hashing on the way, and renames it into place only on the pinned SHA-256; a mismatched file on disk is refused (`npm run cutout:fetch-model` replaces it). `main.ts` verifies (or starts downloading) it at boot, so any `node dist/main.js` (`start:dev` and `start:prod` included) fetches 940 MB into `./models` once; point `MODELS_PATH` at a copy to avoid it. Tests never boot `main.ts`: Playwright, the load test and Lighthouse run `npm run start:test`. The queue waits for the model (`ModelRunner.ready`) before it claims a job, outside the 60 s limit and outside the job's lease.
- **The page** (`garment-page.tsx`, `GarmentPhotoView`): pending shows the original with "Removing background…" and polls `GET /wardrobe/:id/cutout` (`hx-trigger="every 2s"`, `hx-swap="outerHTML"`, its own `hx-indicator` so the app bar's spinner stays still); the answer without the trigger ends the polling. Failed shows the original and a `PostForm` to `POST /wardrobe/:id/cutout/retry`. `none` (a photo from before 2026-09-26) shows its cutout and the pencil, without polling. The phone downscales every photo first (`public/js/photo-input.js`: 1600 px JPEG, or the file as it is when the browser cannot decode it).
- **Logs** (contexts `Cutout`, `CutoutModel`): the queue's start with its worker id; one line per job start and end (`Cutout ready|failed|discarded (<reason>): garment <id> photo <file id> (<name prefix>) ...; queue wait, inference, total ms, model process RSS and peak`, and what became of the lease when it was not cleared by the result), a lapsed lease taken over (warn), model process start/load/exit (expected or not), model verify/download; the listener's connected, lost or could not connect (with the retry delay) and closed, and each notification at debug.
- **Measured on linux-box** (2026-09-26, 4 threads, the production image with a real photo): pending to ready 7.1 s cold (2.9 s model load, 3.8 s inference; the boot's checksum took 0.5 s), 3.6 s warm; model process peak RSS 2.9 to 3.3 GB, container 1.6 GB while the model stays loaded. The image grew 66 MB (onnxruntime-node, linux-x64 only). `test/integration/cutout-model.spec.ts` measures it with the real model when `MODELS_PATH` (or `./models`) holds it, and is skipped otherwise (CI never downloads 940 MB).

## Commands

```
npm run cutout:fetch-model    # downloads or verifies the background-removal model in MODELS_PATH (replaces a
                              # mismatched file); docker exec closet npm run cutout:fetch-model
```

## Layout

```
                       state.ts (the cutout state machine, pure), queries.ts (applyCutoutEvent, the only
                       writer of the file row's cutout columns; the leased claim, retry, the queued NOTIFY), queue.ts
                       (CutoutQueue: the database is the queue; retryFailedCutouts), listener.ts
                       (CutoutListener: the queue's LISTEN connection), runner.ts (ModelRunner: the child
                       process's lifecycle), child.ts + protocol.ts (the model process and its IPC),
                       model.ts (the pinned model, download and checksum), fetch-model.cli.ts
                       (`npm run cutout:fetch-model`)
```

## Gotchas

- **Cutout bytes are stored before the row lock, under a new variant key; the transaction only swaps the key** (#141). `Photos.writeCutout` writes the nobg and its thumb as `<uuid>-nobg-<key>.webp` / `-thumb-<key>.webp` (a fresh `newVariantKey()`), then locks the row, and `applyCutoutEvent` writes `variant_key` with the new version only when the machine accepts the event (succeed and edit carry the key: a version never moves without the bytes it names). Nothing in `applyCutoutEvent`'s transaction touches storage: with NFS I/O under the lock, a slow mount ran into the server pool's idle-in-transaction limit, and a file renamed over the served name before a COMMIT that then failed left new bytes live under the old row. A refused event (a late job result over a user's mask, a replaced photo) and a rolled-back swap delete their own files, logged (`Deleted ... : edit refused (not-allowed)`, `... rolled back`); the swap's winner deletes the set it replaced after the commit. When the transaction throws, the row is read before deleting (a COMMIT whose answer was lost may have landed: then it is the outcome); if even that read fails, the files stay for reconciliation's superseded-variant pass. The state machine still decides every race: `test/integration/cutout-io.spec.ts` (a failed COMMIT, two results for one job, concurrent edits, an edit against a job) and `cutout-queue.spec.ts` (edits, replacements and bumps while a job runs). Writing into the served names and checking after would let a late job result overwrite a mask the user saved meanwhile.
- **onnxruntime-node**: `.npmrc` sets `onnxruntime-node-install-cuda=skip` (its postinstall otherwise downloads 300+ MB of CUDA/TensorRT providers on linux-x64; the Dockerfile copies `.npmrc` into both stages), and the runtime image deletes the darwin, win32 and linux-arm64 binaries. It is pinned (1.21.0, what the benchmark measured): bump it deliberately and rerun `cutout-model.spec.ts` with the real model. `src/cutout/child.ts` imports nothing from `src/` at runtime (types only): in the tests it runs as TypeScript under Node's type stripping, where a relative import would need an extension.
- **sharp orders a pipeline's operations itself.** `composeCutout` joins the alpha (`joinChannel`), reads the RGBA back, and only then pads (`extend`) in a second pipeline; a single-channel raw mask needs `extractChannel(0)` after `resize` or sharp emits it as 3-channel sRGB (the benchmark's traps).
