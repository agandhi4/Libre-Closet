# Background removal

The server makes every photo's cutout: the photo form posts the photo alone and the upload queues it (model choice: `docs/audits/2026-09-25-program2/bg-removal-benchmark.md`). A page the installed app cached earlier may still post the browser's cutout (`nobgPhoto`) with the photo: `Photos.storeUploadParts` drains and ignores it and the photo is queued like any other; the upload route accepts two files for it (`cutout-upload.spec.ts`). A leftover `CUTOUT_MODE` in an env file is ignored.

- **The state machine** (`src/cutout/state.ts`) is the one place that decides a cutout's state: `none -> pending` (request: every upload; `none` is left only on old photos whose cutout the browser made), `pending -> pending` (start: attempts + 1, the job's photo version recorded, the row leased; release: a job cut short by shutdown frees its own lease), `pending -> ready | failed` (succeed/fail, accepted only while pending and on the photo version the job started for), `failed -> pending` (retry: "Try again", the nightly retry; refused on a pending row, so a running job keeps its result), `any -> edited` (edit: the mask editor, which always wins), except `unwanted`: an outfit selfie keeps its background, so it is stored `unwanted` (`initialCutoutState('unwanted')`, by `setEntrySelfie`) and no event applies to it, request and edit included, so no job, backfill or mask ever cuts the person out of the room. Every event but start leaves the row without a lease. The columns (`file.cutout_status`, `cutout_attempts`, `cutout_job_version`, `cutout_requested_at`, `cutout_worker`, `cutout_started_at`, `variant_key`; a check constraint on the status, `file_cutout_lease_check`: both lease columns or neither, only on a pending row, and `file_variant_key_check`: a key only on a ready or edited row) are written only by `applyCutoutEvent` (`src/cutout/queries.ts`) under the row's `FOR UPDATE` lock, or its batch form `applyCutoutEventToRows` (one UPDATE; the nightly retry). A new row starts through `initialCutoutState` (upload: `pending`; clone: the source's status; rotate: `edited` with the mask turned along, else `pending`). `src/cutout/state.spec.ts` covers every edge.
- **The queue** (`CutoutQueue`, `queue.ts`) is the pending rows no live lease holds, oldest `cutout_requested_at` first, one at a time (`claimNextCutout`, `SKIP LOCKED`; see Across servers). Before each claim it waits for the runner's model (`CutoutRunner.ready`), so no lease is held through a first boot's download; while the model cannot be had it claims nothing, logs `Cutout queue cannot run the model (...)`, and retries every 5 min, so photos wait rather than fail. `createApp()` builds it for every app and stops it on close; only `serve()` (`server.ts`) starts it, with the runner it is given (`main.ts`: the `ModelRunner`; `test/support/test-server.ts`: `cutout-stub.ts`), so the harness and the CLIs never run jobs (a spec starts it with a fake runner: `fakeRunner()` in `test/integration/cutouts.ts`, then `t.cutouts.whenIdle()`, which only a look starting after the call answers). **It looks for work four ways**: a write in this process wakes it (`cutouts.wake()`); every write that makes a row pending, in any process (the seed, a second server mid-deploy), sends `NOTIFY closet_cutout_queued` inside its transaction, delivered only on commit (`CUTOUT_QUEUED_NOTIFY` in the write's own RETURNING, costing no statement: `applyCutoutEvent`'s update for request, retry and release (and its batch form's) and `insertPhotoRow`'s insert for a pending row; a new writer of pending rows goes through one of them), and the listener wakes the queue; at start it resumes pending work; and while idle it polls every `CUTOUT_POLL_SECONDS` (default 60), one indexed claim, never while a job runs. A poll that finds work logs `Cutout poll found photo <id> (<name prefix>) pending without a notification`. A job cut short by shutdown stays pending, its lease released, so it runs again at once. The nightly retry (`retryFailedCutouts`, 03:00 from `server.ts`) requeues failed rows under `MAX_CUTOUT_ATTEMPTS` (3), in one statement when none failed and five otherwise; "Try again" has no cap.
- **The listener** (`CutoutListener`, `listener.ts`) is one dedicated `pg` Client outside the pool (LISTEN belongs to a session), opened by the queue's `start()` and ended by its `stop()`, so the harness and the CLIs never hold one. It connects with `connectionOptions(dbConfig)` as `application_name` `closet-cutout-listener` (in `pg_stat_activity`), with TCP keepalive and a 10 s connect timeout. A dropped connection is reopened with backoff (1 s, doubling to 60 s, reset once listening), and every (re)connect wakes the queue, because notifications sent while it was down are lost. **Pool budget**: a server with its queue running holds the pool's 10 connections plus this one. `test/integration/cutout-notify.spec.ts` covers a second connection's insert, the poll, `pg_terminate_backend` and reconnect, and shutdown.
- **Stopping is bounded and cannot lose its signal.** Each `start()` gets its own `AbortController`; the loop, its sleeps and a job's cancellation all watch that signal, so a `stop()` landing while a claim is in flight still ends the loop (a flag could lose the wake-up). `stop()` always resolves: the listener owns its socket (pg's `stream` option) and destroys it if a clean close takes over 5 s, and the runner's close plus the loop's end get 10 s (`settlesWithin`, `deadline.ts`), then it warns and returns, leaving a running job pending under its lease (releasing it could start a second run beside it), which lapses. It never rejects (a failed runner close is logged), so the app still ends the pool. Any new wait inside the loop must take the `halt` signal.
- **Across servers a photo is run once and written once: a lease** (`drizzle/0021_cutout_lease.sql`). A started job stays `pending` (a crashed server's job must stay claimable), so the claim's own statement also leases the row: `start` sets `cutout_worker` (`<host>:<pid>:<8 hex>`, new per `start()`, logged as `Cutout queue started as worker ...`) and `cutout_started_at` (the database's `now()`, so server clocks never matter). `claimNextCutout` skips a row whose lease is younger than `CUTOUT_LEASE_MS` (`queries.ts`: 5 min, five times the model's 60 s kill): `SKIP LOCKED` keeps servers apart while one claims, the lease while it runs. Succeed, fail and edit clear the lease with the status; a shutdown releases it (`release`, only the worker's own: a lapsed lease taken since is left alone), as does a result refused as `stale` on a still-pending row. **A crash** leaves the lease to lapse: after 5 min the next claim takes the row over and logs `Cutout lease of worker <id> lapsed after 5 min; running ... again` at warn. A lease, not an advisory lock: visible in the data (`select file_name, cutout_worker, cutout_started_at from file where cutout_worker is not null`), survives connection drops, costs no connection per job. The state machine still keeps the first result should two runs meet: `Cutout discarded (not-allowed)`. `cutout-notify.spec.ts` runs two servers on one and on eight pending photos; `cutout-queue.spec.ts` covers a live lease skipped, a lapsed one taken, the shutdown release and "Try again" mid-job.
- **The runner** (`runner.ts`) runs the model in a forked child (`child.ts`), not a worker thread: onnxruntime cannot be interrupted, so the 60 s limit per image kills the process; an idle one exits after 15 min, freeing ~3 GB; an OOM kill takes the child, not the server. CPU only, `enableCpuMemArena: false`, `CUTOUT_THREADS` intra-op threads (default 4). Pixels go over IPC with `serialization: 'advanced'`.
- **The model** (`model.ts`, `BIREFNET_512`) is not in the image: `CutoutModel.ready()` downloads it into `MODELS_PATH` (local, not NFS) from a revision-pinned Hugging Face URL, renaming it into place only on the pinned SHA-256; a mismatched file on disk is refused (`npm run cutout:fetch-model` replaces it). `main.ts` verifies (or starts downloading) it at boot, so any `node dist/main.js` (`start:dev`, `start:prod`) fetches 940 MB into `./models` once; point `MODELS_PATH` at a copy to avoid it. Tests never boot `main.ts`: Playwright and Lighthouse run `npm run start:test`. The queue awaits `ModelRunner.ready` before claiming, outside the 60 s limit and the lease.
- **The page** (`garment-page.tsx`, `GarmentPhotoView`): pending shows the original with "Removing background…" and polls `GET /wardrobe/:id/cutout` (`hx-trigger="every 2s"`, `hx-swap="outerHTML"`, its own `hx-indicator`); the answer without the trigger ends the polling. Failed shows the original and a `PostForm` to `POST /wardrobe/:id/cutout/retry`. `none` shows its cutout and the pencil, without polling. The phone downscales every photo first (`public/js/photo-input.js`: 1600 px JPEG, or as is if undecodable).
- **Logs** (contexts `Cutout`, `CutoutModel`): the queue's start with its worker id; one line per job start and end (`Cutout ready|failed|discarded (<reason>): garment <id> photo <file id> (<name prefix>) ...; queue wait, inference, total ms, model process RSS and peak`, and the lease's fate when the result did not clear it), a lapsed lease taken over (warn), model process start/load/exit, model verify/download; the listener's connect, loss, failure and close; each notification at debug.
- **Measured on linux-box** (4 threads, production image): pending to ready 7.1 s cold (2.9 s model load), 3.6 s warm; model process peak RSS 2.9 to 3.3 GB. `test/integration/cutout-model.spec.ts` measures it with the real model when `MODELS_PATH` (or `./models`) holds it, and is skipped otherwise; the nightly (`nightly.yml`) caches the model under its checksum, runs the spec with `CUTOUT_MODEL_REQUIRED=1` (missing fails, not skips) and cuts out one photo in the built image (`scripts/smoke-image.sh` with `MODELS_DIR`).

## Commands

```
npm run cutout:fetch-model    # downloads or verifies the model in MODELS_PATH (replaces a mismatched
                              # file); docker exec closet npm run cutout:fetch-model
```

## Layout

```
state.ts (the cutout state machine, pure), queries.ts (applyCutoutEvent and its batch form, the only
writers of the file row's cutout columns; the leased claim, retry, the queued NOTIFY), queue.ts
(CutoutQueue: the database is the queue; retryFailedCutouts), listener.ts (CutoutListener: the LISTEN
connection), runner.ts (ModelRunner: the child's lifecycle), child.ts + protocol.ts (the model process
and its IPC), model.ts (the pinned model, download, checksum), fetch-model.cli.ts (`npm run cutout:fetch-model`)
```

## Gotchas

- **Cutout bytes are stored before the row lock, under a new variant key; the transaction only swaps the key.** `Photos.writeCutout` writes the nobg and its thumb as `<uuid>-nobg-<key>.webp` / `-thumb-<key>.webp` (a fresh `newVariantKey()`), then locks the row, and `applyCutoutEvent` writes `variant_key` with the new version only when the machine accepts the event (succeed and edit carry the key: a version never moves without the bytes it names). Nothing in `applyCutoutEvent`'s transaction touches storage: NFS I/O under the lock runs into the pool's idle-in-transaction limit, and a rename over the served name before a failed COMMIT leaves new bytes live under the old row. A refused event and a rolled-back swap delete their own files, logged (`Deleted ... : edit refused (not-allowed)`, `... rolled back`); the winner deletes the set it replaced after commit. When the transaction throws, the row is read before deleting (a lost COMMIT answer may have landed); if even that read fails, the files stay for reconciliation's superseded-variant pass. The state machine decides every race: `test/integration/cutout-io.spec.ts` (a failed COMMIT, two results for one job, concurrent edits, an edit against a job) and `cutout-queue.spec.ts` (edits, replacements and bumps while a job runs). Writing into served names would let a late job result overwrite a mask saved meanwhile.
- **onnxruntime-node**: `.npmrc` sets `onnxruntime-node-install-cuda=skip` (else its postinstall downloads 300+ MB of CUDA providers; the Dockerfile copies `.npmrc` into both stages), and the runtime image deletes the darwin, win32 and linux-arm64 binaries. It is pinned (1.21.0): bump it deliberately and rerun `cutout-model.spec.ts` with the real model. `src/cutout/child.ts` imports nothing from `src/` at runtime (types only): in the tests it runs under Node's type stripping, where a relative import would need an extension.
- **sharp orders a pipeline's operations itself.** `composeCutout` joins the alpha (`joinChannel`), reads the RGBA back, and only then pads (`extend`) in a second pipeline; a single-channel raw mask needs `extractChannel(0)` after `resize` or sharp emits it as 3-channel sRGB.
