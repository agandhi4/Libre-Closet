# Weather

`src/weather/` (pure) and `src/web/weather/`. **`WEATHER_ENABLED=false`** (default true): `createApp()` builds no service, so there is no `/weather` route (404), no weather on any page or in the profile, no MCP weather tool, and the seed stores no location: nothing is fetched or stored (`weather.spec.ts`, "weather off").

- **Location** (`user_weather`, `drizzle/0015_weather.sql`): a **home** city from the geocoding search (`home_name`, `home_latitude`, `home_longitude`) and the installed app's **"Use my location"** (`here_*`, `here_located_at`), which stands in for home for `HERE_FRESH_HOURS` (12). Every coordinate is rounded to 2 decimals (~1 km) by `roundedLocation` (`src/weather/location.ts`) before it is stored, used as the cache key or sent; the phone rounds too (`public/js/locate.js`), so a precise position never leaves it. Check constraints keep each group whole and on the globe. One writer per group (`queries.ts`).
- **Provider: Open-Meteo, from the server only** (`open-meteo.ts`): the forecast (16 days: hourly apparent temperature, precipitation chance and weather code; daily high, low, code) requested with `timezone=APP_TIMEZONE`, so its days are calendar days and its hours the occasions' hours (`OCCASION_HINTS`); plus the geocoding search. Through the outbound fetcher with `hosts` (Request security, Outbound fetches); the request carries the rounded coordinates (or the typed city) and nothing about the user. Answers are checked against TypeBox schemas.
- **Cache** (`weather_forecast`, `service.ts`): one row per rounded location, no user id: the last good forecast (`jsonb`), `fetched_at`, `attempted_at`. Fresh for an hour; **past that the cached answer is served at once and refreshed in the background**; **only a cold miss** (no answer kept) waits, for at most the fetcher's 10 s. **A one-shot decision never acts on a stale forecast**: "Plan my week" (route and MCP) reads with `{ fresh: true }` (`forecastFor`/`userWeather`'s `read`), waiting for a stale row's refresh (falling back to it only if that fails). **Batch jobs refresh together first**: the daily re-plan and the morning reminders call `refreshForecastsFor` with the minute's people, which reads every person's settings and row in one statement (`findWeathersWithForecast`, `weatherWithForecastSql` as a list), refreshes their distinct places `BATCH_REFRESH_CONCURRENCY` (4) at a time within one `BATCH_REFRESH_DEADLINE_MS` (12 s), and answers each person's weather (no one's weather is read again; one whose place failed or overran is read without `fresh`): N places cost about one fetch (a skipped reminder minute is still sent within `LATE_LIMIT_MINUTES`). Pages keep serve-stale. A new scheduled reader of the forecast joins its batch's refresh (`refresh-batch.spec.ts`, `push-reminders.spec.ts`). A failed refresh keeps the last good answer and waits 10 minutes before asking again. **A kept answer to another question is no answer** (`mismatch`): a forecast whose `timeZone` is not APP_TIMEZONE or normals whose `years` are not `normalYears` of today is never served, however young, nor as the fallback: the ask waits like a cold miss (`service.spec.ts`). One refresh per location at a time per process, and the row is not read while one runs: an ask meanwhile is served what the refresh started from (a cold one joins it), so an ask that read the stale row just before the save can never fetch again. That discipline is `createLocationCache` (`location-cache.ts`, `location-cache.spec.ts`), used by both caches: a new Open-Meteo answer kept per location goes through it, not a copy. A background refresh never rejects (failures are logged), and **the app's close awaits `WeatherService.settled()`** before ending the pool, so an in-flight refresh still saves. No timer: only asks start refreshes. Specs counting fetches after a stale ask await `t.weather.settled()`, never a poll (`refreshed` in `weather.spec.ts`, `climate-normals.spec.ts`); one asserting what concurrent asks got during a refresh holds the stand-in's answer (`stub.hold(true)`) until they are in. **One read for the person**: `userWeather` reads the settings and the active location's cache row in one statement (`findWeatherWithForecast`: activeLocation's rule in SQL, used only when it agrees with the JS rule) and hands the row in as `known`; the cache decides from it unless a read or refresh of that place is under way or this process wrote the row after it was read (`written`), so the single-flight rule holds (`location-cache.spec.ts`). The summary is 2 statements. The read is a scalar subquery (`weatherWithForecastSql`, via `readWeatherWithForecast` and `userWeatherFrom`), so `ideasFor` carries it in its one statement (JSON timestamps come back as strings; the reader makes Dates). **A table, not memory**: restarts start warm, overlapping deploys share it, and the last good answer survives a restart.
- **Where it shows** (`views.tsx`, one `WeatherLine` and one `WeatherDay`): `WeatherSlot` in the page header (the wardrobe, outside `#wardrobe-main` so filtering never reloads it; the calendar) loads `GET /weather/summary` once in place (`hx-trigger="load"`, own `hx-indicator`): today's line (icon, range, rain, "take a layer", place, "as of") or, without a location, the link to set one; with `?from=&to=` the calendar's day chips arrive out of band into each day's `WeatherDaySlot` (with `&view=month`, the month grid's compact chips alone: Calendar). **Tab roots never render the forecast themselves**: they must render byte for byte the same while nothing changes (stale-while-revalidate), and an hourly forecast would mark them changed. Today is the exception: network first, it renders `UserWeatherLine` from the read its ideas use (see Today). Offline the worker answers the fragment from its cache (`url|hx`), "as of" saying how old (`test/weather.spec.ts`). Settings: `WeatherSettings`, on the profile.
- **Matching** (`src/weather/match.ts`, pure, `match.spec.ts` across seasons and occasions): `weatherNeeds(day, occasion, offset)` reads the occasion's window, its feels-like range plus the personal offset, and sets targets: the **torso** (top or one-piece plus layer, combined 1 to 9: one step per 4 °C down from 26 °C; a tee 2, a sweater under a parka 9) and **legs and feet** (one garment, 1 to 5); **a layer** when the window's coolest and warmest hours are two torso steps apart (judged with the layer at the coolest hours, without at the warmest; a swing inside the heat asks for nothing); **rain** when an hour of the window reaches 50 %, wanting a water-resistant layer, footwear or accessory (not a bag). `assessOutfit(needs, garments)` lists the problems and a score (0 fits) and judges only the parts an outfit has; `matchGarment` counts an unknown warmth as the type's preset (its weight step included), else the role's usual. Availability (`isAvailable`) is separate: filter, then match.
- **Personal offset and units** (`temperature.ts`): °C added to every feels-like, within ±5, moved half a degree by "I was too warm" / "I was too cold" (`nudgeTemperatureOffset`, one SQL statement so quick taps all count). Everything is computed and stored in °C; `temperature_unit` (°F by default; the constant and the migration default must agree) is only display.
- **Routes** (session; `weather/routes.tsx`): `GET /weather/summary[?from=&to=[&view=month]]` (always a fragment; both or neither, at most 42 days, else 400), `GET /weather/places?q=` (2-100 chars; `WEATHER_SEARCH_LIMIT`, 20 a minute per user; `secretPath`, so the request log never shows the typed city; a failed search is a 200 message so htmx shows it), `POST /weather/home`, `/home/clear`, `/here`, `/here/clear` (home and here: `WEATHER_LOCATION_LIMIT`, 10 a minute per user (each is a fetch and a row); "Use my location" re-enables itself and says so when its post fails, `locate.js`), `/unit`, `/feedback`, `/offset/reset` (htmx: only the part each changed, never the whole section, which holds the unit's `AutosaveForm`: the location forms `#weather-location`, the feedback `#weather-offset`, the unit its status line and the offset out of band; a plain post: 303 to `/auth/profile#weather`; `data-needs-network`).
- **Logs** (context `Weather`): a refresh's start (`Forecast for 40.69,-73.98: refreshing; the one from <instant> kept meanwhile`, or `none kept, the ask waits`), its outcome `Forecast for 40.69,-73.98: 16 days in 120 ms` or a failure with its reason and what is served instead, `Place search: 1 result(s) in 80 ms`: the rounded location, never the user or the query. The settings routes log the user (context `Web`), never a location; the fetcher's line names the host only.
- **Climate normals** (`src/weather/normals.ts`, pure, `normals.spec.ts`; `drizzle/0025_weather_normals.sql`): what a calendar day is usually like at a place, for **a trip's days past the forecast only**. From Open-Meteo's **historical archive** (`archive-api.open-meteo.com/v1/archive`, ERA5), not its biased climate API: one request for `NORMAL_YEARS` (10) whole years before the household's current one (`normalYears`) of daily highs, lows, feels-like and precipitation, at the rounded location, in `APP_TIMEZONE` (~140 KB under the 512 KB cap). `climateNormals` averages each calendar day over `NORMAL_WINDOW_DAYS` (7) either side in every year (wrapping New Year; 29 February kept); the rain chance is the share of wet days (`WET_DAY_MM`, 1 mm). Cached in **`weather_normals`**, a table beside `weather_forecast` (another endpoint, answer and lifetime), **one row per location holding all 366 days**: the archive answers a date range, so any month costs the ten years' fetch anyway. Fresh for 30 days (`NORMALS_FRESH_FOR_MS`), with the same last-good, 10-minute retry and single-flight (`normalsFor`). **The typical day** (`typicalDay`) turns a day's normals into a `DayForecast` so `weatherNeeds`/`assessOutfit` judge it with the same inputs: 24 hours whose feels-like follow a clear day's curve (`diurnalPhase`, shared with the seed) from the low at 6:00 to the high at 15:00, every hour's precipitation chance the day's rain chance, household hours, a condition of only dry, rain or snow. **Never for Today, the calendar, the gallery's own days, the weekly plan or its re-plan**: those stay forecast-only (a typical day must never swap a planned outfit); only `tripForecast` and `ideasFor` with a trip's `place` ask for normals (`climate-normals.spec.ts` checks Today, a far gallery day and "Plan my week" fetch no archive; `week-plan.spec.ts`'s fake service rejects `normalsFor`). Logs: `Climate normals for 30.27,-97.74: 366 days from 2016-2025 in 140 ms`, a failure like the forecast's.
- **Trips**: a trip's forecast is its destination through the same geocoding and `forecastFor`, for its days within the 16, and its climate normals past them (`tripForecast`; see Trips); `ideasFor` takes the destination as `place`. `get_weather` stays the user's own location; `get_trip` carries the trip's.
- **Tests never call Open-Meteo**: `test/support/weather-stub.ts` (an HTTP server on 127.0.0.2, admitted by the weather fetcher's own policy) serves the seed's simulated New York weather from today in the requested zone, and the same simulated days for the archive's years (`archiveAnswer`). The harness runs with `WEATHER_ENABLED=false` and refuses to boot a spec that turns it on without the stub; the e2e test server always starts it.

## Layout

```
weather/   The weather, pure: location.ts (rounding to ~1 km, the only form a coordinate is kept or
           sent in), temperature.ts (units, the personal offset), forecast.ts (the forecast shape,
           WMO conditions, a clear day's curve), match.ts (what a day asks of an outfit for an
           occasion, and how an outfit answers it), normals.ts (climate normals and the typical day)
```

## Gotchas

- **Weather is off in the integration harness.** `BASE_ENV` sets `WEATHER_ENABLED=false`; a spec that turns it on must pass `weather: (await startWeatherStub()).options`, or `createTestApp` refuses to boot: a spec must never reach Open-Meteo. The e2e test server always serves the stand-in.
- **Climate normals are a trip's far days' alone.** `WeatherService.normalsFor` is asked only by `tripForecast` and by `ideasFor` for a trip's `place` past the forecast. Today, the calendar, the gallery's own days and the weekly plan and its re-plan must stay forecast-only: a typical day is not a forecast, and the re-plan swaps outfits when the weather changes. A new `normalsFor` caller labels its output as typical.
- **The weather's days and hours are the household's, not the location's.** The forecast is requested in `APP_TIMEZONE`, so "today", the calendar's chips and the occasion windows line up; derive them with `todayIn`/`hourIn`, never `toISOString()` or UTC getters. The integration spec pins the clock (`vi.useFakeTimers({ toFake: ['Date'] })`) at 00:30 UTC on a Sunday, still Saturday evening in New York.
