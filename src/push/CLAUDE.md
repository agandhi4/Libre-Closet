# Web Push

`src/web/push/` (rebuilt 2026-09-26; the old module never delivered anything, audit A1). Registered only when `PWA_ENABLED` (`WebConfig.vapid`); without it `/push/*` is a 404, the profile shows no controls and nothing is scheduled. What it is for (#5, decided 2026-09-26, built in #15): a morning "Today's outfit" and an evening "What did you wear?" reminder, **opt-in per device**, besides the profile's test send; the week's re-plan (#16) tells the devices with the morning reminder on what it swapped (see Weekly auto-plan), and runs before a person's morning reminder is composed (#76). A shared wardrobe notifies nobody else: reminders are about the person's own day.

- **Routes** (session required; fetches get the 401): `GET /push/vapid-public-key` (text), `POST /push/subscribe` (the browser's `PushSubscription.toJSON()`: https endpoint up to 2048 chars, base64url `p256dh` of 65 bytes and `auth` of 16, else 400; 204), `POST /push/unsubscribe` (`{ endpoint }`, deletes only the caller's row; 204 either way), `POST /push/test` (htmx button, always a 200 fragment saying how many devices it reached, failed or removed).
- **`user_device` is keyed by endpoint** (`UNIQUE`, text) and written only by `upsertDevice` (`INSERT ... ON CONFLICT (push_endpoint) DO UPDATE`): renewed keys update the row, and the same browser signed in as someone else moves it to that user. Keys are columns (`key_p256dh`, `key_auth`), not JSON.
- **One sender** (`createPushSender`, `sender.ts`, built once by `createApp()` when `PWA_ENABLED`, context `Push`, handed to the routes as `WebOptions.push` and to `server.ts`): `sendToUser(userId, payload, { ttlSeconds })` (the test send), or `sendEach(messages)` for a job's batch (#173: each message a user's claimed device ids or their devices with the morning reminder on; every user's devices read in one statement, `devicesOfUsers`, at send time and never earlier, so a device revoked or signed in as someone else meanwhile gets nothing), sends to every chosen device in parallel with web-push (aes128gcm, VAPID passed per request, 10 s socket timeout), deletes a device on 404/410, logs any other failure with the device id and never throws for a device. Endpoints are capability URLs: never log them (a `WebPushError` carries one). The VAPID keys and `SITE_URL` (must be https, web-push's rule) are validated when the sender is created, so a bad config fails the boot.
- **The payload is `PushPayload` (`payload.ts`: `title`, `body`, `url`, optional `tag`)**, imported by both the sender and the service worker; `parsePushPayload` is the worker's check. `notificationclick` opens `notificationTarget(url)` (same origin only, else `/`): focuses a window already on it, else navigates the first open window, else opens one.
- **Client** (`public/js/push.js`, imported by `pwa.js` only on pages the layout marks `data-signed-in` on `<html>`: the cookie is httpOnly, so no script can tell): `syncSubscription()` re-sends an existing subscription once per document (keeps keys current, moves the device to whoever is signed in); `<push-settings>` on the profile (`settings.tsx` renders every state's text hidden, the element shows one: checking, on, off, blocked, unsupported, install, error). Permission is only ever requested by `pushManager.subscribe()` as the first await of the enable tap (iOS drops the gesture across other awaits; the registration and key are fetched beforehand). iOS/iPadOS has push only in the Home Screen app (16.4+): a Safari tab has no `PushManager` and `navigator.standalone === false`, which is the "install" state.
- **Signing out drops the subscription** in the service worker (with the page cache); the row goes on the next send's 410 or with the account (the foreign key cascades, and `push_reminder`'s claims with the row).
- **Revoked with the session** (#73): a signed-out device receives nobody's notifications, including one signed out away from itself (the reminders name planned outfits on its lock screen). **One remover, `revokeDevicesStatement(db, userId, keep?)`** (`queries.ts`), used by every path: a new password (`updatePasswordHash`, the change-password route and `user:set-password`) deletes the account's rows in the password's own statement, as a CTE; the route keeps the device that made the change, named by the endpoint its form posts (`pushEndpoint`, `PushEndpointField` in `settings.tsx`, filled by `<push-endpoint>` in push.js from `syncSubscription`; empty or absent, from a browser without push or a page cached before it, every row goes and that device's next signed-in page subscribes it again without its reminders; another account's endpoint keeps nothing), so its reminders survive; the CLI has no device and removes all. A secret rotation is an ops step, `npm run push:revoke-all` (`src/maintenance/revoke-push.ts`, per user through the same statement (`revokeDevices`), one transaction), not automatic: detecting a rotation needs a stored secret fingerprint, and rotations are rare and manual. Account deletion cascades. The browser half: the login page shown signed out (never to a signed-in visitor) carries `<push-signed-out>` (`PushSignedOut`), which drops the browser's subscription (`dropSubscription`, push.js; pwa.js imports push.js for it on a signed-out page; a boosted tap that lands there upgrades it in the page it left), so every device whose cookie the session resolver rejected drops its subscription on the page the gate sends it to; the push service then 410s any send to it. Logs: `Password changed for user <id>: other sessions, N access tokens and M other push devices revoked` (context `Web`), `Password set for user <id> via CLI: ...` (`SetPassword`), `Push devices revoked for user <id>: N` and the total (`RevokePush`); never an endpoint. `test/integration/push-revocation.spec.ts` (rows, the scheduler, the CLIs, the pages) and `test/push-revocation.spec.ts` (the form and the drop in Chromium, document and boosted).
- **Reminders, per device** (`user_device.morning_reminder`, `evening_reminder`: minutes after midnight in `APP_TIMEZONE`, null when off; `reminders_set_at`; `drizzle/0019_push_reminders.sql`). The times are quarter hours in `REMINDER_WINDOWS` (morning 05:00-11:00, evening 17:00-23:00; `src/push/reminders.ts`, which the check constraints are built from): away from midnight and from the 01:00-03:00 hours US and EU DST changes skip or repeat. Only the browser knows which device it is (its subscription's endpoint), so `<push-settings>`, once on, posts it (`POST /push/reminders/form`, a POST though it reads: the endpoint is a capability URL and never goes in a logged URL) and htmx swaps the form into `#push-reminders`; every change posts `POST /push/reminders` (`endpoint`, `morningOn` + `morning`, `eveningOn` + `evening`; a time off the choices is a 400; another user's endpoint changes nothing and says to turn notifications on), which answers **only the status line** (`ReminderStatus`), never the form: the form is an `AutosaveForm` (Gotchas), in order and whole each time, in the slot `#push-reminders` push.js loads it into. One writer, `saveReminderSettings`, stamps `reminders_set_at`. `upsertDevice` clears a device's reminders when the browser signs in as someone else.
- **The scheduler** (`src/web/push/reminders.ts`, `sendDueReminders(deps, now)`): `server.ts` runs it every minute (`scheduleMinutely`, a second past the minute) and prunes claims of past days nightly; **`createApp()` never schedules it, so the integration harness and the CLIs send nothing** (a spec calls it with the instant it wants). A run: `dueReminders` (pure) lists each device's reminder whose wall-clock time today (`instantAt`, so 07:30 stays 07:30 on both DST days) has come, came after `reminders_set_at` (a device that turns one on after its time today gets it tomorrow) and is at most `LATE_LIMIT_MINUTES` (30) ago (a restart across its minute catches up; a server down for hours never sends a morning reminder at noon); `claimReminders` inserts them into `push_reminder` (`(device_id, kind, day)` primary key) with `ON CONFLICT DO NOTHING RETURNING` in one statement, and only what it inserted is this run's to send. **Two servers overlapping in a deploy** both find a reminder due and both insert; Postgres makes the second wait on the first's key and skip it, so each goes out once (`push-reminders.spec.ts` runs two servers' runs at once for 20 minutes' worth). The claim comes before the send: a crash between them loses a reminder rather than sending it twice. It raises no unique violation, so it names no `UniqueConstraint`. Then, with what serves everyone read once for the minute (#173: the mornings' forecasts, who of them is due a re-plan, the evenings' days; see Maintenance, Statements per run), per person and kind: **morning**, from `todayFor` (the page's model, with the batch's weather), "Today's outfit", composed **after that person's re-plan for today** (`replanToday`, run first if nothing has run it: once a day whoever asks, its claim committed with the work, so a 05:00 reminder never names an outfit the day's re-plan is about to swap, whatever the two minute timers' order or which of two servers claims what; a failed re-plan is logged and the reminder names the plan as it stands; `ReminderDeps.replan` is the same deps the minutely re-plan uses), **what that re-plan swapped today first, one line each** (`reminderSwapLine`: "Swapped in Wool coat: it turned cold", "Swapped in Chelsea boots: Bean Boots is at repair"; `weekPlan.why.*`), so the person gets one push rather than a swap notice beside it (other days' swaps still get the `week-replan` notice), the weather line as text (`weatherLineText`) and the planned outfits (`Work: Navy suit · Evening: Summer date`), with the top idea first while nothing dresses the day; **evening** "What did you wear?", naming what is planned, and **skipped when anything is marked worn today** (claimed all the same: it is decided at its minute); it reads only the day's bare entries and the worn check, every evening person's in one statement (`eveningDays`), never Today's weather or ideas. Every composed message goes out in one `sendEach` at the end; a person whose composing fails is logged and counted, the others still sent. Both open Today (`url: '/'`), tagged `today-morning`/`today-evening` (a later one replaces an unread one), TTL 3 h and 1 h (never the next day).
- **Logs** (context `Push`): `Push reminders runs every minute`, one line per run that claimed something (`Reminders at <instant>: N claimed of M due, S sent, K skipped, F failed`), a skipped evening per user, the sender's per-user line, the prune. The settings route logs the user and device id (context `Web`), never the endpoint.
- **Manual check** (CI has no push service): on an installed phone, Profile, enable notifications, turn the morning reminder on at the next quarter hour; it arrives at that minute and opens Today; mark something worn and set the evening one: nothing arrives.

## Gotchas

- **A notification about the day follows the day's re-plan, by construction, not by the clock.** Two minutely timers have no order (#76: a 05:30 reminder named the outfit the 06:00 re-plan then swapped, and at the same minute it was a race), so the morning reminder calls `replanToday` for its person before reading Today, and the re-plan's claim commits in the same transaction as its writes: a claim that commits before the work (the first re-plan's `claimReplans`) lets another reader find the day "done" while it is still being done. `REPLAN_HOUR` is derived from `REMINDER_WINDOWS.morning.from`, never a second constant. A new scheduled send that describes the plan runs the re-plan first the same way.
- **A push reminder is claimed before it is sent, and claimed once.** `push_reminder`'s primary key (device, kind, day) is the only thing standing between two overlapping servers and a double notification; a new kind of scheduled send claims the same way (an insert that lands, `ON CONFLICT DO NOTHING RETURNING`), never "check, then send". A reminder's time is a wall-clock minute in `APP_TIMEZONE`, turned into an instant per day with `instantAt`; never add 24 h to yesterday's instant (DST).
- **Playwright's default Chromium (the headless shell) reports `Notification.permission` as `'denied'`** even after `grantPermissions(['notifications'])` (the Permissions API says `'granted'`), so the profile's push controls read "blocked". `test/push-settings.spec.ts` runs on the full Chromium build (`test.use({ channel: 'chromium' })`, installed by `playwright install chromium`). Headless Chromium has no push service either: that spec stubs `PushManager` in the page and lets everything server-side run for real.
