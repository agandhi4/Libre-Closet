# MCP server

`src/web/mcp/` (#33; plan section 14): the owner's own Claude (Code, Desktop) works on the wardrobe through MCP. `POST /mcp` is a Streamable HTTP endpoint on the official `@modelcontextprotocol/sdk` in **stateless** mode: a `McpServer` and a `WebStandardStreamableHTTPServerTransport` per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`: JSON answers, no SSE, no `Mcp-Session-Id`), fed a Web `Request` built from the Fastify request and the body Fastify already parsed, its `Response` copied onto the reply, so the root hooks (security headers, the request log line, compression) apply as to any route. `GET` and `DELETE /mcp` are 405. Tool inputs are zod (`zod/v4`, the SDK's schema language; the only zod in the app).

- **Auth: personal access tokens** (`src/web/auth/personal-tokens.ts`, table `personal_access_token`, `drizzle/0012_personal_access_token.sql`): `closet_` plus 32 random bytes in base64url, stored as its SHA-256 (hex, `personal_access_token_token_hash_unique`) with an 11-character display prefix; `created_at`, `last_used_at` (written at most once a minute), `revoked_at` (revoked rows stay, hidden from the list). At most `MAX_ACTIVE_TOKENS` (20) in force per user. Created, listed and revoked at `/auth/tokens` ("Agent Access" on the profile; native-post `PostForm`s). **Creating needs the current password** (`currentPassword`, checked with `verifyPassword` like change-password; the step-up rule, Stack Auth): a wrong one re-renders the form 400 with the field's message and the name kept, the password never echoed or logged; a missing one is a schema 400; every attempt counts against `ACCOUNT_LIMIT`. A created token is answered once in the page, `Cache-Control: no-store`, beside the `claude mcp add` command. Revoking needs no password (it only narrows access); `POST /auth/tokens/:id/revoke` is a 404 for anyone else's. A new password revokes them all. The endpoint's own preValidation hook reads `Authorization: Bearer` (never the cookie) into `request.accessToken`; a missing, malformed, unknown or revoked token is the same bare 401 with `WWW-Authenticate: Bearer realm="closet"`.
- **An API route, not a page: `config: { bearer: true }`** (declared in `require-session.ts`). Three places honour it: the root preValidation hook skips the session and the page context (so its errors are JSON, as on a static path), `requireSession` lets it through, and the same-origin hook accepts it without Origin (Request security, CSRF). `secretPath` is set too, so the request log shows `/mcp` even if a client put a token in the query string.
- **A token acts exactly as its user.** Every tool resolves the wardrobe it addresses (`ownerId`, from `list_shared_wardrobes`) through the same `authorizeWardrobe` as a page's `?ownerId=` (`wardrobeFor`, `tool.ts`), and calls the pages' own query and write functions: no SQL of its own for a write. Refusals are `HttpError`s as in a route and answer a tool error with the page's message (`Wardrobe not found`, `Forbidden`, `Garment not found`); anything else is logged with its stack and answered without detail.
- **Tools** (`tools/`): read `search_garments` (the grid's filters through `garmentSummaries`, which shares `gridWhere`; a type needs its category; `needsWash` on a shared wardrobe is a 403, where the grid silently drops it; each entry's `selfie: true|false`, never the image, #19), `laundry_status`, `wardrobe_stats` (`tools/insights.ts`: the insights page's figures through the same `readInsights`, the caller's own, `unwornDays` 30, 90 or 180), `list_shared_wardrobes` (the first name, never an email), `compare_with_shared_wardrobe` (`compare.ts`, pure: the closet vs a shared one by role and type, gaps with brands, colours, prices and links); write, each description starting `WRITES`: `add_garment_from_link` (`importLink` + `importedForm`, the caller's overrides, then the form's own post through `formPost` and `readGarmentForm` and `createGarmentWithPendingPhoto`; Today's (#15, `tools/today.ts`): read `get_today` (`todayFor`, the home screen as data: the day, whether anything is worn, the planned rows with entry and outfit ids, the all-day suggestions while nothing dresses the day, and with the weather what today asks of an all-day outfit). Trips (#10, `tools/trips.ts`, the caller's own): read `list_trips`, `get_trip` (`tripModel`: days, outfits, the packing list with each garment's wears, copies needed, copies to pack, packed and warnings, the extras, and with `WEATHER_ENABLED` the destination's forecast through `tripForecast`, and past it `typicalDays`, each `typical: true` with the normals and what a typical day asks); write `plan_trip_outfit` (a saved `outfitId` through `addTripOutfit`, or an idea's `garmentIds` through `pickForTrip`; a day of the trip and an occasion optional; idempotent).
- **Photos: the one exception to "no photos leave the homelab"** (#90, owner decision on #11's re-scope; plan section 14). `get_garment_photo` (read, `tools/garments.ts`) answers a garment's **400px thumb** (`Photos.getVariant(..., 'thumb')`, the cutout's when there is one, never the original) as an MCP `image` content block (`image/webp`, base64) after a text block naming the garment, so the owner's own authenticated Claude can tag garments (`search_garments` with `needsTagging`, then `update_garment`, MANAGE or owner as ever). A tool answers a picture by returning an `ImageAnswer` (`tool.ts`), which `registerTools` turns into those blocks; everything else is JSON text. Scope is `get_garment`'s: the caller's own garments and a wardrobe shared with them at VIEW or more (`wardrobeFor`), another user's garment without a share is "Garment not found"/"Wardrobe not found", a garment without a photo "Garment has no photo". **Never a selfie**: a garment's photo is its own `file` row, but the tool still asks `publicPhoto` (which also names the thumb its row points at) and answers a selfie's file as "Garment not found" with a warn line (context `Web`), as the public `/file/**` routes do. Rate limited by `MCP_LIMIT` like every call; logged by the one `Mcp` line (tool, user, token row, outcome), never the bytes. Nothing else in the MCP server answers a photo or a photo URL. `test/integration/mcp-photos.spec.ts`.
- **Logs** (context `Mcp`): one line per call, `MCP <tool> by user <id> (token <row id>): ok|refused <status>|failed <status> (<detail>)|error <ms>` (failed: a chosen 5xx, the owner lock's 503), never the arguments or the token; a refused credential logs the reason and the client address. The writers the tools call log through `Web` as for a page, marked `(MCP)`. `test/integration/mcp.spec.ts` asserts no token or prefix reaches any log line.
- **Connect**: `claude mcp add --transport http closet https://closet.kashhq.dedyn.io/mcp --header "Authorization: Bearer <token>"` (README, Connect your Claude). Tailnet only: Claude's hosted connectors cannot reach it, and OAuth is not built.

## Gotchas

- **`/.well-known/*` answers `{}` to anything** (`src/web/shell/routes.tsx`, to keep browser and tool probes out of the error log). An MCP client refused with a 401 may look for OAuth metadata there (`/.well-known/oauth-protected-resource`) and gets an empty object: harmless, since `/mcp` offers no OAuth, but its error can read oddly. Real OAuth for `/mcp` would need real documents there.
- **`@fastify/rate-limit`'s `createRateLimit()` answers `isAllowed: true` only for the allow list.** A counted request is `isAllowed: false` whatever its count; over the limit is `isExceeded`. `/mcp`'s link import budget reads both (`src/web/mcp/routes.ts`).
