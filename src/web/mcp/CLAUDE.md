# MCP server

`src/web/mcp/` (#33; plan section 14): the owner's own Claude (Code, Desktop) works on the wardrobe through MCP. `POST /mcp` is a Streamable HTTP endpoint on the official `@modelcontextprotocol/sdk` in **stateless** mode: a `McpServer` and a `WebStandardStreamableHTTPServerTransport` per request (`sessionIdGenerator: undefined`, `enableJsonResponse: true`: JSON answers, no SSE, no `Mcp-Session-Id`), fed a Web `Request` built from the Fastify request and the body Fastify already parsed, its `Response` copied onto the reply, so the root hooks (security headers, the request log line, compression) apply as to any route. `GET` and `DELETE /mcp` are 405. Tool inputs are zod (`zod/v4`, the SDK's schema language; the only zod in the app).

- **Auth: personal access tokens** (`src/web/auth/personal-tokens.ts`, table `personal_access_token`, `drizzle/0012_personal_access_token.sql`): `closet_` plus 32 random bytes in base64url, stored as its SHA-256 (hex, `personal_access_token_token_hash_unique`) with an 11-character display prefix; `created_at`, `last_used_at` (written at most once a minute), `revoked_at` (revoked rows stay, hidden from the list). At most `MAX_ACTIVE_TOKENS` (20) in force per user, checked on the list `createToken` reads under the user's row lock and hands back for the page,. Managed at `/auth/tokens` ("Agent Access"). **Creating needs the current password** (`currentPassword`, checked with `verifyPassword` like change-password; the step-up rule, Stack Auth): a wrong one re-renders the form 400 (name kept, password never echoed or logged); a missing one is a schema 400; every attempt counts against `ACCOUNT_LIMIT`. A created token is answered once in the page, `Cache-Control: no-store`, beside the `claude mcp add` command. Revoking needs no password; `POST /auth/tokens/:id/revoke` is a 404 for anyone else's. A new password revokes them all. The endpoint's own preValidation hook reads `Authorization: Bearer` (never the cookie) into `request.accessToken`; a missing, malformed, unknown or revoked token is the same bare 401 with `WWW-Authenticate: Bearer realm="closet"`.
- **An API route, not a page: `config: { bearer: true }`** (declared in `require-session.ts`). Three places honour it: the root preValidation hook skips the session and the page context (so its errors are JSON, as on a static path), `requireSession` lets it through, and the same-origin hook accepts it without Origin (Request security, CSRF). `secretPath` is set too, so the request log shows `/mcp` even if a client put a token in the query string.
- **A token acts exactly as its user.** Every tool resolves the wardrobe it addresses (`ownerId`, from `list_shared_wardrobes`) through the same `authorizeWardrobe` as a page's `?ownerId=` (`wardrobeFor`, `tool.ts`), and calls the pages' own query and write functions: no SQL of its own for a write. Refusals are `HttpError`s as in a route and answer a tool error with the page's message (`Wardrobe not found`, `Forbidden`, `Garment not found`); anything else is logged with its stack and answered without detail.
- **Tools** (`tools/`): each tool's contract: `tools.md`. Read tools are annotated read-only; write tools start their description with `WRITES`, and nothing deletes or archives. A tool acts on the caller's own data unless it takes an `ownerId`; suggestions, outfits, the calendar, wears and trips are always the caller's own.
- **Photos: the one exception to "no photos leave the homelab"** (#90). `get_garment_photo` (read, `tools/garments.ts`) answers a garment's **400px thumb** (`Photos.getVariant(..., 'thumb')`, the cutout's if any, never the original) as an MCP `image` content block (`image/webp`, base64) after a text block naming the garment, so the owner's own authenticated Claude can tag garments (`search_garments` with `needsTagging`, then `update_garment`, MANAGE or owner as ever). A tool answers a picture by returning an `ImageAnswer` (`tool.ts`), which `registerTools` turns into those blocks; everything else is JSON text. Scope is `get_garment`'s: the caller's own garments and a wardrobe shared with them at VIEW or more (`wardrobeFor`), another user's garment without a share is "Garment not found"/"Wardrobe not found", a garment without a photo "Garment has no photo". **Never a selfie**: a garment's photo is its own `file` row, but the tool still asks `publicPhoto` (which also names the thumb its row points at) and answers a selfie's file as "Garment not found" with a warn line (context `Web`), as the public `/file/**` routes do. Logged by the one `Mcp` line, never the bytes. `test/integration/mcp-photos.spec.ts`.
- **Statements** (#172; production pays a round trip per statement, so count them; `test/integration/mcp-statements.spec.ts` pins every tool's, as the page audit calls them, `npm run audit:pages -- --only '#172'`). Every call starts with the token's read (`authenticateToken`, plus its last-use write once a minute); a tool on the caller's own wardrobe pays no share read (`resolveWardrobeAccess`). A tool reads what the page it mirrors reads, through the page's own fragments, never a query path of its own: `garmentOut` (get_garment, update_garment, add_garment_copy, add_garment_from_link) reads the capsules, the owner's wears and the repair log in one `selectScalars` beside the garment (`capsulesOfGarmentSql`, `wearSummarySql`, `repairLogSql`, as `garmentContext`); get_today asks `todayFor` for worn today (`worn`), which rides with the entries and the weather, and answers the model's weather (`weatherOfDays`); get_calendar reads its entries and the weather row in one statement (`userWeatherFrom` then fetches only a cold forecast, and only when there are entries); create_outfit reads its garments once (`namedGarments`, judged by `goneOf`); schedule_outfit takes the occasion kept from `scheduleOutfit` (read with the ownership check, under the owner lock); set_capsule_membership reads no capsule first: `changeMembership` answers which capsules took part, and another's is the 404 after a write that changed nothing; get_wardrobe is the garments then every garment's wears (two; a grantee's has the share read and no wears); get_style_profile is one statement (`styleProfileSql` with `weekTemplateSql`); get_suggestion_feedback is one, writing nothing; suggest_garment's refusals are one statement before the fetch (`suggestionRoom`). What is left is the writers' own cost (`begin`, the owner lock, its writes, `commit`) and the pages' reads: search_garments' page and count, list_suggestions' inbox and Muse outfits, get_closet_coverage's closet, the link import's two transactions.
- **Logs** (context `Mcp`): one line per call, `MCP <tool> by user <id> (token <row id>): ok|refused <status>|failed <status> (<detail>)|error <ms>` (failed: a chosen 5xx, the owner lock's 503), never the arguments or the token; a refused credential logs the reason and the client address. The writers the tools call log through `Web` as for a page, marked `(MCP)`. `test/integration/mcp.spec.ts` asserts no token or prefix reaches any log line.
- **`INSTRUCTIONS`** (`routes.ts`, the server's `instructions`): what Closet is, then Muse's workflow in rounds (#337; the design `docs/plans/2026-10-05-muse-suggestions.md` section 5): `get_suggestion_feedback` then `list_suggestions` first in every conversation, acting on every reason; read the style profile, the closet, `wardrobe_stats`, `get_sizes` and photos; `get_closet_coverage` for real gaps (`replace_soon` pieces are gaps); `create_option_group` per need, its note naming the closet pieces it pairs with; 2 to `MAX_OPTIONS_PER_GROUP` products each through `suggest_garment`, with note, rank, price and size; `goes_with_closet`; `suggest_outfit` a few per occasion of the week, every option in one; `finish_round` once at the end with the feedback read's `until`. The rules: never buy, mark owned, archive or delete, never propose again what was set aside. The README's "Styling with an agent" is the owner's side: change them together.
- **`ToolContext.tokenId`** is the calling token's row id: the call's log line, the provenance of what the agent suggests (a need's, a pick's, an outfit's) and the key of its feedback cursor. Never the token.
- **Muse's tools are the app's writers, never their own** (#337): a need is `createOptionGroup`'s, a pick the link import's garment marked by `markSuggestedProduct` in the garment's own transaction (`withGarment`), an outfit `proposeOutfit`'s (the outfit writer's proposal), the gaps `matchPlan`'s; a read is the page's (`readInbox`, `museOutfitsSql`). The wardrobe plans' tools are 410 stubs naming their successor (`tools/retired.ts`), removed with plans. `test/integration/mcp-muse.spec.ts`, `mcp-muse-races.spec.ts`, `mcp-style.spec.ts`.
- **Connect**: `claude mcp add --transport http closet https://closet.kashhq.dedyn.io/mcp --header "Authorization: Bearer <token>"` (README, Connect your Claude). Off the tailnet: `https://closet-mcp.kashhq.com/mcp` through `closet-mcp-gate` (`docs/deployment.md`). Hosted connectors need OAuth, not built.

## Gotchas

- **`/mcp` is publicly reachable, and the token is the whole gate.** The public hostname (`closet-mcp.kashhq.com`) reaches only `POST /mcp`, through a gate that 404s everything else, so nothing in closet may assume `/mcp` callers are on the tailnet. A token must never appear in a log line or error (asserted by `mcp.spec.ts`).
- **`/.well-known/*` answers `{}` to anything** (`src/web/shell/routes.tsx`, to keep browser and tool probes out of the error log). An MCP client refused with a 401 may look for OAuth metadata there (`/.well-known/oauth-protected-resource`) and gets an empty object: harmless, since `/mcp` offers no OAuth, but its error can read oddly. Real OAuth for `/mcp` would need real documents there.
- **`@fastify/rate-limit`'s `createRateLimit()` answers `isAllowed: true` only for the allow list.** A counted request is `isAllowed: false` whatever its count; over the limit is `isExceeded`. `/mcp`'s link import budget reads both (`src/web/mcp/routes.ts`).
