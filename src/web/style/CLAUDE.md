# Style profile

`src/wardrobe/style.ts` (the value sets), `src/web/style/` (#34, slice 34a). How a person dresses and toward what: what Muse reads of their taste (`get_style_profile`, `src/web/mcp/tools/style.ts`), beside the feedback their decisions give it. **The user's own**: no route takes `?ownerId=`, shares never reach it (`authorization-account.spec.ts`). It outlived the wardrobe plans it was built with (#337).

- **Table** `style_profile` (one row per user, `drizzle/0016_wardrobe_plans.sql`): `styles` and `palette` as `text[]` sets (`storedSet`), the `budget` band, notes. Every value set is a check constraint from `style.ts` and `properties.ts`, as on `garment`, so a new style or band is a migration. **Not stored here**: the week's rhythm, derived from the week template (#16, `weeklyRhythm`, see Weekly auto-plan), and the home city, the weather's (`user_weather`, #14), which the page shows read-only (`homeNameSql`, with a link to Profile › Weather; nothing with `WEATHER_ENABLED` off) and never copies.
- **One writer**, `saveStyleProfile` (`queries.ts`, an upsert): the page's post and the seed. One reader, `styleProfileSql`, a scalar subquery so the page and `get_style_profile` read it with the week template in one statement (#251, #172).
- **Routes** (`routes.tsx`): `GET|POST /auth/profile/style`, a section of the Profile (`profile.EDIT_STYLE`). A native post (`PostForm`): the chips post only their own sets (anything else is a 400 from `StyleProfileBody`), `readStyleProfileForm` stores them in their set's order, then 303 back with the saved toast (`?saved=1`). A form cached before #16 still posting the week's `times-*`/`per-*` fields has them stripped by the schema, unread.
- **Labels** (`labels.ts`): `style.style.<value>` and `style.budget.<band>`; `labels.spec.ts` fails on a value without one.
