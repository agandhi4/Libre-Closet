# PWA and the service worker

`public/sw.js` is a build artifact. Edit `views/assets/src-sw.ts` and run `npm run generate:sw`: esbuild bundles and minifies it with `process.env.NODE_ENV` defined as `"production"`, which strips Workbox's development logging and assertions (130 KB to 30 KB), then Workbox injects the precache manifest from `workbox-config.js` globs. Every `workbox-*` module the worker imports is a declared devDependency. The worker's only console output is its own `[sw]` lines. Service workers and Web Push require a secure context, which is why production is served over HTTPS (see Deployment).

Delivery model (audit fixes, see `src-sw.ts`, `public/js/pwa.js`, `public/js/connectivity.js`):

- **Static cache key.** Every first-party static URL carries `?v=<appVersion>` (the layout, the importmap, the garment page's module import). `appVersion` is `src/build-info.ts`: package.json version plus the commit (or build time) from `public/build.json`, which `scripts/write-build-info.ts` writes during `npm run build`. `src/static-assets.ts` serves `/modules`, `/js`, `/vendor`, `/assets` and `bundle.css` as `public, max-age=31536000, immutable`, so **the key is the only thing that rolls the cache**: `npm version`, a new commit in a built tree, or `GIT_SHA` passed to the Docker build all change it; a build with none of those still gets a unique timestamp. `sw.js` and `manifest.json` stay `no-cache`. `NODE_ENV=development` turns the immutable policy off so `tailwind --watch` output shows on a plain reload.
- **Precompressed static files** (#116): `static-delivery.md` beside this file (one `public/` root, `.br`/`.gz` from the build, never served stale). Read it before touching `src/static-assets.ts` or the build's generate steps.
- **Service worker strategies.** public/ files are precached by content hash (`?v` ignored on match). The tab roots opened as a document are stale-while-revalidate (below); every other navigation and every htmx request is NetworkFirst (3 s timeout). Both page strategies share one cache, `pages-v2` (400 entries), and one plugin list; navigation preload is on, so a navigation's request starts while a cold worker boots and both answer or revalidate with the preload response (every GET navigation must stay routed to one of them, or the preload is wasted); fragments are keyed `url|hx` by `src/htmx/fragment-request.ts`, which the server uses for the same decision. A followed redirect is not stored under the URL that redirected. Versioned scripts are StaleWhileRevalidate (`assets-v1`; `/vendor/` is precached as well, being under public/), `/file/**` `<img>` loads CacheFirst (`images-v2`, 600 entries, no age limit: the URLs are immutable; a session cache, below); `/selfies/**` matches no route. Unmatched requests (other POSTs, `/healthz`) bypass the worker, and so does every request to `/mcp` and the wardrobe export, navigations included (`bypassesWorker`, `page-cache.ts`; the GET navigations deliberately left unrouted). On activate the worker deletes retired caches (`RETIRED_CACHES`: the in-browser model's, up to ~42 MB on a phone that used it, `pages-v1`, whose pages were neither stamped nor owned, and `images-v1`, which outlived sessions).
- **Stale-while-revalidate tab roots** (issue #2). `/wardrobe`, `/styling`, `/outfits` and `/calendar` (`OPENS_STALE`, `page-cache.ts`: every dock tab but Today, which is network first, see Today), exactly (no query), loaded as a document (the app opening, a reload, pull to refresh) are answered from the page cache at once while the worker fetches the page again (`StaleTabRoot` in `src-sw.ts`, `servesStaleWhileRevalidate` in `src/web/page-cache.ts`); without a cached copy they are NetworkFirst; a copy stored before this worker activated (an older build rendered its `<head>`, whose importmap must not meet this build's precached scripts) is deleted first, so not even NetworkFirst's offline fallback serves it (the offline page does). In-app taps stay NetworkFirst on purpose: they follow the user's own writes (an archive lands on `/wardrobe` through `HX-Location`), which must show at once; the cold open is where the wait was. The revalidation compares the server's body with the cached one (`revalidationOutcome`: current, updated, signed-out, account-changed, failed), so **a tab root must render byte for byte the same while nothing changes** (`delivery.spec.ts` checks it): no timestamps, nonces or random ids in those pages. There are no `updated_at` columns and none are needed: the freshness shown is the copy's age, not the data's.
- **Freshness stamp and indicator** (#240): `freshness.md` beside this file. Every stored copy carries a cache-arrival stamp (`X-SW-Cached-At`, a `Server-Timing` entry); `public/js/freshness.js` shows it as "Updated N minutes ago" and asks the worker to revalidate (`REVALIDATE_PAGE`), swapping in a newer page only when the page is untouched. Read it before touching the stamp, revalidation, or a worker message that expects state to survive past a fetch event (WebKit gotcha).
- **Session caches** (#121, #131, #226): `session-caches.md` beside this file. `pages-v2` and `images-v2` hold one account's pages and photos and are dropped together (`dropSession`, `SESSION_CACHES`) on a sign-in, sign-out or account deletion POST's redirect, `X-Session-Ended`, a page for another account (`X-Page-Account`, `claimPageCache`), a tab root revalidated signed out or for another account, and a followed redirect to the login page (`sentToLogin`); a page or photo requested before a drop is never stored after it (generations). Selfies are never the worker's, and only HTML is a page (`isRenderedPage`). Read it before touching what the worker stores for an account or how it learns the account changed.
- **Offline warm** (#286): `offline-warm.md` beside this file. Once a day, after a signed-in page loads, `pwa.js` asks (`WARM_PAGES`) and the worker fetches the account's whole wardrobe from `GET /offline/warm` (the session's own, never a shared one; 300 garments, 80 outfits): tab roots, this week and the next, every garment and outfit page, the grid's later pages and every thumb, through the session caches' own plugins, so a drop mid-warm stores nothing more. Offline, a cutout never viewed is drawn from its thumb. Every HTML answer is `Cache-Control: private, no-cache` (`send()`). Read it before touching the warm, the list or the caches' caps.
- **Updates.** The worker does not `skipWaiting()` on install. `pwa.js` shows an "Update available: Reload" toast on `waiting`, posts `SKIP_WAITING` on tap, and reloads on `controlling`. Never force a reload. Another window of the app is claimed by the new worker without reloading and keeps its toast, whose Reload then only reloads; pwa.js keeps the update's state itself (none, waiting, active), not Workbox's `isUpdate`, which is false in a page opened before the first worker (#180). `test/sw-update.spec.ts` deploys a second worker behind a proxy: `docs/testing-service-worker.md`.
- **Connectivity.** `connectivity.js` probes `GET /healthz` (204, `no-store`, skips the session hook) every 30 s while visible, on every `htmx:sendError`/`responseError`, and every 5 s while offline; it drives `#connectivity-banner` in `src/web/layout/app-status.tsx` and dispatches `connectivity:change` on the document (freshness.js revalidates a cached display on it). `navigator.onLine` is only a hint. Those two probes are suppressed while the page is leaving (`pagehide`/`beforeunload`, until `pageshow`) or hidden: a native form post cancels any htmx request in flight, which WebKit turns into `htmx:sendError` (#241), not evidence the server is unreachable. The heartbeat and the `visibilitychange` probe still catch a real drop.
- **Per navigation, only the body.** A boosted navigation swaps the body and nothing else should run again: `pwa.js` sits in the head; the install dialog (below) is mounted once on `<html>`, outside the swapped body (in the body every navigation re-mounted it and re-fetched `/manifest.json`); pull to refresh (iOS standalone only) is rebound when the body is swapped, not on fragment swaps. The htmx config has no view transitions (taps are dropped while one runs) and keeps 3 history snapshots (`layout.tsx` has the measurements). The app bar's back arrow returns to those snapshots through history (`public/js/back.js`, which keeps its own per-entry trail in `history.state` around htmx's rewrites: `src/web/layout/CLAUDE.md`). Tap feedback: the body's inherited `hx-indicator="#loading, closest a"` lights the app bar's spinner for every request and marks the tapped link `htmx-request` (`main.css` dims it and its card).
- **Install dialog** (issues #4, #48). `<pwa-install>` (`@khmyznikov/pwa-install` 0.7) costs whoever mounts it the bundle (160 KB, 45 KB compressed; 0.5.8 was 100/30 KB but read `/manifest.json` twice when handed the prompt event), `/manifest.json` once and the manifest's first icon, so `pwa.js` imports it only on a load that can offer an install: never standalone (`display-mode: standalone`, or `navigator.standalone` on iOS); in Chromium only on `beforeinstallprompt` (installable, not installed); in a browser without that event only on the platforms the element has instructions for (`manualInstallPlatform`: iPhone and iPad, Safari on macOS, Android), so never in desktop Firefox. The element shows itself; there is no install button in the app. It shows the manifest's `icons[0]` (fetching no other), so the manifest lists the small rasters smallest first (`src/web/app-icon.ts`: `icon-192.png`, 5 KB, and `icon-512.png`, from `npm run generate:icons`); the 1000 px `ICON_NAME` (45 KB) is only for Open Graph and the watermark, and the apple-touch-icon (which Firefox also fetches on every cold load) is the 192 px one. On Chromium 155+ 0.7 installs through the Web Install API (`navigator.install()`, the manifest's `id`) and keeps the prompt event as its fallback. **No screenshots** (owner decision): the manifest has none, the element gets `disable-screenshots`, and `public/assets/screenshots/` is gone. Nothing under `public/assets/` is precached (`workbox-config.js`): no page renders the icon (the OS reads it at install, link previews and the dialog online), and precaching it cost every fresh install 45 KB. `test/install-dialog.spec.ts` proves a cold load of the installed app (Android and iPhone) fetches no icon, no dialog and the manifest at most once, desktop Firefox loads nothing, the Chrome dialog fetches the manifest exactly once (the browser's own read, which the element's `getInstalledRelatedApps()` triggers in headless Chromium, is told apart by resource type) and only the 192 px icon, and the Chrome and iPhone dialogs still work; Chromium stands in for Safari (user agent, `navigator.platform`, no `BeforeInstallPromptEvent`) and the spec dispatches the `beforeinstallprompt` headless Chromium never fires.
- **Page-only libraries** (Styling's `styling`, which imports the shared `snap-strip` through the importmap too; the garment page's `mask-editor`) load from the page that needs them, as ES modules through the importmap (`src/web/layout/layout.tsx`) so boosted navigations cannot race a global. A page-only library whose package ships no minified ESM gets an esbuild entry in `npm run generate:vendor` (which `generate:tailwind` and its watch run first, so `generate` and `start:dev` do too) that bundles and minifies it into `public/vendor/` (gitignored), which the importmap maps its name to; the package directory is not served (sortablejs went this way until Styling retired it, #91). Styling imports `styling` from an inline module (a fixed string through `dangerouslySetInnerHTML`, `src/web/styling/styling-page.tsx`) that calls `initStyling` for this visit's rows: a `<script type="module" src>` runs once per document, so it would not run again when a boosted navigation returns to the page. The module registers its delegated listeners on the document once, at evaluation; an inline module registers its own on an element of the page, never on the document, or every visit would add another. No page loads a background-removal model or WASM (`pwa.spec.ts` asserts none is ever requested, through a whole upload). The mask editor's pencil is wired by a listener delegated on `#garment-photo-slot` that reads its URLs from the button's data attributes at the tap, because the cutout polling swaps the button. `photo-input` is no page module: the file inputs' `onchange` (`PREPARE_AND_SUBMIT_PHOTO`, `src/web/layout/parts.tsx`; the photo sheet and selfies) imports it at the pick and submits only when a file came back, so an empty pick posts nothing and no page script has to re-run after a boosted navigation.
- **Wardrobe fragment.** `GET /wardrobe` with a fragment request (`HX-Request` without `HX-Boosted`/history restore) returns `WardrobeMain` (`#wardrobe-main`) with `Vary`, and the ⋯ menu out of band (`WardrobeFragment`), so its Select keeps the new filters; the scope row (capsule menu, chips, search) and the filter modal's own GET form target `#wardrobe-main` with `hx-push-url`, so filtering never re-renders the app bar, tabs and dock. The wardrobe switcher is a plain full-page link: switching changes the title, the tabs and what may be done. The grid's later pages come from `GET /wardrobe/tiles`, always htmx requests, so the worker caches each under its own `url|hx` key; offline, the pages scrolled through or warmed (`offline-warm.md`) are what the cache has.

## Gotchas

- **WebKit never settles a fetch whose opaque redirect carries `Clear-Site-Data`** (#239): the worker must not `fetch()` a navigation's own request (redirect mode `manual`) where the answer can be a redirect with that header. The auth POSTs follow it and answer with `Response.redirect` (`session-caches.md`); GET navigations go through the navigation preload, which is unaffected.

- **Chromium hides `Clear-Site-Data` from the response it applies**, the worker's own `fetch` included, so the worker cannot read it: `endSession` also sends `X-Session-Ended` (`SESSION_ENDED_HEADER`, `page-cache.ts`), which it reads (#131).

- **Playwright's `context.setOffline` does not cut the worker's own fetches** (Chromium): the page's requests and the navigation preload fail, but NetworkFirst for an htmx request, a `REVALIDATE_PAGE` or an image the worker fetches still reaches the server. `networkSwitch` (`test/support/service-worker.ts`) also fails them through `context.route`, which does see a worker's requests (and turns the HTTP cache off).

- **`@fastify/static` 10 applies `setHeaders` after `send`'s own Cache-Control**, passing the `FastifyReply` (`reply.header()`), which is what makes the per-file policy in `registerStaticAssets` (`src/static-assets.ts`) work; before 10 it was the raw response and `send` overwrote it. Its `path` is `sw.js.br` for a precompressed worker: `staticCacheControl` judges the source, or the worker would be cached for a year. `test/integration/delivery.spec.ts` asserts the headers.
