# PWA and the service worker

`public/sw.js` is a build artifact. Edit `views/assets/src-sw.ts` and run `npm run generate:sw`: esbuild bundles and minifies it with `process.env.NODE_ENV` defined as `"production"`, which strips Workbox's development logging and assertions (130 KB to 30 KB), then Workbox injects the precache manifest from `workbox-config.js` globs. Every `workbox-*` module the worker imports is a declared devDependency. The worker's only console output is its own `[sw]` lines. Service workers and Web Push require a secure context, which is why production is served over HTTPS (see Deployment).

Delivery model (audit fixes, see `src-sw.ts`, `public/js/pwa.js`, `public/js/connectivity.js`):

- **Static cache key.** Every first-party static URL carries `?v=<appVersion>` (the layout, the importmap, the garment page's module import). `appVersion` is `src/build-info.ts`: package.json version plus the commit (or build time) from `public/build.json`, which `scripts/write-build-info.ts` writes during `npm run build`. `src/static-assets.ts` serves `/modules`, `/js`, `/vendor`, `/assets` and `bundle.css` as `public, max-age=31536000, immutable`, so **the key is the only thing that rolls the cache**: `npm version`, a new commit in a built tree, or `GIT_SHA` passed to the Docker build all change it; a build with none of those still gets a unique timestamp. `sw.js` and `manifest.json` stay `no-cache`. `NODE_ENV=development` turns the immutable policy off so `tailwind --watch` output shows on a plain reload.
- **Precompressed static files** (#116). One `@fastify/static` root, `public/` (`src/static-assets.ts`); `/modules/*` is `public/modules/`, libraries copied from node_modules (`CLIENT_MODULES`, `scripts/static-assets.ts`). The build's last step (`generate:precompress`) writes `.br` (brotli 11) and `.gz` beside each text file of 1 KB+; `preCompressed` serves the one asked for with the source's type and `Vary: Accept-Encoding`, and `@fastify/compress` only compresses what has no variant (pages). At boot a variant older than its source, or orphaned, turns them off with a warning (never stale); development never uses them. Workbox globs match no variant and skip `modules/**`. The integration globalSetup lays out `public/` the same way.
- **Service worker strategies.** public/ files are precached by content hash (`?v` ignored on match). The tab roots opened as a document are stale-while-revalidate (below); every other navigation and every htmx request is NetworkFirst (3 s timeout). Both page strategies share one cache, `pages-v2`, and one plugin list; navigation preload is on, so a navigation's request starts while a cold worker boots and both answer or revalidate with the preload response (every GET navigation must stay routed to one of them, or the preload is wasted); fragments are keyed `url|hx` by `src/htmx/fragment-request.ts`, which the server uses for the same decision. A followed redirect is not stored under the URL that redirected. Versioned scripts are StaleWhileRevalidate (`assets-v1`; `/vendor/` is precached as well, being under public/), `/file/**` images CacheFirst (`images-v1`, 500 entries, 30 days). Unmatched requests (other POSTs, `/healthz`) bypass the worker, and so does every request to `/mcp`, navigations included (`bypassesWorker`, `page-cache.ts`; the one GET navigation deliberately left unrouted). On activate the worker deletes retired caches (`RETIRED_CACHES`: the in-browser model's, up to ~42 MB on a phone that used it, and `pages-v1`, whose pages were neither stamped nor owned).
- **Stale-while-revalidate tab roots** (issue #2). `/wardrobe`, `/styling`, `/outfits` and `/calendar` (`OPENS_STALE`, `page-cache.ts`: every dock tab but Today, which is network first, see Today), exactly (no query), loaded as a document (the app opening, a reload, pull to refresh) are answered from the page cache at once while the worker fetches the page again (`StaleTabRoot` in `src-sw.ts`, `servesStaleWhileRevalidate` in `src/web/page-cache.ts`); without a cached copy they are NetworkFirst; a copy stored before this worker activated (an older build rendered its `<head>`, whose importmap must not meet this build's precached scripts) is deleted first, so not even NetworkFirst's offline fallback serves it (the offline page does). In-app taps stay NetworkFirst on purpose: they follow the user's own writes (an archive lands on `/wardrobe` through `HX-Location`), which must show at once; the cold open is where the wait was. The revalidation compares the server's body with the cached one (`revalidationOutcome`: current, updated, signed-out, account-changed, failed), so **a tab root must render byte for byte the same while nothing changes** (`delivery.spec.ts` checks it): no timestamps, nonces or random ids in those pages. There are no `updated_at` columns and none are needed: the freshness shown is the copy's age, not the data's.
- **Freshness stamp and indicator.** Every copy the worker stores carries `X-SW-Cached-At` (epoch ms, the device's clock), so any response served from the cache says when it arrived. `public/js/freshness.js` (started by `pwa.js`) tracks the display on screen: a document asks the worker how it was served (`PAGE_FRESHNESS` over a `MessageChannel`: fresh, or cached with the stamp and then the revalidation's outcome; the worker notes what it served by the navigation's `resultingClientId` and answers the message's client, so two tabs opening one tab root each get their own answer); an htmx swap reads the stamp from its own response; htmx history restores reuse the stamp kept on `#freshness` in the snapshot. A cached copy a minute old or more shows "Updated 3 minutes ago" (`#freshness` under the app bar's title, `public/js/age-label.js`, unit-tested in `src/web/layout/age-label.spec.ts`), after a 1 s grace while a revalidation is in flight so an online open never flashes it. **When the server's page differs it is swapped in only if the page is untouched** (no tap, key or wheel yet, scrolled to the top, no dialog open); otherwise a persistent toast offers it ("Newer version of this page", Refresh), so content never moves under a thumb or a half-typed form. Signed-out or account-changed reloads the page (the worker has dropped every page). Back online (`connectivity:change`), a cached display asks the worker to revalidate it (`REVALIDATE_PAGE`), with the same handling; a display that is a URL-pushing fragment (the wardrobe's filters) says so, the worker asks for the fragment (`HX-Request`, so it meets the `|hx` copy) and the page swaps it back into its target with the requester's `hx-swap`. The new page arrives in the worker's answer and is swapped with `htmx.swap` (no second fetch).
- **Page cache ownership.** The cache holds one account's pages; no page is ever served to a session it was not rendered for. The worker cannot read the httpOnly cookie, so: (1) a POST to `/auth/login`, `/auth/register`, `/auth/logout` or `/auth/delete-account` that answers with a redirect drops the cache before the redirect is answered (sign-out also drops the push subscription); (2) every HTML answer names its account (`X-Page-Account`, the user id, set by `send()` in `src/web/render.ts`; absent signed out), and the worker drops the whole cache before storing a page for an account other than the recorded owner (`claimPageCache`; the owner and the activation time are records in the cache under off-origin `page-cache.invalid` keys, so a drop takes them too); (3) a tab root whose revalidation comes back signed out or for another account drops the cache and reloads the page; (4) a page request whose followed redirect lands on the login page (`sentToLogin`, `page-cache.ts`: a boosted tap after the session was ended elsewhere, which no sign-out POST announced) claims the cache for nobody, dropping another account's pages (a document load gets the same from the signed-out login page it stores, through (2)). (1) covers every sign-in made in the app; (2) and (3) are the backstop for one the worker never saw (only possible from outside the page, as `page.request` in a spec): the first page of the new session empties the cache, and at worst a tab root opened straight after shows the old copy until its revalidation lands and reloads it. (5) **Generations** (#121): every drop starts a new one; a page request records the one it started in (`pageStore`'s `handlerWillStart`) and its answer is stored, or claims the cache, only while that is still current, checked in `claimPageCache` under the lock that serializes claims and drops. Without it a slow page for A that landed after signing out and in as B reclaimed the cache for A (offline, where no later page puts it right, B then opened A's wardrobe). In memory on purpose: a stopped worker has no requests in flight. Workbox writes after the claim, so a drop can still fall between the two; `ownedCopies` reads a copy back only for the account that owns the cache. `test/stale-pages.spec.ts` covers (1) to (3) and (5), `test/session-revocation.spec.ts` (4).
- **Updates.** The worker does not `skipWaiting()` on install. `pwa.js` shows an "Update available: Reload" toast on `waiting`, posts `SKIP_WAITING` on tap, and reloads on `controlling`. Never force a reload.
- **Connectivity.** `connectivity.js` probes `GET /healthz` (204, `no-store`, skips the session hook) every 30 s while visible, on every `htmx:sendError`/`responseError`, and every 5 s while offline; it drives `#connectivity-banner` in `src/web/layout/app-status.tsx` and dispatches `connectivity:change` on the document (freshness.js revalidates a cached display on it). `navigator.onLine` is only a hint.
- **Per navigation, only the body.** A boosted navigation swaps the body and nothing else should run again: `pwa.js` sits in the head; the install dialog (below) is mounted once on `<html>`, outside the swapped body (in the body every navigation re-mounted it and re-fetched `/manifest.json`); pull to refresh (iOS standalone only) is rebound when the body is swapped, not on fragment swaps. The htmx config has no view transitions (taps are dropped while one runs) and keeps 3 history snapshots (`layout.tsx` has the measurements). The app bar's back arrow returns to those snapshots through history (`public/js/back.js`, which keeps its own per-entry trail in `history.state` around htmx's rewrites: `src/web/layout/CLAUDE.md`). Tap feedback: the body's inherited `hx-indicator="#loading, closest a"` lights the app bar's spinner for every request and marks the tapped link `htmx-request` (`main.css` dims it and its card).
- **Install dialog** (issues #4, #48). `<pwa-install>` (`@khmyznikov/pwa-install` 0.7) costs whoever mounts it the bundle (160 KB, 45 KB compressed; 0.5.8 was 100/30 KB but read `/manifest.json` twice when handed the prompt event), `/manifest.json` once and the manifest's first icon, so `pwa.js` imports it only on a load that can offer an install: never standalone (`display-mode: standalone`, or `navigator.standalone` on iOS); in Chromium only on `beforeinstallprompt` (installable, not installed); in a browser without that event only on the platforms the element has instructions for (`manualInstallPlatform`: iPhone and iPad, Safari on macOS, Android), so never in desktop Firefox. The element shows itself; there is no install button in the app. It shows the manifest's `icons[0]` (fetching no other), so the manifest lists the small rasters smallest first (`src/web/app-icon.ts`: `icon-192.png`, 5 KB, and `icon-512.png`, from `npm run generate:icons`); the 1000 px `ICON_NAME` (45 KB) is only for Open Graph and the watermark, and the apple-touch-icon (which Firefox also fetches on every cold load) is the 192 px one. On Chromium 155+ 0.7 installs through the Web Install API (`navigator.install()`, the manifest's `id`) and keeps the prompt event as its fallback. **No screenshots** (owner decision): the manifest has none, the element gets `disable-screenshots`, and `public/assets/screenshots/` is gone. Nothing under `public/assets/` is precached (`workbox-config.js`): no page renders the icon (the OS reads it at install, link previews and the dialog online), and precaching it cost every fresh install 45 KB. `test/install-dialog.spec.ts` proves a cold load of the installed app (Android and iPhone) fetches no icon, no dialog and the manifest at most once, desktop Firefox loads nothing, the Chrome dialog fetches the manifest exactly once (the browser's own read, which the element's `getInstalledRelatedApps()` triggers in headless Chromium, is told apart by resource type) and only the 192 px icon, and the Chrome and iPhone dialogs still work; Chromium stands in for Safari (user agent, `navigator.platform`, no `BeforeInstallPromptEvent`) and the spec dispatches the `beforeinstallprompt` headless Chromium never fires.
- **Page-only libraries** (Styling's `styling`; the garment page's `mask-editor`) load from the page that needs them, as ES modules through the importmap (`src/web/layout/layout.tsx`) so boosted navigations cannot race a global. A page-only library whose package ships no minified ESM gets an esbuild entry in `npm run generate:vendor` (which `generate:tailwind` and its watch run first, so `generate` and `start:dev` do too) that bundles and minifies it into `public/vendor/` (gitignored), which the importmap maps its name to; the package directory is not served (sortablejs went this way until Styling retired it, #91). Styling imports `styling` from an inline module (a fixed string through `dangerouslySetInnerHTML`, `src/web/styling/styling-page.tsx`) that calls `initStyling` for this visit's rows: a `<script type="module" src>` runs once per document, so it would not run again when a boosted navigation returns to the page. The module registers its delegated listeners on the document once, at evaluation; an inline module registers its own on an element of the page, never on the document, or every visit would add another. No page loads a background-removal model or WASM (`pwa.spec.ts` asserts none is ever requested, through a whole upload). The mask editor's pencil is wired by a listener delegated on `#garment-photo-slot` that reads its URLs from the button's data attributes at the tap, because the cutout polling swaps the button. `photo-input` is no page module: the file inputs' `onchange` (`PREPARE_AND_SUBMIT_PHOTO`, `src/web/layout/parts.tsx`; the photo sheet and selfies) imports it at the pick and submits only when a file came back, so an empty pick posts nothing and no page script has to re-run after a boosted navigation.
- **Wardrobe fragment.** `GET /wardrobe` with a fragment request (`HX-Request` without `HX-Boosted`/history restore) returns `WardrobeMain` (`#wardrobe-main`) with `Vary`, and the ⋯ menu out of band (`WardrobeFragment`), so its Select keeps the new filters; the scope row (capsule menu, chips, search) and the filter modal's own GET form target `#wardrobe-main` with `hx-push-url`, so filtering never re-renders the app bar, tabs and dock. The wardrobe switcher is a plain full-page link: switching changes the title, the tabs and what may be done. The grid's later pages come from `GET /wardrobe/tiles`, always htmx requests, so the worker caches each under its own `url|hx` key; offline, the pages already scrolled through are what the cache has.

## Gotchas

- **Playwright's `context.setOffline` does not cut the worker's own fetches** (Chromium): the page's requests and the navigation preload fail, but NetworkFirst for an htmx request or a `REVALIDATE_PAGE` still reaches the server. `networkSwitch` in `test/stale-pages.spec.ts` also fails them through `context.route`, which does see a worker's requests.

- **`@fastify/static` 10 applies `setHeaders` after `send`'s own Cache-Control**, passing the `FastifyReply` (`reply.header()`), which is what makes the per-file policy in `registerStaticAssets` (`src/static-assets.ts`) work; before 10 it was the raw response and `send` overwrote it. Its `path` is `sw.js.br` for a precompressed worker: `staticCacheControl` judges the source, or the worker would be cached for a year. `test/integration/delivery.spec.ts` asserts the headers.
- **`preCompressed` with several roots misses files** (`@fastify/static` 10.1): one without a variant in the first root is then sought in the last only. Keep one root.
