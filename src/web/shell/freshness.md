# The freshness protocol: stamp, revalidation, WebKit's scope-freeing gotcha (#240)

Linked from `CLAUDE.md` in this directory (PWA and the service worker). Read it before touching the freshness stamp, `REVALIDATE_PAGE`, or `public/js/freshness.js`.

**Freshness stamp and indicator.** Every copy the worker stores carries `X-SW-Cached-At` (epoch ms, the device's clock) and the same stamp as a `Server-Timing` entry (`CACHED_AT_TIMING_NAME`, `page-cache.ts`), so any response served from the cache says when it arrived. `public/js/freshness.js` (started by `pwa.js`) tracks the display on screen: a full navigation reads that Server-Timing entry itself, through Navigation Timing (`performance.getEntriesByType('navigation')[0].serverTiming`, the same way `src/metrics` reads the route template) — not by asking the worker how it was served, which a worker that had to remember the answer across the fetch and a later message could get wrong (see the WebKit gotcha below); an htmx swap reads the stamp from its own response; htmx history restores reuse the stamp kept on `#freshness` in the snapshot.

**Revalidation.** A cached load (any page, not only a tab root) asks the worker to revalidate it (`REVALIDATE_PAGE` over a `MessageChannel`, a fresh, self-contained request each time; `StaleTabRoot` itself starts none). A fresh copy a minute old or more shows "Updated 3 minutes ago" (`#freshness` under the app bar's title, `public/js/age-label.js`, unit-tested in `src/web/layout/age-label.spec.ts`), after a 1 s grace while that revalidation is in flight so an online open never flashes it. **When the server's page differs it is swapped in only if the page is untouched** (no tap, key or wheel yet, scrolled to the top, no dialog open); otherwise a persistent toast offers it ("Newer version of this page", Refresh), so content never moves under a thumb or a half-typed form. Signed-out or account-changed reloads the page (the worker has dropped the session caches). Back online (`connectivity:change`) a cached display asks again, the same `REVALIDATE_PAGE`; a display that is a URL-pushing fragment (the wardrobe's filters) says so, the worker asks for the fragment (`HX-Request`, so it meets the `|hx` copy) and the page swaps it back into its target with the requester's `hx-swap`. The new page arrives in the worker's answer and is swapped with `htmx.swap` (no second fetch).

**The WebKit gotcha: a worker cannot count on remembering anything from a fetch event until a later message arrives.** WebKit can free a worker's whole script scope once a fetch event's own `waitUntil` settles, before the page's next script line runs, let alone before it posts a question back. A tab root's freshness once relied on exactly that (a promise kept in a module-level map, keyed by the navigation's `resultingClientId`, for `PAGE_FRESHNESS` to collect once the page asked): the ids always matched (proven with a temporary log of both), yet the map was already empty by the time WebKit answered. Read the answer from the response itself (a header, a `Server-Timing` entry) or ask fresh each time (`REVALIDATE_PAGE`) instead of banking on the worker's memory surviving an event boundary. This is why the stamp is read from Navigation Timing and every revalidation is a fresh round trip, never a cached promise.
