# Layout

Navigation and rendering rules are in the root `CLAUDE.md` (Web layer).

- **The app bar** (#82, `src/web/layout/app-bar.tsx`): `<AppBar ctx title titleMenu? back? formPage? scope? actions? />` is every page's header; there is no navbar, drawer or menu (the account's links live on Profile, `/auth/profile`, reached by the avatar, the email's initial; Login when signed out). `title` is the page's only h1 (`expectFullPage` in `test/integration/pages.ts` asserts one app bar, one h1 and the avatar or a way in, on the whole route table), `titleMenu` turns the title into a dropdown (the Wardrobe's switcher), `back` an optional back arrow (see The back arrow), `formPage` marks an add or edit page, `scope` what the page is scoped to (Styling's capsule menu), `actions` at most two. It also carries `#loading` (the body's `hx-indicator`) and `#freshness` by id, which freshness.js and the layout find. It is rendered into the body, so a cached tab root carries its own bar: nothing in it may vary between two renders of the same page (Stale-while-revalidate tab roots). It is 4rem: pages leave `pt-20` (the bar and a 1rem gutter), or `pt-16` when their first row sits flush under it (the Wardrobe tabs).
- **The back arrow goes back like a native app's** (#105, `public/js/back.js`, loaded by the layout on every page): the app bar's `BackLink historyBack` (`data-history-back`) goes back in history, to the page as htmx's snapshot kept it (Styling's rows as left), whenever the entry before is in the app, and follows `back` (its href, the page's fixed parent) only on a cold entry: a shared link, a push notification, a fresh launch, a new tab. A destination line's own `BackLink` (Styling's, Ideas', `DayDestinationLine`) stays a fixed link. **"In the app" is recorded, never guessed**: every entry carries its trail (the app's entries from the cold one to itself) in `history.state.closetTrail`, per entry, so back/forward, a reload and the bfcache find theirs; a same-origin referrer cannot tell after a boosted navigation, sessionStorage cannot say which entry back/forward landed on, and the Navigation API reached Safari only in 26.x. A native post (every `PostForm`) starts a new document without state: its submit hands the trail over in sessionStorage, taken only by the next document whose referrer is the posting page. **Back skips a form that is done**: a `formPage` (add and edit pages, Styling where it can save, the self-saving style, sizes and tokens pages) is done once saved or cancelled. Its Cancel is `CancelLink` (`parts.tsx`), a back arrow in words; on a cold entry the arrow or Cancel goes forward to its href and that entry counts as the form's exit (other links a form page holds, Styling's garments, do not). From the page a save or exit lands on, the arrow goes past the form (and a refused attempt's re-render) and, inside that chain only, past entries of the same pathname (the page before the save, a `?saved=1` copy): Garment, Edit, Save, back lands where the garment was opened from, while Insights, `?unworn=30`, back is Insights. A new add or edit page passes `formPage` to its `AppBar`, uses `CancelLink`, and is listed with `form(...)` in `pageRoutes` (`test/integration/pages.ts`): `expectFormPageFlag` fails a page whose flag disagrees with the table. **A save refreshes what history restores**: each trail entry keeps when its page was rendered (`at`), a native post records the tab's last save (sessionStorage), and an entry restored from history (htmx's restore, a bfcache `pageshow`, a document a back/forward loads again from the HTTP cache, reloaded once loaded) that was rendered before the save is reloaded in place, which also revalidates a stale tab root. Each stale entry refreshes once however far back; entries rendered after the last save (anything after signing in) restore as they were. htmx writes (autosave, hx-post) are not saves here. **The console never names a path**: `back.js` logs a route's first segment only (`routeKind`), since paths carry secrets (an invite token). `test/back-navigation.spec.ts` covers each case at 390 px (the rename showing after Wardrobe, Edit, Save, back); `app-shell.spec.ts` the markup it reads.
- **Dates a user reads come from `src/web/date-labels.ts`, never an ISO string** (#356; `test/integration/date-labels.spec.ts` strips tags and fails a page whose text has `YYYY-MM-DD`). A past day relative to today is `relativeDay` (today, yesterday, 2 to 6 days ago, then `dateLabel`: "Tue, Sep 29" in today's year, else "Sep 29, 2025"); a date on its own `dateLabel`; a planned day `dayLabel` ("Tuesday, Sep 29") or `shortDayLabel` ("Sep 29"). Today is the caller's `todayIn(APP_TIMEZONE, now)`. A list of days heads each with `DayHeading` (`day-heading.tsx`: weekday, the date muted, a Today badge), as the calendar week and a trip do.
- **A garment's status mark is `<GarmentMark>`** (#357, `garment-mark.tsx`, beside `parts.tsx`): every badge that says where a garment stands (to buy, archived, lent, at repair, needs a wash, set aside) derives its marks with `garmentMarks(garment, { ownerView })` (`src/wardrobe/marks.ts`, pure: the order, and the gate that keeps away and the wash from a viewer of a shared wardrobe) and draws them here, never a hand-made `badge` with a status string. One variant and one `mark.*` string per mark, in `MARKS`: to-buy `badge-accent`, archived `badge-neutral`, away (both) `badge-warning` (can't wear it now), set-aside `badge-outline` (its dot a border), needs-wash `badge-info`; always `badge-xs`. Needs-wash's words take the copies of a multiple (`wash`: "Wash 2/3", `mark.NEEDS_WASH_COPIES`). The first mark is in words, the rest only in its accessible name, so a tile never stacks status badges. `dot` is the frame too small for words (the collage's thumbs), `text` other words in the first mark's look (Muse's price), `class` placement only (position, a responsive size step). A surface marks only what it already reads (an absent field is no mark): the grid status, away and the wash (the owner's grid alone reads them); Styling and the garment page status (the page's away and wash are its wear section's); Muse status and set aside; the share page to-buy only; the collage to-buy, plus archived, away and (today's cards) the wash where it warns (`collagePieces`, #358: Today, the calendar from today on, the outfit page). Tests find a mark by `data-mark="<kind>"`; `test/integration/garment-marks.spec.ts` holds "Archived" and "To buy" to one markup across the grid, Styling and the garment page. Condition ("Needs repair") and copies ("×3") are not status marks and keep their own badges.

## Gotchas

- **htmx overwrites `history.state` with `{htmx: true}`** whenever it snapshots a page (before every boosted navigation, on every history restore), so anything kept on an entry must be written back after it: `back.js` keeps the trail on screen in a variable and rewrites it on `htmx:beforeHistoryUpdate` (the entry left), `htmx:pushedIntoHistory`/`replacedInHistory` (the new one) and `htmx:historyRestore`; a `popstate` listener reads `event.state` before htmx's handler clobbers it (htmx sets `window.onpopstate` at DOMContentLoaded, after the module registered). The arrow's click listener is on the document in the capture phase, ahead of htmx's listener on the boosted link.
- **The dock stacks above every page, and its active tab comes from one route table.** `.dock` and `.app-bar` are z-index 900 in `main.css` (daisyUI gives the dock 1, so the outfit card's `relative z-10` calendar button drew over it); page content stays at z-20 or below, the toasts at 999 above both. The bar and the dock never overlap, so they need no order between them. A bar fixed above the dock uses `bottom-dock` (`--spacing-dock` in `main.css`: the dock's height with the safe area). A tab is lit on every page of its section: `sectionOf` (`src/web/layout/sections.ts`) maps the request path, whole segments (`/capsules/*` and `/laundry` are Wardrobe, `/wardrobe-share` is nothing). A new top-level route shows no tab until it is added there. `DOCK_TABS` is which sections the dock shows, in order; `SECTION_HOME` (the tabs' links) minus Today is the service worker's stale-while-revalidate tab roots (`OPENS_STALE`, `page-cache.ts`): a new tab root must render byte for byte the same while nothing changes, or be left out of it on purpose like Today. `test/dock.spec.ts` probes the dock at 390 px on each page with floating controls.
- **A page's `<main>` needs `w-full` beside `max-w-* mx-auto`.** The body is `flex flex-col`, and a flex item with auto margins does not stretch: it sizes to its content, capped by the max width. A horizontal scroll strip (its max-content is every card) then widened the garment page to 512 px on a 390 px phone (#18b); short content made pages narrower than the screen. Every such `<main>` carries `w-full` since; the gallery's `sm:mx-auto` only applies past the phone.
- **At `lg` (1024 px) the dock is a left rail, from the same markup.** `main.css` restyles `.dock` (a 5rem column, the active mark on its left edge, links unchanged, so keyboard order is the dock's and `aria-current` marks the tab). Never a second markup or a width-dependent render: the server cannot know the viewport and the tab roots are cached byte for byte. Where the page has a dock, `:root:has(.dock)` sets `--rail-width` (5rem; 0 otherwise) and `--spacing-dock` to 0: the body pads left by the rail, `.app-bar` and the pull-to-refresh bar start at it, and anything fixed to the screen's left uses `left-rail` (the bars above the dock, the connectivity banner; the toast host centres on the content column). A new fixed bar uses `left-rail` and `bottom-dock`, never `left-0`. Dialogs (z 999) cover the rail; the rail is z 900 like the app bar.
- **Page widths come from `PageMain`, never a `max-w-*` on a page's `<main>`** (`page-main.tsx`; tokens `--container-page-narrow` 40rem, `--container-page-wide` 80rem in `main.css`). `narrow` is the default (forms, reading, single-column lists); `wide` is for galleries. Only the page-level wrapper chooses; dialogs, cards and controls keep their own `max-w-*`. Chosen so far: Calendar week, the garment page and the garment form `narrow`; Today, Outfits (the saved grid is `OUTFIT_GRID`), Ideas, Styling, the Calendar month, Insights, the Wardrobe (`#wardrobe-main`), the plan page and the plans list `wide`; the plan change page and item form `narrow`. What sits outside `<main>` but must line up (the Wardrobe's tab strip and weather line) goes in `PageColumn` of the same width. Column steps are named once in `columns.ts` (`GALLERY_GRID`, `CARD_COLUMNS`, `OUTFIT_GRID`, `PAIR_GRID`), never copied `grid-cols-*`. Not yet converted (still `max-w-lg`/`sm:max-w-lg`, which works inside the rail): the other `<main>`s, the rest of Plans' pages, trips, capsules, auth, sizes.
