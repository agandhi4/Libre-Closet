# Wardrobe plans

`src/wardrobe/plans.ts`, `src/wardrobe/shopping.ts`, `src/wardrobe/style.ts`, `src/web/plans/`, `src/web/mcp/tools/plans.ts` and `shopping.ts` (#34, slices 34a and 34b; plan section 15). What the wardrobe should be, and what the closet lacks. **The owner's own, like outfits** (owner decision on #34): no route takes `?ownerId=`, another user's plan or item is a 404, shares never reach plans or the style profile. Matrix rows in `authorization-plans.spec.ts`.

- **Tables** (`drizzle/0016_wardrobe_plans.sql`): `style_profile` (one per user: `styles` and `palette` `text[]` sets, `budget` band, notes; its week's rhythm is derived from the week template, #16, see Weekly auto-plan); `wardrobe_plan` (owner, name unique per owner in any case, notes, `active`: `wardrobe_plan_owner_id_active_unique` keeps one per owner; `drafted_by_token_id`, `0032`, #269: the personal access token whose agent drafted it, `ON DELETE SET NULL`; revoking keeps the token row, so its name stays); `plan_item` (category, optional type, `colors` and `materials` sets, warmth and formality ranges as min/max pairs, quantity, priority, budget per piece, the agent's note, `review` with `owner_note` and `changed_at`, #278 below; `plan_item_rejection`, "Not this one"'s snapshots). Every value set is a check constraint from `properties.ts`/`style.ts`, as on `garment`. **No home city of its own**: that is the weather's (`user_weather`, #14); the style page shows it read-only (`homeNameSql`, weather's, with a link to Profile › Weather, nothing when `WEATHER_ENABLED` is off) and never copies it.
- **Which garments fulfil an item is never stored.** `matchPlan` (pure, `plans.spec.ts`) derives it on every read against `inCloset` garments: same category, the item's type if named, every colour and material it names, warmth and formality inside its ranges; copies count toward the quantity (owned, partly, missing). One garment fulfils one item with all its copies; greedy and deterministic (fewest candidates first, then priority, then id; closest garment first). **`replace_soon` never fulfils** (it is the gap to refill, reason `replace-soon`); `needs_repair` does, flagged. `planGaps`/`allPlanGaps` (`gaps.ts`) read items and the closet in two statements and run it; the page and the MCP tools share them.
- **One writer each** (`queries.ts`): `createPlan` (a name the owner typed or `create_plan` passed, with items; active when the owner has none, except a draft: `PlanDraft.draftedByTokenId` stores the agent's token and never activates; `'name-taken'` for the form and the tool), `createGeneratedPlan` (a name the app makes up: a duplicate's "(copy 2)", "Like Theo’s wardrobe 2"; the first free try is chosen under the owner lock, in the insert's transaction, so two taps queue and name their copies apart instead of the loser's 500, and every try is cut to `PLAN_NAME_MAX` in its base, never its suffix, so the edit form takes it back; #123), `updatePlan`, `deletePlan`, `setActivePlan` (the old one cleared first). **Every plan and item write holds the owner lock** (`ownerTransaction`, Calendar's Owner lock; `addItems` looks the plan up under it, so an item added to a plan deleted meanwhile is a 404, not a foreign key error). **Which plan is active is decided under `lockOwner`** (`src/web/auth/queries.ts`: the owner's `user` row, `FOR NO KEY UPDATE`; the gallery's pick uses it too): locking the plans would not do, because a user's first two plans made at once (a double tap) have no plan row to lock and would both take the one-active index; `plans.spec.ts` interleaves two such transactions. `insertItems` (an entry review), `copyItems` (the duplicate), `updateItem` (whole; `'owner'` or `'agent'` decides the review move), `reviewItems` (the owner's moves), `deleteItems` (the edit form's Delete), `saveStyleProfile` (upsert). Forms read through `readPlanForm`, `readPlanItemForm`, `readStyleProfileForm` (`validation.ts`), which the MCP tools and the seed post through too.
- **The agent proposes, the owner decides.** `create_plan` (MCP, #269) drafts a plan of the agent's own, never active, so its work stays out of the plan the owner keeps; the list and the gap view say "Drafted by <token name>" (`PlanDetail.draftedBy`, a scalar subquery in `PLAN_COLUMNS`) and never the token's hash. While a draft holds proposals, Today shows a card linking to its review (`waitingDraftsSql`, #295; see Today).
- **The item review is a state machine** (#278; `src/wardrobe/plan-review.ts`, the table and its story in `docs/plans-review.md`): `proposed`, `accepted`, `revise` (the owner's "Change this", note required, a check constraint), `declined` ("Don't buy", kept so the agent never proposes it again). **Only `accepted` is matched** (`isAccepted`): gaps, the shopping list, Compare and "Bought it"'s statuses; `PlanGaps.review` holds the rest apart. `propose_plan_item` inserts `proposed`; `update_plan_item` reproposes a revise or accepted item (the note kept) and is a 409 on a declined one; the owner's form save accepts. Plan page: Accept, Change this… (its own form, `GET|POST .../change`), Don't buy (`/decline`), Reconsider (`/reconsider`), each a native post, a 409 when the item moved already; Delete stays the edit form's. A declined item takes no new candidate (`CandidateForDeclinedItem`, 409; `resolveCandidateFor` refuses it before any fetch).
- **Routes**: `GET /wardrobe/plans` (the list, active first with its tally; "start from a wardrobe"), `GET|POST /wardrobe/plans/new` / `POST /wardrobe/plans`, `POST /wardrobe/plans/from-wardrobe` (`ownerId` of a wardrobe the requester can view, `authorizeWardrobe`: the closet grouped into items by `planItemsFromWardrobe`, keyed on the colour set as `storedSet` writes it, since the check constraint allows any order and repeats; as a new plan of the requester's), `GET /wardrobe/plans/:id` (the gap view, #295/#312: Items by type (cards: photo, name, one status line, a `<dialog>` sheet each) or Outfits, `?view=`; `docs/plans-views.md`), `GET /wardrobe/plans/:id/edit`, `POST /wardrobe/plans/:id`, `DELETE /wardrobe/plans/:id` (`navigateTo` the list), `POST /wardrobe/plans/:id/activate` and `/duplicate` (the original read and copied in one owner transaction), `GET /wardrobe/plans/:id/items/new`, `POST /wardrobe/plans/:id/items`, `GET .../items/:itemId/edit`, `POST .../items/:itemId`, `POST .../items/:itemId/accept|decline|reconsider`, `GET|POST .../items/:itemId/change`, `DELETE .../items/:itemId`, `GET|POST /wardrobe/plans/:id/review` (#271, below), `GET|POST /auth/profile/style`. Forms are `PostForm`s (400 re-renders); the item form's category is a text field with the built-in and closet categories as suggestions (`categorySuggestions`, as the garment form), so a plan can ask for a custom category the closet does not hold yet (#123); the plan's ⋯ menu submits hidden forms through the `form` attribute. **The list is the Wardrobe's Plans tab** (#295; `WardrobeTabs`, its add sheet's "New plan"), left out of a shared wardrobe's tabs like Laundry, where the ⋯ menu links Plans instead; the Profile links the style profile.
- **Candidates (34b)**: a plan item's candidate products are **wishlist garments**, linked in `plan_item_candidate` (`(plan_item_id, garment_id)` primary key; a link, not a column on the garment, so shares and MANAGE grantees never read plan data). **One writer**, `changeCandidates` (`candidates.ts`): only items of the owner's plans, only wishlist garments, **at most `MAX_CANDIDATES_PER_ITEM` (5) per item** (`TooManyCandidates`, a 400, counted under `lockOwner`). Readers go through `onWishlist`, so a bought candidate's link stops mattering. `planItem` on the garment form and link import is resolved by `resolveCandidateFor` and linked in the garment's own transaction (`linkNewCandidate`). **A candidate link is not a proposal** and counts for nothing. The full rules (the cap's races, the pickers' re-renders, every entry point), in `docs/plans-candidates.md`.
- **The shopping list** (`GET /wardrobe/shopping[?plan=]`, `shopping-page.tsx`, `planShoppingList`): the active plan's missing and partly items (another plan's with `?plan=`), highest priority first, then missing before partly; each with the copies to buy, the budget per piece and its candidates as a grid of cards (#316, `CANDIDATE_GRID`: 2 across on a phone, 4 at `lg`, `PageMain wide`; photo, name, price against the budget, product link and "Bought it", no snap strip; each card's `id` (`candidateAnchor(itemId, garmentId)`, unique per item) is where Today's next-step card anchors), matching ones first, then within budget, over, unpriced, then cheapest with unpriced last (`comparePrices`: without a budget every fit is unknown, and a null that compared equal to everything put unpriced ones first); a candidate that is not the kind the item asks for says how ("Doesn't match the item: blue vs black", `targetDifferences` in words by `differencesText`). The totals (`shoppingTotals`): pieces, the budget over items that have one, the cheapest matching priced candidates, and `withoutPricedMatch`, the items left out of that sum (no candidate at all, or only unpriced or non-matching ones: "without a matching, priced candidate", `itemsWithoutPricedMatch` in `get_shopping_list`; it once said "without a candidate" of items that had one).
- **"Bought it" for a plan (34b; `purchase.ts`; the page's every case in `docs/plans-purchase.md`)**: buying is the wishlist's `buy`; matching being derived, the item becomes owned (or partly) by itself **when the garment is the kind the item asks for**, and the owner's Bought it page says when it is not (with "Change the item to match" **unticked**), offers the item's other candidates for removal and, when replacing a closet garment, archiving it. `buyCandidate` does the buy and its follow-ups in one transaction.
- **Comparing two plans** (`GET /wardrobe/plans/compare[?a=&b=]`, `compare-page.tsx`; `planComparison`, `comparePlans`): accepted items paired by kind (category, type and colour set), what B adds and drops, pairs whose quantity, priority or details changed, a count of the same, each with its status in its own plan. A defaults to the active plan, B to the next; fewer than two plans shows why.
- **Routes (34b)** (`shopping-routes.tsx`; path-id lookups in `require.ts`): the shopping list, compare, the item's candidates (`returnTo` through `safeReturnTo`), `GET|POST /wardrobe/:id/plan-items` (the owner's own wishlist item; not on the wishlist: a 302 to the garment, a 409 to the post), and `POST /wardrobe/:id/bought`'s `adjustItems`/`removeCandidates`.

- **The plan review** (`GET|POST /wardrobe/plans/:id/review`; the rule atop `review.ts`, in full in `docs/plans-review.md`): a snap strip per proposal under its role's heading (Don't buy, Change this…, Keep, the candidates), a note for the agent under each and "Not this one" with a reason on each candidate, **all in the one "Accept these" post**. `readReview` pairs notes with `shown` and reasons with `offered` by form order; a mismatch is the page as it stands, 400; Change this without a note is the page as posted, 400; a rejected pick reads as Keep. **`applyReview` is one owner transaction** deciding only `shown` items still proposed; a rejection is recorded (`plan_item_rejection`) and its product deleted from the wishlist only when every link it has is let go by this post, else unlinked from the item. Revise and declined items show apart, read-only.
- **Candidate research** (#293; `docs/plans-review.md`): the agent's `note` and `rank` on a link, written only by `changeCandidates` (`add`, `update`); ranked options lead every strip.
- **Looks** (#290-#292; `looks.ts`, `look-tile.tsx`; in full in `docs/plans-review.md`): the agent's outfits from a plan (closet garments plus its candidates); `plan_look(_slot)`; machine `look-reaction.ts`; owned/to-buy/missing derived. A strip on the review (reactions in its one post) and the plan page (`POST .../looks/:lookId/love|decline|reconsider|save`, `GET|POST .../change`). Save as outfit is `saveLookAsOutfit` through `createOutfit`, linked by `plan_look.outfit_id`.
- **Covers and Today's next step** (#302; `covers.ts`, `rankedPurchasesSql` and `nextPurchaseOf` in `candidates.ts`): each card on the list carries a photo row of up to 5 cells (looks' collages, loved first, then each item's top candidate; `planCovers`, ONE statement for every plan, beside the list's reads) and "N items · N looks · N to buy". Today's card (ranked in SQL by `rankedPurchasesSql`; `nextPurchaseOf` takes the first that `itemsToBuy` still lists, and is not called while a draft waits) names the product that completes the most loved looks of the ACTIVE plan (`completedLookCountSql`: every other slot an owned closet garment; ties: `lookCountSql`'s total, then lowest id). A cover's looks need a photo among usable pieces, judged in the statement before the per-plan limit; covers never check drafts.
- **What each page reads, and why** (#167): `docs/plans-review.md`. Every plan read of a gap view reads the whole closet (`closetPieces`); a write guarded under the owner lock reads nothing first; the duplicate copies items, rejections and candidates in one statement each.

## Gotchas

- **A plan item never names a garment, and matching must stay derived.** Which garments fulfil an item is computed on every read (`matchPlan` over `inCloset`), so a purchase, an archive or a retag moves the gap view with nothing to update. A stored link (the issue's `plan_item_garment`) would need every garment writer to keep it in step; add one only as an explicit owner's pin, never as a cache. A new reader of a plan's gaps goes through `planGaps`, and only accepted items are matched.
- **A candidate link is read only through `onWishlist`, and is never a fulfilment.** `plan_item_candidate` keeps a bought garment's link (it stops mattering; nothing deletes it on buy, so a grantee's purchase never writes the owner's plans). A new reader that joins the table without `onWishlist` would list closet garments as things to buy; one that counts links toward an item would break derived matching (the gotcha above). Writes go through `changeCandidates`, where the same-owner and wishlist-only rules live.
