# Outfit gallery

`src/wardrobe/generator.ts` (pure) and `src/web/gallery/` (#9; plan section 3, redesign section 1). The model: **the gallery chooses whole outfits** (Ideas and Saved, the Outfits page's tabs); composing row by row is Styling (#42, see Styling); **the generator is the one source of suggestions**, reached only through `ideasFor` (`ideas.ts`): the Ideas tab, `suggest_outfits`, Today (#15: today's all-day ideas, 3 a page, through `todayIdeas`) and Styling's Shuffle (#42: its locked rows as `IdeasInput.locked`, read by `styledGarmentsSql` in the same statement through `ideasColumns` and `ideasFrom`, #163); and its siblings `goesWithCloset` (#18b, see Wishlist: the whole closet with a wishlist item locked) and `browseIdea` (Styling's Shuffle over a shared wardrobe, see Styling). A pick goes where its destination says through `pickTo` (`pick.ts`, shared with Styling's Save) and a `?for=` is aimed through `aimIdeas` (`aim.ts`, shared with Shuffle). Private like outfits: the signed-in user's garments, capsules and outfits; `?ownerId=` is not read. The tabs' labels are catalog strings only (`gallery.TAB_*`): the dock and naming (#43) are still the owner's call, and Ideas lives inside the current Outfits page (`outfit-tabs.tsx`: static without a destination, so `/outfits` stays byte-stable for the service worker; a day's `?for=` travels between the tabs).

- **The generator** (`generateIdeas`, generic over the caller's garment type so ideas hand back the pool's objects; `generator.spec.ts`): templates top + bottom + footwear or one-piece + footwear (footwear only when the closet has any; each weighted by its anchor garments), a layer only when the weather asks (the option with the best score, then no layer, then the most rested). **The pool is the caller's**: `ideaPoolSql` reads `availableGarment()` (in the closet, not away, a clean copy left) and `inCapsule`; the generator never widens it, draws only layer, one-piece, top, bottom and footwear, and lets locked garments (any role, clean or not) ride along. Rotation: each role is drawn weighted by days since its last wear day (`1 + min(idle, 60) / 10`; never worn is the cap), so the least recently worn come up most. **Hard rules** (never relaxed): at most two colours beyond the neutrals (`neutralFor(role, color)`, the one place: black, white, grey, beige and brown on anything, and **blue on bottoms**, owner's rule from the #9 review: jeans and navy chinos go with anything, so a blue top or layer counts as a colour and blue trousers do not; a colour counts once however many garments carry it) and one patterned garment (anything but solid, or the colour `pattern`); no pair in `generator_avoid`; no combination equal to a saved outfit, compared on the drawn roles (a saved outfit with a belt still counts); every locked garment in every idea. **Soft rules, a score**: `assessOutfit` against the day's `weatherNeeds` (the occasion's window, the personal offset) plus one per formality step outside `OCCASION_HINTS`' range; ideas scoring 0 come first in draw order, then, once the draws run out, the near misses best first, each with its problems named (`IdeaProblem`).
- **Seeded and paged, never materialized**: the draws are `seededRandom('generator', GENERATOR_VERSION, seed)`; a page asks for `offset + limit + 1` fitting ideas and stops drawing once it has them, else spends all `MAX_DRAWS` (2000) and appends the sorted near misses. **It stops sooner only where the page cannot change** (#168). The root cause of #167's slow layer checks: the loop stopped only on `want` ideas scoring 0, so when none can (the "Goes with my closet" item and a layer of another formality, judged at the item's own formality, already miss it, and misses only add up), it drew all 2000 times for a page its first few draws had settled. It now stops once `want` ideas score the floor (`scoreFloor`: the formality misses add up garment by garment and the weather's part is never negative, so the locks' misses plus each open role's smallest is the least any idea can score; 0 when a fit is possible, the old rule); no later draw scores lower, and a tie ranks after. It also stops when the locks break a colour, pattern or clash rule (no idea: those rules only get worse as garments are added, `HardRules.compatible`) and once every distinct base has been drawn (`baseCount`). On the demo, "Goes with my closet" for a top went from about 50 to 6 ms. The gallery's own pages are unchanged in draws: a page past what fits (page 50, an evening on a casual closet) still spends 2000, since the weather part has no floor. Within a draw, a base that breaks a colour, pattern or clash rule on its own is never scored, layers are tried in preference order so the first that scores 0 and passes wins without scoring the rest (the weather's `assessOutfit` is most of a draw's cost), and rotation weights are computed once a request. `generator-output.spec.ts` pins the exact output (ideas, order, scores, `more`) of seeded closets, recorded before these changes: a speed-up that changes it is not one. The fitting list is a prefix-stable sequence, so page 1 never changes when page 3 is read, and the same (pool, seed, page) is the same page. A base is judged deterministically (its layer included), so it is one idea however often it is drawn. The day's seed (`dailySeed(today)`) opens the gallery; Shuffle is `shuffledSeed(seed)`; both are seeded too (no `Math.random` or `Date.now` anywhere in the data path).
- **Routes** (`routes.tsx`, own plugin): `GET /outfits/ideas[?for=day:D&occasion=O][&capsule=][&with=][&seed=][&page=]` (the page), `GET /outfits/ideas/more?...&page=N` (the strip's next cards and sentinel, always a fragment), `POST /outfits/ideas/pick` (native `PostForm`: `garmentId` × n plus the destination; 303 to the week for a day, else to the new outfit; with `replace` the idea takes that entry's place through `replaceEntryOutfit`, #69, and `replace` without a day is a 400), `POST /outfits/ideas/feedback` (too warm / too cold, through the weather's `nudgeTemperatureOffset`; 404 without `WEATHER_ENABLED`; 303 back to the same gallery), `POST /outfits/ideas/avoid` ("Clashes": `garmentId` × 2; htmx answers 200 empty and the card is swapped away with `hx-swap="delete"`, a plain post 303 back), `POST /outfits/ideas/allow` (the garment page's undo; 303 to the first garment). `?for=`/`?occasion=` are navigation state through `parseDestination` (none: today, all day, and a pick just saves), `?seed=`/`?page=` fall back to the day's seed and page 1 (past `MAX_IDEAS_PAGE`, 50, too); the paging surfaces (the strip, `suggest_outfits`) read through `ideasPage`, which answers `more: false` on that page, so the sentinel never asks for page 51 and restarts at 1 (#123); `?capsule=`/`?with=` name data: not an id 400, not the user's own capsule or closet garment 404. A write's `for` is data: a malformed day is a 400 (it must read back as posted, `destinationTarget`). `for=trip:ID[:day]` (#10) names the owner's trip (else a 404; a day that is not one of its days is dropped for the trip's day): its ideas use the destination's forecast and its pick is `pickForTrip`, 303 to the trip (`?picked=1`).
- **A pick is one transaction, and happens once**: `pickIdea` (`ideas.ts`, a Queryable) runs in `ownerTransaction` (the owner lock, Calendar's rule for every calendar writer), checks every garment is the owner's and in the closet (else refused whole, nothing written, the garments named by the route: `garmentsGoneError`, a 409 for an archived or wishlist one, a 404 for one not theirs; see Outfits, #219) and **keeps them locked `FOR SHARE`, in id order, until the outfit is saved** (`pickedGarments`, #122): an archive or delete waits for the pick, or the pick waits for it and leaves the garment out, so no pick saves an archived garment or a slot a delete emptied, and in the same statement looks for an outfit of the owner's with exactly these garments (`sameGarmentsOutfit` from `src/web/outfits/queries.ts`, empty slots aside; only the garments are locked). **One exists** (a double tap, a retried post, a retried `pick_outfit`): it is the answer, `alreadySaved`, planned on the destination's day through `insertEntry` (once a day, as ever), and nothing is created; a person's pick (not the planner's `plannedBy: 'auto'`) of an outfit "Plan my week" created **takes it over** (`reuseOutfit`'s `adoptPlannerOutfit`, `src/web/week-plan/adopt.ts`: its `week_plan_entry.outfit_created` rows cleared in the pick's transaction, #77), so the "Already saved" it was told stays true through Undo and the re-plan (`PickResult.adopted`, logged "taken over from the week planner"); the redirect carries `?alreadySaved=1`, which the outfit page and the week show as "Already saved" (`AlreadySavedToast`, stripped from the address). **None**: the slots top to toe (`OUTFIT_ORDER` by role), the name (`ideaName`: the garments' names, or their category, top to toe, within `OUTFIT_NAME_MAX`) and `createOutfit`, which joins the pick's owner transaction and writes the outfit (asking once more, in its insert, for one of these garments: the rule every save keeps, see Outfits), its slots and the calendar entry. `gallery.spec.ts` makes the entry's insert fail and finds no outfit or slot, picks twice in a row, and holds one pick's transaction open while a second waits on the lock (one outfit, one entry).
- **`generator_avoid`** (`drizzle/0018_generator_avoid.sql`): `(owner_id, garment_a_id, garment_b_id)` primary key, `garment_a_id < garment_b_id` by a check, both garments and the owner cascade. One writer, `avoidPair` (both garments the owner's, owned now or once, locked `FOR SHARE`; `on conflict do nothing`: 'added', 'already' or 'not-found'), and `allowPair`, its undo. The garment page lists a garment's pairs ("Never paired with", `avoided.tsx`) with "Allow again", for the owner only.
- **The page** (`ideas-page.tsx`): full-width cards (`snap-center shrink-0 w-full`) in a strip (`overflow-x-auto snap-x snap-mandatory`): swiping is the browser's scrolling, no library and no touch handlers. The last child is the sentinel (`hx-trigger="intersect once"`, `hx-swap="outerHTML"`): `revealed` watches the window's scroll and would never fire inside a horizontal scroll container. A card is the shared `OutfitCollage` (`src/web/outfits/collage.tsx`: layer and top side by side, the bottom, the shoes, accessories down the side, contained on the plinth; sizes `card` (Ideas, Today, the outfit page), `tile` (the Saved grid) and `thumb` (the garment page's "In N outfits", the calendar)), the generated name, its reasons (problems, "Fits the weather", "Not worn lately"), the pick ("Save this outfit", or "Plan for Tuesday" with a day) and "Not this" (too warm / too cold with the weather, "Not today" which only removes the card, and the clash pairs). The header: the day and occasion with a back link to the plan page, the capsule menu, "With …" for `?with=`, the weather line ("Feels 57–66 °F · take a layer"), Shuffle. An unnamed garment is its category's label wherever the page names it ("With Tops", the clash pairs), as everywhere else (`name ?? categoryLabel(category)`). The forecast is read only for days it covers (today to 15 days ahead); past it only a trip day has weather, its destination's typical day (see Trips). **Offline**: the cards the worker cached show; every write is `data-needs-network`; a `data-offline-note` says picking needs a connection.
- **Entry points**: the calendar's plan page ("Choose from ideas" with its `?for=`), a capsule's "Swipe outfits" (`?capsule=`, the owner's), the Saved tab. "Style this" (a garment, insights' unworn rows) opens Styling since #42; the gallery's `?with=` stays for its links and `suggest_outfits`.
- **What a request reads, and why** (#168; `gallery.spec.ts`, `today-home.spec.ts` and `weather.spec.ts` pin the counts). **`ideasFor` is one statement** (`selectScalars`), each part a scalar subquery owned by its module, as `gridContext` does: the pool (`ideaPoolSql`: the drawn garments with their last-worn day for rotation and the photo for the card, a JSON array read back by `readPool`), saved outfits and clashes (`generatorMemorySql`, the duplicate and clash rules), the person's weather settings with their location's cached forecast row (`weatherWithForecastSql`, weather's; only with `WEATHER_ENABLED`, a day from today on, and not when the caller read it already, Today's `ownWeather`), and, for the page, the capsule menu (`capsuleNamesSql`, capsules'; `IdeasInput.capsuleMenu`). The forecast is fetched or read again only on a miss or when a trip names another place. So the page is 2 statements (the session, the ideas) and `/more` 2 without the menu; `?capsule=` (`findCapsule`), `?with=` (`styledGarment`) and a trip (`findTrip`) each add one before it, since the route validates them first; reading them inside the statement would change `ideasFor`'s input, which Today and MCP share (Styling does: it reads its checks beside `ideasColumns` and answers with `ideasFrom`, the two halves of `ideasFor`). A pick: the owner lock's transaction and one statement (`pickedGarments`: the garments `FOR SHARE OF garment` joined to the outfit they already are), then the outfit (`createOutfit`, whose slots check their garments inside the insert) or, already saved, the planner take-over. A clash is one statement (`avoidPair`: a CTE locks both garments and inserts only when it found both).
- **Logs** (context `Web`): `Idea picked by user <id>: outfit <id> of garments <ids>, planned <day> (<occasion>)|saved`, `Garments <a> and <b> avoided|already avoided together by user <id>`, the allow and the temperature feedback; the page's generation at debug (count, page, seed, day, occasion, scope, weather, ms).

## Gotchas

- **Suggestions come from the generator, through `ideasFor`, and its randomness is seeded.** A new surface that suggests outfits (Today #15, Styling's Shuffle #42) calls `ideasFor` (or `generateIdeas` with a pool from `ideaPoolSql`; "Goes with my closet" #18b is one other pool, `closetGarmentsSql`, with its item only ever `locked`, and the week planner #16 the other, `weekPool`: dirty garments included, judged per day by `cleanCopies` with the week's own wears), never a query of its own, or the availability, colour, clash and duplicate rules fork. Nothing in its data path may use `Math.random` or the clock: a gallery page is a function of (pool as a set, seed, page), and the sentinel's page 2 must continue page 1. The pool is a query's rows, whose order Postgres never promises without ORDER BY (it follows the heap and the plan: a reseed, an update or an index choice reorders them), so `generateIdeas` orders each role by id before it draws by position; a planned week that differed after `--reset` was this (#16). A new seeded path that draws by position does the same, never trusting row order. Bump `GENERATOR_VERSION` to reshuffle every seed on purpose.
- **A sentinel inside a scroll container triggers on `intersect`, and a delete swap needs a 200.** htmx's `revealed` listens to the window's scroll, so a sentinel at the end of a horizontal strip (the gallery) never fires with it; `intersect` uses an IntersectionObserver, which sees the container's clipping. htmx swaps nothing on a 204, so a write whose answer removes its element (`hx-swap="delete"`, the gallery's "Clashes") answers 200 with an empty body.
