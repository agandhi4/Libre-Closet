# Calendar

`src/web/calendar/`. A calendar day is a plain date: `outfit_calendar.day` is a Postgres `date`, a `'YYYY-MM-DD'` string everywhere in TypeScript, and all arithmetic is on day numbers in `src/calendar-date.ts` (pure, shared by the pure layers, so it lives beside `random.ts`). No JS `Date` represents a calendar day (DST mislabels days). The one conversion from an instant is `todayIn(APP_TIMEZONE, now)`: "today" is the household's date in `APP_TIMEZONE` (IANA name, default `America/New_York`, checked at boot), never UTC or the container's zone. Weeks run Sunday to Saturday. `calendar-view.ts` builds the page model from plain dates (pure, unit-tested in New York time).

- **Routes**: `GET /calendar[?week=YYYY-MM-DD]` (missing or malformed is the current week: navigation state, never a 400; `?calMonth=` is ignored); `GET /calendar/month[?month=YYYY-MM]` (owner only; malformed is this month; network first, not a tab root); `GET /calendar/plan?for=day:D&occasion=O[&replace=E]` (missing or malformed destination is today, all day; a `replace` not the user's entry there plans one more); `POST /calendar` (`date`, `outfitId`, optional `occasion` (all day without one), `week` and `replace` (an entry id: change its outfit); 302 to the week; malformed input, an unknown occasion included, is a 400); `POST /calendar/:id/delete` (`navigateTo` the week to htmx, else 303) and `/worn` (the pill fragment to htmx, else 303), whose optional body only picks the redirect: the week, or `returnTo` through `safeReturnTo` (Today's "Wore it" and its undo come back to `/`). Entries are the signed-in user's own: 404 for no such entry and for someone else's.
- **Scheduling is idempotent**: `UNIQUE (owner_id, day, outfit_id)`, and the one writer, `insertEntry` (`src/web/calendar/queries.ts`, taking a `Queryable`), inserts with `ON CONFLICT DO UPDATE ... WHERE`: **a person's write (`planned_by` `user`, the default) that meets the week planner's `auto` entry of that outfit on that day takes it over** (`planned_by` becomes `user`, nothing else; the answer is `already-scheduled` with `adopted`, told from an insert by `xmax = 0` in `RETURNING`), and the planner's `auto` write never downgrades a person's entry. Callers: `scheduleOutfit` (POST /calendar, ownership check first), the outfit form's save transaction, the gallery's pick (and "Plan my week", `planned_by` 'auto'), the seed. The unique index leads with `(owner_id, day)`, so it also serves the week query and the owner foreign key.
- **Owner lock**: **every write to `outfit_calendar`, the week planner's tables (`week_plan`, `week_plan_entry`, `week_replan`) and Muse's needs and suggestions (`option_group`, a suggestion's columns) runs in `ownerTransaction`** (`src/web/auth/queries.ts`: a transaction (a savepoint in a caller's) whose first statement is `lockOwner`, the owner's `user` row `FOR NO KEY UPDATE` plus the lock timeout; **nested in an `ownerTransaction` of the same owner it joins it**: no savepoint, no second lock, so a nested writer's failure is its caller's). The writers take it themselves: `insertEntry`, `scheduleOutfit`, `wearOutfitOn`, `setEntryWorn`, `setEntrySelfie`, `deleteEntry`, `replaceEntryOutfit`, `createOutfit` (always), `updateOutfit`, `deleteOutfit`, `pickIdea`, `planMyWeek`, `undoWeekPlan`, the re-plan (and its claim after a failure), `decide`, `markSuggestion`, `createOptionGroup`, `buyWishlistItem`, and the repair log's `addRepair` and `deleteRepair` (`src/web/wardrobe/repairs.ts`, for the bounded waits); the helpers below them (`setEntryOutfit`, `removeAutoEntries`, `recordAutoEntry`, ...) are called only inside one. **Why a lock, not conflict-safe statements**: the re-plan, Undo and a replace read several rows, judge, then write; `ON CONFLICT` makes one statement safe but cannot keep a judgement true. **Order**: the owner lock before any row lock of the transaction (an entry, an outfit, a garment; a trip's lock is the one taken before it), because the re-plan and Undo lock outfits under it: `updateOutfit` and `deleteOutfit` take it before the outfit, `buyWishlistItem` before the garment. A new writer uses `ownerTransaction(db, ownerId, '<its name>', work)`; `test/integration/owner-lock.spec.ts` holds one writer open while the other waits. **Exempt, because they judge nothing**: `pruneReplanClaims` (nightly; no writer reads old `week_replan` rows). **Bounded waits**: `lockOwner` sets `lock_timeout` to `OWNER_LOCK_TIMEOUT_MS` (5 s, `SET LOCAL`, so nested it lasts to the caller's commit); past it the writer throws `OwnerLockTimeout`, a 503 "still saving, try again" page, logged `-> 503: ... (<writer> for owner <id> waited 5000 ms for a lock)`; the re-plan defers to the next minute instead. The pool's `statement_timeout` and `idle_in_transaction_session_timeout` (`src/db/CLAUDE.md`) end a stalled holder. A missing owner row is a 404, not an unlocked write. **A savepoint that took the lock first and rolled back releases it**: a caller that catches a nested `ownerTransaction`'s failure and carries on is unlocked from there (none does; take `lockOwner` first if one must).
- **Occasions**: `outfit_calendar.occasion` (text, default and check constraint from `src/wardrobe/occasions.ts`) is the part of the day an entry is for: `all-day`, `workout`, `work`, `daytime`, `evening`, `night-out`, in that display order. `OCCASION_HINTS` gives each a weather window (hours in `APP_TIMEZONE`, e.g. work 8 to 18) and a formality range on the garment scale (work 3 to 4, workout 1): the one source for the weather and the generator. **Several outfits a day are separate entries; the same outfit is on a day once**, whatever the occasion: planning it again for another occasion inserts nothing and keeps the first occasion (so a form re-saved at the default never moves an evening entry to all day). No "change an entry's occasion" write yet: delete and plan again. Labels: `occasionLabel` (`src/web/calendar/labels.ts`, catalog `occasion.<value>`).
- **Changing an entry's outfit**: `replaceEntryOutfit` (`replace.ts`), the one replace write, reached from POST /calendar's `replace`, the gallery's pick with `replace` and `schedule_outfit`'s `replaceEntryId`. One owner transaction: the entry (the owner's, on that day and, when given, that occasion; else 404) locked, then the outfit (`ownsOutfit`, or an idea via `pickIdea`), then `setEntryOutfit` (the entry keeps its id, day and occasion). Rules: **a worn entry is refused** (409: it records that day's wears; Change shows on unworn entries only); **its selfie is kept as a look on its day** (`detachEntrySelfie`); **the entry becomes the person's** (`planned_by` 'user'), also when the choice is the outfit it already has (an `auto` entry taken over, `adopted`, logged `... already holds outfit <id>; taken over from the week planner by user <id>`); **an outfit "Plan my week" created for it** goes once nothing holds it (`removeUnheldOutfits`, `outfitIsHeld`), only while the entry was `auto`; **the new outfit already on that day** is refused (409, naming its occasion). Idempotent: a double tap's second request waits on the lock and finds `unchanged` ("Already saved"). Logs (context `Web`): `Calendar entry <id> (<day> <occasion>) changed by user <id>: outfit <a> -> [new ]outfit <b>[, selfie <id> kept as a look][, planner's outfit <a> removed]`, `... already holds outfit <id> ...; nothing changed`, `... not changed for user <id>: <reason>`. `test/integration/replace-entry.spec.ts`.
- **The page**: a day stacks its entries in occasion order (`buildCalendarView` sorts; `findEntries` reads by day and id) through **`OccasionRow`** (`occasion-row.tsx`: label, Change (unworn only), ×, an `OutfitCollage` thumb linking to Styling, the selfie, the worn pill; `returnTo` is `dayUrl`, the week scrolled to the day), the one way the week draws an entry. The agenda (`calendar-page.tsx`): tabs, weather, "Plan my week", ‹ week › (with its year, `weekRangeLabel`), a strip of days linking to each `<section data-day>` (specs split on it: `test/integration/calendar-page.ts`): its weather chip, its rows, **open slots** (`OpenSlotRow`: the week template's occasions it has no outfit for, from today on; computed at hour 0 so `/calendar` stays byte-stable all day), its looks, then "+ Plan" (empty) or "+ Another outfit" **only on a day without open slots** (one way in per day). **The month** (`month-page.tsx`, `GET /calendar/month`): a grid, each day its first entry's collage, "+N" and a worn dot, linking to `dayUrl`; the cell's collage drops accessories and bags (`bodyOf`, beside `SIDE` in `outfits/collage.tsx`). **Its weather** is the week's mechanism, not a second one: `buildMonthView` gives the days the forecast reaches (`forecast`, today to `FORECAST_DAYS` on; null outside: nothing asked), each such cell reserves a `h-4` `WeatherCellSlot` under its date, and one hidden `WeatherMonthLoader` loads `/weather/summary?from=&to=&view=month` with `hx-swap="none"`: the same cached forecast, only the chips out of band, so nothing moves. The cell's `aria-label` hides its content, so it points `aria-describedby` at the chip. `weather.spec.ts` proves the month costs no Open-Meteo call beyond the week's.
- **The plan page** (`plan-page.tsx`): occasion chip links, "Choose from ideas" and "Style a new outfit" (same `?for=`), and the saved outfits as buttons of one native `PostForm` to POST /calendar (`data-needs-network`); an outfit already on the day is disabled, saying for which occasion (`readDayChoice`, shared with the Saved tab; `entriesOfDaySql`). **The "+ Plan" sheet** (`plan-sheet.tsx`, a `<dialog>` per day, static so `/calendar` stays byte-stable): occasion radios, then ideas / saved outfits (`/outfits?for=`) / Styling, one GET form whose buttons' `formaction` all carry `?for=day:D&occasion=O`; its openers name the radio to check in `data-plan` and share one one-line inline handler (`OPEN_PLAN_SHEET`) under the existing CSP. With `&replace=` of an unworn entry it is "Change outfit" (no chips; every choice carries `replace`); for a worn entry it plans another and says why.
- **`OutfitDestination`** (`src/web/outfits/destination.ts`, pure, unit-tested) is the one parser of `?for=day:YYYY-MM-DD&occasion=O[&replace=E]` (`parseDestination`, lenient: malformed is `none`, an unknown occasion all day, a malformed `replace` dropped) and its writer (`destinationQuery`). `replace` (a day's only) names the entry a choice replaces; the writes check it (`replaceEntryOutfit`); an outfit opened in Styling to edit refuses it (it changes in place). Trips are `for=trip:ID[:YYYY-MM-DD][&occasion=O]` (no occasion is not all day there); `destinationTarget` writes the `for` value alone for a hidden field; Styling saves for a trip through `pickForTrip`, as the gallery's pick does.
- **Worn** is `setEntryWorn` (`src/web/wears/queries.ts`): `worn_at` and the wear rows change together. Days after today have no pill and are refused. **"Wearing this"** for a whole outfit off the calendar is `wearOutfitOn` (`queries.ts`): planned and locked in one statement (`planToWear`), then `changeEntryWorn`; idempotent.
- **Round trips** (production pays ~114 ms a statement, so count them; `calendar.spec.ts`, `selfies.spec.ts`, `occasions.spec.ts` assert them): the week is 2: the session, then `weekContext` (`week-context.ts`: every read as `selectScalars` columns, `entriesSql` and siblings; `findEntries` is `entriesSql` alone), the month 2, the plan page 3. A write is the session, begin, the lock, its work, commit: delete 6 (no look-up first: the selfie's delete is owner-scoped, the entry's answers the 404), worn 6, a selfie 10 (`setEntrySelfie` is the owner transaction `setEntryWorn` joins).
- **Tabs**: `CalendarTabs` (Week, Month, Trips), static like the Outfits tabs (`/calendar` is a stale-while-revalidate tab root).
- **Selfies**: each row (`OccasionRow`) shows its entry's selfie, or up to today a way to take one (marks it worn); a day also shows looks whose outfit was deleted (`DayLooks`, `detachedLooksSql`). Deleting an entry goes through `removeEntry` (`writes.ts`), which unlinks its selfie after commit. See Outfit selfies.

## Gotchas

- **The calendar's unit specs (`src/web/calendar/*.spec.ts`) run in America/New_York through their own project**, `unit-new-york` in `vitest.config.ts` (`env: { TZ }`, `pool: 'forks'`), to prove the date logic ignores the process's zone. Node reloads the zone on Vitest's `process.env` assignment only in a child process, so the project must stay on forks. Each spec first asserts the offset. Another zoned spec gets its own project likewise (named `unit*` to stay under `npm test`).
- **`src/calendar-date.ts` keeps one `Intl.DateTimeFormat` per zone and shape** (`perZone`: `todayIn`, `hourIn`, `instantAt`'s offset). Building one is the cost (2.2% of server CPU per call); formatters are stateless. A new zone-aware helper takes a `perZone` formatter.
