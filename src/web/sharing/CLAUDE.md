# Sharing (`/wardrobe-share/*`, the access resolver)

- **One resolver:** `resolveWardrobeAccess` / `authorizeWardrobe` (`access.ts`) decide whose wardrobe a request addresses (`?ownerId=`, `''` or absent for your own) and what the caller may do there (view, manage, own). Share-aware pages and MCP tools go through it (MCP via `wardrobeFor`, `mcp/tool.ts`); never re-derive access from `sessionUserId` plus a share lookup.
- **The access check costs no round trip of its own** (#170): a request whose `?ownerId=` is a plain row id naming another user's wardrobe reads that share inside the session's statement (`shareToReadAhead` and `sharePermissionSql`, called by `findSessionAccount`; stored per request by `rememberShareReadAhead`, only for a cookie that opened a session). A route passes `request` (a `Requester`) to `authorizeWardrobe`, which uses the share read ahead when its owner id matches and otherwise reads it itself (a body's `ownerId`, `?ownerId=05`, the MCP tools, which pass a user id). Nothing is cached past the request, so a revoked share stops access on the next one. Pass `request`, not `sessionUserId(request)`: a user id still works but pays the lookup again. A repeated `?ownerId=` parses as an array: never read ahead, and a 400. **Layering**: `auth/queries.ts` imports `sharePermissionSql` from `sharing/access.ts`, and `sharing/access.ts` imports only `auth/require-session.ts` (`sessionUserId`); `access.ts` must never import `auth/queries.ts` or `auth/session.ts`, or the modules form a cycle. `sharing-statements.spec.ts` pins each grantee page's count (the grid, garment page, wishlist and Styling 3, capsules 2) and the invite and Profile counts below.
- **Statements**: accepting an invite is a read (the invite with the share its grantor already gave the user, `existing`) and one write guarded by the token (`unanswered`: an invite answered meanwhile is "not found" and nothing changes), with no transaction; folding a second invite into an existing share is one statement (the delete and the upgrade as data-modifying CTEs). Decline and remove are one guarded `delete ... returning` each (the answerer is `coalesce(grantee_id, grantor_id)`). Profile › Sharing reads its three lists in one statement and sorts them in `sharesOf`. The invite landing (`findInvite`, public) reads the permission and the inviter's first name, never an email.
- **Which surfaces are share-aware** (take `?ownerId=` and serve a grantee): the wardrobe grid and garment pages (link import included), the wishlist, capsules, Styling, wears (owner only, but resolved through it), and the MCP tools that address a wardrobe. Plans' "start from a wardrobe" reads another wardrobe through the resolver but writes the plan into the requester's own.
- **Owner-only by design** (session user only, no `?ownerId=`): saved outfits (`/outfits`: every query scoped to the signed-in user, `?ownerId=` ignored), plans, the style profile and the shopping list (requester-owned; another user's plan is a 404), the calendar (week and month), Ideas/gallery, insights and the year in review (`/wardrobe/recap`, #26: wear data never reaches a grantee, so `?ownerId=` is ignored and the menu offers it only on one's own wardrobe), trips, Today, the weekly auto-plan, selfies, sizes, and Profile. The wardrobe export (#200, `/wardrobe/export.*`) is owner-only too, but through the resolver: `?ownerId=` of a shared wardrobe is a 403 even for MANAGE, since it hands over the whole wardrobe with the owner's own records. They are one person's planning and history, and a grantee must never see them.
- **A new feature decides which list it joins, and says so here.** Don't copy a sibling's route shape without checking: a share-aware sibling routes through the resolver, and an owner-only one reads `sessionUserId` alone.
- Sharing's own pages live in Profile › Sharing (`/auth/profile#sharing`); `GET /wardrobe-share/manage` 301s there (R2 #82). The public share-link page is `share/`, not this directory.
