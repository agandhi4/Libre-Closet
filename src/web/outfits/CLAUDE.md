# Outfits

`src/web/outfits/` (ported to plain Fastify and Drizzle 2026-09-26). Outfits are private: every query is scoped to the signed-in owner, shares never reach them, `?ownerId=` is ignored, and another user's outfit id is a 404.

- **Composition is `outfit_slot`** and nothing else: `(outfit_id, position)` primary key, `category` text, `garment_id` nullable (`ON DELETE SET NULL`: deleting a garment empties its slot). Styling saves them top to toe (the rows' order); the outfit form old cached pages post keeps the order posted, and an empty slot is a row kept without a garment. `drizzle/0002_outfit_slot.sql` built it from the old `outfit.slots` JSON and `outfit_garments` pivot and aborts the boot if the two disagree for any outfit (compared as garment sets, owner-checked). A slot only ever names a garment of the outfit's owner, owned (closet or archived; see "A save never drops a garment"). Archived garments stay in outfits.
- **One outfit per garment set, at save time** (#219): `createOutfit` is the one writer of new outfits (every pick through `pickIdea`: the gallery, Styling's Save, Today, trips, a replace, `pick_outfit`, the week planner; the outfit form's POST /outfits, `create_outfit`, the seed) and always runs in `ownerTransaction`. Its outfit insert is one statement (`insertOutfitOnce`, a CTE over `sameGarmentsOutfit`: the owner's outfit whose non-empty slots are exactly these garments, the oldest) that inserts only when there is none, else answers that one: `alreadySaved`, nothing created, its own name and notes kept, planned on the save's day when asked (`insertEntry`, once a day), and a person's save (not `plannedBy: 'auto'`) of a planner-made outfit takes it over (`reuseOutfit`: `adoptPlannerOutfit`, `src/web/week-plan/adopt.ts`, #77). A pick asks first, in its garments' locked read (`pickedGarments` joins `sameGarmentsOutfit`, #168), and goes straight to `reuseOutfit` when it finds one, so a repeated pick costs no insert. Under the lock two saves of the same garments take turns, so a concurrent Save and pick make one outfit. **Why not a unique key on the set**: the set is not stable data. A garment delete empties its slots (`ON DELETE SET NULL`) and can leave two outfits alike; an edit (`updateOutfit`) may make one match another (allowed: the rule is about what a save creates). A key would have to refuse the delete or merge outfits that carry entries, wears, selfies and trips. Occasions live on calendar entries, so one outfit serves every occasion; the one thing lost is the same garments twice on one day (an outfit is on a day once), which the pick already refused. An outfit with no garments (the form's empty outfit) is never "the same". The seed throws if a bible repeats an outfit's garments. The outfit form redirects with `?alreadySaved=1` on a reuse; `create_outfit` answers `alreadySaved`. `outfit-saves.spec.ts` interleaves each save with a pick (held transaction, `test/integration/interleave.ts`).
- **A save never drops a garment** (#219): a garment it cannot hold refuses the whole save, nothing written, the answer naming it (`OutfitGarmentsGone`, `gone-garments.ts`): "Not saved: Linen shirt is archived." A 409 when every gone garment is the owner's (archived for a pick, on the wishlist: named), a 404 when any is not a garment of theirs (deleted, another's, unknown: those are indistinguishable, counted, never named, as Request security wants). What a save may hold is the writer's (`Holdable`): a pick takes closet garments (`pickedGarments`), a slot write owned ones (`insertSlots`, which locks them `FOR SHARE` in id order in its insert, so a delete either waits for the save or makes it refuse; never a slot emptied behind the save's back, never a foreign-key 500). Before #219 `insertSlots` stored such a slot empty and logged it. Where a pick answers `'not-found'` (it locked and judged), the route names the garments afterwards with `garmentsGoneError` (pickTo, Wear this, `pick_outfit`). **Styling answers it with its page** (see Styling), the rows and sheet as posted and the gone rows back to None; the outfit form and the MCP tools answer the error page and the tool error with the same words. The week planner's own pick of a garment gone meanwhile skips that slot (it saves nothing partial either).
- **Pages read slots by position**: the list (newest outfit first), the outfit page and the calendar chips go through `db.query` with `slots` ordered by `position`, one statement for all outfits with their garments and thumbs.
- **Composing is Styling** (#42, see Styling). The builder's pages are redirects: `GET /outfits/new` to `/styling` (carrying `?for=`, a pre-#13 `?scheduleDate=` as all day, `?capsule=`, `?returnTo=`) and `GET /outfits/:id/edit` to `/styling?outfit=ID` (its `returnTo=/calendar&returnToWeek=W` as `returnTo=/calendar?week=W`), so cached links and the manifest's old shortcut still land. `/outfits/row-fragment` is gone (htmx-only, nothing links it).
- **The outfit form's writes** (POST /outfits, POST /outfits/:id; kept for pages the installed app cached before Styling, and the specs' fixtures, test/support/e2e-data.ts): `category` and `garmentId` arrive one pair per row, in document order (a single row as scalars, which ajv's `coerceTypes: 'array'` turns into arrays); unequal counts are a 400. `scheduleDate` and `returnToWeek` are `''` or a real date (else 400). The outfit, its slots (replaced whole) and the calendar entry commit in one owner transaction (a create reuses an outfit of the same garments, above); an update locks the outfit row (`FOR UPDATE`) so two saves cannot collide on the slot key. An update without `name`/`notes` leaves them; blank ones are stored as null ("Untitled Outfit"). Both are `text` columns since `0005`; the caps are the form's (`OUTFIT_NAME_MAX` 255, `OUTFIT_NOTES_MAX` 4000 in `form-page.tsx`, shared by the inputs' `maxlength` and the route schema, a longer post is a 400). The redirect goes back to `/calendar?week=` when `returnTo` is `/calendar`, else to the outfit. "Add to calendar" is the date plus an occasion select (`scheduleOccasion`, all day when absent: forms cached before #13).
- **The Saved tab** (R5, `list-page.tsx`; plan "Outfits"): a two-column grid of `OutfitCollage` `tile`s (a 4:5 frame so rows line up), each with its name and `outfitActivity`'s line ("Planned Oct 3 · Worn 4×": one grouped statement over the owner's entries; worn is `entryWorn`, marked worn or with a selfie, the outfit page's Worn strip's own predicate, so the two agree; it depends on the day, never the hour, so bare `/outfits` stays a byte-stable tab root). No per-card calendar dropdown: planning is the outfit page's. **With `?for=day:D&occasion=O[&replace=E]`** (navigation state through `parseDestination`; a trip or anything malformed is the plain grid) it picks for that day, the calendar's "Pick a saved outfit": one native `PostForm` to `POST /calendar` (date, occasion, week, and `replace` only while that entry can still change, `pickDestination`), each tile a submit button stretched over it; an outfit already on the day is disabled, saying for which occasion. The plan page and it read the day through one `dayChoice` (`src/web/calendar/day-choice.ts`: what is on the day, the entry `replace` names, `plannedNote`), so they never disagree. `DayDestinationLine` (`day-destination.tsx`, "For Tuesday, Sep 29 · Evening" with the way back to the plan page) heads both tabs; `OutfitTabs` carries a day destination between Saved and Ideas (`savedUrl`, `ideasUrl`) and is static without one.
- **The outfit page** (R5, `show-page.tsx`): the collage (`card`), **Plan** (a `modal-bottom` sheet: a date from today and the occasions as chip radios, a `PostForm` to `POST /calendar`, 302 to that week) and **Edit in Styling** (`stylingUrl({ outfitId, returnTo })`), then its entries read by `outfitEntries` (one statement: `planned`, the unworn ones from today on, soonest first, each linking its week; `worn`, the Worn strip), then its garments in saved order, each opening its page. Share and Delete are in the app bar's ⋯ menu (`#outfit-menu`). The name and notes caps (`OUTFIT_NAME_MAX`, `OUTFIT_NOTES_MAX`) live in `queries.ts`.

## Gotchas

- **Never delete an outfit with a plain `DELETE`.** `outfit_calendar.outfit_id` and `garment_wear.outfit_calendar_id` both cascade, so it erases every wear of the days the outfit was worn. Go through `deleteOutfit`, which detaches them first (`detachOutfitWears`; Wears and washes). Deleting one calendar entry does cascade its wears, deliberately; account deletion takes everything. A new path that deletes outfits or calendar entries in bulk must choose between the two on purpose; `wears.spec.ts` covers both.
- **"Delete the outfit once nothing holds it" asks one predicate, `outfitIsHeld`** (`src/web/outfits/references.ts`: a calendar entry on any day, worn or not, and a trip's `trip_outfit`), like `photoIsReferenced` for photos. `deleteOutfit` cascades every holder, so a holder missing from the list is a row silently deleted with the outfit: until #69's review, `removeUnheldOutfits` (Undo, the daily re-plan's swap, Change) asked only `outfit_calendar` and took planner-made outfits off the trips that held them, packing lists included. A new table with an `outfit_id` joins the predicate in the same change. `removeUnheldOutfits` locks the outfits (`FOR UPDATE`) before asking, so a holder being inserted meanwhile either committed first and is seen, or waits and fails on the deleted outfit's foreign key; never a silent cascade. `replace-entry.spec.ts` and `week-plan.spec.ts` hold a planner-made outfit on a trip through each of the three paths.
