- **The form is validated in two layers** (`garment-input.ts`): TypeBox caps shape and length (a 400 error page; the inputs carry the same `maxlength`), then `readGarmentForm` re-renders the form with a 400 and messages for a blank category, a colour outside `GARMENT_COLORS` or a date that is not one. Categories are stored trimmed and lower case (the filter value and the builder's key), one-line fields trimmed, blank fields NULL, sizes normalized (`XL` is `X-Large`). The date field keeps its historical name `dateAquired` (cached pages post it); the column is `acquired_on date`.
- **Colours are a fixed set** (`GARMENT_COLORS`, `src/wardrobe/properties.ts` since #34, so the schema's style checks can list them; each has a `.ms-swatch--<name>` class). **`garment.colors` is a `text[]` set** (#28), one model with `materials` and `style_profile.palette`: in `GARMENT_COLORS` order, each once, null for none (never an empty array), checked by `garment_colors_check`; every writer of a set column normalises through `storedSet` (`properties.ts`: the list's order, each once, null for none; `readColors` and `readProperties` for the garment form, bulk edit's material, the plan and style forms, "Bought it"'s fitted item), and readers take `colors ?? []`, never a string to split. `drizzle/0023_garment_colors.sql` converted the comma-joined `color` column (trimmed, lower case, blanks dropped, reordered, duplicates dropped) after aborting the boot, naming the rows, on any item outside the set. The form's field is still `color` (one per checked box), so forms the installed app cached post what they always did and need no marker; the MCP tools' output was already `colors: string[]`. `public/js/color-multiselect.js` only mirrors the server-rendered checkboxes as pills, built with `createElement`/`textContent`: a stored colour rendered through `innerHTML` was a stored XSS (audit2-correctness H5), and free-text colours are gone with it.
- **Properties** (#12; plan section 6): `type`, `warmth` (1-5), `formality` (1-4), `materials` (`text[]`, a set, null for none), `pattern`, `fit`, `sleeve`, `length`, `fabric_weight` (gsm, entered in oz or gsm; 6 oz is 203) and `water_resistant`, all optional, each with a check constraint listing `src/wardrobe/properties.ts`'s values. The form renders only what the category's role has (`propertyApplies`: no sleeve on shoes; a custom category gets the general ones and no type) and a save stores null for the rest, so recategorising drops what no longer applies. Type, warmth and weight sit beside the category; the rest in the collapsed "More details". Changing the category or anything in either block posts the form to `POST /wardrobe/properties-fragment` (reads and writes nothing; the triggers are `autosaveAttributes`, see Gotchas), which answers both blocks' contents (`#garment-props-main`'s in place, `#garment-props-more`'s out of band; never the blocks, which carry the triggers) with **presets filled only where the user has not chosen**: the form carries hidden `presetCategory`/`presetType`/`presetWeight` (where the shown presets came from), and `applyPresets` moves a value to the new preset only when it is unset or still equals the old one. A heavier fabric of the same type is warmer (`weightSteps`: a 6 oz tee is warmth 3). Labels are the catalog's `property.<name>.<value>` strings through `tKey` (`labels.ts`; `labels.spec.ts` proves every value has one).
- **Product link and price** (`source_url` text, `price` numeric(10,2); added for the seed and link import #6): optional fields in "More details", read by `readSourceUrl` (an absolute http(s) URL, stored as the parser writes it; anything else is a message, so a `javascript:` link never reaches the page) and `readPrice` (`$1,299` and `49.9` read as `1299.00` and `49.90`; never negative), both backed by check constraints. The garment page shows the price (`priceLabel`: US dollars, the household's one currency) and a "View product" link with `target="_blank" rel="noopener noreferrer"`. A clone keeps both.
- **Link import**: `link-import/CLAUDE.md`.
- **Photo writes** (`writes.ts`): the garment is looked up before a multipart body is read, so a refused upload stores nothing; `Photos.storeUploadParts` writes the bytes; `commitWithPhoto` inserts the `file` row with the garment write in one transaction and deletes the new bytes if it fails; replaced or deleted photos are unlinked after commit. An upload and a rotate replace the photo through one path, `swapPhoto` (a rotate adds a check under the garment lock that the photo it turned is still the garment's, at the version it read: a status check let a second mask saved meanwhile be deleted).

## Gotchas

- **A garment form without properties must not clear them.** An edit writes every field, and a form the installed app cached before properties existed posts none. Every form that renders them posts `props=1` (a hidden field in `PropertiesMain`); `readGarmentForm` reads and writes properties only with it (`garment-properties.spec.ts` saves an old-shaped form over a tagged garment). The product link and price have their own marker, `product=1` (a hidden field beside them in "More details"), because forms cached between the two post `props=1` without them (`garment-product.spec.ts`). The care fields (quantity, wash after, condition, #7) have `care=1`, the care label (#23) `careLabel=1`. A new garment field that old cached forms lack needs the same care: a marker of its own, posted beside the fields it guards.
- **A garment's status changes only through `setGarmentStatus`, and closet reads only through `inCloset`.** A new query that lists "the wardrobe" without the predicate shows wishlist items (things not owned) in the closet, the builder or laundry; one that writes `garment.status` directly skips the machine's refusals. `insertGarment` takes an entry status (closet or wishlist, never archived). The grid's `?archived=true` is the URL contract kept from before the status; internally it is `scope: 'owned'`.
