# The care label and the repair log

Part of the Wardrobe (`CLAUDE.md` in this directory); #23, plan section 17.

- **The care label** is five garment properties (`care_wash`, `care_bleach`, `care_dry`, `care_iron`, `care_dry_clean`; value sets in `src/wardrobe/care.ts`, each with its check constraint). `propertyApplies('careWash', category)` is the one role rule for all five (not shoes or bags). The form renders them in "More details" under the other properties (`CareLabelFields`, `property-fields.tsx`), inside `#garment-props-more`, so the properties fragment redraws them. **Their own marker, `careLabel=1`**, posted for every role (shoes included, so recategorising clears the label): `readGarmentForm` reads them through `readCareLabel` only beside it, because forms cached before #23 post `props=1` without them. Labels are the catalog's `property.care<Name>.<value>` strings through `valueLabel`.
- **Presets come from the materials** (`carePresetsFor`: per instruction the most careful material's; never dry cleaning). `withPresets` ends in `withCarePresets`, which fills what is unset or still at the previous materials' presets (`applyCarePresets`, properties.ts' `followPreset` rule) and moves the hidden `presetMaterials` (comma-joined, rendered with the chips it describes: the `presetType` lag argument holds). `storedPropertyValues` sets it to the stored materials. `update_garment` calls `withCarePresets` when it changes the materials. A wishlist form's "Find a replacement" starts without the old garment's label (`withoutCareLabel`, `destination.ts`); a clone keeps it.
- **The garment page** shows it as `#garment-care` (the chips, then the free-text care notes, still `washing_details` / `name="washingDetails"`), for anyone who sees the garment.
- **The wash filter** (`?wash=`, `GridFilters.wash`, `search_garments`' `wash`): a stored value, 400 outside the set; the modal offers only washes held (`filterOptions.washes`). No bulk edit or tagging mode for the label.
- **The repair log** (`garment_repair`; `repairs.ts`: `RepairBody`, `readRepairForm`, `repairLog` (`repairLogSql`), `addRepair`, `deleteRepair`, `repairPanel`; views in `repair-log.tsx`): the owner's own record, like wears. The garment page reads it only through `garmentContext`'s owner records (`#garment-repairs`: newest first, "Spent on it", the same `repairCostSql` sum as the wear line (`RepairLog.total`, from `wearSummarySql`), "Log a repair" to the editor); the edit page gets the editor (`RepairEditor`, `#garment-repairs`, below and outside the garment form) from `repairPanel`, the one rule (the owner, an owned garment) for the edit page, its refused save and a refused entry. Routes (`repair-routes.tsx`, its own plugin): `POST /wardrobe/:id/repairs` (303 to the garment page `?repairSaved=1#garment-repairs`; a refusal re-renders the edit page 400) and `POST /wardrobe/:id/repairs/:repairId/delete` (303 to the editor). A grantee is refused as for wears (403 with `?ownerId=`, 404 without), a wishlist item 409. **Both writes run in `ownerTransaction`**; the day is never after `APP_TIMEZONE`'s today and a cost reads as a price (`readPrice`).
- **Cost per wear includes the repairs** (#151): what a garment cost is `totalCost` (`src/wardrobe/insights.ts`: price × copies plus the repairs' costs, once; null without a price, repaired or not), and `perWearCost` divides it, on every surface (the wear line, insights, the recap, `wardrobe_stats`, `get_garment`). The sum is `repairCostSql(garment.id, through)` (`repairs.ts`), a scalar subquery in the statement that already reads the wears (`insightGarments`, `wearSummarySql`), never a query of its own; repairs dated after `through` (a past year's December 31) do not count, as wears do not. **Only an owner-only read may select it**: `wearSummarySql` is read only by `garmentContext`'s owner records, the wear routes' `wearStatusOf` and `get_garment`'s own-wardrobe branch, and insights and the recap are one's own; a grantee sees the price (`GarmentDetails`) and no cost per wear (`repair-cost.spec.ts`). **One sum, one source**: "Spent on it" is `wearSummarySql`'s `repairCost` (`garmentContext` builds `RepairLog`), never a sum of the loaded entries, so it and the wear line cannot drift; the edit page's editor lists entries and shows no total.
