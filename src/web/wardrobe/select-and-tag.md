# Select mode, bulk edit and tagging mode

Part of the Wardrobe (`CLAUDE.md` in this directory).

- **Select mode and bulk edit** (`?select=1`, owner and MANAGE only): tiles become checkboxes (`SelectTile`, `name="ids"`) inside one native-post `#bulk-form`; the sentinel asks `/wardrobe/tiles?select=1`, so later pages arrive as checkboxes inside the same form. The bar's "N selected" is rendered for the first page and recounted by `public/js/select-count.js` on every toggle and every swap that settles into the form (the picker's members on an appended page arrive checked, with no change event). "Set…" opens `#bulk-dialog`, which sits outside the form (forms cannot nest; the backdrop is a dialog form) and joins it through `form="bulk-form"`: daisyUI radio tabs whose radio is the posted `property`, each tab's chips that property's field. `POST /wardrobe/bulk` (`bulkSetProperty`, one transaction, rows locked) sets it on the selected garments of the addressed wardrobe whose role has it, ignores other ids, adds a material rather than replacing the set, stored through `storedSet` in `MATERIALS` order like the form's (type and weight are per garment, not bulk), and answers 303 to the same filters with `bulkUpdated`/`bulkSkipped` for the toast (`SavedToast` + `StripFlags`, `src/web/layout/parts.tsx`, which the garment page's saved toasts use too). **The capsule picker** is the same select mode (`?pick=<capsuleId>`, owner and MANAGE; a viewer gets the plain grid): `SelectForm` with the capsule's members pre-checked and a hidden `shown` per tile, posting to `POST /capsules/:id/garments` (see Capsules); no bulk dialog, no scope row, Cancel back to the capsule.
- **Tagging mode** (`/wardrobe/tag`, owner and MANAGE; `tag-page.tsx`): one card at a time for garments that still need their type (where the category has types), warmth (where the role has one) or formality (`needsTags` in `queries.ts`, archived left out), newest first; the wardrobe shows a "N garments need details" prompt while any do. The card's chips are one `AutosaveForm` posted on every change to `POST /wardrobe/:id/tag`, which saves at once and answers the chips as saved (`#tag-fields`, never the form) and the count left out of band: the tapped values replace the stored ones, and a new type (not the stored one posted again) brings its presets into properties still unset or still at the **stored** type's presets (`readTags`: `applyPresets` from the stored type, as the form uses its hidden `presetType`). The first tag has no source, so it only fills what is unset and never overwrites what the garment form set; a second type tap moves what the first type filled (the card saves every tap, so without the stored type as the source the first type's presets would stick). Next is the form's submit button (`next=1`): it saves what the card holds (a tap still waiting in the form's queue rides along); like every tap it writes only the fields that differ from the stored garment (`readTags`), so Next on a card left alone writes nothing; and answers the card after this garment (`HX-Retarget: #tag-card`), so a garment left alone waits for the next pass. Past the oldest one the card is "all done" only when nothing is left (`left` 0); a pass that skipped garments ends on `PassDone` instead: how many still need details, and Start over (the newest again). `GET /wardrobe/tag?before=<id>` still answers the card to pages cached with the old Next link.
