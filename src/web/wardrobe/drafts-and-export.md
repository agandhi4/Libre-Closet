# Several photos at once, and the export

Part of the Wardrobe (`CLAUDE.md` in this directory); #200, decisions in `docs/plans/2026-09-28-multi-add-and-export.md`.

## The draft queue

- **A library pick of two or more photos is a batch of drafts.** The add sheet's library input is `multiple`; `photo-input.js`'s `preparePhoto` prepares every file and still returns the first (cached pages call it by that name). `POST /wardrobe/new/photo` goes through `stagePhotoUploads` (`writes.ts`): each `photo` part stored in turn through `storeUpload`, then one photo kept as today's pending photo (`keepPendingPhoto`, its refusal the request's), or several as a batch (`recordDraftBatch`, `src/web/files/pending-photos.ts`: `batch_id`, `batch_position`, `batch_owner_id` on `pending_photo`). A photo that cannot be read (a 4xx from `storeUpload`) is left out and named on the first draft (`?leftOut=`); none readable is a 400. The 303 opens the first draft.
- **Drafts are never evicted.** `MAX_PENDING_PER_USER` (10) and its eviction apply to unbatched pending photos only; drafts count against `MAX_DRAFTS_PER_USER` (30), and an upload that would pass it is refused whole (409, nothing kept). The route sets the parser's `files` limit to the room left (at least 1: a single photo is no draft), so the parser stops at the first photo past it; `recordDraftBatch` checks again under the user's advisory lock.
- **A draft is the new garment form** (`GET /wardrobe/new?photo=`), so the duplicate check, the presets and the owner-only fields apply unchanged. `pendingPhotoSql` (read in the form's one statement, `form.md`; `pendingPhotoOf` alone where a take found nothing) says whether the photo is still the requester's and, for a draft, its batch and the drafts waiting; **a draft belongs to its batch's wardrobe**: the lookup, the claim (`takePendingPhoto`) and the discard all take a `PendingScope` (the user and the addressed `access.ownerId`), so a grantee with MANAGE on two wardrobes can neither save one's draft into the other nor discard it there; the form, the save and Discard answer such a draft 404 (`draftNotFound`, `render-form.tsx`), and nothing is written; `renderGarmentForm` (given `pendingPhoto`) then shows the queue (`DraftQueue`, `draft-queue.tsx`) above the form (`#draft-queue`: how many wait, their thumbs, Skip `[data-draft-skip]`, Discard), the category asked before the name (`NameAndCategory`, `garment-form.tsx`), and a hidden `draftsSaved`.
- **The queue moves on through the server.** `POST /wardrobe`'s claim answers what it took (`takePendingPhoto`: the draft's batch and place, and the drafts still waiting, read in the take's own statement, #161) and the route answers 303 to the next draft after it in picked order (`afterDraft`, `nextDraft`, wrapping round), so one skipped earlier comes back once the rest are done; after the last, to select mode with the batch checked (`batchDoneUrl`: `/wardrobe?select=1&checked=<ids>`, the first page's tiles pre-checked, the count and a status line; `StripFlags` drops `checked`). Skip is a link to the same `nextDraft`; `POST /wardrobe/new/drafts/discard` (owner or MANAGE) discards through `discardPendingPhoto` with `draftsOnly` (a single pending photo is never this button's) and goes to the next after it (nothing left to discard ends the queue). Only when nothing was taken does either read the photo again (`pendingPhotoOf`), to answer a draft of another wardrobe 404. The saved garments' ids are navigation state (`saved=` on links, `draftsSaved` in the form; `readIdList`/`idListValue` in `validation.ts`), never stored: resuming from the grid starts the list again.
- **Resuming**: the closet grid's prompt "N photos waiting to be added · Continue" (`draftsWaitingSql`, read with the grid's context, `grid.md`) shows the requester's own drafts whose `batch_owner_id` is the wardrobe on screen, so a grantee's drafts for a shared wardrobe resume there. Drafts are pending photos with a longer life: reconciliation removes a draft after a week (`DRAFT_LIFETIME_MS`, `pendingCutoffs`), a single pending photo after a day, and the queue says photos wait a week.

## The export

- **`GET /wardrobe/export.csv` and `/wardrobe/export.json`** (`export-routes.ts`, its own plugin; `wardrobeExportPath` in `src/web/page-cache.ts`), linked from Profile › Export. **Owner only**: `authorizeWardrobe(..., 'own')`, so `?ownerId=` of a shared wardrobe is a 403 for MANAGE and VIEW alike and a stranger's a 404. The export carries the owner's own records (away, last washed, wash limit) that a share never shows. Repair costs are not garment fields and are not exported.
- **The columns are the schema's** (`EXPORT_COLUMNS`, `export.ts`: `getTableColumns(garment)` minus `owner_id`, `photo_id` and a suggestion's token id, under their database names), then (CSV) `option_group`, a suggestion's need by name (#333), then the photo as absolute URLs on the request's origin (`cutout` only when shown). The JSON bundle ends with `optionGroups`, the owner's Muse needs (`EXPORT_GROUP_COLUMNS`: not the owner, token or plan item). `test/integration/wardrobe-export.spec.ts` fills every column and compares both formats with the rows, so a new garment column is exported, or the spec says why not (add it to `OMITTED`, with the reason).
- **Streamed**: keyset pages of `EXPORT_PAGE_SIZE` (200) by id through a `Readable`; every status, oldest first. The browser never caches it (`no-store`) and neither does the service worker (`bypassesWorker`): as a page it would sit in the page cache and be served stale offline.
- **CSV**: stored values (not labels), sets joined by `, `, null as empty, UTF-8 BOM, CRLF. `csvCell` prefixes `'` to a cell starting with `=`, `+`, `-`, `@`, tab or CR before RFC 4180 quoting. The JSON keeps the columns' types (`price` a decimal string) and is not escaped that way.
