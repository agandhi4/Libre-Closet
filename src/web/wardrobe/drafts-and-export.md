# Several photos at once, and the export

Part of the Wardrobe (`CLAUDE.md` in this directory); #200, decisions in `docs/plans/2026-09-28-multi-add-and-export.md`.

## The draft queue

- **A library pick of two or more photos is a batch of drafts.** The add sheet's library input is `multiple`; `photo-input.js`'s `preparePhoto` prepares every file and still returns the first (cached pages call it by that name). `POST /wardrobe/new/photo` goes through `stagePhotoUploads` (`writes.ts`): each `photo` part stored in turn through `storeUpload`, then one photo kept as today's pending photo (`keepPendingPhoto`, its refusal the request's), or several as a batch (`recordDraftBatch`, `src/web/files/pending-photos.ts`: `batch_id`, `batch_position`, `batch_owner_id` on `pending_photo`). A photo that cannot be read (a 4xx from `storeUpload`) is left out and named on the first draft (`?leftOut=`); none readable is a 400. The 303 opens the first draft.
- **Drafts are never evicted.** `MAX_PENDING_PER_USER` (10) and its eviction apply to unbatched pending photos only; drafts count against `MAX_DRAFTS_PER_USER` (30), and an upload that would pass it is refused whole (409, nothing kept). The route sets the parser's `files` limit to the room left (at least 1: a single photo is no draft), so the parser stops at the first photo past it; `recordDraftBatch` checks again under the user's advisory lock.
- **A draft is the new garment form** (`GET /wardrobe/new?photo=`), so the duplicate check, the presets and the owner-only fields apply unchanged. `pendingPhotoOf` says whether the photo is still the requester's and, for a draft, its batch; `renderGarmentForm` then gets `draft` (`DraftQueue`, `draft-queue.tsx`): the queue above the form (`#draft-queue`: how many wait, their thumbs, Skip `[data-draft-skip]`, Discard), the category asked before the name (`NameAndCategory`, `garment-form.tsx`), and a hidden `draftsSaved`.
- **The queue moves on through the server.** `POST /wardrobe` reads the draft before its claim (`postedDraft`, `routes.tsx`) and answers 303 to the next draft after it in picked order (`nextDraft`, wrapping round), so one skipped earlier comes back once the rest are done; after the last, to select mode with the batch checked (`batchDoneUrl`: `/wardrobe?select=1&checked=<ids>`, the first page's tiles pre-checked, the count and a status line; `StripFlags` drops `checked`). Skip is a link to the same `nextDraft`; `POST /wardrobe/new/drafts/discard` (owner or MANAGE) discards through `discardPendingPhoto` and goes to the next after it. The saved garments' ids are navigation state (`saved=` on links, `draftsSaved` in the form; `readIdList`/`idListValue` in `validation.ts`), never stored: resuming from the grid starts the list again.
- **Resuming**: the closet grid's prompt "N photos waiting to be added · Continue" (`draftsWaiting`) shows the requester's own drafts whose `batch_owner_id` is the wardrobe on screen, so a grantee's drafts for a shared wardrobe resume there. Drafts are pending photos: reconciliation removes day-old ones, and the queue says photos wait a day.

## The export

- **`GET /wardrobe/export.csv` and `/wardrobe/export.json`** (`export-routes.ts`, its own plugin; `wardrobeExportPath` in `src/web/page-cache.ts`), linked from Profile › Export. **Owner only**: `authorizeWardrobe(..., 'own')`, so `?ownerId=` of a shared wardrobe is a 403 for MANAGE and VIEW alike and a stranger's a 404. The export carries the owner's own records (away, last washed, wash limit) that a share never shows. Repair costs are not garment fields and are not exported.
- **The columns are the schema's** (`EXPORT_COLUMNS`, `export.ts`: `getTableColumns(garment)` minus `owner_id` and `photo_id`, under their database names), then the photo as absolute URLs on the request's origin (`cutout` only when shown). `test/integration/wardrobe-export.spec.ts` fills every column and compares both formats with the rows, so a new garment column is exported, or the spec says why not (add it to `OMITTED`, with the reason).
- **Streamed**: keyset pages of `EXPORT_PAGE_SIZE` (200) by id through a `Readable`; every status, oldest first. The browser never caches it (`no-store`) and neither does the service worker (`bypassesWorker`): as a page it would sit in the page cache and be served stale offline.
- **CSV**: stored values (not labels), sets joined by `, `, null as empty, UTF-8 BOM, CRLF. `csvCell` prefixes `'` to a cell starting with `=`, `+`, `-`, `@`, tab or CR before RFC 4180 quoting. The JSON keeps the columns' types (`price` a decimal string) and is not escaped that way.
