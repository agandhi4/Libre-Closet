# Images

Every photo is a set of WebP files sharing one base name: `<uuid>.webp` (original, 1080px, q90), `<uuid>-nobg.webp` (the cutout, made by the server, padded to a transparent square; photos stored before 2026-09-26 keep the one the browser made), `<uuid>-thumb.webp` (400px, q80, derived from the cutout when present). Only the original has a `File` row, which also carries the cutout's state (see Background removal). **A cutout written onto an existing row** (a mask edit, a server job) is a new nobg and thumb under a **variant key**, `<uuid>-nobg-<key>.webp` and `-thumb-<key>.webp` (`image-variant.ts`), and `file.variant_key` says which set is the photo's (null: the unkeyed ones stored with it); the original never changes. A `StoredPhoto` (`{ fileName, variantKey }`, selected with `STORED_PHOTO_COLUMNS`) is what serving and deleting need; `unkeyedPhoto(name)` only for bytes without a row yet and selfies (never keyed: `file_variant_key_check`). `File.version` is bumped with every new key. A variant URL names its exact files, `?v=<version>&k=<key>&s=<signature>` (`k` absent while unkeyed), so the `/file` routes (`src/web/files/routes.ts`) serve all three `private, immutable` for a year and, when the signature holds, straight from storage without a statement (see Gotchas, Signed URLs). Views never build `/file/...` by hand: `imageUrl(photo, 'thumb')` (an `ImageRef`: select `PHOTO_REF_COLUMNS`, `PHOTO_REF_RELATION` or `photoRefJson`, `queries.ts`) (`src/web/files/image-url.ts`; grids and strips, with `loading="lazy"` and dimensions) or `'nobg'` (detail, share, Open Graph). Thumbs missing in storage are generated on first request, single-flighted, which backfills old photos. Deletion always goes through `deleteVariants`. An outfit selfie (#19) is the same set without the cutout (`unwanted`: original and thumb only), served under `/selfies/` by `selfieUrl`, never under `/file/` (Outfit selfies).

All of it is `Photos` (`src/web/files/photos.ts`, plain TypeScript, Drizzle for the `file` table) over `PhotoStorage` (`storage.ts`: a flat directory, `DATA_PATH`, the only storage; atomic writes through `.incoming/`). One instance per process, built by `createPhotos()`: the thumb single-flight map lives in it, so everything in the server shares it (`createApp()` builds it from config with `photosConfig()`, hands it to `webPlugin` as `photos` and returns it to `server.ts` for the nightly reconciliation; the reconcile CLI, a separate process, builds its own). Uploads (`storeUpload`, and `storeUploadParts` for the garment form's multipart: its `photo` part, every other part drained unread; both adapt `storeImage`, which takes any `ImageSource` stream: the seed's art, link import's fetched photo #6) and copies (`copy`) write bytes only and return the `file` row to insert (`NewPhotoRow`); see Gotchas for the commit contract. `pendingPhotoRow` builds that row for a pending photo stored earlier (while its bytes are still there), and `preview` makes a small WebP in memory, never stored (link import's choices), whose decodes `inputPixels` lets a caller budget: the pixel count from the header (a HEIC's container), none decoded, with a decode's refusals. A photo stored before its garment form is saved (link import's fetch, the add sheet's upload, #97) is a **pending photo**: bytes plus a `pending_photo` row (`src/web/files/pending-photos.ts`: file name, the user who stored it, when, and a draft's batch), kept only through `keepPendingPhoto` (`src/web/wardrobe/writes.ts`: the row, bytes deleted if it fails), at most `MAX_PENDING_PER_USER` (10) unbatched ones a user (storing another evicts their oldest, bytes and row, in the same step); a library pick of several is a batch of drafts (#200: `batch_id`, `batch_position`, `batch_owner_id`), never evicted and capped at `MAX_DRAFTS_PER_USER` (30) by refusing the upload (`recordDraftBatch`; Wardrobe, `drafts-and-export.md`); only that user may claim it (the save, which deletes the row in the transaction that inserts the `file` row) or discard it (link import's other pick); reconciliation removes day-old ones (a draft: week-old, `DRAFT_LIFETIME_MS`; `pendingCutoffs`/`isAgedPending`, the one rule) outside its guard, and account deletion removes a user's with their photos. A cutout of an existing photo (`saveEditedCutout`, the mask editor; `saveModelCutout`, the server job) is stored by `writeCutout` under a new variant key before any transaction, and the row points at it only when the cutout state machine accepts it (see Background removal, Gotchas). **Rotating** a garment photo (#199, `rotateStored`) never modifies the original: it streams the stored original through `storeImage` with `rotate` (a quarter turn after `autoOrient`) into a new unkeyed photo, and with `withCutout` (an `edited` cutout, a mask: turning the padded-square cutout is what cutting out the turned original gives) turns the cutout the row points at into the new set's unkeyed nobg, the thumb from it; any other cutout is re-made (the new row is `pending`). The caller swaps it in like an upload (`rotateGarmentPhoto`, `src/web/wardrobe/writes.ts`: the commit-then-unlink swap, a 409 when the photo changed after it was read). `cutoutInput` and `composeCutout` hold the server cutout's image rules (the model's stretched input; the original with the mask as alpha, padded square). Failures are `HttpError`s (400 unreadable, 400 "Image too large", 413 HEIC over the byte cap, 404 missing original), which the error handler answers with their status.

**Every decode is bounded by `MAX_INPUT_PIXELS`** (64 MP, `photos.ts`): sharp pipelines are only built through `decoder()` (`limitInputPixels`, which refuses from the header, before any pixel), and a HEIC's dimensions are checked before heic-decode allocates its pixels. sharp's own default (~268 MP) let a few KB of PNG or HEIC claim a gigabyte. A new sharp call site goes through `decoder()` or passes the limit itself; `writes.spec.ts` uploads such a bomb.

## Layout

`photos.ts` (Photos), `storage.ts` (PhotoStorage, the disk), `queries.ts`, `pending-photos.ts` (pending_photo rows: link import's and the add sheet's photos), `routes.ts` (`/file/**`), `image-variant.ts` (names), `image-url.ts` (the one URL builder), `references.ts` (what points at a file row, and which photos are private), `heic.ts`.

## Gotchas

- **Photo bytes are written before any row, and rows commit together.** `Photos.storeUpload` / `copy` write the files and return a `NewPhotoRow` without inserting it; the caller inserts it with `insertPhotoRow(tx, row)` inside the transaction that points a garment at it and calls `deleteVariants` if that transaction fails (`commitWithPhoto`, `src/web/wardrobe/writes.ts`). Garment deletion and photo replacement delete the `file` row in the same transaction and unlink after commit. Nothing in `src/web/files` inserts or deletes a `file` row; it only changes `version` and the cutout columns, through `applyCutoutEvent`.
- **The DB cascade deletes rows, never bytes.** `deleteRule: 'cascade'` on `File.createdBy` and `Garment.owner` drops the rows when a user goes, but only `Photos.deleteVariants` removes the files. Every path that removes a `file` row (`removeGarment`, photo replacement, `POST /auth/delete-account`) must unlink through `Photos` after commit; account deletion also deletes the user's `pending_photo` rows in its transaction and unlinks those bytes (the cascade would leave them unexplained); the cascade is the safety net and `reconcileStorage` (`src/maintenance/reconcile.ts`: nightly, or `npm run maintenance:reconcile`) is the backstop that deletes photo sets and rows older than a day that nothing references. Outfits own no files; **a calendar entry owns its outfit selfie** (#19): deleting the entry deletes the selfie's `file` row in its transaction and unlinks after commit (`removeEntry`); deleting the outfit keeps the selfie as a look (`selfie.outfit_calendar_id` set null). **What "references" a photo is one list, `photoIsReferenced`** (`src/web/files/references.ts`: `garment.photo_id` and `selfie.photo_id`): a new table with a photo column must join it, or reconciliation deletes each of its photos the night after it is stored (`reconcile.spec.ts` proves selfies survive).
- **Every stored image honours EXIF orientation**: `storeImage` builds one `decoder(raw).autoOrient()` for both the photo and the `alphaIsCutout` art path (the art path skipped it until #199, so a sideways cutout upload stayed sideways; `photos.spec.ts` stores a PNG tagged orientation 6). The browser side is `photo-input.js`'s `imageOrientation: 'from-image'`.
- **HEIC uploads are buffered.** sharp's libvips has no HEIC decoder, so `image/heic`, `image/heif` and an `application/octet-stream` named `.heic`/`.heif` are read whole (capped by `MAX_HEIC_BYTES`, 413 past it), their dimensions checked against `MAX_INPUT_PIXELS`, and decoded with heic-decode to raw RGBA that sharp reads as `raw` input (no JPEG round trip). libheif applies the container's rotation while decoding and raw pixels carry no EXIF, so HEIC photos are stored as decoded. Chrome/Android cannot decode HEIC in a canvas: `photo-input.js` leaves such a file as it is (no downscale) and the form submits the original; the server decodes it and makes the cutout.
- **Abandoned pending photos must never reach reconciliation's guard.** A link import, or an add-sheet upload whose form is never saved, leaves bytes without a `file` row. The guard refuses a whole run past 25 unexplained photo sets (or a fifth of them), and at 10 imports a minute one person browsing without saving passes that in a day; then nothing is cleaned, legitimate orphans included. So every stored pending photo has a `pending_photo` row: reconciliation deletes day-old ones (row and bytes) in a pass of its own before the plan, reports them as `pendingPhotosDeleted` apart from the guard's count, leaves younger ones out of the plan, and deletes pending rows whose bytes are gone (`pendingRowsWithoutFiles`). The guard keeps its thresholds for what nothing explains. A new feature that stores bytes ahead of their `file` row keeps them through `keepPendingPhoto` (the cap of 10 a user, nightly deletion after a day, removal with the account), or it jams the nightly clean-up. The form field stays `linkPhoto` whatever the source: installed apps' cached forms post it. A pending photo has no cutout; it is queued when the save inserts its `file` row.
- **`/file/**`serves from DATA_PATH, which also holds`app.log`.** The route accepts only a photo base name as `parseStoredName`defines it (the same rule reconciliation uses); a looser "safe characters" regex served`/file/app.log`, session cookies included, on the public hostname until 2026-09-25. Never add a second definition of a stored name. `test/integration/file-route.spec.ts` covers it. **Public by name is only for photos a share may show**: an outfit selfie's name is a 404 there (`publicPhoto`, `references.ts`, which also answers the row's variant key in the same statement) and its share id makes no preview; a new kind of private photo gets its own session-checked route (as `/selfies/\*`), joins `publicPhoto`'s refusal and gets a photo type `imageUrl` does not take (as `SelfiePhoto`), or a signed URL serves it to anyone.
- **Signed URLs: a photo request costs no statement** (#162). Asking the row per image made a cold wardrobe grid 48 statements over production's WiFi link to the database. `imageUrl` signs (HMAC-SHA256, 96 bits, keyed from `ACCESS_TOKEN_SECRET` by `configurePhotoUrls` in `createApp`) the name, variant key and version, not the variant, so a photo's three URLs differ only in path. The route (`signedPhoto`) then opens exactly that set's file (`openStoredVariant`: no fallback, no thumb made, which could write one under a retired key); a missing file, an unsigned or altered URL, or another secret's goes to the row (`publicPhoto`) as before, which serves the current set and makes a missing thumb; `photo_requests_total{lookup}` counts both. Why it is safe: **only garment and pending photos reach `imageUrl`** (`ImageRef` requires the variant key, which a selfie's `SelfiePhoto` never carries), a name never changes kind (a selfie always gets a fresh row), and a keyed file is never rewritten, so a signed URL can only ever serve what its page was shown; after a swap, rotate or delete its set is unlinked and the row answers. A client never builds or edits a `/file` URL (the mask save answers the new ones). Rotating `ACCESS_TOKEN_SECRET` only sends old URLs through the row. **Revocation is unchanged**: a garment photo's URL is a capability, as its bare name always was (Outfit selfies); unsharing ends the pages that show it, and only deleting the photo ends its URLs (the unlink after commit: a 404 at once).
- **`PhotoStorage.store` must be atomic.** A variant is read (the thumb writer, `/file/**`) while another write may replace it (a cutout job or mask save rewriting the cutout and thumb); storage writes to `DATA_PATH/.incoming/` and renames. Writing to the final name made every real photo+cutout upload fail with 500 when the browser still uploaded its cutout beside the photo: the thumb step read a half-written cutout. Boot removes `.incoming` entries older than an hour, never fresh ones (the reconcile CLI boots beside a live server). A cutout of an existing photo never overwrites a served name: it stores a new keyed set and the row swaps to it (writeCutout).
- **No storage I/O inside a server-pool transaction** (#141). The pool ends a session idle in a transaction, production's photos are on NFS, and a rename cannot roll back. Store first, commit the row, unlink after (the commit contract above); check a file's existence before the transaction (`createGarmentWithPendingPhoto` asks `pendingPhotoRow` first: a pending photo's bytes are deleted only by whoever took its pending row, which the claim then finds gone). **Deleting a row-backed photo needs its variant key**: every query that deletes a `file` row takes `STORED_PHOTO_COLUMNS` from the DELETE itself (`.returning`: a key read before it, unlocked, can be the one a waiting cutout swap replaces) for `deleteVariants`, which removes the original, the unkeyed pair and the keyed one; reconciliation deletes orphaned sets by the names it scanned and a live photo's day-old variants under another key that are older than the row's own set (`supersededVariantsDeleted`, counted by its guard; a newer set with a cutout, as after a database restore, is kept: Maintenance).
- **Pipelines started inside a multipart `for await` loop must be armed with a no-op catch at creation.** `Photos.storeUploadParts` starts the photo's pipeline without awaiting it (an unconsumed part hangs busboy; later parts, such as an old page's `nobgPhoto`, are drained) and the caller awaits it after the loop; a rejection while later parts are still being read (an undecodable HEIC/JPEG) was an unhandled rejection that exited the process with an empty reply. `startPipeline()` attaches the catch and returns the same promise, so the real error still surfaces from the await. `test/integration/heic.spec.ts` records `unhandledRejection` and asserts the app answers the next request. Node's default (crash loudly) is kept on purpose; do not add an `unhandledRejection` handler (main.ts's `uncaughtException` one reports the crash and still exits 1; see Metrics, Error tracking).
