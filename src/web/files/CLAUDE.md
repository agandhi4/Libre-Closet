# Images

Every photo is a set of WebP files sharing one base name: `<uuid>.webp` (original, 1080px, q90), `<uuid>-nobg.webp` (the cutout, made by the server, padded to a transparent square; older photos keep the browser's), `<uuid>-thumb.webp` (400px, q80, from the cutout when present). Only the original has a `File` row, which also carries the cutout's state (see Background removal). **A cutout written onto an existing row** is a new nobg and thumb under a **variant key**, `<uuid>-nobg-<key>.webp` and `-thumb-<key>.webp` (`image-variant.ts`), and `file.variant_key` says which set is the photo's (null: the unkeyed ones); the original never changes. Serving and deleting need a `StoredPhoto` (`{ fileName, variantKey }`, `STORED_PHOTO_COLUMNS`); `unkeyedPhoto(name)` only for bytes without a row yet and selfies (never keyed: `file_variant_key_check`). `File.version` is bumped with every new key. A variant URL, `?v=<version>&k=<key>&s=<signature>` (`k` absent while unkeyed), names its exact files, so the `/file` routes (`src/web/files/routes.ts`) serve all three `private, immutable` for a year (Request security) and, when the signature holds, straight from storage (Gotchas, Signed URLs). Views never build `/file/...` by hand: `imageUrl(photo, 'thumb')` (a branded `SignablePhotoRef`, made only by `queries.ts`' photo-ref helpers: `photoRefJson`, `photoWithCutoutJson`, `plinthPhoto` (over `plinthPhotoJson`), `readPhotoRef` over `PHOTO_REF_RELATION`, `pendingPhotoRef`) (`src/web/files/image-url.ts`; grids, `loading="lazy"`) or `'nobg'` (detail, share, Open Graph). Missing thumbs are made on first request, single-flighted. Deletion always goes through `deleteVariants`. An outfit selfie is the same set without the cutout (`unwanted`), served under `/selfies/` by `selfieUrl`, never `/file/` (Outfit selfies).

All of it is `Photos` (`src/web/files/photos.ts`) over `PhotoStorage` (`storage.ts`: a flat directory, `DATA_PATH`, the only storage; atomic writes through `.incoming/`). One instance per process, built by `createPhotos()`, so everything in the server shares its thumb single-flight map (`createApp()` builds it with `photosConfig()` for `webPlugin` (`photos`) and `server.ts`; the reconcile CLI builds its own). Uploads (`storeUpload`, and `storeUploadParts` for the garment form's multipart: its `photo` part, every other part drained unread; both adapt `storeImage`, over any `ImageSource` stream) and copies (`copy`) write bytes only and return the `file` row to insert (`NewPhotoRow`) (Gotchas: the commit contract). `pendingPhotoRow` builds that row for a pending photo stored earlier, and `preview` makes a small WebP in memory, never stored (link import's choices); `inputPixels` budgets its decodes from the header. A photo stored before its garment form is saved is a **pending photo**: bytes plus a `pending_photo` row (`src/web/files/pending-photos.ts`), kept only through `keepPendingPhoto` (`src/web/wardrobe/writes.ts`: the row; bytes deleted if it fails), at most `MAX_PENDING_PER_USER` (10) unbatched ones a user (another evicts their oldest); a library pick of several is a batch of drafts (`batch_id`, `batch_position`, `batch_owner_id`), never evicted and capped at `MAX_DRAFTS_PER_USER` (30) by refusing the upload (`recordDraftBatch`; Wardrobe, `drafts-and-export.md`); only that user may claim it (the save deletes the row in the transaction inserting the `file` row) or discard it; reconciliation removes day-old ones (a draft: week-old, `DRAFT_LIFETIME_MS`; `pendingCutoffs`/`isAgedPending`, the one rule) outside its guard, and account deletion removes a user's with their photos. A cutout of an existing photo (`saveEditedCutout`, the mask editor; `saveModelCutout`, the server job) is stored by `writeCutout` under a new variant key before any transaction; the row points at it only if the cutout state machine accepts it. **Rotating** a garment photo (`rotateStored`) never modifies the original: it streams it through `storeImage` with `rotate` (a quarter turn after `autoOrient`) into a new unkeyed photo, and with `withCutout` (an `edited` cutout, a mask) turns the row's cutout into the new set's unkeyed nobg, the thumb from it; any other cutout is re-made (the new row is `pending`). The caller swaps it in like an upload (`rotateGarmentPhoto`, `src/web/wardrobe/writes.ts`; a 409 if the photo changed since read). `cutoutInput` and `composeCutout` hold the server cutout's image rules. Failures are `HttpError`s (400, 413, 404).

**Every decode is bounded by `MAX_INPUT_PIXELS`** (64 MP, `photos.ts`): sharp pipelines are only built through `decoder()` (`limitInputPixels`, refusing from the header, before any pixel), and a HEIC's dimensions are checked before heic-decode allocates. sharp's default (~268 MP) lets a few KB of PNG or HEIC claim a gigabyte. A new sharp call goes through `decoder()` or passes the limit; `writes.spec.ts` uploads such a bomb.

## Layout

`photos.ts` (Photos), `storage.ts` (PhotoStorage, the disk), `queries.ts`, `pending-photos.ts`, `routes.ts` (`/file/**`), `image-variant.ts` (names), `image-url.ts` (the one URL builder), `references.ts` (what references a file row; which are private), `heic.ts`.

## Gotchas

- **Photo bytes are written before any row, and rows commit together.** `Photos.storeUpload` / `copy` write the files and return a `NewPhotoRow` without inserting it; the caller inserts it with `insertPhotoRow(tx, row)` inside the transaction that points a garment at it and calls `deleteVariants` if that fails (`commitWithPhoto`, `src/web/wardrobe/writes.ts`); removals delete the row in the transaction and unlink after commit. Nothing in `src/web/files` inserts or deletes a `file` row; it only changes `version` and the cutout columns, through `applyCutoutEvent`.
- **The DB cascade deletes rows, never bytes.** `deleteRule: 'cascade'` on `File.createdBy` and `Garment.owner` drops the rows when a user goes, but only `Photos.deleteVariants` removes the files. Every path removing a `file` row (`removeGarment`, photo replacement, `POST /auth/delete-account`) must unlink through `Photos` after commit; account deletion also deletes the user's `pending_photo` rows in its transaction and unlinks those bytes; `reconcileStorage` (`src/maintenance/reconcile.ts`, `npm run maintenance:reconcile`) is the backstop for day-old unreferenced sets and rows. Outfits own no files; **a calendar entry owns its outfit selfie**: deleting the entry deletes the selfie's `file` row in its transaction and unlinks after commit (`removeEntry`); deleting the outfit keeps the selfie as a look (`selfie.outfit_calendar_id` set null). **What "references" a photo is one list, `photoIsReferenced`** (`src/web/files/references.ts`: `garment.photo_id` and `selfie.photo_id`): a new table with a photo column must join it, or reconciliation deletes its photos the next night (`reconcile.spec.ts` proves selfies survive).
- **Every stored image honours EXIF orientation**: `storeImage` builds one `decoder(raw).autoOrient()` for both the photo and the `alphaIsCutout` art path (`photos.spec.ts`). The browser side is `photo-input.js`'s `imageOrientation: 'from-image'`.
- **HEIC uploads are buffered.** sharp's libvips has no HEIC decoder, so `image/heic`, `image/heif` and an `application/octet-stream` named `.heic`/`.heif` are read whole (capped by `MAX_HEIC_BYTES`, 413 past it), checked against `MAX_INPUT_PIXELS`, and decoded by heic-decode to RGBA sharp reads as `raw`. libheif applies the container's rotation and raw pixels carry no EXIF, so HEIC photos are stored as decoded. Chrome/Android cannot decode HEIC in a canvas: `photo-input.js` sends it untouched.
- **Abandoned pending photos must never reach reconciliation's guard.** An unsaved link import or add-sheet upload leaves bytes without a `file` row. The guard refuses a whole run past 25 unexplained photo sets (or a fifth of them), which one person browsing without saving passes in a day, and then nothing is cleaned. So every stored pending photo has a `pending_photo` row: reconciliation deletes day-old ones (row and bytes) in its own pass, reports them as `pendingPhotosDeleted` apart from the guard's count, leaves younger ones out of the plan, and deletes pending rows whose bytes are gone (`pendingRowsWithoutFiles`). A new feature that stores bytes ahead of their `file` row keeps them through `keepPendingPhoto`, or it jams the nightly clean-up. The form field stays `linkPhoto` whatever the source: installed apps' cached forms post it. Its cutout is queued when the save inserts its `file` row.
- **`/file/**` serves from `DATA_PATH`, which also holds `app.log`.** The route accepts only a photo base name as `parseStoredName` defines it (the rule reconciliation uses); a looser regex once served `/file/app.log`, session cookies included. Never add a second definition of a stored name. `test/integration/file-route.spec.ts` covers it. **Public by name is only for photos a share may show**: an outfit selfie's name is a 404 there (`publicPhoto`, `references.ts`, which also answers the row's variant key in the same statement) and its share id makes no preview; a new kind of private photo gets its own session-checked route (`/selfies/\*`), joins `publicPhoto`'s refusal and gets a photo type `imageUrl` does not take (as `SelfiePhoto`), or a signed URL serves it to anyone.
- **Signed URLs: a photo request costs no statement** (per-image row reads made a cold grid 48 statements). `imageUrl` signs (HMAC-SHA256, 96 bits, keyed from `ACCESS_TOKEN_SECRET` by `configurePhotoUrls` in `createApp`) the name, variant key and version, not the variant, so a photo's three URLs differ only in path. The route (`signedPhoto`) opens exactly that set's file (`openStoredVariant`: no fallback, no thumb made under a possibly retired key); a missing file or an unsigned, altered or other-secret URL goes to the row (`publicPhoto`), which serves the current set and makes a missing thumb; `photo_requests_total{lookup}` counts both. Safe because **only garment and pending photos reach `imageUrl`**: it takes a branded `SignablePhotoRef`; `photo-ref-guard.spec.ts` fails if `src/web/selfies` touches a maker or anything outside `queries.ts` asserts the brand; the fast path does no selfie check, so a new maker must never read a selfie's row, a name never changes kind (a selfie always gets a fresh row), and a keyed file is never rewritten, so a signed URL only serves what its page showed; after a swap, rotate or delete the row answers. A client never builds or edits a `/file` URL. Rotating `ACCESS_TOKEN_SECRET` only routes old URLs via the row. Never log a `/file` URL's query: `s=` spares a lookup. **Revocation is unchanged**: a garment photo's URL is a capability; unsharing ends the pages showing it, only deleting the photo ends its URLs.
- **`PhotoStorage.store` must be atomic.** A variant is read while another write may replace it; storage writes to `DATA_PATH/.incoming/` and renames, so no reader sees a half-written file. Boot removes `.incoming` entries older than an hour, never fresh ones (the reconcile CLI may boot beside a live server). A cutout of an existing photo never overwrites a served name: it stores a new keyed set and the row swaps to it (writeCutout).
- **No storage I/O inside a server-pool transaction.** The pool ends idle-in-transaction sessions, photos are on NFS, and a rename cannot roll back. Store first, commit the row, unlink after (the commit contract above); check a file's existence before the transaction (`createGarmentWithPendingPhoto` asks `pendingPhotoRow` first: only whoever took the pending row deletes its bytes). **Deleting a row-backed photo needs its variant key**: every query that deletes a `file` row takes `STORED_PHOTO_COLUMNS` from the DELETE itself (`.returning`: an earlier read may miss a cutout swap) for `deleteVariants` (original, unkeyed pair, keyed pair); reconciliation deletes orphaned sets by the names it scanned and a live photo's day-old variants under another key older than the row's own set (`supersededVariantsDeleted`, counted by its guard; a newer set is kept: Maintenance).
- **Pipelines started inside a multipart `for await` loop must be armed with a no-op catch at creation.** `Photos.storeUploadParts` starts the photo's pipeline without awaiting it (an unconsumed part hangs busboy; later parts, like `nobgPhoto`, are drained) and the caller awaits it after the loop; a rejection while later parts are read would be an unhandled rejection that exits the process. `startPipeline()` attaches the catch and returns the same promise, so the real error still surfaces from the await. `test/integration/heic.spec.ts` records `unhandledRejection` and checks the app still answers. Node's default (crash loudly) is kept on purpose; do not add an `unhandledRejection` handler (main.ts's `uncaughtException` one reports and exits 1; see Metrics).
