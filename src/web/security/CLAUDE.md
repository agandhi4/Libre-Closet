# Request security

- **CSRF**: `createSameOriginHook` (`src/web/security/same-origin.ts`) is a root `onRequest` hook added in `createApp()` before any route, so it runs before all of them and before the body is read. A POST, PUT, PATCH or DELETE must name in `Origin` (or `Referer` when there is no Origin) either the origin it was sent to (`requestOrigin`: scheme and Host as Fastify trusts them, see Trusted proxies) or `SITE_URL`'s origin; anything else, no header included, is a 403. Browsers send Origin on every such request; tools do not: the integration harness adds `Origin: http://localhost` by default (`sameOrigin: false` opts out), Playwright's `page.request` posts use `SAME_ORIGIN` / `signUpHeaders()` (`test/support/e2e-session.ts`), and the page audit (`scripts/audit/fixture.ts`) sets it. The cookie is also `SameSite=Lax`. Nothing changes state on a GET: signing out is a POST since 2026-09-26 (a cross-site link or image could sign someone out). A bearer route (`config: { bearer: true }`: `/mcp`) is the one exception to "no header is a 403": programs send no Origin, a cookie grants nothing there, and a page cannot add `Authorization` cross-site without a CORS preflight (never answered); a present foreign Origin is still a 403 (the MCP spec's DNS-rebinding rule).
- **Rate limits**: `@fastify/rate-limit`, registered at the root with `global: false` (`src/web/security/rate-limit.ts`); a route opts in with `config: { rateLimit: SIGN_IN_LIMIT }` (login, registration: 5 a minute per client address, before the body is read) or `ACCOUNT_LIMIT` (change password, change email, delete account, create a personal access token: every route that checks the current password; 5 a minute per signed-in user, a preHandler after the session gate) or `LINK_IMPORT_LIMIT` (the link import and its photo choice, the routes that fetch a user's URL: 10 a minute per signed-in user between them, counted on one `createRateLimit` checker both handlers call, not route config, see Link import) or `WEATHER_SEARCH_LIMIT` (the weather's and a trip's city search: 20 a minute per user) or `WEATHER_LOCATION_LIMIT` (`POST /weather/home`, `/weather/here`, `/trips/:id/destination`: each new rounded location is an Open-Meteo fetch and a cached row; 10 a minute per user) or `VITALS_LIMIT` (the devices' timing beacon, `POST /metrics/vitals`: 30 batches a minute per signed-in user, same shape; see Metrics) or `CLIENT_ERROR_LIMIT` (the pages' error beacon, `POST /errors/client`, forwarded to Bugsink: 10 a minute per signed-in user; see Metrics, Error tracking) or `MCP_LIMIT` (`/mcp`: 120 a minute per personal access token, a preHandler after the endpoint authenticated it). The MCP tool `add_garment_from_link` gets its own 10 a minute per user through the plugin's `createRateLimit` (`MCP_LINK_IMPORT_LIMIT`), since it is a call to `/mcp`, not a route. Counters are in process memory, one per route config and one per `createRateLimit` call (never shared between them: a budget two routes share is one checker). A refusal is the 429 error page (`tooManyAttempts` for a checker's). Tests give each sign-up its own `X-Forwarded-For` (`uniqueClient()` in the harness, `signUpHeaders()` for Playwright), which only works because 127.0.0.1 is a trusted proxy there.
- **Trusted proxies**: `request.ip`, `request.protocol` and `request.host` read `X-Forwarded-*` only from peers in `TRUSTED_PROXIES` (Fastify `trustProxy`). Behind Caddy it **must** include Caddy's address, or every visitor is Caddy's IP to the rate limiter (one person's typos lock out the household for a minute) and the same-origin check falls back to `SITE_URL` for the https name. The homelab audit found production's value does not cover Caddy: a homelab config change.
- **Refusals do not reveal ids**: what the requester cannot see does not exist for them, a 404 like an unknown id (another user's wardrobe without a share, a garment or capsule outside the addressed wardrobe, anyone else's outfit or calendar entry, a share the user is no party to); what they can see but may not change is a 403 (a VIEW grantee writing, a grantee archiving or deleting). `WardrobeAccess` (`src/web/sharing/access.ts`) documents it; `test/integration/authorization-*.spec.ts` is the matrix.
- **Public pages never show an email**: the share page (`/share`) and its Open Graph and Twitter tags say "Shared by" the owner's first name when set (`sharedBy`, `src/web/share/share-page.tsx`), else nothing and the layout's default description; its query reads no email. Anonymous visitors and link-preview crawlers keep what they read.
- **Outbound fetches (SSRF)**: the server sits on the homelab LAN beside the NAS, pgvault and the router, so a URL a user supplies (the link import, #6) is fetched only through `createOutboundFetcher` (`src/web/security/outbound-fetch.ts`): http(s) on the default port, no credentials in the URL; the name is resolved once and refused if any answer fails `isPublicAddress` (`public-address.ts`: loopback, RFC 1918, 100.64/10, link-local, multicast, documentation and reserved ranges, IPv6 outside 2000::/3 or in its special blocks, and IPv4-mapped, NAT64 and 6to4 forms judged by their IPv4 address); the socket then connects to **the checked address** through a pinned `lookup` (no second DNS query, so DNS rebinding cannot swap it) while Host, SNI and the certificate check keep the name; at most 3 redirects, each checked the same way; one 10 s timeout over the whole chain; the body is read only for a content type the caller accepts and refused the moment its decoded bytes pass 2 MB (HTML) or 15 MB (images); no cookies are sent or kept; one log line per fetch naming hosts only (a product link can carry tokens). A refusal is an `OutboundFetchError` whose `reason` names the rule. **A fixed third-party API** (the weather's Open-Meteo, #14) uses the same fetcher: its requests name their `hosts` (the allow-list, checked on every hop, so a redirect elsewhere is `host-not-allowed` before it resolves) and accept `json` (512 KB cap); `createApp()` builds the weather its own instance of it (same rules, so a spec's stand-in is admitted for the weather alone). **A credential** (`authorization`) or a JSON body (`json`, a POST) is accepted only with `hosts` (else a thrown programming error), and such a request follows no redirect (a 3xx is an `http-status` refusal), so the credential reaches the named hosts alone: the order mail's JMAP client (#25, `src/web/wardrobe/order-mail.md`) sends its Fastmail token so, through an instance of its own. `createApp()` builds the one fetcher of user URLs (context `OutboundFetch`) and hands it to the web layer as `WebOptions.fetcher`; the per-user rate limit belongs on the route that calls it (`LINK_IMPORT_LIMIT`). The link import turns each `reason` into a translated sentence (`REFUSALS`, `link-import/import.ts`) that never names a host or an address. `test/integration/outbound-fetch.spec.ts` covers each rule against real sockets.
- **Redirect targets**: a user-supplied "go back here" value (`?returnTo=` on Styling and the pages it came from) goes through `safeReturnTo` (`src/web/security/return-to.ts`): same-site paths only, anything else becomes the route's default. Never render or redirect to such a value without it.
- **Timing**: a function that checks a secret a request carries (a password, an access or invite token) calls `markSecretChecked()`, and that request answers without `Server-Timing` (see Metrics).
- **Secrets in logs**: a route whose path carries a secret (the invite token) sets `config: { secretPath: true }`; every log line names requests through `loggableUrl()`, which then logs the route pattern. Invite links are built on `requestOrigin`, not the raw Host header, and reach their copy handler as a data attribute (`copyAndFlash`, `src/web/share/share-button.tsx`), never spliced into script text.
- **Logout**: `POST /auth/logout` (public, CSRF-checked by the same-origin hook like every POST) clears the cookie, sends `Clear-Site-Data: "cache"` (both through `endSession`, `src/web/auth/session.ts`, the one way a session ends on a device: sign-out, account deletion and a revoked cookie, see Session revocation) and answers 303 to `/auth/login`; the service worker drops its page cache when a POST to `/auth/logout` or `/auth/delete-account` answers with a redirect (`views/assets/src-sw.ts`) and re-warms the offline page signed out (it does the same when `/auth/login` or `/auth/register` answers with one; see PWA, Page cache ownership). `images-v1` stays: its URLs are unguessable and only reachable from a page that shows them. The control is one native `PostForm` (`#logout-form`, `src/web/auth/logout.tsx`, `needsNetwork`: disabled offline) in Profile › Sign out, the only place to sign out. `GET /auth/logout` signs nobody out: pages cached by the installed app before the change still link there, so it shows a one-button "Sign out" page to a signed-in visitor and sends anyone else to the login page.
- **Session revocation**: a session token lives a year and carries `pwf`, the last 8 characters of the user's bcrypt hash. `createSessionResolver` compares it with the row on every request, so any new hash (change password, `user:set-password`; bcrypt salts every hash, so even the same password again) ends every token issued before it, which is what an `iat` check against a password-changed timestamp would do, without the column. Deleting the account ends them with the row. Signing out ends only this browser's cookie: a copied token stays valid until the password changes, which is the one server-side revocation (there is no session table). Rotating `ACCESS_TOKEN_SECRET` signs everyone out. A new password also revokes every personal access token and every push subscription but the changing device's (`updatePasswordHash`, the one writer of a password, does all three in one transaction; see Web Push, Revoked with the session); rotating the secret touches neither (tokens are random, not signed; subscriptions go with `npm run push:revoke-all`, Deployment, Rotating the secret). **A revoked cookie clears its device** (#19's gap, closed): when a request carries a session cookie that no longer opens a session (the fingerprint moved, the user row is gone, the signature fails after a secret rotation or on a garbled value, the token expired), `createSessionResolver` ends it on that reply with `endSession`: the cookie cleared and `Clear-Site-Data: "cache"`, on whatever route it arrived (public ones included) and whatever the gate answers (the 302, the htmx or `/selfies/*` 401 with `HX-Redirect`), so the device's HTTP cache (selfies, pages) goes on its first request after the revocation, with one info line (context `Session`, `Rejected access token (<reason>): cookie cleared, Clear-Site-Data sent`). No cookie, no header: a first visit never gets it. The device that changed its password is reissued a cookie in the same answer and keeps its cache. `"cache"` and not `"storage"`: storage would unregister the service worker and empty its precache (the installed app's offline shell) and the push subscription; the worker's page cache is dropped by the worker (PWA, Page cache ownership), which reads `X-Session-Ended`, sent beside it (Chromium hides `Clear-Site-Data` from the response, #131). `Clear-Site-Data` needs a secure context: `http://closet.box` ignores it, as it ignores the service worker. `test/integration/session-revocation.spec.ts` covers each path and `test/session-revocation.spec.ts` the browser's cache.

## Gotchas

- **All user-supplied URL fetches go through `outbound-fetch`.** Never `fetch()`, `http.get` or an HTTP library on a URL a user typed, pasted, shared or that a fetched page named (an image candidate, a redirect): linux-box reaches the NAS, pgvault and the router, and a check of the URL's name followed by a normal request is open to DNS rebinding (the socket resolves again). `createOutboundFetcher` checks every resolved address and pins the connection to it (Request security, Outbound fetches). Its `destinations` and `resolve` options exist for the specs only; production passes neither. The spec stands in for the internet with the loopback alias `127.0.0.2`, which Linux routes (all of 127/8 is `lo`) and macOS does not without `sudo ifconfig lo0 alias 127.0.0.2`.
- **The request log never holds a credential and skips static paths.** One line per request from the root onResponse hook (`GET /wardrobe 200 3.1ms`, context `Http`): method, `loggableUrl`, status, time, never headers. The session cookie is a year-long bearer credential and the logs reach `app.log` and Loki; the logger also redacts `cookie`, `authorization` and `set-cookie` under any logged `req`/`res` (`src/logger.spec.ts`). Fastify's own request logging stays off (`LogController({ disableRequestLogging: true })`): it would log every thumbnail and heartbeat.
